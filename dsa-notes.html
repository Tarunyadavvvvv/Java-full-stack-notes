Part I — Foundations

1. Complexity Analysis (Big-O) Basic

1.1 Why it matters

Big-O describes how an algorithm's running time (or memory) grows as input size n grows — ignoring constants and lower-order terms. It's about scalability, not exact speed.

1.2 The growth hierarchy (best → worst)

Big-ONameExamplen=1M roughly
O(1)ConstantHash lookup, array indexinstant
O(log n)LogarithmicBinary search~20 steps
O(n)LinearSingle loop1M
O(n log n)LinearithmicMerge/Heap sort~20M
O(n²)QuadraticNested loops10¹² (too slow)
O(2ⁿ)ExponentialSubsets, naive recursioninfeasible
O(n!)FactorialPermutationsinfeasible

1.3 Three cases & notations

NotationBoundMeaning
O (Big-O)UpperWorst case (most used)
Ω (Omega)LowerBest case
Θ (Theta)TightBoth bounds equal

1.4 Rules of thumb

  • Drop constants: O(2n) → O(n); O(n/2) → O(n).
  • Drop lower-order terms: O(n² + n) → O(n²).
  • Different inputs → different variables: O(a + b), not O(n).
  • Nested loops multiply; sequential loops add.
  • Recursion: time ≈ (number of nodes in the call tree). Space includes the recursion stack depth.

1.5 Amortized analysis

Amortized O(1): a dynamic array's append is usually O(1), but occasionally O(n) when it doubles & copies. Averaged over many operations, the cost is O(1) per op — that's the amortized cost. (Same idea for HashMap resize.)

1.6 What "n" to target

Constraint (n)Acceptable complexity
n ≤ 10–12O(n!), O(2ⁿ) (brute force / backtracking)
n ≤ 20–25O(2ⁿ) subsets
n ≤ 500O(n³)
n ≤ 5,000O(n²)
n ≤ 10⁶O(n log n) or O(n)
n ≥ 10⁸O(n), O(log n), O(1)
Interview trick: the input size hints at the target complexity. n=10⁶ almost always means "find an O(n log n) or O(n) solution."
What's the time & space complexity of a recursive Fibonacci?
Naive recursion: O(2ⁿ) time (each call branches into two) and O(n) space (max recursion depth). With memoization it drops to O(n) time and O(n) space; bottom-up with two variables is O(n) time, O(1) space.

3. Arrays & Strings Basic

3.1 Array operations & complexity

OperationArrayDynamic Array (ArrayList)
Access by indexO(1)O(1)
Search (unsorted)O(n)O(n)
Insert/delete at endO(1)O(1) amortized

Strings are immutable in Java/Python — concatenation in a loop is O(n²). Use StringBuilder / list + join for O(n).

3.2 Prefix sum (a must-know technique)

Precompute cumulative sums so any range sum is answered in O(1).

prefix[0]=0; prefix[i] = prefix[i-1] + arr[i-1]
sum(l..r) = prefix[r+1] - prefix[l]      // O(1) per query after O(n) build
arr:    [2, 4, 1, 3]
prefix: [0, 2, 6, 7, 10]   -> sum(1..2)=prefix[3]-prefix[1]=7-2=5 (=4+1) ✓
Related: "subarray sum equals K" → prefix sum + HashMap of seen prefix counts (O(n)). Kadane's algorithm for max subarray sum (below).

3.3 Kadane's algorithm (max subarray sum)

int maxSubArray(int[] a){
    int best = a[0], cur = a[0];
    for(int i=1;i<a.length;i++){
        cur = Math.max(a[i], cur + a[i]);   // extend or restart
        best = Math.max(best, cur);
    }
    return best;            // O(n) time, O(1) space
}
// Dry run [-2,1,-3,4,-1,2,1]: cur->-2,1,-2,4,3,5,6 ; best->...6  Answer: 6

3.4 Common mistakes

Off-by-one errors in loops/boundaries; integer overflow on sums (use long); modifying a list while iterating; assuming sorted when it isn't; not handling empty arrays.

4. Two Pointers & Sliding Window Intermediate — very common

4.1 Two pointers

Two indices move toward each other (or same direction) to avoid an O(n²) brute force.

// Pair with target sum in a SORTED array -> O(n)
int l=0, r=n-1;
while(l<r){
    int s = a[l]+a[r];
    if(s==target) return {l,r};
    else if(s<target) l++;     // need bigger -> move left up
    else r--;                  // need smaller -> move right down
}

Uses: 2-sum (sorted), 3-sum, remove duplicates in-place, reverse, palindrome check, container with most water.

4.2 Sliding window

A window [left, right] expands/contracts over a contiguous range — turns many O(n²) substring/subarray problems into O(n).

// Longest substring without repeating characters
int longest(String s){
    Map<Character,Integer> last = new HashMap<>();
    int left=0, best=0;
    for(int right=0; right<s.length(); right++){
        char c = s.charAt(right);
        if(last.containsKey(c) && last.get(c)>=left)
            left = last.get(c)+1;          // shrink past the duplicate
        last.put(c, right);
        best = Math.max(best, right-left+1);
    }
    return best;                            // O(n)
}
Window typeUse
Fixed size kMax sum of k elements, averages
Variable (grow/shrink)Longest/shortest window meeting a condition
Pitfall: forgetting to shrink the window correctly, or recomputing the window contents each step (defeats O(n)). Maintain a running aggregate (sum/count/freq map) incrementally.
How do you recognize a sliding-window problem?
Keywords like "contiguous subarray/substring," "longest/shortest/maximum window," or "at most K distinct." If the answer is a contiguous range and brute force is O(n²), a window that expands and shrinks usually gives O(n).

5. Hashing Basic — foundational

Hash tables (HashMap/HashSet) give average O(1) insert/lookup/delete — the single most useful tool for "have I seen this?" and counting.

OperationAverageWorst (bad hashing)
insert / get / removeO(1)O(n)
// Two Sum (unsorted) in O(n): map value -> index
int[] twoSum(int[] a, int t){
    Map<Integer,Integer> seen = new HashMap<>();
    for(int i=0;i<a.length;i++){
        if(seen.containsKey(t-a[i])) return new int[]{seen.get(t-a[i]), i};
        seen.put(a[i], i);
    }
    return new int[]{};
}

Common uses: frequency counts, deduplication, grouping (anagrams by sorted key), caching/memoization, detecting cycles/duplicates, prefix-sum counts.

Pitfalls: mutating a key after insertion (breaks lookup); relying on iteration order (HashMap has none — use LinkedHashMap/TreeMap); custom objects as keys without proper equals/hashCode.
When would you use a HashMap vs a TreeMap?
HashMap for O(1) unordered lookups (the default). TreeMap (balanced BST) when you need sorted order or range/floor/ceiling queries, at O(log n) per op.

6. Stack & Queue Basic

6.1 Stack (LIFO) & Queue (FIFO)

Stack (LIFO)Queue (FIFO)
Add/removepush/pop (top)enqueue/dequeue (ends)
OpsO(1)O(1)
UsesUndo, recursion, parsing, DFSBFS, scheduling, buffering
Use ArrayDeque in Java for both stack & queue (faster than legacy Stack/LinkedList). Variants: Deque (both ends), Priority Queue (heap, §12), Circular queue.

6.2 Monotonic stack (key pattern)

A stack kept in increasing/decreasing order — solves "next greater/smaller element" in O(n).

// Next Greater Element to the right
int[] nextGreater(int[] a){
    int n=a.length; int[] res=new int[n]; Arrays.fill(res,-1);
    Deque<Integer> st=new ArrayDeque<>();    // stack of indices, decreasing values
    for(int i=0;i<n;i++){
        while(!st.isEmpty() && a[i]>a[st.peek()])
            res[st.pop()] = a[i];            // a[i] is the next greater for popped
        st.push(i);
    }
    return res;                              // O(n) — each index pushed/popped once
}

Classic stack problems: valid parentheses, min stack, evaluate RPN, largest rectangle in histogram, daily temperatures, trapping rain water.

How do you implement a queue using two stacks?
Use an "in" stack for pushes and an "out" stack for pops. To dequeue, if "out" is empty, pour all of "in" into "out" (reversing order), then pop from "out". Amortized O(1) per operation.

7. Linked Lists Intermediate

7.1 Types & complexity

OperationSingly/Doubly LLvs Array
Access by indexO(n)Array O(1)
Insert/delete (with node ref)O(1)Array O(n)

When LL beats arrays: frequent insert/delete at known positions, no need for random access, unknown size (no resizing). Doubly LL allows O(1) delete given a node (used in LRU cache).

7.2 Reverse a linked list (must-know)

Node reverse(Node head){
    Node prev=null, cur=head;
    while(cur!=null){
        Node next=cur.next;   // save
        cur.next=prev;        // flip pointer
        prev=cur; cur=next;   // advance
    }
    return prev;              // new head — O(n) time, O(1) space
}

7.3 Fast & slow pointers (Floyd's)

// Detect a cycle: slow +1, fast +2; if they meet -> cycle
boolean hasCycle(Node head){
    Node slow=head, fast=head;
    while(fast!=null && fast.next!=null){
        slow=slow.next; fast=fast.next.next;
        if(slow==fast) return true;
    }
    return false;
}

Uses: cycle detection, find middle (slow ends at middle), find cycle start, palindrome check, nth node from end (two pointers k apart).

Pitfalls: null-pointer on fast.next.next; losing the list by not saving next before re-pointing; forgetting to use a dummy head node to simplify edge cases (insert/delete at head).
Why use a dummy/sentinel node?
It removes special-casing for operations at the head (insertion, deletion, merging). You always have a node before the "real" head, so the same code handles the first element as any other — fewer bugs.

Part III — Recursion, Searching & Sorting

8. Recursion & Backtracking Intermediate

8.1 Recursion essentials

A function that calls itself, reducing toward a base case. Every recursion needs: (1) a base case, (2) progress toward it, (3) a recursive call.

int factorial(int n){
    if(n<=1) return 1;          // base case
    return n * factorial(n-1);  // recursive case
}
Pitfalls: missing/incorrect base case → StackOverflowError; recomputing overlapping subproblems (→ add memoization, see DP); deep recursion on large n (consider iterative).

8.2 Backtracking template

Build a solution incrementally; abandon ("backtrack") a path as soon as it can't lead to a valid solution. Used for combinations, permutations, subsets, N-Queens, Sudoku, word search.

void backtrack(State s, List<Solution> res){
    if(isComplete(s)){ res.add(copy(s)); return; }
    for(Choice c : choices(s)){
        if(!valid(c, s)) continue;
        apply(c, s);              // choose
        backtrack(s, res);        // explore
        undo(c, s);               // un-choose (backtrack)
    }
}
// Subsets of [1,2,3] -> 2^n subsets
void subsets(int[] a, int i, List<Integer> cur, List<List<Integer>> res){
    if(i==a.length){ res.add(new ArrayList<>(cur)); return; }
    cur.add(a[i]); subsets(a,i+1,cur,res); cur.remove(cur.size()-1); // include
    subsets(a,i+1,cur,res);                                          // exclude
}
ProblemCountComplexity
Subsets2ⁿO(2ⁿ · n)
Permutationsn!O(n! · n)
CombinationsC(n,k)varies
Recursion vs iteration — trade-offs?
Recursion is cleaner for tree/graph/divide-and-conquer problems but uses stack space (O(depth)) and risks overflow. Iteration is more memory-efficient and often faster but can be harder to read. Any recursion can be converted to iteration with an explicit stack.

9. Binary Search Intermediate — high frequency

9.1 The core

Search a sorted space by halving each step — O(log n).

int binarySearch(int[] a, int target){
    int lo=0, hi=a.length-1;
    while(lo<=hi){
        int mid = lo + (hi-lo)/2;     // avoid overflow (not (lo+hi)/2)
        if(a[mid]==target) return mid;
        else if(a[mid]<target) lo=mid+1;
        else hi=mid-1;
    }
    return -1;
}
Bug magnets: lo+hi overflow (use lo+(hi-hi... ) i.e. lo+(hi-lo)/2); wrong loop condition (< vs ≤); infinite loops from mid not moving. Pick one template and reuse it.

9.2 Binary search on the answer (the powerful variant)

When asked to minimize/maximize a value with a monotonic feasibility check, binary-search the answer space.

// e.g. "minimum capacity to ship packages in D days"
// feasible(cap) is monotonic: false...false true...true -> find the first true
int lo=max(weights), hi=sum(weights);
while(lo<hi){
    int mid=lo+(hi-lo)/2;
    if(feasible(mid)) hi=mid;     // try smaller
    else lo=mid+1;                // need bigger
}
return lo;
VariantUse
Lower/upper boundFirst/last position of a value
Rotated sorted arraySearch in O(log n)
Search on answerMin/max with monotonic predicate
Peak element / sqrtBinary search variations
How do you spot a "binary search on the answer" problem?
It asks for the minimum/maximum value satisfying a condition, and you can write a feasible(x) check that's monotonic (once true, stays true). Then binary-search x over its numeric range — O(log(range) × checkCost).

10.2 Merge sort (divide & conquer)

Split array in half -> sort each half (recursively) -> merge two sorted halves.
[38,27,43,3] -> [38,27][43,3] -> [27,38][3,43] -> merge -> [3,27,38,43]
Always O(n log n); stable; needs O(n) extra space. Great for linked lists & external sort.

10.3 Quick sort

Pick a pivot -> partition (smaller left, larger right) -> recurse on both sides.
Avg O(n log n), in-place. Worst O(n²) on already-sorted with bad pivot ->
fix with random/median-of-three pivot. Not stable.

10.4 When to use which

SituationChoice
General in-memoryQuick sort (or library Timsort)
Stability requiredMerge sort / Timsort
Linked listMerge sort
Nearly sorted / smallInsertion sort

Library sorts: Java's Arrays.sort uses dual-pivot quicksort for primitives and Timsort (merge+insertion hybrid, stable) for objects. Python's sorted is Timsort.
Why is quicksort often faster than merge sort despite the same average complexity?
Quicksort sorts in place with better cache locality and smaller constant factors, and does less data movement on average. Merge sort needs O(n) extra space and more copying. But quicksort has an O(n²) worst case (mitigated by randomized pivots), while merge sort is guaranteed O(n log n) and stable.
What does "stable sort" mean and when does it matter?
A stable sort preserves the relative order of equal elements. It matters when sorting by multiple keys sequentially (e.g. sort by name, then by age, keeping name order within equal ages).

11.4 Classic tree problems

  • Height/diameter; check balanced; lowest common ancestor (LCA); validate BST (use bounds, not just parent check); level-order & zigzag; serialize/deserialize; path sum; invert tree.
int height(Node n){ return n==null?0:1+Math.max(height(n.left),height(n.right)); }
How do you validate a BST?
Recurse with a valid (min, max) range for each node (not just comparing with its parent). Each node must satisfy min < val < max; go left with max=val, right with min=val. Alternatively, an in-order traversal must be strictly increasing.

12. Heaps / Priority Queue Intermediate

A heap is a complete binary tree (stored in an array) where every parent ≤ children (min-heap) or ≥ (max-heap). Gives O(1) peek-min/max and O(log n) insert/extract.

OperationComplexity
peek (min/max)O(1)
insert / extractO(log n)
build heap (heapify)O(n)
Array layout: node i -> children 2i+1, 2i+2; parent (i-1)/2
// Top-K largest elements with a MIN-heap of size k -> O(n log k)
PriorityQueue<Integer> pq = new PriorityQueue<>();  // min-heap
for(int x : a){ pq.add(x); if(pq.size()>k) pq.poll(); }  // keep k largest
// pq now holds the k largest; pq.peek() is the kth largest

Uses: Top-K, Kth largest/smallest, merge K sorted lists, median of a stream (two heaps), Dijkstra, task scheduling, heap sort.

Find the median of a data stream — approach?
Keep two heaps: a max-heap of the lower half and a min-heap of the upper half, balanced in size. The median is the top of the larger heap (or the average of both tops). Each insert is O(log n); median query is O(1).

13. Tries (Prefix Trees) Intermediate

A tree where each path from root spells a word; children indexed by character. Great for prefix queries and dictionaries.

class TrieNode { TrieNode[] children = new TrieNode[26]; boolean isWord; }
// insert / search / startsWith are O(L) where L = word length
void insert(String w){
    TrieNode cur=root;
    for(char c: w.toCharArray()){
        int i=c-'a';
        if(cur.children[i]==null) cur.children[i]=new TrieNode();
        cur=cur.children[i];
    }
    cur.isWord=true;
}
OperationComplexity
insert / search / startsWithO(L) (word length)
SpaceO(total chars × alphabet)

Uses: autocomplete/typeahead, spell-check, word search (boggle), IP routing, longest common prefix, word dictionaries.

Trie vs HashMap for word lookups?
HashMap gives O(L) exact lookups but can't do prefix queries efficiently. A trie supports fast prefix operations (autocomplete, "all words starting with...") and shares storage for common prefixes — at the cost of more memory and pointer overhead.

14.2 BFS & DFS (the foundation)

// BFS - shortest path in UNWEIGHTED graph; uses a queue; level by level
void bfs(int src, List<List<Integer>> adj){
    boolean[] vis=new boolean[n]; Queue<Integer> q=new LinkedList<>();
    q.add(src); vis[src]=true;
    while(!q.isEmpty()){
        int u=q.poll();
        for(int v: adj.get(u)) if(!vis[v]){ vis[v]=true; q.add(v); }
    }
}
// DFS - recursion or stack; used for paths, cycles, components, topo sort
void dfs(int u, boolean[] vis, List<List<Integer>> adj){
    vis[u]=true;
    for(int v: adj.get(u)) if(!vis[v]) dfs(v, vis, adj);
}

14.4 Union-Find (Disjoint Set Union)

int find(int x){ return parent[x]==x ? x : (parent[x]=find(parent[x])); } // path compression
void union(int a,int b){ parent[find(a)]=find(b); }   // + union by rank for near O(1)

Uses: number of connected components, detect cycle in undirected graph, Kruskal's MST, "accounts merge", redundant connection.

14.5 Grid problems

Grids are graphs: each cell is a node connected to its 4 (or 8) neighbours. "Number of islands", "flood fill", "rotting oranges", "shortest path in maze" are BFS/DFS on a grid. Mark visited to avoid revisiting (O(rows×cols)).
When BFS vs DFS vs Dijkstra for shortest path?
BFS for unweighted graphs (fewest edges). Dijkstra for non-negative weighted edges. Bellman-Ford if negative weights exist (and to detect negative cycles). BFS on a 0/1-weighted graph → 0-1 BFS with a deque.
How do you detect a cycle in a directed graph?
DFS with three states (white/unvisited, gray/in-progress, black/done): if you reach a gray node, there's a back edge → cycle. Alternatively, Kahn's topological sort — if you can't order all nodes, a cycle exists.

Part V — Advanced Topics

15. Dynamic Programming Advanced — the big one

15.1 When is it DP?

Two signals together: (1) Overlapping subproblems (same sub-results recomputed) + (2) Optimal substructure (optimal answer built from optimal sub-answers). Question words: "count the number of ways", "minimum/maximum", "is it possible", "longest/shortest".

15.2 Two approaches

Top-down (Memoization)Bottom-up (Tabulation)
HowRecursion + cache resultsIteratively fill a table
ProsIntuitive, only needed statesNo recursion overhead, easy space-optimize
ConsStack space, function overheadMust order states correctly

15.3 The DP recipe

1. STATE   : what does dp[i] (or dp[i][j]) represent?
2. CHOICE  : at each state, what decisions can we make?
3. RECURRENCE: dp[i] = f(previous states)
4. BASE CASE
5. ORDER   : compute states before they're needed
6. ANSWER  : which dp cell holds the result?
7. OPTIMIZE: reduce space if only last row/few states are needed

15.4 Worked example: Fibonacci → Climbing Stairs

// dp[i] = ways to reach step i = dp[i-1] + dp[i-2]
int climb(int n){
    int a=1,b=1;                 // ways to reach step 0 and 1
    for(int i=2;i<=n;i++){ int c=a+b; a=b; b=c; }
    return b;                    // O(n) time, O(1) space
}

15.6 Coin Change (unbounded knapsack)

// min coins to make amount; dp[x] = fewest coins for amount x
int coinChange(int[] coins, int amount){
    int[] dp=new int[amount+1]; Arrays.fill(dp, amount+1); dp[0]=0;
    for(int x=1;x<=amount;x++)
        for(int c: coins) if(c<=x) dp[x]=Math.min(dp[x], dp[x-c]+1);
    return dp[amount]>amount ? -1 : dp[amount];   // O(amount * coins)
}
Common DP mistakes: wrong state definition (the #1 cause of failure); incorrect base cases; wrong iteration order (using a not-yet-computed state); off-by-one in table sizes; forgetting to handle "impossible" (e.g. -1 / infinity).
Strategy: first write the brute-force recursion, confirm it's correct, find the repeated subproblems, then add memoization. Convert to tabulation only if you need to optimize space/stack.
How do you tell DP from greedy?
Greedy makes one locally-optimal choice and never reconsiders — it works only when local optima compose into a global optimum (provable). DP explores all choices via overlapping subproblems and combines optimal sub-results. If a greedy choice can be "wrong" later, you need DP.
Memoization vs tabulation — which to use?
Memoization (top-down) is easier to derive from the recursion and only computes reachable states. Tabulation (bottom-up) avoids recursion overhead/stack limits and makes space optimization (rolling arrays) straightforward. Start with memoization; switch to tabulation if needed.

16. Greedy Algorithms Intermediate

Make the locally optimal choice at each step, hoping for a global optimum. Fast and simple — but only correct when the problem has the greedy-choice property and optimal substructure (must be proven/justified).

Greedy fails for 0/1 knapsack and coin change with arbitrary denominations — those need DP. Always sanity-check greedy with a counterexample before trusting it.
How do you prove a greedy algorithm is correct?
Two common techniques: exchange argument (show any optimal solution can be transformed into the greedy one without getting worse) and proving the greedy-choice property + optimal substructure. If you can't justify it, prefer DP.

int single(int[] a){ int x=0; for(int v:a) x^=v; return x; }   // O(n), O(1)
// Count set bits (Brian Kernighan): repeatedly drop lowest set bit
int count(int n){ int c=0; while(n!=0){ n&=(n-1); c++; } return c; }

Uses: single number, counting bits, subsets via bitmask, power-of-two checks, swapping without temp, bitmask DP, flags/permissions.

Why does n & (n-1) remove the lowest set bit?
Subtracting 1 flips the lowest set bit to 0 and all bits below it to 1. ANDing with the original clears that lowest set bit (and leaves higher bits unchanged). Repeating it counts set bits in O(number of set bits).

18.3 Misc must-know patterns

  • Cyclic sort — numbers 1..n in place → find missing/duplicate in O(n), O(1).
  • Dutch national flag — sort 0s/1s/2s in one pass (three pointers).
  • Boyer-Moore voting — majority element in O(n), O(1).

Find the missing number in 1..n — multiple ways?
(1) Sum formula: expected n(n+1)/2 minus actual sum. (2) XOR all indices and values — pairs cancel, leaving the missing one. (3) Cyclic sort then scan. XOR and sum are O(n) time, O(1) space.

19.4 Interview execution checklist

  1. Clarify — restate problem, ask about input ranges, edge cases, duplicates.
  2. Examples — walk a small example by hand.
  3. Brute force — state it + its complexity (shows baseline).
  4. Optimize — identify the pattern/bottleneck; pick a better DS/approach.
  5. Dry run — trace your idea before coding.
  6. Code — clean, named variables; think out loud.
  7. Test — edge cases: empty, single element, duplicates, negatives, overflow, max size.
  8. Complexity — state final time & space.
Universal edge cases to always check: empty input, single element, all-same elements, negative numbers, integer overflow, duplicates, already-sorted/reverse-sorted, very large input, null pointers.
Revision strategy: master one pattern at a time; do 5–10 problems per pattern until recognition is instant. Re-solve from scratch, don't just read solutions. Track problems you missed and revisit them. Quality of patterns > quantity of problems.
