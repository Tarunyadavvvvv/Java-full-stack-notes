Part I — Foundations

1. DevOps Culture, SDLC & Metrics Basic

1.1 What is DevOps?

DevOps is a culture + set of practices that unites Development and Operations to deliver software faster, more reliably, and continuously. It breaks down silos via automation, collaboration, and feedback loops.

Core idea: "You build it, you run it." DevOps is not a tool or a job title alone — it's a way of working that emphasizes shared ownership and automating everything repeatable.

1.2 The DevOps lifecycle (infinity loop)

Plan -> Code -> Build -> Test -> Release -> Deploy -> Operate -> Monitor
  ▲                                                                │
  └──────────────────── continuous feedback ──────────────────────┘

1.3 CALMS & the Three Ways

CALMSMeaning
CultureCollaboration, shared responsibility
AutomationAutomate builds, tests, deploys, infra
LeanEliminate waste, small batches
MeasurementMetrics drive decisions
SharingKnowledge & feedback across teams

The Three Ways: (1) Flow/Systems thinking, (2) Amplify feedback loops, (3) Continuous experimentation & learning.

1.4 DORA metrics (how DevOps performance is measured)

MetricMeasures
Deployment FrequencyHow often you deploy to prod
Lead Time for ChangesCommit → production time
Change Failure Rate% deploys causing failures
MTTRMean time to restore after an incident
Interview gold: the first two measure velocity; the last two measure stability. Elite teams score high on both — speed and stability aren't a trade-off when automation is strong.

1.5 Related concepts

  • Agile = iterative dev methodology; DevOps extends it through to operations.
  • CI/CD — continuous integration / delivery / deployment (the automation backbone).
  • Shift-left — move testing & security earlier in the lifecycle.
  • GitOps — Git as the single source of truth for infra & deployments (declarative, auto-reconciled).
Is DevOps a tool, a role, or a culture?
Primarily a culture and set of practices enabled by tools. Tools (Jenkins, Docker, K8s) implement DevOps, but without the cultural shift — shared ownership, automation mindset, blameless feedback — the tools alone don't deliver DevOps outcomes.

2.5 Process & resource troubleshooting

NeedCommand

What's listening on a port?ss -tlnp / netstat -tlnp

A server is slow — how do you investigate from Linux?
Check CPU/load (top, uptime), memory (free -h — is it swapping?), disk (df -h, iostat), I/O wait, network (ss), and the offending process. Then logs (journalctl, /var/log). Localize the bottleneck before acting.
Difference between SIGTERM (15) and SIGKILL (9)?
SIGTERM asks a process to shut down gracefully (it can clean up/flush). SIGKILL forcibly terminates it immediately — no cleanup, can't be caught. Always try SIGTERM first; SIGKILL is the last resort.

3. Shell Scripting Intermediate

3.1 Script basics

#!/bin/bash            # shebang - interpreter
set -euo pipefail      # safety: exit on error, undefined vars, pipe failures

NAME="world"           # variable (no spaces around =)
echo "Hello, $NAME"
echo "Args: $1 $2  count=$#  all=$@"   # positional args
result=$(date +%F)     # command substitution

3.2 Conditionals & loops

if [ -f "$file" ]; then echo "exists"; elif [ -d "$dir" ]; then echo "dir"; else echo "no"; fi

for f in *.log; do echo "$f"; done
for i in {1..5}; do echo "$i"; done
while read line; do echo "$line"; done < input.txt

case "$1" in
  start) echo "starting";;
  stop)  echo "stopping";;
  *)     echo "usage: $0 {start|stop}";;
esac
TestMeaning
-f / -d / -efile / dir / exists
-z / -nstring empty / non-empty
-eq -ne -lt -gtnumeric comparisons
== / !=string comparisons

3.3 Functions & exit codes

deploy() {
  local env="$1"
  echo "Deploying to $env"
  return 0
}
deploy "prod" || { echo "failed"; exit 1; }
echo "last exit code: $?"     # 0 = success, non-zero = failure
Best practices: always set -euo pipefail; quote variables ("$var") to avoid word-splitting; use shellcheck to lint; prefer $(...) over backticks; handle errors & exit codes; make scripts idempotent.
Pitfalls: unquoted variables breaking on spaces; using rm -rf $VAR when VAR is empty (catastrophic — rm -rf /); not checking exit codes; assuming cd succeeds.
What does set -e do and why use it?
It makes the script exit immediately if any command returns a non-zero (error) status, preventing the script from blindly continuing after a failure. Combined with -u (error on undefined variables) and -o pipefail (catch failures in pipelines), it makes scripts fail fast and safely.

Part III — CI/CD

5. CI/CD Concepts Intermediate — core

5.1 The three terms

TermMeaning
Continuous IntegrationMerge & auto build+test on every commit — catch issues early
Continuous DeliveryEvery passing build is release-ready; deploy to staging auto, prod with a manual approval
Continuous DeploymentEvery passing change auto-deploys to prod (no manual gate)

5.2 A typical pipeline

Commit -> [Checkout] -> [Build] -> [Unit Tests] -> [Static Analysis/Lint]
       -> [Security Scan] -> [Package/Image] -> [Push to Registry]
       -> [Deploy to Staging] -> [Integration/E2E Tests] -> [Approve] -> [Deploy to Prod]

5.3 Deployment strategies Important

StrategyHowTrade-off
RollingReplace instances graduallyNo downtime; mixed versions briefly
Blue-GreenTwo identical envs; switch trafficInstant rollback; needs 2× resources
CanaryRelease to small % first, then rampLimits blast radius; more complex routing
RecreateStop old, start newSimple; causes downtime
A/B / Feature flagsToggle features per userDecouple deploy from release
Blue-green vs canary deployment?
Blue-green keeps two full environments and switches all traffic at once (instant rollback by switching back). Canary gradually shifts a small percentage of traffic to the new version, monitors, then ramps up — limiting the blast radius of a bad release. Canary needs finer traffic control; blue-green needs double resources.
How do you achieve zero-downtime deployment?
Rolling/blue-green/canary + health checks + readiness probes so traffic only hits ready instances; backward-compatible DB migrations (expand-contract); graceful shutdown (drain connections); and load-balancer integration to add/remove instances cleanly.

6. Jenkins Intermediate

6.1 Architecture

[Controller (master)] --- schedules jobs, UI, plugins
      │
   [Agent 1] [Agent 2] [Agent 3]   <- run builds (distributed)
Triggers: SCM webhook, poll, cron, manual, upstream job
  • Controller orchestrates; agents/nodes execute builds (scale horizontally).
  • Plugins extend everything (Git, Docker, K8s, Slack...).
  • Pipeline as code: Jenkinsfile (Declarative or Scripted) checked into the repo.

6.2 Declarative Jenkinsfile example

pipeline {
  agent any
  environment { IMAGE = "myapp:${env.BUILD_NUMBER}" }
  stages {
    stage('Build')  { steps { sh './mvnw -B package' } }
    stage('Test')   { steps { sh './mvnw test' }
                      post { always { junit 'target/surefire-reports/*.xml' } } }
    stage('Docker') { steps { sh 'docker build -t $IMAGE .' } }
    stage('Deploy') {
      when { branch 'main' }
      steps { sh './deploy.sh $IMAGE' }
    }
  }
  post { failure { mail to: 'team@x.com', subject: 'Build failed' } }
}
ConceptMeaning
Stage / StepLogical phase / individual task
AgentWhere the stage runs
CredentialsSecrets stored in Jenkins, injected securely
Shared librariesReusable pipeline code across projects
Webhook triggerGit push auto-starts the pipeline
Pitfalls: storing secrets in the Jenkinsfile (use the Credentials store); running everything on the controller (use agents); no cleanup of workspace/old builds (disk fills); flaky tests blocking the pipeline.
Declarative vs Scripted pipeline?
Declarative is structured, opinionated, and easier to read/validate (the recommended default). Scripted is full Groovy — more flexible for complex logic but harder to maintain. Most teams use Declarative with shared libraries for reusable logic.

7. GitHub Actions & GitLab CI Intermediate

7.1 GitHub Actions

# .github/workflows/ci.yml
name: CI
on:
  push: { branches: [main] }
  pull_request:
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4

      - run: npm ci
      - run: npm test
      - name: Build & push image
        run: docker build -t ghcr.io/org/app:${{ github.sha }} .
        env: { TOKEN: ${{ secrets.GHCR_TOKEN }} }
TermMeaning
WorkflowYAML file of automated jobs
JobSet of steps on one runner (parallel by default)
Step / ActionA command / reusable unit
RunnerMachine executing the job (hosted or self-hosted)
SecretsEncrypted credentials

7.2 GitLab CI

# .gitlab-ci.yml
stages: [build, test, deploy]
variables: { IMAGE: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" }
build:
  stage: build
  script: [ "docker build -t $IMAGE .", "docker push $IMAGE" ]
test:
  stage: test
  script: [ "npm ci", "npm test" ]
deploy:
  stage: deploy
  script: [ "./deploy.sh $IMAGE" ]
  only: [ main ]
  environment: production
GitLab Runners execute jobs (shell/docker/k8s executors). GitLab CI is built into the platform; GitHub Actions has a huge marketplace of reusable actions. Both keep secrets in the platform's secret store — never in YAML.
Jenkins vs GitHub Actions/GitLab CI — when to choose?
Jenkins: self-hosted, plugin-rich, maximum flexibility, good for complex/legacy/on-prem needs — but more ops overhead. GitHub Actions/GitLab CI: tightly integrated with the repo, YAML-native, less infra to manage, great for cloud-native teams. Many orgs are migrating from Jenkins to the integrated CI of their SCM.

Part IV — Containers & Orchestration

8. Docker Advanced — must-know

8.1 Why containers

A container packages an app + its dependencies into a portable, isolated unit that runs identically anywhere. Solves "works on my machine."

VMContainer
IsolationFull OS per VM (hypervisor)Shares host kernel (namespaces/cgroups)
SizeGBsMBs
StartupMinutesSeconds
OverheadHeavyLight
How isolation works: Docker uses Linux namespaces (isolate PID, network, mount, users) and cgroups (limit CPU/memory). Containers are processes, not mini-VMs — that's why they're lightweight.

8.2 Key concepts

ConceptMeaning
ImageRead-only template (layers) — the blueprint
ContainerA running instance of an image
DockerfileRecipe to build an image
RegistryImage store (Docker Hub, ECR, GHCR)
LayersEach instruction = a cached layer
VolumePersistent storage outside container lifecycle
Networkbridge (default), host, none, overlay

8.3 Essential commands

docker build -t app:1.0 .          # build image from Dockerfile
docker run -d -p 8080:80 --name web app:1.0   # run detached, map ports
docker ps / docker ps -a           # running / all containers
docker logs -f web                 # follow logs
docker exec -it web sh             # shell into a running container
docker stop/start/rm web           # lifecycle
docker images / docker rmi app:1.0 # list / remove images
docker push/pull ghcr.io/org/app   # registry
docker system prune -a             # clean up everything unused

8.4 Multi-stage Dockerfile (best practice)

# Stage 1: build (heavy tooling)
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                         # cached unless deps change
COPY . .
RUN npm run build

# Stage 2: runtime (small, no build tools)
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
HEALTHCHECK CMD wget -qO- localhost || exit 1
CMD ["nginx", "-g", "daemon off;"]
Image best practices: use small base images (alpine/distroless); multi-stage builds; order layers least→most-changing for caching (copy deps before code); one process per container; run as non-root; use .dockerignore; pin versions; never bake secrets into images.

8.5 CMD vs ENTRYPOINT, COPY vs ADD

Difference
CMD vs ENTRYPOINTCMD = default args (overridable); ENTRYPOINT = the executable (fixed). Often combined.
COPY vs ADDCOPY = plain copy (preferred); ADD also untars & fetches URLs (use sparingly)
Volume vs bind mountManaged by Docker vs maps a host path
Why are my Docker builds slow / images huge?
Likely poor layer caching (copying all code before installing deps invalidates the cache on every change) and a fat base image with build tools. Fix: copy dependency manifests first & install (cached), then copy source; use multi-stage builds and a slim runtime base; add .dockerignore.
How do you persist data in a container?
Containers are ephemeral — their writable layer is lost on removal. Use volumes (Docker-managed, portable) or bind mounts (host path) to persist databases/uploads outside the container lifecycle.

9. Docker Compose Intermediate

Define & run multi-container apps with a single YAML file — ideal for local dev & small stacks.

# docker-compose.yml
services:
  web:
    build: .
    ports: ["8080:80"]
    depends_on: [db, redis]
    environment:
      - DB_URL=postgres://db:5432/app
  db:
    image: postgres:16
    volumes: ["pgdata:/var/lib/postgresql/data"]
    environment: { POSTGRES_PASSWORD: secret }
  redis:
    image: redis:7
volumes:
  pgdata:
docker compose up -d        # start all services
docker compose ps / logs -f # status / logs
docker compose down -v      # stop & remove (with volumes)
Service discovery: Compose puts services on one network; they reach each other by service name as hostname (e.g. db:5432). depends_on controls start order (but not readiness — use healthchecks for that).
Docker Compose vs Kubernetes?
Compose is for defining multi-container apps on a single host (great for local dev). Kubernetes orchestrates containers across a cluster of machines with scaling, self-healing, rolling updates, and service discovery at scale. Compose for dev; K8s for production at scale.

10.5 A Deployment + Service manifest

  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }

10.6 kubectl essentials

kubectl get pods/svc/deploy -n ns       # list resources
kubectl describe pod <name>              # detailed state + events (debug!)
kubectl logs -f <pod> [-c container]     # logs

10.7 Probes & self-healing

ProbePurpose
LivenessIs the app alive? Fail → restart the pod
ReadinessReady for traffic? Fail → remove from Service endpoints
StartupFor slow-starting apps; gates the other probes
Common K8s pitfalls: no resource requests/limits (noisy-neighbour, OOMKills); missing readiness probe (traffic to not-ready pods); using latest tag (no reproducibility); storing secrets in ConfigMaps; CrashLoopBackOff from bad config; ignoring pod describe events when debugging.
What happens when you run kubectl apply?
kubectl sends the desired state to the API Server, which persists it in etcd. Controllers notice the diff between desired and actual state and reconcile — the Deployment controller creates a ReplicaSet, which creates Pods; the Scheduler assigns them to nodes; kubelets pull images and run containers. K8s continuously reconciles to keep actual = desired.
Pod is in CrashLoopBackOff — how do you debug?
kubectl describe pod (events: image pull error? OOMKilled?), kubectl logs <pod> --previous (crash output), check resource limits, config/secret mounts, and the liveness probe. CrashLoopBackOff means the container keeps exiting and K8s keeps restarting with backoff.
Deployment vs StatefulSet?
Deployment is for stateless apps — interchangeable pods, any can be replaced. StatefulSet gives stable network identities (pod-0, pod-1), stable persistent storage per pod, and ordered rollout/scaling — needed for databases, Kafka, etc.

11. Helm Intermediate

Helm is the package manager for Kubernetes — bundles related manifests into a versioned, parameterized chart.

ConceptMeaning
ChartA package of K8s templates
values.yamlDefault config (overridable per environment)
TemplateManifest with {{ .Values.x }} placeholders
ReleaseAn installed instance of a chart
RepositoryCollection of charts
helm install myapp ./chart -f values-prod.yaml   # install with prod values
helm upgrade myapp ./chart --set image.tag=1.3   # upgrade
helm rollback myapp 1                             # roll back to revision 1
helm list / helm uninstall myapp
Why Helm: avoids copy-pasting near-identical YAML per environment. One templated chart + different values files = dev/staging/prod. Supports versioning, rollback, and sharing (e.g. install Prometheus via a community chart in one command).
Helm vs Kustomize?
Helm uses templating + a values file and a package/release model with rollback — powerful for complex, reusable, distributable apps. Kustomize uses overlays to patch base manifests without templating (built into kubectl) — simpler for environment variations. Many teams use Kustomize for in-house apps and Helm for third-party packages.

12.3 Key cloud concepts

  • Regions & Availability Zones — deploy across AZs for HA; across regions for DR/latency.
  • VPC — isolated virtual network; subnets (public/private), route tables, security groups (instance firewall), NACLs.
  • IAM — users, roles, policies; least privilege; prefer roles over long-lived keys.
  • Auto Scaling Groups + Load Balancer — elastic, self-healing compute.
  • Shared Responsibility Model — cloud secures "of the cloud", you secure "in the cloud".
Cost & reliability: right-size instances, use spot/reserved for savings, set budgets/alerts, design for failure across AZs, tag resources, and automate teardown of non-prod.
Region vs Availability Zone?
A region is a geographic area (e.g. us-east-1). An AZ is an isolated datacenter within a region. Spreading instances across multiple AZs survives a datacenter failure (high availability); spreading across regions handles regional outages and reduces latency for global users.
Security Group vs NACL?
Security Groups are stateful instance-level firewalls (return traffic auto-allowed; allow rules only). NACLs are stateless subnet-level firewalls (allow + deny rules, evaluated in order, return traffic must be explicitly allowed). SGs are the primary control; NACLs add a coarse subnet layer.

13. Terraform (Infrastructure as Code) Advanced

13.1 What & why IaC

Infrastructure as Code = define infrastructure in version-controlled files instead of clicking consoles. Benefits: reproducible, reviewable, auditable, automatable. Terraform is the leading declarative, cloud-agnostic IaC tool.

13.2 Core workflow

terraform init      # download providers, set up backend
terraform plan      # preview changes (dry run) — review before applying!
terraform apply     # create/update infra to match config
terraform destroy   # tear down

13.3 Example configuration (HCL)

provider "aws" { region = "us-east-1" }

resource "aws_instance" "web" {
  ami           = var.ami_id
  instance_type = "t3.micro"
  tags = { Name = "web-${var.env}" }
}

variable "env" { type = string; default = "dev" }
output "public_ip" { value = aws_instance.web.public_ip }
ConceptMeaning
ProviderPlugin for a platform (aws, azure, k8s...)
ResourceAn infra object to create
Variable / OutputInputs / exported values
ModuleReusable group of resources
StateMaps config to real resources (terraform.tfstate)

13.4 State — the critical concept

Terraform state tracks what it has created. Store it remotely (S3 + DynamoDB lock, or Terraform Cloud) for team use — never commit it to Git (it can contain secrets) and never edit it by hand. Use state locking to prevent concurrent applies corrupting it.

StrengthCloud resource lifecycleApp/OS config, orchestration
Often usedTogether: TF provisions, Ansible configures
What's the difference between plan and apply, and why does plan matter?
plan computes and shows the diff between desired config and current state without changing anything — a safety review. apply executes those changes. Always review the plan (especially "destroy" actions) before applying, ideally in a PR/CI gate.
How do you manage multiple environments (dev/staging/prod) in Terraform?
Use separate state per environment (workspaces or separate backends/directories) + variable files (dev.tfvars, prod.tfvars) + reusable modules. This keeps environments isolated and consistent. Many teams use a directory-per-env layout for clearer separation.

14. Ansible (Configuration Management) Intermediate

Ansible automates server configuration, app deployment, and orchestration. Agentless (uses SSH), idempotent, and uses simple YAML playbooks.

ConceptMeaning
InventoryList of target hosts (grouped)
PlaybookYAML file of plays/tasks
TaskA single action using a module
ModuleUnit of work (apt, copy, service, template...)
RoleReusable, structured bundle of tasks/vars/templates
HandlerTask triggered by change (e.g. restart on config change)
# playbook.yml
- hosts: webservers
  become: true                       # sudo
  tasks:
    - name: Install nginx
      apt: { name: nginx, state: present, update_cache: true }
    - name: Deploy config
      template: { src: nginx.conf.j2, dest: /etc/nginx/nginx.conf }
      notify: Restart nginx          # triggers handler
    - name: Ensure running
      service: { name: nginx, state: started, enabled: true }
  handlers:
    - name: Restart nginx
      service: { name: nginx, state: restarted }
ansible-playbook -i inventory playbook.yml
ansible all -i inventory -m ping     # ad-hoc connectivity check
Idempotency: Ansible modules describe desired state, so re-running a playbook makes no changes if the system already matches — safe to run repeatedly. Push-based & agentless (only needs SSH + Python on targets).
Why is idempotency important in configuration management?
It means running the same playbook multiple times always converges to the same state without unintended side effects. You can re-run safely after partial failures or to enforce drift correction, making automation predictable and reliable.

Why put Nginx in front of an app server?
To offload SSL termination, serve static files efficiently, load-balance across app instances, add caching/compression/rate-limiting, and hide/protect the backends. App servers focus on business logic while Nginx handles edge concerns.

Push vs pull monitoring — why is Prometheus pull-based?
Pull (Prometheus scrapes targets) makes targets simpler (just expose /metrics), lets the server control scrape rate, and easily detects "target down". Push suits short-lived jobs (via a Pushgateway) and ephemeral functions. Prometheus chose pull for service-discovery-friendly, reliable scraping.
How do you set up effective alerting without alert fatigue?
Alert on symptoms that affect users (golden signals / SLO burn rate), not every metric. Make alerts actionable, severity-tiered, and de-duplicated; use multi-window burn-rate alerts; route via Alertmanager; and continuously prune noisy/non-actionable alerts.

18. Security & DevSecOps Advanced

18.1 DevSecOps = shift security left

Integrate security into every stage of the pipeline (not a final gate). "Security as code", automated scanning, and shared responsibility.

Code -> [SAST + secret scan] -> Build -> [SCA: dependency scan]
     -> Image -> [container/image scan] -> Deploy -> [DAST + runtime/policy]

18.2 Secrets management

Never hard-code secrets in code, images, or YAML. Use a secrets manager: HashiCorp Vault, AWS Secrets Manager, K8s Secrets (+ encryption at rest / external secrets), or SOPS. Rotate regularly, inject at runtime, audit access, and scan repos for leaks. If leaked → rotate immediately.

18.3 Core security principles

  • Least privilege (IAM, RBAC), defense in depth, zero trust.
  • Encrypt in transit (TLS) & at rest.
  • Patch & update base images/dependencies; minimal images reduce attack surface.
  • Run containers as non-root; read-only filesystems; drop capabilities; network policies.
  • Supply chain security — sign images (cosign), SBOMs, verify provenance.
  • Audit logging & compliance (CIS benchmarks).
How do you secure a CI/CD pipeline?
Store secrets in a vault (never in code/logs); use short-lived, least-privilege credentials/OIDC for cloud access; scan code, dependencies, images, and IaC in the pipeline; sign and verify artifacts; protect branches with reviews; isolate runners; and audit every deploy. The pipeline is a high-value target — treat it like production.
What is shift-left security?
Moving security checks earlier (left) in the development lifecycle — into the IDE, commit, and CI stages — instead of only at the end. Catching vulnerabilities early is cheaper and faster to fix and prevents insecure code from progressing.

21. SRE Concepts Advanced

Site Reliability Engineering = applying software engineering to operations. "SRE is what happens when you treat operations as a software problem." (Google)

ConceptMeaning
SLIService Level Indicator — a measured metric (e.g. latency, error rate)
SLOObjective — target for an SLI (e.g. 99.9% < 200ms)
SLAAgreement — contractual promise to customers (with penalties)
Error budgetAllowed unreliability (100% − SLO); spend it on velocity
ToilManual, repetitive ops work — automate it away
MTTR / MTBFMean time to recover / between failures
Error budget in action: if your SLO is 99.9%, you have ~43 min/month of allowed downtime. While budget remains, ship features fast. If you burn it, freeze risky releases and focus on reliability. It turns the dev-vs-ops "stability vs speed" fight into a shared, data-driven decision.

21.1 Reliability practices

  • Blameless postmortems — learn from incidents, fix systems not people.
  • Incident management — roles, runbooks, on-call rotations, escalation.
  • Chaos engineering — deliberately inject failures to test resilience (Chaos Monkey).
  • Capacity planning, graceful degradation, redundancy, automate toil.
SLI vs SLO vs SLA?
SLI is the measurement (e.g. % of requests under 200ms). SLO is your internal target for that SLI (e.g. 99.9%). SLA is the external, contractual commitment to customers (usually looser than the SLO, with penalties). You set SLOs stricter than SLAs to have a safety margin.
What is an error budget and why is it useful?
It's the acceptable amount of failure (100% minus the SLO). It quantifies the trade-off between reliability and feature velocity: with budget remaining, teams ship aggressively; when it's exhausted, they prioritize stability. It aligns dev and ops on objective data rather than opinion.

Part IX — Interview Preparation

22. Scenarios & Cheat-Sheet Essential

22.1 Scenario questions

Walk me through what happens from git push to production.
Push triggers a CI pipeline (webhook) → checkout, build, unit tests, lint, security scans → build & push a container image to a registry → deploy to staging (Helm/kubectl/Terraform) → run integration/E2E tests → manual approval gate → progressive deploy to prod (canary/blue-green) with health checks → monitor metrics/logs/traces → auto-rollback if SLOs breach.
Production is down — how do you respond?
Acknowledge & declare an incident; check dashboards/alerts (golden signals) to localize; look at recent changes (a deploy?) — roll back if so; check logs/traces; mitigate first (restore service) then root-cause; communicate status; afterward run a blameless postmortem and add safeguards (alerts/tests/automation).
How would you design a CI/CD pipeline for a microservices app on Kubernetes?
Per-service pipelines: build & test → scan (SAST/SCA/image) → push image → update a Helm chart / GitOps repo (Argo CD reconciles) → deploy to namespaces per env → canary with metrics-based promotion → observability + auto-rollback. Use trunk-based dev, immutable images promoted across envs, and secrets from a vault.
How do you reduce a slow Docker build in CI?
Layer caching (copy deps before code), multi-stage builds, a slim base image, BuildKit cache mounts, caching dependencies between CI runs, and only rebuilding changed services. Also parallelize independent jobs.
