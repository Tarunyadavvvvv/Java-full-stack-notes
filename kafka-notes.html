Part I — Foundations

1. Introduction & Why Kafka Basic ↑ Contents

1.1 What is Apache Kafka?

Apache Kafka is a distributed event streaming platform — a high-throughput, fault-tolerant, durable system for publishing, storing, and processing streams of records (events) in real time. Originally built at LinkedIn, it acts as a distributed, append-only, replicated commit log.

Think of Kafka as the central nervous system for data: producers write events, Kafka durably stores them in order, and many independent consumers read them at their own pace.

🔍 In plain terms: a "commit log" is just a notebook you can only add to — you write each new event on the next line and never erase or insert in the middle. Kafka is that notebook, but copied across several machines for safety, and readers each keep their own bookmark so they can read at their own speed and even flip back to re-read.

1.2 The problem it solves

Without Kafka, N source systems talking to M target systems need N×M point-to-point integrations — brittle, tightly coupled, and hard to scale. Kafka decouples them: every source writes once to Kafka, every target reads from Kafka.

Before:  Sources --+--+--+--> Targets   (N x M spaghetti integrations)
After:   Sources --> [ KAFKA ] --> Targets   (N + M, fully decoupled)

1.3 Messaging models — where Kafka fits

There are two classic ways to deliver messages, and a common interview trap is thinking you must pick one. The distinction below matters because it decides who gets which message — and Kafka's clever trick is that it does both, chosen simply by how you group your consumers.

ModelBehaviourKafka equivalent
Queue (point-to-point)One message consumed by one consumerConsumers in the same group
Pub/Sub (topic)Each subscriber gets every messageConsumers in different groups
Kafka unifies both: within a consumer group it behaves like a queue (load balanced); across groups it behaves like pub/sub (broadcast). The data stays on disk so consumers can replay.

1.4 Key characteristics

High throughputHorizontally scalableDurable (disk)Fault-tolerant (replication)DistributedReplayableLow latency

1.5 Real-world use cases

The reason Kafka shows up in so many architectures is that "a durable, replayable stream of events" is a shape that fits a surprising number of problems. Each row below is really the same idea — write events once, let many systems react — applied to a different domain.

Use caseDescription
Messaging / decouplingBackbone between microservices
Activity trackingClicks, page views, user events (original LinkedIn use)

1.6 Advantages & disadvantages

Kafka is powerful but not free — it earns its keep at scale and becomes overkill for small, simple needs. The table pairs each strength with the cost that comes with it, so you can judge whether Kafka is the right tool rather than just a fashionable one.

AdvantagesDisadvantages / costs
Massive throughput (millions msg/s)Operational complexity (cluster, tuning)
Durable & replayable storageNot ideal for tiny/low-volume needs
Horizontal scalability via partitionsNo per-message priority; limited routing
Strong ordering per partitionNo global ordering across partitions
Rich ecosystem (Connect, Streams)Steep learning curve; needs careful capacity planning
Is Kafka a message queue or a database?
Neither exactly — it's a distributed, durable commit log. It behaves like a queue/pub-sub for delivery, but unlike a traditional queue it retains messages on disk for a configured time and lets multiple consumers replay them independently.
Why is Kafka so fast despite writing to disk?
Sequential disk I/O (append-only log) is nearly as fast as memory; the OS page cache serves reads; zero-copy (sendfile) sends data from page cache to socket without copying into user space; batching and compression reduce overhead.

These terms recur constantly, so it pays to anchor them early. The three that carry the most weight are broker (a server), partition (an ordered log), and offset (a position in that log) — almost every other Kafka concept is ultimately defined in terms of these three.

2.4 The role of the Controller

  • One broker is elected controller; it manages partition leader elections, tracks broker liveness, and propagates metadata.
  • If the controller fails, a new one is elected (via ZooKeeper, or the KRaft quorum in newer versions).
🔍 In plain terms: the controller is the cluster's "shift manager." The other brokers do the actual work of storing and serving data; the controller just keeps the org chart up to date — who's alive, who's the leader of each partition — and reshuffles duties when someone leaves. There's exactly one on duty at a time.
What exactly does a broker do?
It receives records from producers, assigns offsets, persists them to the partition log on disk, replicates them, and serves fetch requests to consumers. Brokers are stateless about consumers — consumers track their own offsets.

3. Topics, Partitions & Offsets Intermediate ↑ Contents

3.1 Partitions = parallelism + ordering

A topic is split into partitions. Each partition is an ordered, append-only sequence of records identified by a monotonically increasing offset. Partitions are how Kafka scales (spread across brokers) and how it parallelizes consumption.

🔍 In plain terms: a topic is a highway; partitions are its lanes. Cars (records) stay in strict order within a lane, but across lanes there's no guaranteed order. Adding lanes lets more traffic flow at once (parallelism) — and the "offset" is just the position of a car counted from the start of its own lane.
Topic "orders" with 3 partitions:
P0: [0][1][2][3][4]                 <- offsets per partition (NOT global)
P1: [0][1][2]
P2: [0][1][2][3]
Order is guaranteed WITHIN a partition, NOT across partitions.

3.2 Producer partitioning

How a record is assigned to a partition is one of the most consequential decisions in Kafka, because the partition choice decides ordering: records that must stay in order have to land in the same partition. The table shows the four ways that choice is made.

ScenarioPartition chosen by
Key presenthash(key) % numPartitions — same key → same partition (stable ordering)
No keySticky partitioner (batches to one partition, rotates) for efficiency
Explicit partitionProducer specifies the partition number directly
CustomImplement a Partitioner
Pitfall: Increasing partition count later changes key→partition mapping (because of the modulo), breaking ordering guarantees for existing keys. Plan partition count up front.

3.3 Choosing partition count

  • More partitions → more parallelism & throughput, but also more open file handles, more memory, longer leader-election/recovery, and more end-to-end latency.
  • Rough rule: target throughput ÷ per-partition throughput; and partitions ≥ max expected consumers in a group.
  • Max useful consumers in a group = number of partitions (extra consumers sit idle).

3.4 Offsets & positions

Kafka tracks several different "offsets" and interviewers love to see if you can keep them straight. They matter because together they answer three separate questions: where does new data go (LEO), how far can I safely read (high watermark), and how far have I gotten (committed offset / position).

TermMeaning
Log-end offset (LEO)Offset of the next record to be written
High watermark (HW)Highest offset replicated to all in-sync replicas; consumers can only read up to HW
Committed offsetLast offset a consumer group acknowledged processing
Current positionNext offset the consumer will read
🔍 In plain terms: imagine a book being written live. The log-end offset is the blank page the author is about to write next. The high watermark is the last page the publisher has confirmed is safely printed in every copy — you're only allowed to read up to there. Your committed offset is the bookmark you've saved, and your position is the page you're actually on right now.
Where are consumer offsets stored? In an internal compacted topic __consumer_offsets (not in ZooKeeper since modern versions).

4. Producers In Depth Intermediate ↑ Contents

4.1 Producer write flow

send() -> Serializer -> Partitioner -> RecordAccumulator (per-partition batches in memory)
       -> Sender (I/O) thread -> broker (partition leader) -> ack back

Records are buffered and sent in batches per partition, optionally compressed, by a background I/O thread. This batching is key to Kafka's throughput.

4.2 The acks setting (durability vs latency)

The acks setting is the single biggest knob for the "safety vs speed" trade-off: it decides how many copies must confirm a write before the producer calls it done. Turn it down for raw speed and accept possible loss; turn it up for safety and accept some latency. This one setting underlies most "how do I avoid losing data?" answers.

acksGuaranteeTrade-off
acks=0Fire-and-forget; no ackFastest, can lose data
acks=1Leader wrote itLost if leader dies before replication
acks=all (-1)Leader + all in-sync replicasStrongest durability, higher latency
For durability use acks=all + min.insync.replicas=2 + replication factor ≥ 3. Then a write succeeds only if at least 2 replicas have it — you can lose one broker without data loss. (See the fully worked example in §6.2.)

4.3 Key producer configs

The configs below cluster around two goals: throughput (batching and compression) and correctness (ordering and dedup on retry). Knowing which lever does which is what separates "I set acks=all" from actually understanding producer behaviour.

ConfigEffect
batch.sizeMax bytes per partition batch
linger.msWait time to fill a batch (small delay → bigger batches → more throughput)
compression.typenone / gzip / snappy / lz4 / zstd
buffer.memoryTotal producer buffer; blocks/throws when full
max.in.flight.requests.per.connectionUnacked requests per connection (affects ordering on retry)
retries / delivery.timeout.msRetry behaviour on transient failures
enable.idempotenceExactly-once-per-partition writes (dedup on retry)

4.4 Idempotent producer

With enable.idempotence=true (default in modern Kafka), each producer gets a Producer ID (PID) and per-partition sequence numbers. The broker rejects duplicates from retries, preventing duplicate records caused by network retries — exactly-once semantics per partition without losing ordering.

🔍 In plain terms: it's like numbering every letter you mail ("#1, #2, #3..."). If the post office isn't sure your letter #2 arrived and you send it again, the recipient sees it's a duplicate of #2 and throws the copy away. You never worry that a re-send created two identical letters.
Properties p = new Properties();
p.put("bootstrap.servers", "broker:9092");
p.put("key.serializer", StringSerializer.class.getName());
p.put("value.serializer", StringSerializer.class.getName());
p.put("acks", "all");
p.put("enable.idempotence", true);
p.put("linger.ms", 5);
p.put("compression.type", "lz4");

try (KafkaProducer<String,String> producer = new KafkaProducer<>(p)) {
    ProducerRecord<String,String> rec =
        new ProducerRecord<>("orders", order.getId(), order.toJson());
    producer.send(rec, (meta, ex) -> {
        if (ex != null) log.error("send failed", ex);
        else log.info("sent to {}-{}@{}", meta.topic(), meta.partition(), meta.offset());
    });
}  // close() flushes pending records

4.5 Sync vs async send

  • Fire-and-forget: send(rec) — fastest, may lose on failure.
  • Async with callback: send(rec, callback) — recommended; non-blocking with error handling.
  • Synchronous: send(rec).get() — blocks, lowest throughput, used when strict per-record confirmation is needed.

4.6 Retries & ordering — a walkthrough

This is subtle enough to deserve a full walkthrough, because it surprises people: plain retries can silently reorder your records. Suppose the producer is allowed several unacknowledged (in-flight) requests at once for higher throughput, and one of them fails and is retried.

Before — without idempotence (max.in.flight.requests=5, a transient failure on the first batch): 
Producer sends two batches to partition P, back to back:
   Batch B1  (records that should occupy offsets 100,101,102)
   Batch B2  (records that should occupy offsets 103,104,105)

   B1 hits a transient network error  -> queued for RETRY
   B2 was already in flight            -> succeeds first, written at 100,101,102
   B1 is retried                       -> written AFTER B2, at 103,104,105

On disk, by offset:  [B2 records][B1 records]   <-  ORDER FLIPPED
(If B1 had also partly succeeded before the error, you could even get DUPLICATES.)
After — with enable.idempotence=true (the modern default): 
Every record carries a Producer ID (PID) + a per-partition SEQUENCE number.
The broker will only accept sequences in order and rejects duplicates.

   B2 (sequences 3,4,5) arrives before B1 (sequences 0,1,2)
   -> broker sees a gap (expected seq 0 next), REJECTS B2 as out-of-order
   -> B1 is retried and accepted (seq 0,1,2)
   -> B2 is re-accepted right after (seq 3,4,5)

On disk, by offset:  [B1 records][B2 records]   <-  ORDER PRESERVED, no duplicates
Kafka safely allows up to 5 in-flight requests while still guaranteeing order.

So the fix is simply to leave idempotence on. Without it, the only way to guarantee order under retries is max.in.flight.requests.per.connection=1, which throttles throughput.

Best practices: tune linger.ms (5–100ms) + batch.size for throughput; enable compression (lz4/zstd); always handle the send callback; reuse a single producer instance (thread-safe).
How does a producer decide the partition?
If a partition is set explicitly, it uses that. Else if a key is present, hash(key) % partitions. Else the sticky partitioner picks one partition per batch and rotates, maximizing batching efficiency.

5. Consumers & Consumer Groups Intermediate ↑ Contents

5.1 Consumer groups & partition assignment

Consumers label themselves with a group.id. Kafka divides a topic's partitions among the consumers in a group so each partition is read by exactly one consumer in that group. Different groups each get the full stream independently.

🔍 In plain terms: a consumer group is a team splitting up a pile of to-do lists (partitions). Each list is handled by exactly one teammate so no work is done twice. Add teammates and the lists get redistributed; if there are more teammates than lists, the extras have nothing to do. A different team gets its own full copy of every list.
Topic with 4 partitions (P0..P3), Group "billing" with 2 consumers:
  Consumer A -> P0, P1
  Consumer B -> P2, P3
Add Consumer C (3 consumers): A->P0,P1  B->P2  C->P3
Add 5th consumer with 4 partitions -> 1 consumer stays IDLE.
Pull model: Consumers poll brokers for data (consumer.poll()), controlling their own rate (back-pressure friendly) — brokers don't push.

5.2 Offset management & commit strategies

"Committing an offset" is how a consumer bookmarks its progress so that after a restart or rebalance it resumes from the right place. The strategy you pick is really a choice about when you save that bookmark relative to doing the work — and that timing decides whether a crash causes lost messages or duplicate processing.

StrategyHowRisk
Auto commitenable.auto.commit=true, periodicCan lose or reprocess (commits before/after processing)
Manual synccommitSync() after processingBlocking, but reliable; at-least-once
Manual asynccommitAsync()Faster, no retry on failure
props.put("group.id", "billing");
props.put("enable.auto.commit", "false");        // commit manually
props.put("auto.offset.reset", "earliest");        // where to start if no offset

try (KafkaConsumer<String,String> consumer = new KafkaConsumer<>(props)) {
    consumer.subscribe(List.of("orders"));
    while (running) {
        ConsumerRecords<String,String> records = consumer.poll(Duration.ofMillis(500));
        for (ConsumerRecord<String,String> r : records) {
            process(r);                            // do work FIRST
        }
        consumer.commitSync();                     // then commit -> at-least-once
    }
}

5.3 auto.offset.reset

ValueBehaviour when no committed offset exists
earliestStart from the beginning of the partition
latest (default)Start from new messages only
noneThrow an exception

5.4 Rebalancing Important

A rebalance reassigns partitions among group members. Triggered when a consumer joins/leaves, crashes, or partitions change.

🔍 In plain terms: a rebalance is the team pausing to re-divide the to-do lists when someone joins or leaves. The old way made everyone stop and drop everything before re-dividing (a jarring pause); the modern way only hands over the few lists that actually need to change hands, so most people never stop working.
  • Stop-the-world (eager): all consumers stop, revoke everything, then reassign — causes a pause.
  • Cooperative/incremental rebalancing (modern default): only the affected partitions move; the rest keep processing — minimal disruption.
  • Static membership (group.instance.id): avoids rebalances on transient restarts/timeouts.

5.4.1 What actually happens to your app during a rebalance

Abstract descriptions of rebalancing rarely stick. Here is a concrete timeline: group billing reads a topic with 6 partitions; consumers A and B each own 3; a third consumer C starts up.

t0  STEADY STATE
    A owns P0,P1,P2   B owns P3,P4,P5   -> both polling & processing normally

t1  C starts and sends a "JoinGroup" request to the group coordinator (a broker).

t2  REBALANCE BEGINS (cooperative/incremental protocol)
    Coordinator decides B should hand P5 to C. ONLY P5 is affected:
      - B is told to revoke P5 -> B runs onPartitionsRevoked(P5) and
        commits its latest offset for P5 (so C can resume from the right spot)
      - A keeps processing P0,P1,P2 the ENTIRE time  (never pauses)
      - B keeps processing P3,P4 the ENTIRE time     (only P5 paused)

t3  REASSIGNMENT
    C is assigned P5 -> C runs onPartitionsAssigned(P5) and starts reading P5
    from B's last committed offset. Processing on P5 resumes.

t4  NEW STEADY STATE
    A owns P0,P1,P2   B owns P3,P4   C owns P5   -> all three processing.

Only P5 experienced a brief pause (t2->t3). Everything else kept flowing.

--- Contrast: the OLD "eager" protocol at t2 ---
    ALL of A, B, (and C) revoke ALL their partitions and stop processing,
    then wait for a brand-new assignment before anyone resumes.
    That full "stop-the-world" pause is exactly what cooperative rebalancing avoids.
Don't confuse two different "reassignments." A consumer group rebalance (this section) moves ownership of partitions among consumers in a group — it's a client-side event that happens routinely whenever consumers join/leave, and no data moves between machines. Partition reassignment (via kafka-reassign-partitions) moves partition replicas among brokers — a server-side, admin-triggered operation done when you add/remove brokers or fix data skew, and it physically copies partition data across machines. Same word "reassign," completely different mechanisms — interviewers love when you separate them cleanly.
AssignorStrategy
RangeAssignorPer-topic ranges (can imbalance)
RoundRobinEven spread across all partitions
StickyAssignor / CooperativeStickyMinimize movement, keep assignments stable

5.5 Liveness: heartbeats & poll

Kafka has to tell the difference between "this consumer is busy" and "this consumer is dead," and it uses two independent clocks to do it: a background heartbeat that proves the consumer is alive, and the gap between poll() calls that proves it's actually making progress. Understanding both is the key to diagnosing the endless-rebalance bug below.

ConfigMeaning
session.timeout.msNo heartbeat within this → consumer considered dead
heartbeat.interval.msHow often heartbeats are sent (background thread)
max.poll.interval.msMax gap between poll() calls before being kicked out
max.poll.recordsMax records per poll (control batch size/processing time)
Classic bug: slow processing exceeds max.poll.interval.ms → consumer is removed → rebalance → messages reprocessed (duplicates). Fix by reducing max.poll.records, speeding up processing, or offloading to worker threads.

5.6 How consumer lag is actually calculated

"Consumer lag" is the single most important health metric, and it's simpler than it sounds. For each partition it's just one subtraction: how far the log has been written minus how far this group has confirmed reading.

🔍 In plain terms: lag is the size of your unread backlog — like unread emails. If new mail arrives as fast as you read it, your unread count holds steady (keeping up). If it climbs, you're falling behind. If it's near zero, you're caught up.
Per-partition lag = Log-End Offset (LEO)  -  Consumer's committed offset

Worked example, partition orders-0:
   Log-End Offset (newest record produced) = 10,000
   Consumer group's committed offset        =  9,850
   ------------------------------------------------------
   Lag on orders-0                          =    150 records  (backlog)

Total group lag = sum of per-partition lag across every partition the group owns.

You can see all three numbers with:
   kafka-consumer-groups --bootstrap-server broker:9092 \
       --describe --group billing
   ->  TOPIC   PARTITION   CURRENT-OFFSET   LOG-END-OFFSET   LAG
       orders  0           9850             10000            150

What matters is the trend, not the absolute number: steady lag means you're keeping pace; steadily rising lag means consumers can't keep up and you need more partitions/consumers, faster processing, or a fix downstream.

Can two consumers in the same group read the same partition?
No. Within a group, each partition is owned by exactly one consumer. To have multiple readers of the same data, put them in different consumer groups.
How do you achieve more parallelism than partitions allow?
You can't increase group parallelism beyond the partition count — extra consumers idle. Either add partitions (carefully, it remaps keys) or process records concurrently within a consumer (worker threads), managing offset commits carefully.
Best practices: commit after processing for at-least-once; design idempotent consumers; keep processing fast or raise max.poll.interval.ms; prefer CooperativeSticky assignor; use static membership for rolling restarts.

Part II — Internals

6. Replication, ISR & Leader Election Advanced ↑ Contents

6.1 Replication basics

Each partition has a replication factor (e.g. 3). One replica is the leader; the rest are followers. All reads & writes go through the leader; followers replicate by fetching from the leader. If the leader fails, a follower is promoted.

🔍 In plain terms: replication is keeping identical photocopies of each partition on several brokers so one machine dying doesn't lose your data. One copy is "in charge" (the leader) and handles all reads and writes; the others (followers) just keep copying it, ready to take over.
Partition orders-0, RF=3:
  Broker1: LEADER   <- producers/consumers talk here
  Broker2: follower <- fetches from leader
  Broker3: follower <- fetches from leader

6.2 ISR (In-Sync Replicas)

The ISR is the set of replicas (including the leader) that are fully caught up with the leader (within replica.lag.time.max.ms). Only ISR members are eligible to become leader (with clean leader election).

🔍 In plain terms: the ISR is the list of copies that are actually up to date right now. Picture a group chat: the "in-sync" members are the ones who have read every message. Only they are allowed to take over as leader, because only they know the whole story. Anyone who falls behind (slow or offline) quietly drops off the list until they catch back up.
  • acks=all requires all ISR members (not all replicas) to ack.
  • min.insync.replicas — minimum ISR size for a write to succeed; if ISR shrinks below it, producers with acks=all get an error (fail closed, preserving durability).
Durability formula: RF=3 + min.insync.replicas=2 + acks=all tolerates 1 broker failure with zero data loss while staying available.

6.2.1 A fully worked example of the durability formula

Let's make that formula concrete by following one specific write through one specific broker failure. Setup: partition orders-0 with RF=3 — replicas on Broker1 (leader), Broker2, Broker3. Config: min.insync.replicas=2, producer uses acks=all. Initially ISR = {B1, B2, B3}.

STEP 1 - the write arrives
  Producer sends record R (acks=all) -> leader B1 appends R at offset 500.

STEP 2 - replication
  Followers B2 and B3 fetch R and append it to their logs.

STEP 3 - acknowledgement
  acks=all means the leader waits until all IN-SYNC replicas have R.
  Once B2 and B3 confirm, B1 acknowledges to the producer.
  R is now "committed" and visible to consumers (at/under the high watermark).

NOW Broker3 dies.
  - ISR shrinks from {B1,B2,B3} to {B1,B2}.
  - ISR size = 2, which still meets min.insync.replicas=2  -> writes continue.
  - R is safe: it lives on B1 and B2. ZERO data loss, cluster stays AVAILABLE.
  => This is the "tolerate 1 broker failure" the formula promises.

NOW Broker1 (the leader) ALSO dies (a second, simultaneous failure).
  - Clean election promotes B2 (it's in the ISR and has R) to leader.
    R SURVIVES, because a committed record is guaranteed to be on every ISR member.
  - But ISR is now just {B2}, size 1 < min.insync.replicas=2.
    -> New acks=all writes are REJECTED with NotEnoughReplicas
       until another replica catches up.
    -> Kafka chooses to STOP accepting writes rather than risk losing them
       ("fail closed").

Takeaway: RF=3 + min.insync.replicas=2 + acks=all survives one broker failure with zero loss and continued availability. A second simultaneous failure still preserves every already-committed record, but pauses new writes until the cluster heals — Kafka deliberately trades a bit of availability to guarantee it never loses acknowledged data. That's the durability-vs-availability trade-off, made concrete.

6.3 Leader election & unclean elections

When a leader broker dies, someone has to take over — and who is allowed to take over is the whole ballgame for data safety. The table contrasts the safe default with the risky option.

Clean electionUnclean election
New leader fromISR onlyAny replica (even out-of-sync)
Data lossNonePossible
AvailabilityMay be unavailable if no ISRStays available
🔍 In plain terms: think of a relay race. In a clean election, if the runner holding the baton trips, only a teammate who was running right alongside (an in-sync replica) can pick it up — no distance lost. An unclean election lets a runner who was way behind grab the baton: the race keeps going (stays available), but you've thrown away all the ground the leader was ahead by (lost data).
unclean.leader.election.enable defaults to false (favour consistency). Setting it true trades possible data loss for higher availability — avoid for critical data.

6.4 High watermark & consistency

Consumers can only read up to the high watermark (offsets replicated to all ISR). This guarantees consumers never read records that could be lost in a leader failover.

🔍 In plain terms: the high watermark is the "safe to serve" line. Records above it exist on the leader but haven't been copied to all the in-sync replicas yet, so they could still vanish if the leader dies. Kafka simply hides them from you — like a shop only putting an item on the shelf once it's fully paid for and logged, so you can never "buy" something that might later be retracted.
What's the difference between replication factor and ISR?
Replication factor is the total number of copies configured. ISR is the dynamic subset of those copies currently caught up with the leader. ISR can shrink (slow/dead follower) and grow (follower catches up).
Why can't consumers read past the high watermark?
Records above the HW aren't yet on all in-sync replicas, so they could vanish if the leader fails. Hiding them guarantees that everything a consumer reads is durably committed.

7. Storage Internals & the Log Advanced ↑ Contents

7.1 Segments & on-disk layout

Each partition is a directory of segment files. The newest segment is "active" (being written); older ones are immutable. This makes deletion (drop a whole segment file) and sequential reads cheap.

🔍 In plain terms: a partition isn't one giant file — it's a series of fixed-size "chapters" (segments). Only the latest chapter is being written; the rest are sealed. Deleting old data is then as cheap as tossing an entire finished chapter, instead of erasing lines from the middle of one huge file.
/kafka-logs/orders-0/
  00000000000000000000.log     <- records (the actual data)
  00000000000000000000.index   <- offset -> physical position
  00000000000000000000.timeindex <- timestamp -> offset
  00000000000000170243.log     <- next segment...
ConfigEffect
log.segment.bytesRoll a new segment after this size (default 1 GB)
log.segment.msRoll a new segment after this time
log.index.interval.bytesHow densely the offset index is populated

7.2 Why Kafka is fast (performance internals)

Kafka's speed isn't magic — it's a stack of well-known systems tricks that each remove a layer of overhead. The reason they matter to you: they explain why Kafka wants RAM for the OS, fast disks, and batching rather than a giant JVM heap, which directly shapes how you size and tune brokers.

TechniqueBenefit
Sequential I/OAppend-only writes; disk throughput rivals memory
OS page cacheReads served from RAM; Kafka leans on the OS, not a JVM cache
Zero-copy (sendfile)Data goes disk → NIC without user-space copies
BatchingAmortizes network & I/O overhead
CompressionWhole batches compressed end-to-end
Binary protocolCompact, efficient wire format
Implication: Give the OS plenty of RAM for page cache; don't over-size the JVM heap. Use fast disks (SSD/NVMe) and separate disks for logs.

8. Retention & Log Compaction Intermediate ↑ Contents

8.1 Two cleanup policies

Because Kafka keeps data on disk, it needs a rule for what to eventually throw away — and it offers two fundamentally different rules. The choice matters because it reflects what your topic is: a time-bounded stream of events, or a living snapshot of current state per key.

PolicyKeepsUse case
delete (default)All records until time/size limit, then drops old segmentsEvent streams, logs
compactThe latest value per key foreverChangelogs, state snapshots
compact,deleteBoth combinedCompacted but also time-bounded

8.2 Time/size-based retention

ConfigMeaning
retention.msDelete records older than this (default 7 days)
retention.bytesMax partition size before old segments are dropped
Retention is enforced at the segment level — a segment is deleted only once all its records are past the limit. Data is removed regardless of whether consumers read it.

8.3 Log compaction

Compaction guarantees Kafka retains at least the last known value for each key. Old values for a key are eventually removed, keeping a compacted topic as a snapshot of latest state.

🔍 In plain terms: compaction keeps only the most recent value for each key and discards the older ones — exactly like your phone's contacts app storing each person's current number, not the history of every number they've ever had. The topic stops being a full history of changes and becomes a live snapshot of "the current value for every key."
Before compaction (key=value):
  k1=A  k2=X  k1=B  k3=Z  k2=Y  k1=C
After compaction (latest per key kept):
  k3=Z  k2=Y  k1=C
  • A record with a null value is a tombstone — marks the key for deletion.
  • Used by __consumer_offsets and Kafka Streams state-store changelogs.
If a topic is compacted, can I still lose the latest value for a key?
No — compaction always preserves the most recent value per key (until a tombstone + delete.retention window expires). Only superseded older values are removed.

9. Delivery Semantics & Transactions Advanced ↑ Contents

9.1 The three guarantees

Every messaging system has to answer "what happens if something fails mid-delivery?" — and there are exactly three possible promises. The one you pick is a trade-off between the pain of losing a message and the pain of seeing it twice.

SemanticMeaningHow
At-most-onceMay lose, never duplicateCommit offset before processing; acks=0/1
At-least-onceNever lose, may duplicate (most common)Process then commit; retries on
Exactly-once (EOS)No loss, no duplicateIdempotent producer + transactions

"Exactly-once" sounds like the obvious winner, but it's the hardest and costliest to achieve, and it's widely misunderstood. The rest of this section builds it up one step at a time so you can see exactly what each piece fixes.

9.2 Step (a): the duplicate-message problem, in plain terms

Duplicates come from two completely separate places, and conflating them is the root of most confusion:

  • Producer-side duplicates. A producer sends "charge $10." Kafka writes it, but the acknowledgement is lost on the way back. The producer doesn't know it succeeded, so it retries — and now "charge $10" is in the log twice.
  • Consumer-side duplicates. A consumer reads a batch, processes it, but crashes before committing its offset. On restart it re-reads the same records from the last committed offset and processes them again.
🔍 In plain terms: a duplicate is "the same thing done twice by accident." It can happen because the sender wasn't sure the message got through and re-sent it, or because the receiver did the work but forgot to check it off and did it again after a restart. Fixing one does nothing for the other.

9.3 Step (b & c): the idempotent producer — what it fixes, what it doesn't

(b) What it fixes. Turning on enable.idempotence=true gives the producer a Producer ID (PID) and stamps every record with a per-partition sequence number. If a retry re-sends a record the broker already has (same PID + sequence), the broker silently drops the copy. This eliminates producer-side duplicates from retries — and it's on by default in modern Kafka, for free.

(c) What's still broken. Idempotence only dedups one producer session writing to one partition. It does nothing about:
  • the consumer-side duplicate (reprocessing after a crash);
  • writing atomically across multiple partitions/topics;
  • tying an output write to the consumer's offset commit.
So a typical read → process → write app (read topic A, produce to topic B, commit A's offset) can still crash between "write to B" and "commit A," causing the record to be reprocessed and re-written to B. Idempotence alone can't close that gap.

9.4 Step (d): transactions close the gap

Kafka transactions let a producer bundle several actions into one all-or-nothing unit: write to multiple partitions/topics and commit the consumer's input offsets together. Either the whole bundle becomes visible at once (commit), or none of it does (abort). This is precisely the read-process-write pattern that idempotence couldn't handle. Consumers set isolation.level=read_committed so they never see records from an aborted or still-in-progress transaction.

🔍 In plain terms: a transaction is like moving money between bank accounts — the debit and the credit must both happen or neither does. Kafka does the same for "write my output(s) and check off my input" so a crash can never leave you half-done (output written but input not checked off, or vice versa).
producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("out", key, value));
    // atomically commit the input offsets within the same transaction
    producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata);
    producer.commitTransaction();
} catch (KafkaException e) {
    producer.abortTransaction();   // nothing becomes visible
}

9.5 Step (e): where Kafka's guarantee ends and your app begins

Here is the line interviewers want you to draw clearly. Everything above gives exactly-once within Kafka — Kafka topics in, Kafka topics out. The instant a side effect leaves Kafka — writing to a database, calling a REST API, sending an email — Kafka can no longer make it atomic, because it doesn't control that external system.

At that boundary the responsibility becomes your application's. The usual ways to complete end-to-end exactly-once are:

  • make the external write idempotent (e.g. upsert by a business/event key, so re-applying it changes nothing);
  • use the transactional outbox pattern (write the event to your DB in the same transaction as the data, then relay it — see §20.2);
  • store the processed offset in the same DB transaction as the data it produced, so re-processing is detectable and safe.
Pitfall: Exactly-once applies within Kafka (Kafka-to-Kafka). End-to-end EOS to an external system (DB, REST) still needs idempotent writes or the transactional outbox pattern on your side.
Practical default: Most systems use at-least-once + idempotent consumers (dedup by a business/event ID). Full EOS adds latency & complexity — use it only when duplicates are truly unacceptable (e.g. financial ledgers).
Why is at-least-once the most common choice?
It's simple and never loses data. Duplicates are handled by making consumers idempotent (e.g. upsert by primary key, dedup table), which is cheaper and more robust than full transactional exactly-once across systems.

10. Message Ordering & Keys Intermediate ↑ Contents

Ordering is one of the most misunderstood Kafka guarantees, so state it precisely: Kafka orders records within a partition, never across partitions. Everything about keeping related events in order flows from that one fact.

🔍 In plain terms: ordering is per-lane, not per-highway. If two events must be processed in order, you have to put them in the same lane (partition) — and the way you do that is by giving them the same key. Different keys may go to different lanes and race each other.
  • Ordering is per-partition only. Kafka guarantees order within a partition, never across partitions.
  • To keep related events ordered, give them the same key → same partition (e.g. key by userId or orderId).
  • Global ordering requires a single partition — which destroys parallelism, so avoid unless truly needed.
Ordering breakers: (1) adding partitions remaps keys; (2) producer retries with multiple in-flight requests (use idempotence); (3) consumer processing records concurrently across threads. Design around these.
How do you guarantee all events for one customer are processed in order?
Use the customer ID as the message key so all their events land in the same partition, and let a single consumer in the group own that partition. Keep producer idempotence on to preserve order across retries.

12. Kafka Streams Advanced ↑ Contents

A client library (just a JAR in your app — no separate cluster) for building real-time stream processing applications on top of Kafka. Input topics → processing topology → output topics.

🔍 In plain terms: Kafka Streams lets you write "for each event, do X, then aggregate, then output" as ordinary Java in your own app — no extra cluster to run. It's a library you import, not a system you deploy.

  • Stateless: map, filter, flatMap, branch, foreach.

Set processing.guarantee=exactly_once_v2 — Streams uses transactions under the hood so state updates and output are atomic with input-offset commits.

Kafka Streams vs Spark/Flink?
Streams is a lightweight library embedded in your app (no cluster, per-record low latency, tightly Kafka-coupled). Spark/Flink are separate cluster frameworks for heavier, multi-source batch+stream workloads. Choose Streams for Kafka-native microservice-style processing.

13. ksqlDB Intermediate ↑ Contents

A streaming SQL engine on top of Kafka Streams — write stream processing as SQL instead of Java.

🔍 In plain terms: ksqlDB lets you do stream processing by writing SQL — the same SELECT ... GROUP BY you already know — except the query never ends; it keeps producing results as new events arrive.
CREATE STREAM orders (id VARCHAR, amount DOUBLE)
  WITH (kafka_topic='orders', value_format='JSON');

CREATE TABLE paid_totals AS
  SELECT id, SUM(amount) AS total
  FROM orders WHERE status='PAID'
  GROUP BY id EMIT CHANGES;
  • STREAM = unbounded events; TABLE = latest state per key (mirrors KStream/KTable).
  • Push queries (EMIT CHANGES) stream continuous results; pull queries fetch current state point-in-time.
  • Great for rapid prototyping & analysts; for complex logic, drop to Kafka Streams.

14. Schema Registry & Serialization Intermediate ↑ Contents

Kafka stores raw bytes — it doesn't know or enforce a schema. The Schema Registry (Confluent) centrally stores Avro/Protobuf/JSON Schemas and enforces compatibility as schemas evolve, preventing producers from breaking consumers.

🔍 In plain terms: Kafka only sees bytes, like envelopes it never opens. The Schema Registry is a shared rulebook for what's inside those envelopes, and a bouncer that stops a producer from changing the format in a way that would break every consumer downstream.

14.1 How it works

Producer -> register/lookup schema in Registry -> writes [magic byte][schema ID][payload]
Consumer -> reads schema ID -> fetches schema from Registry -> deserializes

Only a small schema ID travels with each message (not the whole schema), keeping payloads compact.

14.2 Serialization formats

The format you choose is a trade-off between being easy for humans to read and being cheap for machines to move and evolve safely. That's why high-volume production systems usually leave JSON behind for Avro or Protobuf despite JSON's convenience.

FormatProsCons
JSONHuman-readable, simpleVerbose, no enforced schema
AvroCompact, rich schema evolution, Registry-nativeNot human-readable
ProtobufCompact, cross-language, gRPC-friendlyTooling needed

14.3 Schema compatibility modes

Compatibility modes exist so producers and consumers can be deployed independently without a coordinated big-bang release. Each mode answers "whose old code must keep working when the schema changes?" — which is really about the order in which you can safely roll out updates.

ModeAllows
BACKWARD (default)New schema reads old data (add optional fields, remove fields)
FORWARDOld schema reads new data
FULLBoth backward & forward
NONENo checks (risky)
Best practice: Use Avro/Protobuf + Schema Registry with BACKWARD/FULL compatibility. Add fields with defaults; never rename/retype in place. This lets producers & consumers deploy independently.
Why not just use JSON everywhere?
JSON has no enforced contract, is verbose (no schema ID dedup), and offers no compatibility guarantees — one producer change can silently break every consumer. Avro/Protobuf + Registry give compact payloads and safe, governed evolution.

16. Reliability, HA & Monitoring Intermediate ↑ Contents

16.1 Designing for no data loss

"No data loss" isn't one setting — it's a chain of choices across producer, broker, and consumer, and the weakest link decides the outcome. The checklist below hardens all three tiers together; skip one and the guarantee leaks.

  • Producer: acks=all, enable.idempotence=true, sufficient retries/delivery.timeout.ms.
  • Broker: RF≥3, min.insync.replicas=2, unclean.leader.election.enable=false.
  • Consumer: commit after processing; idempotent handling; handle rebalance via ConsumerRebalanceListener.
  • Spread replicas across racks/AZs (broker.rack) for failure-domain isolation.

16.2 Dead Letter Queue (DLQ) & retries

For "poison" messages that repeatedly fail, route them to a dead-letter topic after N retries so the main pipeline keeps flowing. Spring Kafka offers DeadLetterPublishingRecoverer + non-blocking retry topics.

🔍 In plain terms: a DLQ is the "put it aside and deal with it later" bin. If one broken message keeps failing, you don't let it block the whole line — you move it to a side topic so everything else keeps flowing, and a human or a separate job inspects the rejects later.

16.3 Key metrics to monitor

You could graph hundreds of Kafka metrics, but a few tell you almost everything about cluster health. Consumer lag answers "are we keeping up?"; the replication metrics answer "are we still safe?" — watch these first and the rest are supporting detail.

17. Spring Kafka Intermediate New ↑ Contents

In a Spring Boot app you rarely use the raw KafkaProducer/KafkaConsumer loops shown earlier. The Spring for Apache Kafka (spring-kafka) project wraps them in familiar Spring idioms — a template for sending and an annotation-driven listener for receiving — while still exposing all the underlying concepts (offsets, commits, retries) you've already learned.

🔍 In plain terms: Spring Kafka is a comfortable steering wheel bolted onto the raw Kafka client. You still drive the same car (same partitions, offsets, commits), but you push events with a one-line KafkaTemplate.send(...) and receive them by just annotating a method with @KafkaListener — Spring runs the poll loop for you.

17.1 Producing with KafkaTemplate

KafkaTemplate is the send side — the Spring equivalent of holding a KafkaProducer and calling send(), returning a future you can chain callbacks onto.

@Service
public class OrderProducer {
    private final KafkaTemplate<String, String> kafkaTemplate;

    public OrderProducer(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public void publish(Order order) {
        // key = order id -> all events for one order share a partition (ordering)
        kafkaTemplate.send("orders", order.getId(), order.toJson())
            .whenComplete((result, ex) -> {
                if (ex != null) log.error("send failed", ex);
                else log.info("sent to offset {}", result.getRecordMetadata().offset());
            });
    }
}

17.2 Consuming with @KafkaListener

@KafkaListener replaces the entire hand-written while (true) { poll(); ... } loop from §5.2 — Spring runs the poll loop in a container and simply calls your method for each record (or batch).

@Component
public class OrderConsumer {

    @KafkaListener(topics = "orders", groupId = "billing")
    public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
        billingService.process(record.value());   // do the work FIRST
        ack.acknowledge();                         // then commit -> at-least-once
    }
}

17.3 Ack modes — mapping back to commitSync / commitAsync

The manual commit concepts from §5.2 don't disappear in Spring — they're selected through the container's ack mode. This table connects the Spring setting to the raw-client behaviour you already know, so you're not learning a new idea, just a new dial for the same one.

17.4 Error handling & non-blocking retries

By default a listener that throws will retry and, if it keeps failing, can hand the record to a recoverer. The modern default error handler is DefaultErrorHandler, which retries with a back-off and then routes the "poison" record to a dead-letter topic (tying back to the DLQ idea in §16.2).

@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<String, String> template) {
    // On repeated failure, publish the record to "<topic>.DLT"
    var recoverer = new DeadLetterPublishingRecoverer(template);
    // Retry 3 times, 1s apart, THEN send to the DLT
    return new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3L));
}

Those retries are blocking (they hold up the partition). For non-blocking retries — where failed records go to separate timed retry topics so the main flow never stalls — use @RetryableTopic:

@RetryableTopic(
    attempts = "4",
    backoff = @Backoff(delay = 1000, multiplier = 2.0),   // 1s, 2s, 4s ...
    dltStrategy = DltStrategy.FAIL_ON_ERROR)              // give up -> DLT
@KafkaListener(topics = "orders", groupId = "billing")
public void onMessage(String payload) {
    billingService.process(payload);   // failures flow to orders-retry-0, -1, ... then orders-dlt
}

19. KRaft — ZooKeeper Removal Advanced ↑ Contents

19.1 Why did Kafka need ZooKeeper at all?

Before appreciating KRaft, it helps to understand the problem it replaced. A Kafka cluster is many independent brokers that must nonetheless agree on things no single broker can decide alone: which broker is the controller, who leads each partition, which brokers are currently alive, and what all the topic and ACL configs are. Reaching reliable agreement among distributed machines (consensus) is genuinely hard to build correctly, so early Kafka didn't build it — it outsourced it to ZooKeeper, a separate, battle-tested coordination service that acted as the cluster's single source of truth and referee.

🔍 In plain terms: the brokers are workers who are great at storing and serving data but need an impartial "records office" to agree on who's in charge and who's on duty. ZooKeeper was that external records office. It worked — but now you had to run, secure, and tune a second distributed system just to keep the first one organized.

That arrangement had real costs: two systems to operate instead of one; slow controller failover (a newly elected controller had to reload all partition metadata from ZooKeeper before the cluster was healthy again); and a ceiling on how many partitions a cluster could manage. Those pain points are exactly what the next section fixes — which is why the contrast makes KRaft's value obvious.

19.2 KRaft

Historically Kafka used ZooKeeper for metadata, controller election, and ACLs. KRaft (Kafka Raft, KIP-500) replaces ZooKeeper with a built-in Raft-based consensus quorum of controller nodes — metadata is itself stored in an internal Kafka log.

🔍 In plain terms: KRaft moves the "records office" inside Kafka. Instead of phoning an external service to agree on cluster state, a small group of Kafka controller nodes votes among themselves (Raft consensus) and writes the agreed metadata into an ordinary Kafka log — one system, keeping its own minutes.
ZooKeeper modeKRaft mode
Metadata storeExternal ZooKeeper ensembleInternal __cluster_metadata log
ComponentsKafka + ZooKeeper (two systems)Kafka only
ScalabilityLimited (~200k partitions)Millions of partitions
FailoverSlower controller failoverMuch faster
StatusDeprecatedDefault / production-ready (Kafka 3.3+; ZK removed in 4.0)
Why it matters: KRaft simplifies operations (one system to run), speeds up recovery, and scales metadata massively. New clusters should use KRaft.
What did ZooKeeper do for Kafka, and what replaced it?
It stored cluster metadata, managed controller election, tracked broker membership, and held ACLs/configs. KRaft replaces all of that with an internal Raft quorum of controllers, removing the external dependency.

20. Patterns & Real-World Use Cases Advanced ↑ Contents

20.1 Event-driven microservices

Services communicate via events instead of synchronous calls — loose coupling, resilience, and replayability. A service publishes domain events; others react independently.

20.2 Transactional Outbox (the dual-write fix)

Problem: writing to your DB and publishing to Kafka in one operation isn't atomic — one can fail. Solution: in the same DB transaction, write the event to an outbox table; a CDC connector (Debezium) tails that table and publishes to Kafka reliably.

BEGIN;
  INSERT INTO orders(...);
  INSERT INTO outbox(aggregate, type, payload) VALUES(...);  -- same tx
COMMIT;
-- Debezium reads the outbox table -> Kafka topic (guaranteed, no dual write)

20.3 Saga pattern (distributed transactions)

A business transaction spanning services is modeled as a series of local transactions linked by events, with compensating actions to undo on failure. Two styles: choreography (services react to each other's events) and orchestration (a central coordinator drives steps).

20.4 CQRS & Event Sourcing

  • Event Sourcing: store state as an append-only log of events; rebuild state by replaying — Kafka is a natural fit.
  • CQRS: separate write model (commands → events) from read models (materialized views built by consuming events).

21. Kafka vs Other Systems Intermediate ↑ Contents

The point of comparing Kafka to other brokers isn't to crown a winner — it's to recognize when Kafka is the wrong tool. The core difference is that Kafka retains and replays a log, whereas a traditional queue deletes on consume; that one distinction drives almost every row below.

Kafka vs traditional Message Queue
Pull (consumer-driven) vs push; data retained & replayable vs deleted on consume; scales via partitions; multiple independent consumer groups read the same data.
When would you pick RabbitMQ over Kafka?
When you need complex routing, per-message priority, request/reply (RPC), or relatively low message volume with simple task-queue semantics. Pick Kafka for high-throughput event streaming, replay, log retention, and stream processing.

22. Interview Scenarios & Cheat-Sheet Advanced ↑ Contents

22.1 Scenario questions

Consumers are lagging badly — how do you fix it?
Diagnose: is it processing speed, partition count, or downstream? Options: add partitions + consumers (up to partition count), optimize/parallelize processing, increase max.poll.records/fetch sizes, check for hot partitions (key skew), scale downstream sinks, and watch GC. Confirm with the consumer-lag metric.
How do you guarantee no message loss end to end?
Producer acks=all + idempotence + retries; broker RF≥3, min.insync.replicas=2, no unclean elections; consumer commits only after successful processing with idempotent handling; DLQ for poison messages.
You need exactly-once from Kafka to a database — how?
Kafka's EOS is Kafka-to-Kafka. To a DB, make the write idempotent (upsert by event/business key) under at-least-once, or use the transactional outbox + CDC, or store the processed offset in the same DB transaction as the data.
A consumer keeps rebalancing — why?
Processing takes longer than max.poll.interval.ms, so the broker thinks it's dead. Reduce max.poll.records, speed up or offload processing, increase the interval, and use static membership + cooperative rebalancing.
How would you reprocess historical data after a bug fix?
Reset the consumer group's offsets to earliest (or a timestamp) with kafka-consumer-groups --reset-offsets, or run a new consumer group from the beginning — possible precisely because Kafka retains data.
