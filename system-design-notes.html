1.4 Capacity estimation (back-of-envelope)

Useful numbers:
  1 day ≈ 86,400 s ≈ 10^5 s
  Read:Write ratio often 100:1 (read-heavy)
  Char/short = 2B, int = 4B, long/double = 8B, UUID ≈ 16B

Derived rules of thumb you can quote in an interview:

  • Memory is ~100,000× faster than disk → cache aggressively; keep hot data in RAM (Redis).
  • SSD is ~20× faster than HDD for random reads → databases moved to SSD for a reason.
  • A same-DC round trip (~0.5 ms) is ~300× a memory read → chatty microservices (N sequential calls) kill latency; batch/parallelize.
  • Cross-continent RTT (~150 ms) dominates any single request → put a CDN/edge near users; replicate read paths regionally.
  • Sequential >> random on every medium → design for sequential access (log-structured stores, append-only, Kafka).
💡 How to use in estimation: "A feed request touches 5 services sequentially in-DC → 5 × 0.5 ms = 2.5 ms just in network hops, before any DB work. If each also does a disk read (10 ms), we're at ~50 ms — so I'll cache and fan out in parallel."

2.3 Reading a class box

A UML class box has three compartments: name → attributes → methods. Visibility markers: - private, + public, # protected. Rendered as a Mermaid class diagram:

Aggregation vs composition — how do you decide?
Ask "if the whole is destroyed, do the parts still make sense?" If yes → aggregation (Team & Players: players exist without the team). If no → composition (House & Rooms: rooms don't exist without the house). Composition implies lifecycle ownership.

3.2 SOLID principles Critical

    else if (s.type == "square") { /* ... */ }

Strategy vs State pattern — they look similar?

A repeatable approach for any "design X" object-modelling question:

1. CLARIFY    requirements & scope (ask questions, list features)
2. IDENTIFY   core entities/objects (nouns) and behaviours (verbs)
3. RELATE     define relationships (is-a, has-a) + multiplicities
4. INTERFACE  design class APIs; apply SOLID

6. Concurrency & Multithreading for LLD Interviews LLD Advanced NEW

Almost every "real" LLD case study has a concurrency twist: two cars racing for one parking spot, two users grabbing the same seat, two threads printing to one log file. Interviewers use it to separate people who model classes from people who ship correct systems. This section gives you the toolkit and shows exactly where each tool appears in the case studies.

6.1 The core problem: shared mutable state

A race condition happens when the correctness of the result depends on the interleaving of threads. The classic example is check-then-act on a shared field:

// BROKEN under concurrency: two threads can both see free == true
if (spot.isFree()) {      // Thread A and Thread B both read true
    spot.assign(vehicle); // both assign → double-booked spot!
}

You fix this by making the check-and-act atomic — only one thread may execute the critical section at a time, or the operation itself is atomic at the hardware/library level.

6.2 synchronized — the built-in lock

The simplest mutual exclusion in Java. Every object has an intrinsic monitor lock; synchronized acquires it on entry and releases it on exit (even on exception).

class SeatBooking {
    private final Object lock = new Object();
    private SeatStatus status = SeatStatus.AVAILABLE;

    public boolean lockSeat() {
        synchronized (lock) {          // only one thread inside at a time
            if (status == SeatStatus.AVAILABLE) {
                status = SeatStatus.LOCKED;
                return true;
            }
            return false;              // someone else already took it
        }
    }
}
Propertysynchronized
GranularityMethod (synchronized method) or block (synchronized(obj){})
FairnessNot fair (arbitrary thread wins)
Interruptible / timeout❌ No — a thread blocks indefinitely
Try-lock❌ No
ReleaseAutomatic (on block exit / exception)
⚠️ Pitfall: lock granularity matters. Synchronizing the whole ParkingLot serializes all gates — a bottleneck. Prefer a lock per floor or per spot so unrelated allocations proceed in parallel.

6.3 ReentrantLock — the flexible lock

java.util.concurrent.locks.ReentrantLock does everything synchronized does, plus timeouts, interruptibility, fairness, and tryLock. The cost: you must unlock in a finally.

class SpotAllocator {
    private final ReentrantLock lock = new ReentrantLock(); // fair: new ReentrantLock(true)

    public boolean tryAssign(ParkingSpot spot, Vehicle v) {
        // give up after 200ms instead of blocking forever
        try {
            if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {
                try {
                    if (spot.isFree()) { spot.assign(v); return true; }
                    return false;
                } finally {
                    lock.unlock();       // ALWAYS unlock in finally
                }
            }
            return false;                // couldn't get the lock in time
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return false;
        }
    }
}

Reach for ReentrantLock over synchronized when you need tryLock (fail fast instead of blocking — great for seat/spot allocation), a timeout, fairness, or multiple condition variables (lock.newCondition()).

6.4 ReadWriteLock — many readers, one writer

When reads vastly outnumber writes (e.g., a display board read constantly but updated rarely), ReentrantReadWriteLock lets any number of readers proceed concurrently but gives writers exclusive access.

class DisplayBoard {
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private int freeSpots;

    public int getFreeSpots() {
        rw.readLock().lock();            // shared: many readers together
        try { return freeSpots; }
        finally { rw.readLock().unlock(); }
    }

    public void update(int delta) {
        rw.writeLock().lock();           // exclusive: blocks all readers
        try { freeSpots += delta; }
        finally { rw.writeLock().unlock(); }
    }
}
📝 When it wins: read-heavy, write-rare state. If writes are frequent, the writer starves readers (or vice-versa) and a plain lock or a ConcurrentHashMap is simpler.

6.5 ConcurrentHashMap & atomic types — lock-free(ish) building blocks

Most of the time you don't need explicit locks — the java.util.concurrent collections do it for you with fine-grained internal locking / CAS.

// Thread-safe inventory count without any explicit lock:
ConcurrentHashMap<String, AtomicInteger> stock = new ConcurrentHashMap<>();

// Atomic "decrement if available" using compute — runs atomically per key:
boolean sold = stock.get(code).getAndUpdate(n -> n > 0 ? n - 1 : n) > 0;

// Atomic seat claim with a single map operation (returns previous value):
ConcurrentHashMap<String, String> seatOwner = new ConcurrentHashMap<>();
boolean gotSeat = seatOwner.putIfAbsent("A5", userId) == null; // true = you won
ToolUse for
ConcurrentHashMapShared maps: inventory, seat→owner, session registry. putIfAbsent / compute are atomic.
AtomicInteger / AtomicLongCounters (free-spot counts, ID sequences) without locks.
AtomicReference + CASLock-free "claim if unchanged" (compare-and-set) on a single object.
CopyOnWriteArrayListRarely-modified, often-iterated lists (observer/listener lists).
💡 Interview line: "I'd model the free-seat map as a ConcurrentHashMap and claim a seat with putIfAbsent — that's a single atomic operation, so no two threads can both win, and I avoid coarse locking entirely."

6.6 ExecutorService & thread pools — don't spawn raw threads

Creating a new Thread() per task doesn't scale (thread creation is expensive; unbounded threads exhaust memory). Use a pool.

// A fixed pool that processes booking/notification tasks:
ExecutorService pool = Executors.newFixedThreadPool(10);

Future<Boolean> result = pool.submit(() -> bookingService.confirm(bookingId));
boolean ok = result.get();          // blocks for this task's result

// Scheduled work (e.g. expire seat locks after TTL):
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);
scheduler.schedule(() -> seatLockService.release(seatId), 10, TimeUnit.MINUTES);

pool.shutdown();                    // graceful; no new tasks accepted
Pool typeUse
newFixedThreadPool(n)Bounded parallelism (most common; caps resource use)
newCachedThreadPool()Many short-lived bursty tasks (reuses idle threads)
newScheduledThreadPool(n)Delayed/periodic tasks — seat-lock TTL expiry, heartbeat checks
newSingleThreadExecutor()Serialize tasks onto one thread (e.g., single-writer log flusher)
⚠️ Pitfall: always shutdown() pools and size them deliberately. A pool sized to Runtime.getRuntime().availableProcessors() suits CPU-bound work; larger pools suit I/O-bound work (threads mostly wait).

In the parking lot, two cars arrive at different gates at the same instant and the system assigns them the same spot. How do you prevent it?
Make spot claiming atomic. Option 1: a ReentrantLock per floor — tryLock, re-check isFree(), assign, unlock in finally. Option 2 (lock-free): store spots in a ConcurrentHashMap and claim with putIfAbsent(spotId, vehicleId) / an AtomicReference CAS — the first thread wins, the second sees the spot taken and retries the next spot. Keep the critical section tiny (just the claim), and keep per-type free counters as AtomicInteger so the display stays O(1).
How do you make a piece of code thread-safe without locking on every access?
Prefer immutable objects (no shared mutable state at all), then lock-free structures (ConcurrentHashMap, Atomic* with CAS), then read-write locks for read-heavy state, and only fall back to synchronized/ReentrantLock for genuine compound critical sections. Lock the smallest scope possible and never hold a lock across I/O.

Why State pattern for vending machine / ATM / elevator?

15.3 Token bucket — thread-safe implementation

interface RateLimitStrategy {
    boolean allow(String clientId);
}

class TokenBucketLimiter implements RateLimitStrategy {
    private final long capacity;         // max burst
    private final double refillPerMs;    // sustained rate
    private final ConcurrentHashMap<String, Bucket> buckets = new ConcurrentHashMap<>();

    TokenBucketLimiter(long capacity, double refillPerSec) {
        this.capacity = capacity;
        this.refillPerMs = refillPerSec / 1000.0;
    }

    public boolean allow(String clientId) {
        Bucket b = buckets.computeIfAbsent(clientId, k -> new Bucket(capacity));
        synchronized (b) {                       // lock only this client's bucket
            long now = System.currentTimeMillis();
            double refill = (now - b.lastRefill) * refillPerMs;
            b.tokens = Math.min(capacity, b.tokens + refill);
            b.lastRefill = now;
            if (b.tokens >= 1) { b.tokens -= 1; return true; }
            return false;                        // rejected → caller returns 429
        }
    }

    static class Bucket {
        double tokens;
        long lastRefill = System.currentTimeMillis();
        Bucket(long initial) { this.tokens = initial; }
    }
}

15.4 Sliding window counter (accuracy/memory balance)

class SlidingWindowLimiter implements RateLimitStrategy {
    private final int limit;
    private final long windowMs;
    private final ConcurrentHashMap<String, Deque<Long>> hits = new ConcurrentHashMap<>();

    public boolean allow(String clientId) {
        long now = System.currentTimeMillis();
        Deque<Long> q = hits.computeIfAbsent(clientId, k -> new ArrayDeque<>());
        synchronized (q) {
            while (!q.isEmpty() && q.peekFirst() <= now - windowMs) q.pollFirst(); // evict old
            if (q.size() < limit) { q.addLast(now); return true; }
            return false;
        }
    }
}

15.5 Concurrency notes

  • Per-client locking (synchronized (bucket)) keeps contention low — clients don't block each other. Compare with a single global lock, which serializes everything.
  • For the hottest paths you can go lock-free with an AtomicLong token count and a CAS retry loop (see §6.5), trading code complexity for throughput.
  • The ConcurrentHashMap.computeIfAbsent for per-client state is itself atomic — no lock needed to create a client's bucket.

16.4 Asynchronous appender (producer–consumer concurrency)

The caller thread should not wait for disk/network I/O. An AsyncAppender enqueues events on a BlockingQueue and a single background thread drains and writes them — the textbook producer–consumer pattern (see §6.6).

class AsyncAppender implements Appender {
    private final BlockingQueue<LogEvent> queue = new LinkedBlockingQueue<>(10_000);
    private final Appender delegate;                 // e.g. FileAppender
    private final ExecutorService worker = Executors.newSingleThreadExecutor();
    private volatile boolean running = true;

    AsyncAppender(Appender delegate) {
        this.delegate = delegate;
        worker.submit(this::drainLoop);
    }

    public void append(LogEvent e) {
        queue.offer(e);          // non-blocking; drops if full (or use put() to block)
    }

    private void drainLoop() {
        while (running || !queue.isEmpty()) {
            try {
                LogEvent e = queue.poll(1, TimeUnit.SECONDS);
                if (e != null) delegate.append(e);   // single writer → no file contention
            } catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
        }
    }

    public void shutdown() { running = false; worker.shutdown(); }
}
💡 Why a single-thread executor for the file sink? It serializes all writes to one file handle, avoiding interleaved/corrupted lines without a lock on the hot path — the producers just enqueue.
⚠️ Back-pressure decision: if the queue fills (consumer slower than producers), you must choose: block producers (put, safest, slows the app), drop logs (offer, protects the app, loses data), or overflow to a fallback sink. State this trade-off explicitly — interviewers look for it.
🏭 Real-world tie-in: this is precisely how Log4j2's async appenders and most metrics clients work — batch on a queue, flush on a background thread — and it generalizes to any write-behind buffer (batching DB writes, flushing analytics events). (your project: ______ — where do you buffer-and-flush to avoid blocking the request path?)
How do you make logging thread-safe and fast?
Don't lock the caller. Enqueue each LogEvent onto a thread-safe BlockingQueue (producers) and let one background consumer thread drain it to the sink (single writer = no output contention). Filter by level before enqueuing to avoid work. Decide back-pressure policy (block vs drop) up front. This keeps the caller's critical path to an O(1) enqueue.

21.1 CAP theorem

A distributed data store can guarantee at most two of three: Consistency, Availability, Partition tolerance. Since network partitions are unavoidable in distributed systems, you really choose between C and A during a partition.

With % N, changing the node count N remaps almost every key (cache wipeout / massive data movement). Consistent hashing remaps only ~1/N of keys when a node joins/leaves, so caches and shards stay mostly intact. Virtual nodes prevent uneven distribution.

25.2 JWT structure & validation

A JWT is three Base64url parts: header.payload.signature.

header:    { "alg": "RS256", "typ": "JWT" }
payload:   { "sub": "user123", "role": "admin", "exp": 1735689600, "iss": "auth.acme.com" }
signature: sign(base64(header) + "." + base64(payload), key)

Validation steps a resource server / gateway performs on every request:

1. Parse the token; check it has 3 parts and a supported alg (reject "alg: none").
2. Verify the SIGNATURE with the issuer's public key (RS256) or shared secret (HS256).
3. Check `exp` (not expired) and `nbf`/`iat` (not used too early).
4. Check `iss` (trusted issuer) and `aud` (token meant for this API).
5. Read claims (`sub`, `roles`/`scopes`) → make the authorization decision.
⚠️ JWT pitfalls: (1) never accept alg: none and pin the expected algorithm (algorithm-confusion attack). (2) JWTs are signed, not encrypted — don't put secrets in the payload. (3) You can't easily revoke a JWT before expiry → keep access tokens short-lived (5–15 min) and pair with refresh tokens + an optional denylist for logout.

25.5 Token refresh strategies

  • Short-lived access token (5–15 min) + long-lived refresh token (days/weeks, stored securely — httpOnly cookie or secure storage).
  • When the access token expires, the client silently exchanges the refresh token for a new access token — no re-login.
  • Refresh token rotation: issue a new refresh token on each use and invalidate the old one. If an old (already-used) refresh token is presented, it signals theft → revoke the whole chain.
  • Store refresh tokens server-side (hashed) so logout / revocation actually works.

Where and how do you validate a JWT in a microservices architecture?
Preferably once at the API gateway: verify signature against the issuer's public key (cached from the JWKS endpoint), check exp/iss/aud, then inject a trusted identity header for downstream services on the private network. Keep access tokens short-lived so revocation lag is small, use refresh-token rotation for renewal, and use mTLS/client-credentials for internal service-to-service auth.
JWT is stateless — so how do you log a user out / revoke access?
You can't un-sign an issued JWT, so: (1) keep access-token TTL short so it self-expires quickly; (2) maintain a small denylist (by token jti) checked at the gateway for immediate revocation; (3) revoke the refresh token server-side so no new access tokens can be minted. The combination bounds the exposure window to the access-token TTL.

27. Idempotency & Exactly-Once Semantics HLD Advanced NEW

An operation is idempotent if performing it multiple times has the same effect as performing it once. In distributed systems, retries are unavoidable (network timeouts, at-least-once queues, client double-clicks), so idempotency is what turns "at-least-once delivery" into "effectively exactly-once processing." True end-to-end "exactly-once delivery" is essentially impossible; idempotent consumers are how we get its practical equivalent.

27.1 Why you need it

  • Client retries: the response was lost, so the client retries a payment — you must not charge twice.
  • At-least-once queues (Kafka/SQS): a consumer may see the same message again after a crash before it acked.
  • Duplicate user actions: double-clicking "Submit order."

Naturally idempotent operations: GET, PUT (full replace), DELETE. Not naturally idempotent: POST (create), "increment balance," "send email" — these need an idempotency mechanism.

27.2 Idempotency keys

The client generates a unique idempotency key (a UUID) per logical operation and sends it (e.g., Idempotency-Key header). The server records the key with the operation's result; a repeat with the same key returns the stored result instead of re-executing.

27.3 The two-layer defense (cache check + DB unique constraint)

A single check-then-act is itself a race (two concurrent retries both miss the cache and both proceed). The robust pattern is two layers: a fast cache check to short-circuit most duplicates, and a DB unique constraint as the authoritative backstop that no race can slip past.

flowchart TD A[Request with Idempotency-Key] --> B{Layer 1:<br/>key in Redis?} B -- hit --> R[Return stored result<br/>no re-execution] B -- miss --> C[Process the operation] C --> D[Layer 2: INSERT row with<br/>UNIQUE idempotency_key in same DB txn] D -- insert ok --> E[Commit side effect + result;<br/>cache key→result in Redis] D -- unique violation --> F[A concurrent request already did it<br/>→ fetch & return its result] E --> R2[Return result] F --> R2 
public PaymentResult charge(String idempotencyKey, ChargeRequest req) {
    // ---- Layer 1: fast path — cache short-circuits the common duplicate ----
    PaymentResult cached = redis.get(idempotencyKey);
    if (cached != null) return cached;                  // already done

    try {
        // ---- Layer 2: authoritative — DB unique constraint is the real guard ----
        // idempotency_keys table: idempotency_key VARCHAR PRIMARY KEY (or UNIQUE)
        db.begin();
        db.insert("INSERT INTO idempotency_keys(key, status) VALUES(?, 'IN_PROGRESS')",
                  idempotencyKey);                       // throws on duplicate key
        PaymentResult result = paymentGateway.charge(req);   // the real side effect
        db.update("UPDATE idempotency_keys SET status='DONE', result=? WHERE key=?",
                  result, idempotencyKey);
        db.commit();

        redis.setEx(idempotencyKey, TTL, result);        // populate Layer 1 for next time
        return result;

    } catch (DuplicateKeyException dup) {
        // A concurrent request won the race and is doing / did the work.
        db.rollback();
        return waitForAndFetchResult(idempotencyKey);    // poll DB until status=DONE, return result
    }
}

Why two layers, not one:

LayerRoleWeakness alone
Redis cache checkFast, handles the vast majority of retries without touching the DBRace: two simultaneous retries both miss; cache can be evicted/lost
DB UNIQUE constraintAuthoritative — the database cannot insert the same key twice, even under concurrencyA DB hit on every request would be slower without the cache in front

Together: the cache absorbs load and latency; the unique constraint guarantees correctness. This mirrors the seat-lock in BookMyShow (§14) — an atomic claim backed by a durable store.

⚠️ Make the key insert and the side effect atomic. If you charge the gateway then record the key and crash in between, a retry re-charges. Put the "record key" write and the "record result" write in the same DB transaction as the local effect (outbox pattern, §22). For external side effects (a real card charge), pass the same idempotency key through to the payment provider — mature providers (e.g., Stripe) are themselves idempotent on that key.
🏭 Real-world tie-in: Stripe's Idempotency-Key header, Kafka consumers deduping by event ID before writing, and "create order" endpoints guarded by a unique (user, cart_hash) constraint all use this exact pattern. (your project: ______ — which write endpoint most needs an idempotency key, and do you have a unique constraint backing it?)
Your payment endpoint is called twice due to a client retry. How do you avoid double-charging?
Require a client-supplied idempotency key per attempt. First check a cache (Redis) for that key and return the stored result if present (fast path). On a miss, within one DB transaction insert the key against a UNIQUE constraint and perform the charge; if the insert throws a duplicate-key error, a concurrent request already handled it — fetch and return that result. The unique constraint is the real guarantee; the cache is just an optimization. Pass the same key to the payment provider so it's idempotent end-to-end.
Isn't "exactly-once" delivery achievable with the right queue?
Not truly — at the delivery layer you get at-most-once or at-least-once; the FLP/network realities make exactly-once delivery impractical. What you achieve instead is exactly-once processing/effects by combining at-least-once delivery with idempotent consumers (dedup by event ID + unique constraint). That's what "exactly-once" means in practice.

  put(k,v): insert at head; if over capacity, evict tail node
  HashMap: key -> node;  DLL maintains recency order.
🏭 Real-world tie-in: this is how Redis Cluster / Memcached scale; the O(1) LRU (HashMap + DLL) is a top LeetCode-style LLD ask, and consistent hashing here is the same primitive as DB sharding (§20). (your project: ______ — is your cache single-node or clustered, and how are keys distributed?)
How do you implement an LRU cache in O(1)?
Combine a HashMap (key → node, O(1) lookup) with a doubly-linked list ordered by recency. On access, move the node to the head; on insert over capacity, evict the tail. Both operations are O(1).

Trie vs inverted index — when?
Trie (with cached top-k) for prefix autocomplete — ultra-fast "starts-with" suggestions. Inverted index (Elasticsearch) for full-text search — matching terms anywhere in documents with relevance ranking. Autocomplete often uses the trie; the results page uses the inverted index.
