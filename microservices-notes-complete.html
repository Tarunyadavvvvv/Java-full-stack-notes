01 Architecture & Communication

Service Decomposition & Boundaries

The hardest question in microservices isn't "how do we split this up" — it's "where does one service's responsibility actually end." Get the boundary wrong and you've built a distributed monolith with worse latency and more YAML.

8 min read

Bounded contexts: the unit decomposition actually happens around

Domain-Driven Design's bounded context is the idea underneath every good service boundary: a bounded context is the area of a domain where a particular model, its terms, and its rules stay internally consistent. "Order" means something specific and complete inside the Orders context — line items, totals, fulfillment status. It might mean something narrower inside Shipping (just an address and a set of items to move) and narrower still inside Billing (a set of charges). A service boundary should line up with a bounded context, not with an arbitrary slice of the codebase — because a bounded context is the largest unit that can change internally without forcing another team's model to change in lockstep.

Cutting by business capability, not by technical layer

There are two instincts for where to draw the lines, and only one of them survives contact with production.

Wrong cut — by technical layer

  • ui-service, business-logic-service, data-access-service — split along the traditional 3-tier lines
  • Every real feature (place an order, cancel an order) touches all three services on every request
  • The three "services" deploy together in practice and share one release train — one team ends up owning all three anyway
  • You've paid for network hops and serialization on every call, and gained none of microservices' actual benefit: independent deployability

Right cut — by business capability

  • orders-service, inventory-service, payments-service — split along what the business does, not how the code is layered
  • Each one owns a full vertical slice: its own API, business logic, and data, for one coherent piece of the domain
  • Orders can deploy on Tuesday and Payments on Thursday, independently, because neither one's internal model leaked into the other
  • A team can own one of these end-to-end — which is what actually makes independent deployment possible

The technical-layer cut feels natural because it mirrors how a monolith's codebase is often already organized internally — but that's exactly the problem: it recreates the monolith's coupling with extra network hops bolted on. It's often called a distributed monolith: all the deployment and operational overhead of microservices, none of the independence.

  • E-commerce platformdecomposed by business capability, not by layer
    • Orders Serviceowns order lifecycle + its own database
    • Inventory Serviceowns stock levels + its own database
    • Payments Serviceowns transactions + its own database

Each service is a complete vertical slice — API, logic, and data — for one business capability. None of them shares a database with another, which is what actually makes independent deployment safe.

Database-per-service: the rule that makes the split real

Splitting the code into separate deployables while leaving one shared database underneath is the single most common way teams accidentally rebuild a monolith. The moment two services read and write the same tables, a schema change in one requires coordinating with every other team that touches those tables — exactly the cross-team coordination cost decomposition was supposed to remove. Database-per-service means each service's data is private to that service; anything another service needs comes through that service's API or an event it publishes, never a direct query against its tables.

The shared-database anti-pattern

A team splits its monolith into five deployable services, each with its own repo and its own CI pipeline — but all five still point at the same Postgres instance, and worse, the same tables. It looks decomposed on an architecture diagram. In practice, a migration on the orders table still needs sign-off from four other teams before it can ship, deploys still get coordinated on a release calendar, and a slow query from one service still starves connections for the others. The organizational coupling the split was meant to remove is still fully intact — it just moved from "shared code" to "shared schema."

Conway's Law

"Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations." In practice: if three teams sit in one big backend group with no clear ownership lines, the system they build ends up with the same tangled, unclear boundaries — no matter how the architecture diagram is drawn. Service boundaries and team boundaries have to be designed together. Drawing a clean bounded context on a whiteboard means nothing if the team that owns it shares a backlog with the team next to it — the org chart wins.

So how big should one service actually be?
There's no line-of-code or endpoint-count answer — "how big" is the wrong axis entirely. A service is correctly sized when one team can change its internal model and deploy it without asking another team for a schema change, an API contract change, or a coordinated release. If two "services" can never actually ship independently because a change in one always forces a change in the other, they're really one bounded context that got split too early — merge them back and re-split later once the seam is clearer.
Chapter summary
  • A service boundary should line up with a DDD bounded context — the area where one model and its terms stay internally consistent.
  • Cutting by business capability (Orders, Inventory, Payments) gives each service a full, independently deployable vertical slice; cutting by technical layer recreates a distributed monolith.
  • Database-per-service is what makes the split real — a shared database silently reintroduces the exact cross-team coupling decomposition was meant to remove.
  • Conway's Law means service boundaries and team boundaries have to be designed together, not independently — the org chart shows up in the architecture whether you plan for it or not.
  • "How big should a service be" is the wrong question — "can a team change and deploy it alone" is the right one.

A feature like "place an order" needs the UI, business-logic, and data layers to change together — so the three "services" end up on the same release train regardless of being separate deployables. Business-capability cuts (Orders, Payments) instead give each service a complete, independently changeable vertical slice.
02 Architecture & Communication

Inter-Service Communication

Every arrow you draw between two service boxes is a decision that shows up again during an incident at 2am — whether the caller blocks and waits, or fires and moves on, decides who gets paged when the callee falls over.

7 min read

Synchronous vs asynchronous, briefly

Synchronous

  • REST over HTTP — simple, cacheable, universally supported tooling; the default choice unless you have a specific reason to reach for something else
  • gRPC — typed contracts, binary Protobuf payloads, HTTP/2 multiplexing and streaming; lower latency for internal service-to-service calls
  • Covered in real depth already in the Spring Boot module's Real-Time & RPC chapter — not re-derived here

Asynchronous

  • Events or messages published to a broker; the caller doesn't wait for the receiver to act on them
  • Covered in depth in the Kafka module (producers, partitions, delivery guarantees) and System Design's async/messaging chapter
  • The interesting content isn't the mechanics — it's when to reach for this instead of a direct call, covered below

The real decision: temporal coupling vs eventual consistency

A synchronous call creates temporal coupling: the caller and callee both have to be up, healthy, and reachable at the exact same instant for the call to succeed. If the callee is slow, the caller is slow. If the callee is down, the caller fails too — and if that caller is itself being called synchronously by something else, the failure keeps propagating backward through the whole chain. Async breaks that coupling: the callee can be completely down, and the message just sits in the queue until it recovers — the caller already got to move on. That safety isn't free — you've traded immediate consistency for eventual consistency, and taken on real complexity: messages can arrive out of order or get delivered more than once, and something has to reason about both.

The decision framework, in one line: use synchronous calls when the caller genuinely cannot proceed without an answer right now (validating a card before showing "payment accepted" on screen); use asynchronous messaging when the caller can proceed and the receiver's work can happen a moment later without anyone noticing (sending a welcome email after signup, updating a search index after a product edit).

Service Acheckout request
Service Bcalls C, blocks and waits
Service C is downrequest fails here

A synchronous chain is only as available as its least available hop. C failing means B's call fails, which means A's original request fails too — the failure propagates backward through every synchronous link.

Service Apublishes an event, returns immediately
Message queueholds the message durably
Worker (was down)processes it once it recovers

A's request already succeeded the moment the message was durably queued. The worker being down for the next five minutes delays processing, but never turns into a failure A has to handle.

Deep synchronous chains compound risk

Each additional synchronous hop multiplies the chain's overall failure probability and adds its own latency — a chain of five services each individually available 99.9% of the time is well under 99.9% available end-to-end. This is the concrete reason "just call the next service directly" stops scaling as an architecture past a couple of hops; it's also exactly the problem the resilience patterns in the next chapter exist to contain.

Doesn't async just move the failure somewhere else instead of solving it?
Yes — and that's a fair trade, not a free lunch. Instead of "the caller sees an error right now," the failure mode becomes "the effect arrives later than expected, or needs a retry." That still needs handling: durable queues, retries with a dead-letter queue for poison messages, and idempotent consumers so a redelivered message doesn't double-charge a card. The System Design module's messaging chapter and the Kafka module both cover that machinery in depth — async doesn't remove the need for resilience thinking, it just relocates where you apply it.
Chapter summary
  • Sync (REST/gRPC) and async (events/messages) are covered in mechanical depth elsewhere — the Spring Boot, Kafka, and System Design modules.
  • Synchronous calls create temporal coupling: caller and callee must both be up at the same instant, and failures propagate backward through the whole call chain.
  • Async decouples availability — the callee can be down without failing the caller — at the cost of eventual consistency and added complexity (ordering, duplicates).
  • Choose sync when the caller genuinely can't proceed without an answer now; choose async when the receiver's work can safely happen a moment later.
  • Async doesn't eliminate the need for resilience — it relocates it to queue durability, retries, and idempotent consumers.

Eventual consistencyTap to reveal

State written by an async step becomes visible to the rest of the system a short time later, not instantly — the cost of decoupling availability.

Idempotent consumerTap to reveal

A consumer that produces the same result even if it processes the same message more than once — needed because async delivery can duplicate messages.

Cascading failureTap to reveal

A failure in one service propagates backward through every synchronous caller in the chain, turning one dependency's outage into everyone's outage.

Service A calls B synchronously, which calls C synchronously. C goes down. What happens to A's request?
Temporal coupling doesn't care how many hops away the failure is — B's call to C fails, which means B can't respond to A, which means A's request fails too. There's no automatic replica fallback unless something explicitly builds one.
Which scenario is the better fit for asynchronous communication?
The welcome email doesn't block the user's flow — the email service being briefly down just delays it invisibly. Card validation and username-availability checks both need an immediate answer the caller can't proceed without, which is exactly what synchronous calls are for.
03 Architecture & Communication

Service Discovery & API Gateway

With services scaling up and down and redeploying constantly, hardcoding an IP address into another service's config is a bug waiting for the next deploy. Something has to keep track of who's actually alive and where.

7 min read

Client-side vs server-side discovery

Client-side discovery

  • The caller itself queries a registry (Eureka, Consul) for healthy instances of a service
  • The caller then load-balances across the returned instances itself
  • Fewer network hops per call, but every client needs discovery-aware logic and a registry client library

Server-side discovery

  • The caller just calls a stable address (a load balancer or gateway); that layer queries the registry and routes the request
  • Clients stay simple — no discovery logic, no registry client needed in every service
  • An extra network hop through the router/gateway, and that layer itself needs to be highly available

The registration lifecycle

Instance starts
Registers itselfwith the registry
Sends heartbeatson a fixed interval
Heartbeats stopregistry marks it unhealthy, removes it
Callers stop routingto the removed instance

Deregistration is rarely a clean explicit step — most outages are ungraceful, so the registry relies on missed heartbeats to notice an instance is gone and stop sending it traffic.

DNS-based discovery in Kubernetes is the increasingly-default answer

A Kubernetes Service gets a stable DNS name (orders-service.default.svc.cluster.local) that always resolves to a healthy pod behind it — the platform handles registration, health checks, and load balancing for you, with no Eureka client library needed in application code. Most new systems built on Kubernetes never touch a discovery library at all; they just call the Service's DNS name and let the platform do what a registry used to do explicitly.

The API Gateway pattern

An API Gateway is the single entry point clients talk to instead of calling services directly. Three things make it worth the extra hop:

  • Routing — mapping an external path or host to the right internal service, so clients never need to know the internal topology
  • Request aggregation — combining several backend calls into one response so a client doesn't have to make five round trips itself
  • Centralizing cross-cutting concerns — authentication, rate limiting, and observability get implemented once at the gateway instead of being reimplemented (and inevitably drifting) inside every individual service

The Backend-for-Frontend (BFF) variant takes this further: instead of one generic gateway serving every client, each client type gets its own gateway shaped around what that client actually needs. A mobile app on a slow connection wants one aggregated, trimmed-down response; a web dashboard wants a richer, more detailed one. Rather than making both over-fetch from a one-size-fits-all gateway, a Mobile BFF and a Web BFF each call the same backend services and assemble a response tailored to their own client.

Gateway vs service-mesh-ingress — not the same hop

An API Gateway is an explicit, application-aware hop sitting in front of all services, usually handling north-south traffic (client-to-service) and business-shaped concerns like BFF aggregation. A service mesh's ingress is a related but architecturally different place to enforce similar concerns (auth, routing, rate limiting) — and it extends that enforcement to east-west traffic (service-to-service), transparently, via sidecars rather than an explicit hop. Chapter 6 goes deep on that distinction.

Doesn't a gateway just become a single point of failure?
It would, if it were one instance — but in practice a gateway is deployed as a horizontally scaled, stateless fleet behind its own load balancer, the same way any other critical service is made highly available. The real risk isn't availability so much as the gateway becoming a dumping ground for business logic that belongs in a service — it should stay focused on routing and cross-cutting concerns, not domain rules.
Chapter summary
  • Client-side discovery puts the registry query and load balancing in the caller; server-side discovery keeps clients simple by pushing that work into a gateway or the platform.
  • The registration lifecycle relies on heartbeats — most deregistration is the registry noticing missed heartbeats, not a clean explicit shutdown step.
  • Kubernetes' DNS-based service discovery is increasingly the default — the platform handles what a registry client used to do explicitly.
  • An API Gateway centralizes routing, request aggregation, and cross-cutting concerns (auth, rate limiting, observability) so individual services don't reimplement them.
  • The Backend-for-Frontend variant tailors the aggregated response per client type instead of forcing one generic shape on everyone.

In Kubernetes, why do most services never need a Eureka-style discovery client library?
A Kubernetes Service gets a stable DNS name that the platform keeps pointed at healthy pods, handling registration and health checks for you — no application-level registry client needed. Pod IPs change constantly and are never meant to be called directly.
What specifically does the Backend-for-Frontend pattern solve that a single generic gateway doesn't?
A single generic gateway forces every client through one response shape — usually shaped around whichever client needs the most data, forcing others to over-fetch. A BFF per client type lets each one get a response aggregated specifically for its own needs.
04 Resilience & Transactions

Circuit Breaker, Bulkhead & Retry

Naming a pattern isn't the same as knowing how it actually behaves under load. This chapter goes past the name and into the actual state machines, thread pools, and backoff math that make these patterns work — or fail quietly when misapplied.

12 min read Core interview topic

Circuit breaker: stop calling a dependency that's already drowning

When a downstream dependency gets slow or starts failing, the naive behavior — keep calling it, the same way you always do — makes things strictly worse. Every caller's thread sits blocked waiting on a response that isn't coming, the caller's own thread pool fills up with stuck requests, and the failure spreads to whoever's calling you. A circuit breaker wraps a call to a dependency and tracks its failure rate; once that failure rate crosses a threshold, the breaker stops even attempting the call — it fails immediately, cheaply, without touching the network. That protects your own threads from piling up on a dead dependency, and — just as importantly — gives the dependency room to actually recover instead of getting hammered by retries while it's already struggling.

CLOSEDrequests flow, failures counted
OPENfails fast, dependency not called
HALF-OPENa few trial requests let through

Closed → Open when the failure-rate threshold is crossed. Open → Half-Open once the reset timeout elapses. From Half-Open, a successful trial sends it back to Closed; a failed one sends it straight back to Open — the loop that doesn't fit in a single straight line but is the whole point of the pattern.

StateBehaviorWhat triggers the next transition
ClosedRequests pass through normally; every success/failure is countedFailure rate crosses the configured threshold → Open
OpenRequests fail immediately — the dependency is never actually calledReset timeout elapses → Half-Open
Half-openA small number of trial requests are allowed through to test recoveryTrial succeeds → Closed. Trial fails → back to Open
Fail fast is the point, not a side effect

An open circuit deliberately answers in microseconds instead of waiting out a multi-second timeout on a call that was going to fail anyway. That protects the caller's own latency budget and thread pool, and it stops adding more load onto a dependency that's already struggling to recover — the exact opposite of what a naive retry-until-it-works loop would do.

Why have a circuit breaker at all if you already have timeouts?
A timeout only bounds how long a single call waits before giving up — it does nothing to stop the next call, or the one after that, from making the exact same doomed attempt. A circuit breaker adds memory across calls: once enough recent calls have failed, it stops trying altogether for a while. Timeouts bound one call's cost; circuit breakers bound the cost of repeatedly rediscovering the same outage.

Bulkhead: contain the blast radius per dependency

A ship is built with watertight compartments so one damaged compartment floods without sinking the whole vessel. The bulkhead pattern applies the same idea to resource isolation: each downstream dependency gets its own bounded pool of resources, so one dependency exhausting its pool can't starve the resources needed to call other, perfectly healthy dependencies.

  • Order Servicecalls three downstream dependencies, each isolated
    • Payments pool — 20 threadsPayments goes slow and exhausts all 20 — contained here
    • Inventory pool — 20 threadscompletely unaffected by Payments being slow
    • Shipping pool — 20 threadscompletely unaffected by Payments being slow

Without isolation, all three calls would share one thread pool — a slow Payments dependency alone could exhaust every thread in that shared pool, and Inventory/Shipping calls would starve even though those dependencies are perfectly healthy.

Thread-pool isolation

  • Each dependency gets its own dedicated, bounded thread pool for calls to it
  • Strongest isolation — a stuck dependency's threads literally can't be borrowed by anything else
  • Also lets timeouts be enforced from a separate thread, not the caller's own
  • Costs real overhead: context switching and per-pool thread stacks add up with many dependencies

Semaphore isolation

  • No separate thread pool — just a counter limiting how many concurrent calls to a dependency are in flight
  • Much cheaper: no extra threads, minimal overhead per dependency
  • Weaker isolation — the call still runs on the caller's own thread, so a truly stuck call can still tie it up
  • A reasonable choice when call volume is high and dependencies are typically fast, so full thread-pool overhead isn't justified

Retry with exponential backoff + jitter

Retrying a failed call seems harmless in isolation — but a naive retry (fail, immediately try again) done by every client at once turns a struggling dependency into a completely dead one: at the exact moment it needs less load to recover, it gets hit with a wave of simultaneous retries on top of its original load. Exponential backoff fixes the "immediately" part — each retry waits longer than the last (100ms, 200ms, 400ms, 800ms...), giving the dependency real breathing room. Jitter fixes a subtler problem: if every client computes the exact same backoff schedule, they all retry at the exact same moments — still a synchronized wave, just spaced out. Adding a small random offset to each delay spreads retries smoothly over time instead of in lockstep pulses.

RetryPolicy.java
long computeBackoffMs(int attempt, long baseMs, long maxMs) {
    // exponential growth, capped at maxMs
    long exp = Math.min(maxMs, baseMs * (1L << attempt));
    // full jitter: a random value between 0 and the exponential delay
    return ThreadLocalRandom.current().nextLong(0, exp + 1);
}

// attempt 0 -> up to 100ms, attempt 1 -> up to 200ms,
// attempt 2 -> up to 400ms, attempt 3 -> up to 800ms, capped at maxMs
Backoff without jitter still synchronizes retries

If 10,000 clients all fail at roughly the same moment (a brief network blip, say) and all compute the exact same "retry after 400ms" schedule, they still retry as one synchronized wave — just a delayed one instead of an immediate one. Jitter is what actually breaks the synchronization; backoff alone only delays it.

Timeout budgets across a call chain

In a chain A → B → C, each hop's timeout has to leave enough room for everything that happens after it — including that hop's own retries. If A gives up on B after 800ms total, and B sets its own timeout to C at 750ms, B has left itself almost no budget to retry a failed call to C before A already gave up and moved on. The retry that might have succeeded never gets the chance to matter.

A concrete budget mismatch

A's overall timeout to B: 800ms. B's timeout to C: 750ms, with one retry on failure. C is slow and B's first call to C times out near 750ms — but A already gives up at 800ms, only 50ms later, leaving no time for B's retry to C (which might have succeeded in 200ms) to ever complete. A gives up right as the fix was about to land. The correct budget shrinks at every hop: if A allows 800ms total, B's timeout to C — including any retry — needs to fit comfortably inside a fraction of that, not right up against it.

Chapter summary
  • A circuit breaker moves through Closed (normal, counting failures) → Open (fail fast, dependency not called) → Half-Open (trial requests) → back to Closed or Open based on the trial's outcome.
  • Failing fast in the Open state protects the caller's own resources and gives the struggling dependency room to recover — it's the point of the pattern, not a side effect.
  • Bulkhead isolation gives each dependency its own bounded thread pool (strong isolation, more overhead) or semaphore (cheaper, weaker isolation) so one dependency's failure can't starve calls to others.
  • Exponential backoff spaces retries out increasingly; jitter randomizes the exact delay so many clients don't retry in a synchronized wave.
  • Timeout budgets must shrink at every hop in a call chain — a downstream timeout set too close to the caller's own timeout leaves no room for a retry that might have succeeded.
Circuit breakerTap to reveal

A guard around a dependency call that trips to fail-fast once a failure-rate threshold is crossed, protecting the caller and giving the dependency room to recover.

BulkheadTap to reveal

Isolating resources (a thread pool or semaphore) per dependency, so one dependency's failure can't starve calls to other, healthy dependencies.

JitterTap to reveal

A small random offset added to a retry delay, spreading many clients' retries out over time instead of letting them retry in a synchronized wave.

Timeout budgetTap to reveal

The shrinking allowance each hop in a call chain gets — a downstream timeout (plus its retries) must fit comfortably inside the caller's overall timeout.

What is the half-open state in a circuit breaker actually for?
Half-open exists specifically to test recovery cheaply — a handful of trial requests, not a full flood. A success sends the breaker back to Closed; a failure sends it straight back to Open.
A team gives every downstream call type a shared thread pool, but does have a circuit breaker per dependency. A slow — not yet outright failing — dependency exhausts the shared pool. What pattern is missing?
The circuit breaker hasn't tripped because the dependency isn't failing outright, just slow — its calls are still "succeeding," just taking a long time. Without per-dependency resource isolation (bulkhead), that slowness alone can exhaust a shared pool and starve calls to otherwise-healthy dependencies.
05 Resilience & Transactions

Saga Pattern & Distributed Transactions

"Just wrap it in a transaction" stops being an option the moment the transaction spans two different databases owned by two different services. Something has to replace ACID — and it isn't going to be another kind of lock.

9 min read

Why a distributed operation can't just be one ACID transaction

Placing an order might need to charge a card (Payments' database), reserve stock (Inventory's database), and schedule a shipment (Shipping's database) — three separate databases, each privately owned by a different service, precisely because of the database-per-service rule from chapter 1. A single ACID transaction requires one database (or at least one transaction coordinator with direct control over all participating resources) — there's no single database here to wrap a BEGIN...COMMIT around. Something has to take over ACID's job of "all of this happens, or none of it does" in a world where each step commits independently, in a different service, at a different time.

Two-phase commit (2PC) — technically possible, rarely used here

2PC is the classic distributed-transaction protocol: a coordinator asks every participant to prepare (lock the affected rows, do the work, but don't commit yet) — and only once every participant votes yes does the coordinator tell everyone to actually commit. It's a real solution to atomicity across systems, but it comes with a cost that makes it a poor fit for microservice boundaries specifically.

Coordinatorasks all participants to prepare
All participants vote yeslocks held the entire time
Coordinator tells all to commitonly now do locks release

Every participant holds its locks for the entire round trip — including the time it takes the coordinator to hear back from every other participant. Fine on a single machine with microsecond round trips; across service boundaries with real network latency, it's locks held far longer than any one of these services would tolerate on their own.

Why 2PC is rarely used across service boundaries

Locks are held across every participant for the full round trip, so one slow participant slows down — and holds locks in — every other one, a direct hit to availability. Worse, if the coordinator itself crashes after participants have prepared but before it sends the commit decision, those participants are stuck holding locks indefinitely, unsure whether to commit or abort. Across independently deployed, independently owned services, that blocking behavior and single point of coordination failure is usually an unacceptable trade for strong atomicity.

Saga: a sequence of local transactions, undone forward when needed

A saga replaces one distributed transaction with a sequence of small local transactions, each owned by a single service, each committing independently and publishing an event (or triggering a call) that kicks off the next step. If step three fails, there's no way to "roll back" steps one and two — they already committed, in different databases, and other things may have already reacted to them. Instead, each earlier step defines a compensating transaction: a new, forward-moving action that undoes that step's effect. "Refund the payment" compensates "charge the payment" — it doesn't erase the charge from history, it adds a new transaction that cancels its effect.

Choreography

  • Each service listens for events and reacts on its own — no central coordinator
Order Servicecreates order, emits event
Payment Servicereacts, charges, emits event
Inventory Servicereacts independently, reserves stock

Simple to build — each service only needs to know what event to listen for. Harder to trace: the overall flow is smeared across every service's event handlers, with no single place that shows the whole saga.

Orchestration

  • A central orchestrator explicitly calls each step, and its compensation on failure
Orchestratorcalls Payment
calls Inventoryreserve stock fails
calls compensating refundon Payment, a backward step

The entire saga's logic — including which compensations run on which failure — lives in one place, easy to reason about and trace. The trade-off: the orchestrator becomes a new coupling point every step now depends on.

Compensations must be idempotent, and don't always fully "undo"

A compensating transaction can itself fail or be retried, so it needs to be safe to apply more than once (issuing the same refund twice should be a no-op, not a double refund). And some steps genuinely can't be perfectly undone — if a notification email already went out, there's no "unsend"; the compensation can only mitigate the effect (a follow-up cancellation notice), not erase it. Saga design has to accept that up front, not treat it as an edge case.

Chapter summary
  • Cross-service operations can't use one ACID transaction — there's no single database spanning the participating services.
  • 2PC gives strong atomicity but holds locks across every participant for the full round trip and blocks badly on coordinator failure — rarely acceptable across service boundaries.
  • A saga is a sequence of local transactions, each committing independently and triggering the next step; failure is undone with forward-moving compensating transactions, not a rollback.
  • Choreography (event-reactive, no coordinator) is simpler but harder to trace; orchestration (a central saga coordinator) is easier to trace but adds a new coupling point.
  • Compensations must be idempotent and sometimes can only mitigate, not perfectly reverse, an earlier step's effect.

Why can't a failed step in a saga simply "roll back" the earlier steps, the way a database transaction would?
Rollback works within a single database transaction log. In a saga, each step is already a separate committed local transaction in a separate database — undoing it needs a new forward-moving compensating transaction, not a rollback.
A team picks two-phase commit to coordinate a checkout flow across three services. What's the most likely operational problem they'll hit?
2PC does provide atomicity and can coordinate any number of participants — its real problem is availability: every participant holds locks for the whole round trip, and a coordinator crash between "prepare" and "commit" leaves participants blocked, unsure whether to commit or abort.

Strangler Fig Pattern & Service Mesh

Almost nobody gets to build microservices on a blank slate — most of this architecture gets built by carefully peeling capability after capability off of a monolith that's still running production traffic the whole time.

8 min read

Strangler fig: migrate by routing, not by rewriting

Named after the strangler fig vine, which grows around a host tree and gradually takes over its structure until the original tree can be removed — the pattern migrates a monolith the same way. A facade (usually the API gateway) sits in front of both the monolith and any new services. Traffic for a given capability routes to whichever one currently owns it. Early on, almost everything still goes to the monolith, with one small capability freshly extracted to a new service. Capability by capability, more traffic routes to new services and less to the monolith — until eventually the monolith handles nothing at all and can be safely retired.

Months later: most capabilities have been extracted one at a time behind the same facade, and clients never had to know the migration was happening underneath them. Once the monolith's slice hits zero, it's retired.

The whole point is that it's reversible and low-risk

Because the monolith keeps running the whole time, a single capability's extraction can be routed back to it instantly if the new service misbehaves — there's no "big bang" cutover where a bug means the entire system is broken. That's the real advantage over a full rewrite: every step is small, independently verifiable, and cheaply reversible.

Service mesh: moving cross-cutting concerns into infrastructure

An Istio-style service mesh deploys a small proxy — a sidecar — alongside every single service instance. Every byte of network traffic in or out of that instance passes through its sidecar first. Once traffic flows through a sidecar instead of directly between application code, a large set of cross-cutting concerns can move out of every service's codebase and into that shared proxy layer: mutual TLS between services, automatic retries, circuit breaking, load balancing, fine-grained traffic routing (canary releases by percentage), and rich observability — all without a single line of code changing inside the services themselves.

Application code on both sides makes a plain, unencrypted local call to its own sidecar — the sidecar-to-sidecar hop is where mutual TLS, retries, and circuit breaking actually happen, completely transparent to the services themselves.

Data plane

  • The sidecars themselves — the proxies actually sitting in the request path, handling every real byte of traffic

Control plane

  • The central system (Istio's Istiod, for example) that configures every sidecar — routing rules, mTLS certificates, traffic-split percentages — pushed out to the whole fleet
Consistency across a polyglot fleet, at a real operational cost

The biggest win is that a Java service, a Go service, and a Python service all get identical mTLS, retry, and circuit-breaking behavior without each team implementing (and subtly getting wrong) their own version in three different languages. The cost is real: another distributed system to run, upgrade, and debug — sidecar resource overhead on every pod, and a genuinely harder failure mode to diagnose when the mesh itself misbehaves rather than the application.

  • It's low-risk specifically because each step is small and reversible — the monolith keeps running the whole time as a fallback.
  • A service mesh's sidecars intercept all traffic in/out of a service instance, moving mTLS, retries, circuit breaking, and observability into infrastructure.
  • Data plane = the sidecars actually handling traffic; control plane = the central system configuring them all.
  • The trade-off is consistent behavior across a polyglot fleet of services, at the cost of real operational complexity — another system to run and debug.

Distributed Tracing

"The checkout API is slow" means nothing in a system with thirty services behind it — until a trace turns that vague complaint into "hop 4 of 9, the Inventory service's DB query, took 4 of the 4.2 total seconds."

6 min read

The conceptual framing — metrics, logs, and traces as the three observability pillars, and what each one answers — already lives in the System Design module's Observability chapter, and isn't re-derived here. What's specific to microservices is the mechanics of keeping one trace connected as a request crosses dozens of independently deployed services.

Trace context propagation: the part that actually breaks in practice

A single incoming request gets one trace ID — an identifier for the entire end-to-end journey across every service it touches. Each individual hop within that journey gets its own span ID, nested under the trace, recording exactly how long that one hop took. The mechanism only works if that trace ID (and the current span's ID, as its parent) gets forwarded on every single hop — as an HTTP header on a REST call, as gRPC metadata on a typed call, and — the case that actually trips teams up — attached to the message itself when a request crosses a message queue, since there's no live call to carry a header on at that point; the context has to be serialized into the message and read back out by whatever consumes it.

Gatewaystarts trace T1, span 1
Service AT1, span 2 (HTTP header)
Service BT1, span 3 (gRPC metadata)
Message queueT1 attached to the message body
Service CT1, span 4 (read from message)

One trace ID (T1) survives an HTTP hop, a gRPC hop, and a hop through a message queue — each service adds its own span underneath it. Drop the propagation at any single hop and the trace splits into disconnected fragments, each looking like an unrelated request.

The actual payoff: localization, not just visibility

Without a connected trace, "checkout is slow" means checking metrics and logs across a dozen candidate services, one at a time, guessing which one is actually the bottleneck. With a connected trace, the span tree shows exactly which hop consumed the time — instantly narrowing a dozen suspects down to one span, one service, one query. That's the entire value proposition of distributed tracing in a microservices system: turning "somewhere in there" into "right here."

Why is the message-queue hop specifically the trickiest one to propagate through?
On an HTTP or gRPC call, the context rides along on a live connection that both sides are actively participating in at the same instant — it's just another header. A message sitting in a queue might not be consumed for seconds or hours, by a completely different process with no live connection back to the producer at all. The only way the trace survives is if the producer serializes the trace context into the message itself (usually as message headers/metadata) and the consumer explicitly reads it back out to continue the same trace — skip that step and the consumer just starts a brand-new, disconnected trace.

  • Context must be forwarded on every hop — HTTP headers, gRPC metadata, and (hardest) serialized into the message body across a queue.

What's the main practical benefit of distributed tracing in a system with many services?
A connected trace's span tree shows exactly where time went across a whole call graph, turning a vague "the API is slow" into a specific hop and service — that localization, not automatic remediation, is the value.

Testing Microservices

Unit and integration tests still matter exactly as much as they always did — the dedicated Testing module covers writing them well. What's specific to microservices is a failure mode neither of those catches: two independently deployed services quietly disagreeing about the shape of the API between them.

6 min read

Contract testing: catching a breaking change before it ships

A consumer and a provider service are built and deployed by different teams, on different schedules — nothing stops the provider from renaming a field or changing a response shape in a way that quietly breaks every consumer, with neither side finding out until it's in production. Consumer-driven contract testing (the Pact-style approach) closes that gap without requiring a full end-to-end environment for every change: the consumer team writes a contract describing exactly the request it will send and the response shape it expects back. That contract then runs against the provider's actual code in the provider's own CI pipeline — if the provider's real response no longer satisfies the contract, the provider's build fails right there, before the change ever reaches a shared environment or production. Both sides can keep evolving independently; the contract is what keeps them honest about compatibility.

Both sides evolve independently, but the provider's own CI catches a broken contract right there — before the change ever reaches a shared environment or production.

09 Interview Room

Interview Questions

Fourteen questions organized by what they're actually testing — internals, trade-offs, traps, and scenarios — because microservices interviews rarely ask "what is a circuit breaker" and almost always ask "what happens when."

Read before the interview, not during it
Internals & Why
01
InternalsWhy does an open circuit breaker fail immediately instead of just letting the existing timeout handle it?

A timeout still lets a request tie up a caller thread for its full duration before failing, and it has no memory — the very next request repeats the identical doomed attempt. An open circuit breaker skips the network call entirely, failing in microseconds instead of seconds, which protects the caller's own thread pool and latency budget, and — just as importantly — stops adding load to a dependency that's actively trying to recover. Timeouts bound the cost of one call; the breaker bounds the cost of endlessly repeating the same failed call.

02
InternalsWhy does bulkhead isolation still matter even with a circuit breaker already in place?

A circuit breaker only trips once a failure-rate threshold is crossed — a dependency that's merely slow, not yet failing outright, keeps looking "healthy" to the breaker while its calls quietly tie up shared resources one request at a time. If every dependency shares one thread pool, that slow dependency alone can exhaust the pool and starve calls to completely healthy dependencies, well before the breaker ever reacts. Bulkhead isolation bounds the blast radius during exactly that window — regardless of whether the breaker has tripped yet — by giving each dependency its own resource budget that can't be borrowed by anything else.

03
InternalsWhy does a saga need compensating transactions instead of a rollback?

A rollback undoes uncommitted work inside a single transaction log. In a saga, each earlier step has already committed independently, in a different service's own database — there's no shared log spanning all of them to roll back, and other systems may have already reacted to that committed step. A compensating transaction is a brand-new, independent forward transaction (like "refund payment") that cancels the effect of an earlier one — it adds to history rather than erasing from it, which is the only option available once each step owns and commits its own data.

Trade-offs
04
Trade-offSync vs async communication — what's actually being traded, beyond "sync is simpler"?

Sync trades availability for immediacy: you get an answer right now, but the caller's success is temporally coupled to the callee being up at that exact instant, and failures cascade backward through the whole chain. Async trades immediacy for availability: the callee can be down entirely and the caller still succeeds, but the system now has to tolerate eventual consistency and handle messages that might arrive late, out of order, or more than once. Neither is strictly better — the choice depends on whether the caller can actually proceed without an immediate answer.

05
Trade-offChoreography vs orchestration for a saga — when would you actually pick one over the other?

Choreography works well for a small number of steps where the flow is simple enough that tracing it across a few event handlers is manageable — it avoids introducing a new coordinator as a coupling point. Once the saga grows to many steps with several different failure and compensation paths, or spans several teams, the cost of choreography's smeared-out visibility outweighs its simplicity — that's the signal to move to orchestration, where the whole flow (and every compensation) lives in one place, at the cost of that orchestrator becoming a dependency every step now shares.

06
Trade-offService mesh vs a resilience library embedded in each service (like Resilience4j) — what's the real trade-off?

A mesh gives every service in a polyglot fleet identical retry, circuit-breaking, and mTLS behavior without each team hand-rolling (and subtly getting wrong) their own version in their own language — at the cost of running an entirely new infrastructure layer, per-pod sidecar overhead, and a harder failure mode when the mesh itself misbehaves. An embedded library gives finer-grained, code-level control specific to each service's needs with no extra infrastructure, but every service — and every language represented in the fleet — needs its own correct implementation, and behavior can quietly drift between teams over time.

07
Trade-offThread-pool bulkhead isolation vs semaphore isolation — what do you give up by choosing the cheaper option?

Semaphore isolation is much cheaper — no extra threads, minimal overhead — but the call still executes on the caller's own thread. A truly hung call (not just slow-but-responding) can still tie up that thread past the point you'd want to abandon it, since there's no separate pool to walk away from independently. Thread-pool isolation costs real memory and context-switching overhead per dependency, but a stuck call can be abandoned on its own dedicated thread without affecting the caller's ability to move on.

Traps
08
TrapA team wraps every individual call site in its own circuit breaker instance, rather than one breaker shared per dependency. What's wrong with that?

Failure counting gets fragmented across many separate breaker instances that never share state, so no single breaker instance ever accumulates enough failures to trip, even while the dependency as a whole is clearly unhealthy across all of them combined. A circuit breaker has to be scoped per-dependency (or at least per downstream instance), aggregating the true failure signal for that dependency — not sliced per call site, where each individual slice can look fine in isolation while the dependency is actually drowning.

09
TrapA retry policy immediately retries a failed call three times with no delay between attempts. Under what condition does this make an outage strictly worse?

When the dependency is failing because it's overloaded rather than because of a one-off transient blip. Immediate retries from every failing caller multiply the load hitting an already-struggling dependency at the exact moment it needs less load, not more — turning a partial degradation into a full outage. Exponential backoff with jitter exists specifically to avoid this: space retries out and desynchronize them across clients instead of adding to the pile-up immediately.

10
Trap · Guess the outcomeService A's overall timeout is 500ms. Service B, which A calls, sets its own timeout to its downstream dependency C at 480ms, with one retry on failure. C is slow. What actually happens?

B's first call to C times out near the 480ms mark, leaving essentially no time for B's retry to C before A's own 500ms timeout fires — A gives up and returns an error to its caller right around when B's retry would have started, let alone completed. The nested timeout budget was never big enough to fit a retry inside it. The fix is for B's timeout to C (including any retry) to fit comfortably inside a smaller fraction of A's 500ms, not right up against it.

11
TrapA saga's compensating transaction for "reserve inventory" is implemented as "delete the reservation row." What breaks under a retried compensation?

If the compensation runs twice — a retried message, a redelivered event — the second delete either errors out on an already-missing row, or worse, if the row ID gets reused, deletes an entirely unrelated reservation. Compensations must be idempotent: check the current state before acting (only delete if the reservation still exists and hasn't already been compensated) so repeated delivery is a safe no-op rather than a second, unintended side effect.

Scenario
12
ScenarioYou're designing the saga for "place an order": charge payment, reserve inventory, schedule shipping. Three steps, a small team, rare failures. Choreography or orchestration?

Choreography is a reasonable fit here — three steps and one small team means the "hard to trace" downside is manageable, and there's no need to introduce a dedicated coupling point for something this simple. If this saga later grows to, say, eight steps with several different failure and compensation paths spread across multiple teams, that growth in complexity is the actual signal to migrate to orchestration, where the whole flow becomes visible and traceable in one place again.

13
ScenarioA mobile app and a web dashboard both call the same backend services, but the mobile app keeps timing out on a slow, over-fetched response shaped for the web client's needs. What pattern addresses this directly?

Backend-for-Frontend. Instead of forcing every client through one generic gateway response shaped around whichever client needs the richest data, a Mobile BFF assembles a smaller, pre-aggregated response tailored to what the mobile app actually needs, while a separate Web BFF keeps serving the richer shape the dashboard wants — both calling the same underlying services.

14
ScenarioA trace shows a request entering a message queue, then a completely new, disconnected trace ID starting on the consumer side. What's the likely root cause, and the fix?

The producer never serialized the trace context into the message (or the consumer never read it back out) before publishing. There's no live connection across a queue hop to carry a header automatically — propagation has to be done explicitly, attaching the trace context to the message itself as headers/metadata, with the consumer continuing that same trace ID instead of starting a fresh one when it picks the message up.

Interview delivery tips

1. When asked about resilience, name circuit breaker, bulkhead, and retry-with-backoff together and immediately explain how they compose (retry, inside a circuit breaker, inside a bulkhead) rather than describing them as three unrelated tools.
2. For any saga question, volunteer the choreography-vs-orchestration trade-off unprompted — it signals you understand the coupling cost, not just the mechanism.
3. If asked "sync or async," don't just pick one — state the actual trade-off (temporal coupling vs eventual consistency) and give a one-line example of when each wins.
4. When discussing service mesh, explicitly mention sidecar transparency ("the application code doesn't know mTLS is happening") — that detail shows you understand the mechanism, not just the marketing term.
5. If given a whiteboard for a timeout-budget question, draw the numbers shrinking hop by hop — interviewers give strong credit for catching a "B's timeout too close to A's" mismatch instead of describing timeouts only in the abstract.
