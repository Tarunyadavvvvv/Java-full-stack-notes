Part I — Foundations

1. What Claude Code Is & How It Works Basic

1.1 What it is

Claude Code is an agentic coding tool that lives in your terminal (also available in IDEs and on the web). It's powered by Claude and can read/write files, run commands, search code, browse the web, and orchestrate multi-step engineering tasks — acting on your codebase, not just chatting about it.

Terminal-nativeReads & edits filesRuns commandsMulti-step agentExtensible (MCP/hooks/skills)Permission-gated

1.2 The agentic loop (mental model)

You give a goal
      │
      ▼
┌─────────────────────────────────────────────┐
│  Claude reasons about the next step          │
│       │                                       │
│       ▼                                       │
│  Calls a TOOL (Read/Edit/Bash/Grep/...)       │
│       │                                       │
│       ▼                                       │
│  PERMISSION check (allow / ask / deny)        │
│       │                                       │
│       ▼                                       │
│  Tool runs -> result returns to Claude        │
│       │                                       │
│       └──── repeat until goal is done ────────┘
└─────────────────────────────────────────────┘
HOOKS can fire around tool calls & lifecycle events.

Claude plans, takes an action via a tool, observes the result, and iterates — the core "agent loop." Your context window holds the conversation, file contents read, tool results, and memory; permissions gate risky actions; hooks let you intercept the loop.

1.3 Where it runs & what loads at startup

SurfaceUse
Terminal CLIPrimary, scriptable
IDE extensions (VS Code, JetBrains)In-editor diffs & context
Desktop / Web (claude.ai/code)GUI, remote sessions

At launch Claude Code loads: the system prompt, your CLAUDE.md memory files, auto-memory, environment info, and (deferred) MCP tools. Understanding this "what's in context" picture is the key to using it efficiently.

How is Claude Code different from a chatbot or autocomplete?
It's agentic: it can take real actions (edit files, run tests, commit) in a loop until a goal is met, and it manages its own context, tools, and sub-tasks. Autocomplete suggests the next token; a chatbot talks. Claude Code does the work on your actual repo, gated by permissions.

2. Getting Started & the CLI Basic

2.1 Core commands

claude                       # start an interactive session in the current repo
claude "fix the failing test"  # start with an initial prompt
claude -c                    # continue the most recent conversation
claude -r "<id-or-name>"     # resume a specific session
claude update                # update to the latest version
claude mcp ...               # manage MCP servers (see §11)
claude auth login            # sign in

2.2 Headless / scriptable mode

claude -p "summarize recent changes"        # print response & exit (non-interactive)
cat error.log | claude -p "what caused this?"   # pipe input in
claude -p "review the diff" --output-format json  # machine-readable output
-p (print/headless mode) is the gateway to automation — run Claude Code in CI, scripts, and pipelines. Combine with --output-format json or stream-json for parsing.

3. Built-in Tools Intermediate

Tools are how Claude Code acts. Knowing them helps you write better prompts, permissions, and hooks.

ToolPurposeNeeds permission?
ReadRead files (code, images, PDFs, notebooks)No
WriteCreate/overwrite a fileYes
EditExact string replacement in a fileYes
BashRun shell commandsYes
GlobFind files by pattern (fast)No
GrepSearch file contents (ripgrep)No
WebFetchFetch & extract a URLYes
WebSearchSearch the webYes
Agent / TaskSpawn a subagent for a sub-taskNo
AskUserQuestionAsk you a multiple-choice questionNo
SkillRun a skill / custom commandYes
NotebookEditEdit Jupyter cellsYes
EnterPlanMode / ExitPlanModePlan before editingExit needs approval
Background tasks & MonitorRun/watch long processesVaries
Edit requires a prior Read of the file, and the target string must match exactly (whitespace-sensitive) and be unique (or use replace-all). Bash runs each command in a fresh process — cd persists within the working dir, but env vars/aliases don't persist between calls. Glob/Grep respect .gitignore by default.
Why does Claude prefer Grep/Glob over grep/find in Bash?
The dedicated tools integrate with the permission system and file-link UI, respect .gitignore, and are optimized (ripgrep). They return cleaner, structured results and don't require Bash permission — so they're safer and faster for searching.

Part II — Context & Memory

4. Context Management Intermediate — pivotal skill

4.1 The context window

Everything Claude "sees" lives in a finite context window: the system prompt, your messages, files read, tool results, and memory. When it fills, quality and speed degrade and cost rises. Managing context is the single biggest lever for effective use.

[ System prompt ][ CLAUDE.md memory ][ conversation + tool results + files read ]
 └──────────────────── finite context window ────────────────────┘  -> fills up

4.2 The three context commands

CommandEffectWhen to use
/clearStart a fresh conversation (empty context); old one stays in /resumeSwitching to an unrelated task
/compactSummarize the conversation, keep the thread, reclaim spaceLong task, context filling up
/contextVisualize what's consuming the windowDiagnosing bloat
Auto-compaction kicks in automatically as the window approaches its limit — Claude summarizes earlier context and continues. On compaction it re-reads CLAUDE.md from disk, so your memory instructions persist across the summary.

4.3 Habits that keep context lean

  • /clear between unrelated tasks — don't let one giant session accumulate irrelevant history.
  • Be specific about which files matter; avoid asking Claude to read the whole repo.
  • Use subagents (§9) for big searches — they explore in their own context and return only the conclusion.
  • Put durable facts in CLAUDE.md instead of repeating them each session.
  • Defer MCP tools (loaded on demand) so dozens of tool schemas don't fill the window.
/clear vs /compact — which when?
Use /clear when starting something unrelated (you don't need the prior history). Use /compact when you're mid-task and want to keep the thread's intent but free space — it summarizes rather than discards. /clear resets; /compact condenses.
Why does a long session get slower and less accurate?
A bloated context window means more tokens to process each turn (slower, costlier) and more "noise" competing with the relevant details (less accurate). Trim aggressively with /clear, /compact, and subagents to keep signal high.

5. Memory (CLAUDE.md) Intermediate — high-leverage

5.1 What memory is

CLAUDE.md files are persistent instructions auto-loaded into context at the start of every session — project conventions, build/test commands, architecture notes, coding style, "always/never" rules. This is how you teach Claude Code your project once instead of every conversation.

5.2 The memory hierarchy (precedence)

ScopeLocationShared?Use for
Enterprise/ManagedOS-level managed pathOrg-wideCompany policies
User~/.claude/CLAUDE.mdYou, all projectsPersonal preferences
Project./CLAUDE.md or ./.claude/CLAUDE.mdTeam (committed)Project conventions
Local./CLAUDE.local.mdYou, this project (gitignored)Personal project notes
Files are concatenated (more specific layers add to broader ones). Subdirectory CLAUDE.md files load on demand when Claude works in those folders — good for module-specific instructions.

5.3 Writing good memory

# Project: Payments Service

## Commands
- Build:  ./mvnw -B package
- Test:   ./mvnw test
- Run:    docker compose up

## Conventions
- Use constructor injection (never field injection)
- All money handled in integer cents
- Never commit secrets; use the vault

## Imports
@docs/architecture.md
@~/.claude/my-global-style.md
  • @path imports pull in other files (relative to the importing file; up to ~4 hops). Great for sharing standards.
  • /init bootstraps a CLAUDE.md by analyzing your repo — run it first, then refine.
  • /memory lists/edits loaded memory; # at the start of a message quickly appends a fact to memory.
  • Auto-memory can let Claude persist learned facts to a per-repo memory folder (toggle via /memory / settings).
Best practices: keep memory concise & high-signal (it costs context every session); record non-obvious facts and conventions, not what the code already shows; commit project CLAUDE.md so the whole team benefits; prune stale entries.
Pitfall: bloated CLAUDE.md files waste context on every turn and bury the important rules. Treat memory like a tight README for the agent, not a dumping ground.
CLAUDE.md vs settings.json — what goes where?
CLAUDE.md = natural-language instructions/context for Claude (conventions, commands, architecture). settings.json = machine config (permissions, hooks, model, env). Memory shapes what Claude knows; settings shape how the tool behaves.

7. Permissions Intermediate — safety core

7.1 How permissions work

Risky tool calls are gated. Each action is checked against rules; the first match wins, evaluated as deny → ask → allow. Read-only tools (Read/Glop/Grep) generally don't prompt; mutating tools (Edit/Write/Bash) do.

7.2 Permission modes

ModeBehaviour
defaultPrompts on first use of each risky action
acceptEditsAuto-accepts file edits & common safe FS commands
planPlan mode: explores/reads but won't edit source
bypassPermissionsSkips prompts (use with extreme care)
bypassPermissions removes the safety net — only use in fully sandboxed/throwaway environments or trusted automation. Never in a sandbox that can reach production or secrets.

7.3 Rule syntax (most-used patterns)

RuleMatches
Bash(npm run test:*)npm test commands (prefix)
Bash(git push:*)git push variants
Read(./src/**)Files under src (gitignore-style globs)
Read(.env*) in denyBlock reading env files
Edit(src/**/*.ts)Edits to TS files in src
WebFetch(domain:*.example.com)Fetches to a domain
mcp__github__*All tools from the github MCP server
Agent(Explore)A specific subagent
// Example: a safe, productive baseline
{
  "permissions": {
    "allow": [
      "Read(**)", "Grep", "Glob",
      "Bash(npm run lint)", "Bash(npm run test:*)", "Bash(git status)", "Bash(git diff:*)"
    ],
    "ask":  ["Bash(git push:*)", "Bash(git commit:*)"],
    "deny": ["Read(.env*)", "Read(**/secrets/**)", "Bash(rm -rf:*)"]
  }
}
Tune permissions to reduce prompts without sacrificing safety: allow your common read-only & test commands, ask for pushes/commits, and deny reads of secrets & destructive commands. Manage interactively via /permissions.
How do you let Claude work fast without constant prompts, but safely?
Allowlist the safe, frequent operations (reads, lint, tests, status/diff), put writes/pushes in ask, and explicitly deny secrets and destructive commands. Use acceptEdits mode for trusted edit-heavy sessions. Reserve bypassPermissions for sandboxes only.
A teammate denied a tool call — what should Claude Code do?
A denial is feedback: don't retry the same call verbatim. Adjust the approach (different command, ask for the needed permission, or propose an alternative). Persisted rules live in settings.json / /permissions.

Part IV — Extensibility

8. Slash Commands & Skills Advanced

8.1 What they are

Custom slash commands / skills are reusable, parameterized prompts (plus optional logic) you invoke with /name. They capture repeatable workflows — "review this PR", "write a migration", "generate tests" — so you don't retype them.

8.2 Where they live

LocationScope
.claude/commands/<name>.mdProject (committed, team-shared)
~/.claude/commands/<name>.mdPersonal, all projects
.claude/skills/<name>/SKILL.mdSkill form (richer, can bundle files)
Subdirectories namespace commands (e.g. .claude/commands/db/migrate.md → /db:migrate). The command name is the filename (or skill directory name).

8.3 Anatomy of a command

---
description: Review a pull request for bugs and style
argument-hint: "[pr-number]"
allowed-tools: Read, Grep, Bash(git diff:*), Bash(gh pr view:*)
model: claude-opus-4-8
---
Review PR #$1.

## Context
- Diff: !`gh pr diff $1`
- Guidelines: @docs/review-checklist.md

Focus on correctness, security, and tests. Post findings as a summary.
FeatureMeaning
$ARGUMENTSAll args as typed
$1, $2 ...Positional args
` !`cmd` `Run a shell command, inject its output
@pathInject a file's contents
allowed-toolsRestrict which tools the command may use
modelForce a model for this command
Use cases: code review, test generation, release notes, scaffolding, "explain this module", standardized commit messages, repetitive QA checks. Commit project commands so the whole team gets the same workflow.
When is a skill/command better than just typing the prompt?
When you (or your team) repeat the same multi-step instruction, want consistent tool restrictions/model, or want to bundle context (files, shell output) automatically. It standardizes and speeds up recurring workflows and removes prompt drift.

9. Subagents Advanced

9.1 What & why

A subagent is a specialized assistant with its own prompt, tool set, and a separate context window. The main agent delegates a sub-task; the subagent does the work and returns only its conclusion — keeping the main context clean and enabling parallelism.

Main agent ──delegates──> [ Subagent: "code-reviewer" ]
                              own context + own tools
                              does the work
                          ◄── returns just the result ──
Main context stays lean; big searches/reviews happen "off to the side".

9.2 Defining a subagent

# .claude/agents/code-reviewer.md  (or ~/.claude/agents/ for personal)
---
name: code-reviewer
description: Reviews code changes for bugs, security, and style. Use after edits.
tools: Read, Grep, Glob, Bash(git diff:*)
model: inherit
---
You are a senior code reviewer. Examine the diff, flag correctness and
security issues with file:line references, and suggest concrete fixes.
Be specific; prioritize real bugs over nitpicks.
FrontmatterMeaning
nameUnique id (lowercase-hyphens)
descriptionWhen Claude should delegate to it (drives auto-delegation)
toolsAllowlist of tools (omit to inherit all)
modelsonnet / opus / haiku / inherit / full ID

9.3 Invoking

  • Automatic: Claude delegates based on the description.
  • Explicit: "Use the code-reviewer subagent to check the auth changes."
  • Manage via the /agents command (create/edit/list, see running agents).
Great subagent use cases: broad codebase exploration ("find everywhere X is used"), adversarial review/verification, parallel independent tasks, and isolating noisy work. Give each a tight tool allowlist and a sharp description.
Why do subagents help with context?
They run in their own context window and return only the conclusion to the main agent. A 50-file search that would flood your main context happens inside the subagent; you just get the answer — keeping the main session fast and focused.

10. Hooks Advanced — automation power

10.1 What hooks are

Hooks are user-defined commands (or HTTP/prompt actions) that fire automatically at points in Claude Code's lifecycle — before/after tool calls, on prompt submit, on stop, etc. They let you enforce policy and automate deterministically (the harness runs them, not Claude).

Key insight: "Whenever X, do Y" automations belong in hooks, not memory — because hooks are guaranteed to run (executed by the harness), while instructions in CLAUDE.md are only suggestions Claude may follow.

10.2 Common hook events

EventFiresCan block?
PreToolUseBefore a tool runsYes (allow/deny/ask)
PostToolUseAfter a tool succeedsNo
UserPromptSubmitBefore your prompt is processedYes
StopWhen Claude finishes respondingYes
SubagentStopWhen a subagent finishesYes
SessionStart / SessionEndSession begins / endsNo
PreCompactBefore context compactionYes
NotificationWhen Claude Code notifies youNo

10.3 Configuring a hook

// settings.json — auto-format files after every edit
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "prettier --write \"$CLAUDE_FILE_PATHS\"" }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "~/.claude/guard-dangerous-cmd.sh" }
        ]
      }
    ]
  }
}

10.4 Hook I/O & control

  • Hooks receive a JSON payload on stdin (session id, tool name, tool input, cwd, event name...).
  • Exit code 0 = success (stdout may carry JSON directives). Exit code 2 = block the action & send stderr back to Claude (for blockable events). Other non-zero = non-blocking error shown to you.
  • For fine control, emit JSON (e.g. a PreToolUse permissionDecision of allow/deny/ask, or updatedInput to rewrite the tool call).
Real-world hooks: auto-format/lint on edit, run tests after changes, block edits to protected paths, scan for secrets before commits, send a desktop/Slack notification on Stop, log all Bash commands for audit, inject project context on SessionStart.
Pitfalls: slow hooks block the loop (set timeouts/async); a buggy blocking hook can wedge sessions; never trust unsanitized paths in hook scripts (quote variables). Use disableAllHooks to debug.
When should I use a hook vs telling Claude in CLAUDE.md?
If it must always happen (format on save, block secret edits, run tests after changes), use a hook — the harness guarantees execution. CLAUDE.md is advisory guidance Claude usually follows but can skip. Determinism → hooks; preferences/context → memory.
How does a PreToolUse hook block a dangerous command?
It reads the tool input from stdin (e.g. the Bash command), decides it's unsafe, and either exits with code 2 (block + explain via stderr) or emits JSON with permissionDecision: "deny" and a reason. Claude then sees the denial and adjusts.

11. MCP (Model Context Protocol) Advanced

11.1 What MCP is

MCP is an open standard that lets Claude Code connect to external tools, data sources, and services — databases, GitHub/Jira, browsers, internal APIs — via standardized "MCP servers." It's how you extend Claude Code beyond the built-in tools.

Claude Code ──MCP──> [ GitHub server ]  -> issues, PRs
            ──MCP──> [ Postgres server ] -> query your DB
            ──MCP──> [ Puppeteer server ]-> drive a browser
Tools appear as:  mcp__<server>__<tool>   (e.g. mcp__github__get_pr)

11.2 Adding servers

# Remote HTTP server (recommended for hosted services)
claude mcp add --transport http github https://api.example.com/mcp \
  --header "Authorization: Bearer $TOKEN"

# Local stdio server (a process on your machine)
claude mcp add --transport stdio postgres -- npx -y @some/db-mcp --dsn "$DB_URL"

claude mcp list           # list configured servers
claude mcp get github     # details for one server
claude mcp remove github  # remove
# In-session: /mcp  -> status, auth (OAuth), enable/disable
TransportUse
stdioLocal process (direct system access)
HTTPRemote servers (recommended; OAuth supported)
SSERemote (legacy; prefer HTTP)

11.3 Scopes & .mcp.json

ScopeWhereShared?
LocalPer-project (your user config)No
Project.mcp.json at repo rootYes (committed)
UserYour user configAll your projects
// .mcp.json (project-shared servers)
{
  "mcpServers": {
    "github": { "type": "http", "url": "https://api.example.com/mcp",
                "headers": { "Authorization": "Bearer ${GH_TOKEN}" } },
    "db":     { "type": "stdio", "command": "npx",
                "args": ["-y","@some/db-mcp"], "env": { "DB_URL": "${DB_URL}" } }
  }
}
Deferred loading: MCP tool schemas load on demand (via a tool-search step) so dozens of tools don't consume your context up front. Permission rules like mcp__github__* control what Claude may call.
Use cases: let Claude read Jira tickets, query a database, open PRs, run browser tests, or hit internal APIs — all within the agent loop. Prefer HTTP transport + OAuth for hosted services; keep secrets in env vars, not committed files.
How are MCP tools named and permissioned?
As mcp__<server>__<tool> (e.g. mcp__github__create_issue). You allow/deny them like any tool: mcp__github__* for all of a server's tools, or a specific tool name. Project servers can be auto-approved via enableAllProjectMcpServers.
MCP server vs a custom slash command — when to use which?
An MCP server adds new capabilities/tools (connect to a system Claude couldn't otherwise reach). A slash command/skill packages a reusable prompt/workflow over existing tools. Use MCP to extend reach; use commands to standardize how you ask.

Part V — Mastery

12. Workflows & Automation Advanced

12.1 Effective interactive workflows

WorkflowHow
Explore → Plan → CodeAsk Claude to investigate & plan first (plan mode), approve, then implement
TDD loop"Write failing tests, then implement until green" — Claude iterates with the test runner
Review & verifyUse a code-reviewer subagent + a verify step after changes
Checkpoint & resume/clear between tasks; --resume to return later

12.2 Plan mode

Plan mode lets Claude read and analyze without editing source, then propose a plan you approve before any changes — ideal for risky or large tasks. Enter via --permission-mode plan or in-session, and exit (with approval) to execute.

12.3 Headless automation & CI

# In CI: have Claude review the PR diff and emit JSON
claude -p "Review the staged diff for bugs and security issues. Be concise." \
  --output-format json --permission-mode plan > review.json

# Generate release notes from git log
git log --oneline v1.2..HEAD | claude -p "Write concise release notes grouped by type."

# Triage a failing build
cat build.log | claude -p "What failed and what's the minimal fix?"
Headless mode (-p) + tight --allowedTools/--permission-mode is the foundation of CI integrations, scheduled jobs, and bots. Pin tools narrowly and avoid bypassPermissions unless the environment is fully sandboxed.

12.4 Scheduling & loops

  • Recurring tasks: the /loop skill runs a prompt on an interval (e.g. poll a deploy, babysit PRs).
  • Scheduled cloud routines: the /schedule skill creates cron-style agents that run on a schedule.
  • Background work: run long tasks/agents in the background and get notified on completion.

12.5 Project structure for Claude Code

├── .claude/
│   ├── settings.json             # team-shared config (permissions, hooks)
│   ├── settings.local.json       # personal overrides (gitignored)
│   ├── commands/                 # custom slash commands

│   │   └── code-reviewer.md

Set a repo up for the whole team: commit CLAUDE.md, .claude/settings.json, shared commands/agents, and .mcp.json. Everyone gets consistent conventions, permissions, automations, and integrations out of the box.

13. Real-World Scenarios Advanced

13.1 Software development

  • Feature implementation: "Explore how auth works, plan adding 2FA, then implement with tests." (explore → plan → code).
  • Bug fix: paste the stack trace; let Claude locate, reproduce, fix, and add a regression test.
  • Refactor: a subagent surveys usages; Claude refactors incrementally with tests after each step (hook).
  • Codebase onboarding: "Explain the architecture and key modules" + /init to seed memory.

13.2 QA automation

  • Test generation: a /gen-tests command that reads a module and writes unit tests with edge cases.
  • Browser/E2E: via a Puppeteer/Playwright MCP server, drive the app and assert behaviour.
  • CI gate: headless claude -p reviews diffs / runs the verify skill; a Stop hook reports results.
  • Flaky-test triage: feed test logs; Claude clusters failures and proposes fixes.

13.3 Productivity & ops

  • Release notes / changelogs from git history (headless).
  • Incident triage: pipe logs/metrics; Claude localizes and suggests mitigations.
  • Repo maintenance: scheduled routine to update deps, fix lint, open a PR.
  • Knowledge: MCP to Jira/Confluence/Notion so Claude works from real tickets & docs.
How would you set up Claude Code to auto-review every PR?
In CI, run claude -p in plan mode with a tight tool allowlist on the PR diff, using a project review command for consistency; output JSON and post it as a PR comment. Optionally add a GitHub MCP server so Claude can read PR metadata and post the comment itself.

14. Best Practices, Pitfalls & Troubleshooting Essential

14.1 Best practices

  • Give context & be specific — name files, paste errors, state the goal & constraints.
  • Plan first for big tasks — use plan mode; approve the approach before edits.
  • Keep context lean — /clear between tasks; subagents for big searches.
  • Invest in CLAUDE.md — encode conventions/commands once.
  • Automate the deterministic — hooks for format/test/guardrails.
  • Tune permissions — allow safe ops, ask for writes, deny secrets/destructive.
  • Verify the work — run tests/the app; use a reviewer subagent.
  • Commit small, reviewable changes — let Claude work in focused increments.

14.2 Common pitfalls

Letting one session balloon (context bloat); vague prompts; over-broad permissions or careless bypassPermissions; bloated/stale CLAUDE.md; expecting "whenever X do Y" to work from memory instead of a hook; committing secrets via .mcp.json/settings; slow blocking hooks wedging the loop; not verifying generated code.
