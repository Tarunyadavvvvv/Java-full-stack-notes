12. Spring Core & IoC / DI Intermediate ↑ Contents

12.1 Inversion of Control (IoC)

IoC means the framework, not your code, controls object creation and wiring. The IoC container (ApplicationContext) instantiates, configures, and assembles beans. Dependency Injection (DI) is the mechanism that implements IoC — dependencies are supplied to an object rather than created by it.

12.2 Types of dependency injection

TypeHowNotes
ConstructorVia constructor argsRecommended — immutable, enables final fields, fails fast, testable
SetterVia setter methodsFor optional dependencies
Field@Autowired on fieldConcise but hard to test & hides dependencies — avoid
@Service
public class OrderService {
    private final PaymentGateway gateway;        // final = enforced dependency
    public OrderService(PaymentGateway gateway){ // constructor injection
        this.gateway = gateway;                  // @Autowired optional if single ctor
    }
}

12.3 Spring stereotypes & configuration

AnnotationRole
@ComponentGeneric Spring-managed bean
@ServiceBusiness logic layer (semantic)
@RepositoryPersistence layer + exception translation
@Controller / @RestControllerWeb layer
@Configuration + @BeanJava-based bean definitions

12.4 @Autowired resolution & ambiguity

  • By type first; if multiple candidates, by name.
  • @Qualifier("beanName") — pick a specific bean.
  • @Primary — default winner when multiple match.
  • @Profile — activate beans per environment (dev/prod).
BeanFactory vs ApplicationContext?
BeanFactory is the basic container with lazy bean instantiation. ApplicationContext extends it adding eager singleton init, i18n, event publishing, AOP integration, and annotation support. Use ApplicationContext in apps.
Why prefer constructor injection?
Dependencies are explicit and mandatory, fields can be final (immutable/thread-safe), the object is always fully initialized, circular dependencies are caught at startup, and unit testing needs no Spring (just new with mocks).
Circular dependency: A → B → A. With constructor injection Spring throws at startup. Fix by redesign, @Lazy, or setter injection (last resort).

14. Spring Boot Essentials Intermediate ↑ Contents

14.1 What Spring Boot adds

  • Auto-configuration — configures beans based on classpath + properties.
  • Starters — curated dependency bundles (spring-boot-starter-web, -data-jpa, -security).
  • Embedded server — Tomcat/Jetty/Undertow; run as a standalone fat JAR.
  • Opinionated defaults — sensible config you can override.
  • Actuator — production-ready metrics/health endpoints.

14.2 @SpringBootApplication

A meta-annotation combining three:

AnnotationPurpose
@ConfigurationMarks a config class (source of bean defs)
@EnableAutoConfigurationTriggers auto-config based on classpath
@ComponentScanScans the package & sub-packages for beans

14.3 How auto-configuration works

  • Auto-config classes are listed in META-INF/spring/...AutoConfiguration.imports (was spring.factories).
  • They are conditional: @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty, etc.
  • Example: if DataSource.class is on the classpath and you haven't defined one, Boot auto-creates it.
Debug: run with --debug or check /actuator/conditions to see the auto-configuration report (matched / not-matched conditions).

14.4 Configuration & profiles

  • application.properties / application.yml — externalized config.
  • Profiles: application-dev.yml, activated via spring.profiles.active=dev.
  • @ConfigurationProperties — type-safe binding of a property group to a POJO (preferred over scattered @Value).
  • Property precedence: command-line args > env vars > profile-specific > application.properties > defaults.
@ConfigurationProperties(prefix = "app.mail")
public record MailProps(String host, int port, boolean tls) {}
How does an embedded server work and how is the app packaged?
The starter pulls in Tomcat as a library; Boot starts it programmatically in main(). The app builds a self-contained "fat JAR" (with a nested-jar layout and JarLauncher) runnable via java -jar.
@ConditionalOnMissingBean — why is it key to auto-config?
It lets Boot back off when you define your own bean. Your explicit bean wins; the auto-configured default only applies when you haven't provided one — giving override-friendly defaults.

15. Aspect-Oriented Programming (AOP) Advanced ↑ Contents

AOP modularizes cross-cutting concerns (logging, security, transactions, metrics) that span many classes, keeping them out of business logic.

15.1 Terminology

TermMeaning
AspectModule of cross-cutting concern (@Aspect class)
Join pointA point in execution (in Spring: method execution)
PointcutExpression selecting join points
AdviceAction at a join point
WeavingLinking aspects to target objects (Spring: runtime via proxies)

15.2 Advice types

  • @Before, @After (finally), @AfterReturning, @AfterThrowing, @Around (most powerful — wraps the call).
@Aspect @Component
public class LoggingAspect {
    @Around("execution(* com.app.service..*(..))")
    public Object logTime(ProceedingJoinPoint pjp) throws Throwable {
        long t = System.nanoTime();
        try { return pjp.proceed(); }
        finally { log.info("{} took {}ns", pjp.getSignature(), System.nanoTime()-t); }
    }
}

15.3 How Spring AOP works (proxies)

  • Spring creates a proxy around the bean: JDK dynamic proxy if it implements an interface, else CGLIB subclass proxy.
  • Advice runs in the proxy, then it delegates to the real method.
Self-invocation pitfall: Calling one @Transactional/advised method from another method in the same class bypasses the proxy — the advice does NOT run. Call via the injected bean reference or refactor to another bean.

16.5 Best practices

  • Version your API (/api/v1), use plural nouns, nest sub-resources.
  • Return DTOs, never entities (decouples API from DB; avoids lazy-loading leaks).
  • Paginate large lists; use proper status codes; document with OpenAPI/Swagger.
  • Make writes idempotent where possible (idempotency keys for POST).
@Controller vs @RestController: @RestController = @Controller + @ResponseBody on every method, so return values are serialized straight to the response body (JSON).

16.6 Idempotent APIs — the two-layer pattern Critical

Networks retry. A client whose POST /payments times out will resend it — and without protection you charge the card twice. An operation is idempotent when repeating it has the same effect as doing it once. GET/PUT/DELETE are naturally idempotent; POST ("create", "charge", "send") is not, so you engineer it.

The robust production pattern uses two layers: a fast in-memory guard to short-circuit the common duplicate, backed by a durable database constraint that cannot be bypassed even under a race.

LayerMechanismRoleWeakness alone
1 — fast pathRedis SETNX key + TTLAbsorbs the vast majority of retries without touching the DB; cheap and O(1)Race: two simultaneous retries can both miss; Redis can evict/restart
2 — backstopDB UNIQUE constraint on the idempotency keyAuthoritative — the database physically cannot insert the same key twiceA DB hit per request would be slower without Layer 1 in front
// Client sends a stable "Idempotency-Key" header per logical operation (a UUID).
@PostMapping("/payments")
public ResponseEntity<PaymentResult> pay(
        @RequestHeader("Idempotency-Key") String key,
        @Valid @RequestBody ChargeRequest req) {

    // ---- Layer 1: Redis fast path (SETNX + TTL) ----
    // setIfAbsent returns false if the key already exists -> a duplicate in flight/recent.
    Boolean fresh = redis.opsForValue()
            .setIfAbsent("idem:" + key, "IN_PROGRESS", Duration.ofMinutes(10));
    if (Boolean.FALSE.equals(fresh)) {
        PaymentResult cached = store.findResult(key);           // return prior result if done
        return cached != null ? ResponseEntity.ok(cached)
                              : ResponseEntity.status(HttpStatus.CONFLICT).build(); // still running
    }

    try {
        // ---- Layer 2: durable unique-constraint backstop ----
        // idempotency_keys(key VARCHAR PRIMARY KEY, ...) in the SAME transaction as the effect.
        PaymentResult result = paymentService.chargeOnce(key, req); // throws on duplicate key
        redis.opsForValue().set("idem:" + key, "DONE", Duration.ofHours(24));
        return ResponseEntity.ok(result);

    } catch (DuplicateKeyException dup) {
        // A concurrent request won the race and already inserted the key -> return its result.
        return ResponseEntity.ok(store.findResult(key));
    }
}
@Transactional
public PaymentResult chargeOnce(String key, ChargeRequest req) {
    // Insert the key and perform the side effect atomically in one DB transaction.
    idempotencyRepo.insert(new IdempotencyKey(key));   // UNIQUE violation => DuplicateKeyException
    PaymentResult result = gateway.charge(req);        // real side effect
    resultStore.save(key, result);
    return result;                                     // commit persists key + result together
}
Why both layers? Redis makes the happy path fast and keeps duplicate load off the DB; the unique constraint is the only thing that actually guarantees exactly-once effects when Redis misses, evicts, or two retries race. Pass the same key through to the payment provider (e.g. Stripe's Idempotency-Key) so it is idempotent end-to-end too.
Your payment endpoint is called twice due to a client retry — how do you avoid double-charging?
Require a client-supplied idempotency key. Check Redis with SETNX + TTL to short-circuit fast (Layer 1); on a miss, insert the key against a DB unique constraint inside the same transaction as the charge (Layer 2). If the insert throws a duplicate-key error, a concurrent request already handled it — return the stored result. The unique constraint is the real guarantee; Redis is the optimization.

18. Exception Handling in Spring Intermediate ↑ Contents

Centralize error handling with @RestControllerAdvice + @ExceptionHandler for consistent error responses.

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ApiError notFound(ResourceNotFoundException ex){
        return new ApiError(404, ex.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ApiError invalid(MethodArgumentNotValidException ex){
        var msgs = ex.getBindingResult().getFieldErrors().stream()
            .map(e -> e.getField()+": "+e.getDefaultMessage()).toList();
        return new ApiError(400, "Validation failed", msgs);
    }
}
MechanismScope
@ExceptionHandlerSingle controller
@RestControllerAdviceGlobal, all controllers
ResponseStatusExceptionThrow with status inline
ErrorController / ProblemDetailFallback / RFC 7807 responses (Boot 3)
Best practice: return a consistent error schema (timestamp, status, code, message, path, fieldErrors). Use RFC 7807 ProblemDetail in Spring Boot 3. Never leak stack traces to clients.

19.4 The N+1 query problem Critical

Loading N parents then one query per parent for its children = N+1 queries. Fix with a JOIN FETCH, an @EntityGraph, or batch fetching (@BatchSize).

@Query("select o from Order o join fetch o.items where o.id = :id")
Optional<Order> findWithItems(@Param("id") Long id);

19.5 Lazy vs Eager & LazyInitializationException

  • LAZY — load on first access (proxy). Accessing it after the session/transaction closes throws LazyInitializationException.
  • Fix: fetch within the transaction, use a fetch join, map to a DTO inside the service, or an @EntityGraph — not "open session in view" (an anti-pattern).

19.6 Persistence context & entity states

StateMeaning
TransientNew, not associated with persistence context
Managed / PersistentTracked; changes auto-flushed (dirty checking)
DetachedWas managed, session closed
RemovedScheduled for deletion
  • First-level cache = the persistence context (per transaction; always on).
  • Dirty checking — Hibernate auto-detects changes to managed entities and issues UPDATEs at flush.
  • Second-level cache (optional, e.g. Ehcache) = shared across sessions.
save() vs saveAndFlush(); when does the INSERT happen?
save() registers the entity; the SQL may be deferred until flush (transaction commit or query trigger). saveAndFlush() flushes immediately, so the SQL runs at once.
FetchType.LAZY default but eager queries still run — why?
Likely the N+1 problem or accidental access of lazy associations during serialization. Map to DTOs and fetch exactly what you need with join fetch / entity graphs.
Pitfalls: serializing entities directly (triggers lazy loads / N+1); CascadeType.ALL + REMOVE deleting too much; bidirectional toString/equals causing infinite loops; using GenerationType.AUTO blindly (can pick a slow strategy on some DBs).
🐛 Production Gotchas — JPA / Hibernate. The classics: (1) N+1 in a serialized response — the endpoint looked fine in tests but fired hundreds of queries in prod because Jackson walked a lazy collection; (2) OSIV (Open-Session-In-View) masking the problem in dev then blowing up connection-pool time in prod; (3) save() in a loop without batch inserts (hibernate.jdbc.batch_size); (4) @Transactional on a read that keeps a DB connection open across a slow external call. 20. Transactions Advanced ↑ Contents

20.1 @Transactional & ACID

@Transactional declaratively wraps a method in a DB transaction (begin / commit / rollback) via an AOP proxy. Transactions guarantee ACID: Atomicity, Consistency, Isolation, Durability.

20.2 Propagation

PropagationBehaviour
REQUIRED (default)Join existing tx, or create new
REQUIRES_NEWAlways new tx; suspend current
SUPPORTSJoin if exists, else non-transactional
MANDATORYMust run within an existing tx (else error)
NESTEDNested tx with savepoint
NEVER / NOT_SUPPORTEDRun non-transactionally

20.3 Isolation levels

LevelPrevents
READ_UNCOMMITTEDnothing (dirty reads possible)
READ_COMMITTEDdirty reads
REPEATABLE_READdirty + non-repeatable reads
SERIALIZABLEall (incl. phantom reads); slowest
AnomalyWhat
Dirty readRead uncommitted data
Non-repeatable readSame row differs within a tx
Phantom readNew rows appear matching a re-run query

20.4 Rollback rules

Default: Spring rolls back on unchecked (RuntimeException) & Errors only — NOT on checked exceptions. Override with @Transactional(rollbackFor = Exception.class).
Self-invocation: like all AOP, calling a @Transactional method from another method in the same bean bypasses the proxy — no transaction. Also: @Transactional only works on public methods (proxy limitation).

20.5 Optimistic vs Pessimistic Locking Critical

When two transactions update the same row concurrently, one must not silently clobber the other (the lost update problem). JPA offers two strategies.

Optimistic lockingPessimistic locking
AssumptionConflicts are rareConflicts are likely
MechanismA version column checked at commit (no DB lock held)DB row lock held for the transaction (SELECT ... FOR UPDATE)
On conflictOptimisticLockException → caller retriesSecond txn blocks until the first commits/rolls back
ConcurrencyHigh (no blocking)Lower (serialized on the row)
RiskWasted work on retry under high contentionDeadlocks & reduced throughput; lock timeouts
Best forRead-heavy, low-contention (most web apps)Hot rows, financial ledgers, short critical sections

Optimistic: @Version

Add a version field; Hibernate appends WHERE version = ? to every UPDATE and increments it. If zero rows match (someone else already bumped the version), it throws OptimisticLockException (Spring wraps it as ObjectOptimisticLockingFailureException).

@Entity
public class Account {
    @Id Long id;
    @Version Long version;      // managed by Hibernate; never set it manually
    BigDecimal balance;
}
// Generated on update:
// UPDATE account SET balance=?, version=version+1 WHERE id=? AND version=?
//   -> 0 rows updated => OptimisticLockException (someone changed it first)

Handling the exception with a retry strategy

Optimistic conflicts are expected, not exceptional — the correct response is usually to reload and retry a bounded number of times, then surface a 409 Conflict if it keeps failing.

// Option A: Spring Retry, declaratively
@Retryable(retryFor = ObjectOptimisticLockingFailureException.class,
           maxAttempts = 3, backoff = @Backoff(delay = 50, multiplier = 2))
@Transactional
public void withdraw(Long accountId, BigDecimal amount) {
    Account acc = accountRepo.findById(accountId).orElseThrow();
    acc.setBalance(acc.getBalance().subtract(amount));   // version checked at commit
}

@Recover  // called when all retries are exhausted
public void recover(ObjectOptimisticLockingFailureException ex, Long accountId, BigDecimal amount) {
    throw new ConflictException("Account " + accountId + " is busy, please retry");
}
// Option B: pessimistic lock when contention is genuinely high
public interface AccountRepository extends JpaRepository<Account, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)   // SELECT ... FOR UPDATE
    @Query("select a from Account a where a.id = :id")
    Optional<Account> findByIdForUpdate(@Param("id") Long id);
}
Rule of thumb: default to optimistic (@Version) — it scales and avoids held locks. Reach for pessimistic only for genuinely hot rows or when a retry storm would be worse than blocking. Each retry must run in a fresh transaction with a fresh entity read, or you'll just re-throw on the same stale version.

20.6 @TransactionalEventListener phases

A plain @EventListener runs synchronously inside the publisher's transaction — so if you publish an "order placed" event and a listener sends an email or enqueues a Kafka message, that side effect fires before the transaction commits. If the transaction then rolls back, you've emailed the customer about an order that doesn't exist. @TransactionalEventListener binds the listener to a transaction phase instead.

PhaseFiresTypical use
BEFORE_COMMITJust before commit (still in the tx)Last-chance validation / extra writes that must be part of the same commit
AFTER_COMMIT (default)Only after a successful commitAsync side effects: publish to Kafka, send email/SMS, invalidate cache, call another service
AFTER_ROLLBACKAfter the tx rolls backCompensation, failure metrics, alerting
AFTER_COMPLETIONAfter commit or rollbackCleanup that must run either way (release resources)
@Service
public class OrderService {
    @Transactional
    public void placeOrder(Order order) {
        orderRepo.save(order);
        events.publishEvent(new OrderPlacedEvent(order.getId())); // published, not yet delivered
    }
}

@Component
public class OrderEventListener {
    // Fires ONLY if the order transaction actually committed -> safe to trigger external effects.
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onCommitted(OrderPlacedEvent e) {
        kafkaTemplate.send("orders", e.orderId());   // no phantom messages on rollback
        mailService.sendConfirmation(e.orderId());
    }
}
Why AFTER_COMMIT matters: it is the clean fix for the dual-write problem in its simplest form — you never publish an event for data that didn't persist. For at-least-once guarantees against a broker outage, combine it with the outbox pattern (write the event to an outbox table in the same transaction, relay it separately). Note: work started in AFTER_COMMIT runs outside the original transaction — if you need to write to the DB there, open a new one (and prefer @Async so you don't block the caller).
When use REQUIRES_NEW?
When an inner operation must commit independently regardless of the outer transaction — e.g. audit logging that should persist even if the main business transaction rolls back.
🐛 Production Gotchas — Transactions. Frequent offenders: (1) @Transactional silently not applied — self-invocation, a non-public method, or a missing proxy; (2) a checked exception that didn't roll back because you forgot rollbackFor; (3) a long transaction spanning an external HTTP call, holding a DB connection and causing pool exhaustion; (4) publishing a Kafka message inside the tx (should be AFTER_COMMIT); (5) REQUIRES_NEW deadlocking against its own parent transaction on the same row. 21.2 Architecture

Security is a chain of servlet filters. Key pieces:

  • SecurityFilterChain — ordered filters intercepting every request.
  • AuthenticationManager → AuthenticationProvider — validate credentials.
  • UserDetailsService — load user + roles.
  • PasswordEncoder — BCryptPasswordEncoder (never store plaintext).
  • SecurityContextHolder — holds the authenticated principal (ThreadLocal).
@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http.csrf(c -> c.disable())                       // stateless API
        .authorizeHttpRequests(a -> a
            .requestMatchers("/api/public/**").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
    return http.build();
}

22. WebSockets with Spring Advanced New ↑ Contents

HTTP is request/response; WebSockets upgrade a single TCP connection to full-duplex, letting the server push to the client without polling — the backbone of chat, live dashboards, notifications, and collaborative editing.

22.1 Raw WebSocket vs STOMP / SockJS

Raw WebSocketSTOMP over WebSocket
LevelLow-level byte/text framesMessaging sub-protocol (frames, destinations, subscriptions)
RoutingYou parse messages & route manuallyDestination-based (/topic, /queue, /app) with a message broker
Pub/SubDIYBuilt in (subscribe to destinations)
FallbackNoneSockJS falls back to HTTP streaming/long-polling when WS is blocked
Use whenSimple, custom binary protocolApp messaging, broadcast, per-user queues (the common choice)
STOMP (Simple Text-Oriented Messaging Protocol) gives you a message broker model on top of WebSocket: clients subscribe to destinations and the server publishes to them — far less plumbing than raw frames. SockJS is the graceful-degradation layer for networks/proxies that block WebSockets.

22.2 Configuration & a STOMP endpoint

@Configuration
@EnableWebSocketMessageBroker
public class WsConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws")          // handshake URL
                .setAllowedOriginPatterns("*")
                .withSockJS();               // enable SockJS fallback
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.setApplicationDestinationPrefixes("/app"); // client -> @MessageMapping
        registry.enableSimpleBroker("/topic", "/queue");    // in-memory broker (dev)
        registry.setUserDestinationPrefix("/user");         // per-user messaging
    }
}

22.3 Handling & broadcasting messages

@Controller
public class ChatController {

    // Client SENDs to /app/chat.send ; return value is broadcast to /topic/room
    @MessageMapping("/chat.send")
    @SendTo("/topic/room")
    public ChatMessage handle(ChatMessage in) {
        return new ChatMessage(in.user(), in.text(), Instant.now());
    }

    // Push to a single user's private queue (/user/{name}/queue/notifications)
    private final SimpMessagingTemplate template;
    public ChatController(SimpMessagingTemplate template){ this.template = template; }

    public void notifyUser(String username, Notification n) {
        template.convertAndSendToUser(username, "/queue/notifications", n);
    }

    // Broadcast from anywhere (e.g. a scheduled job) to all subscribers
    public void broadcast(PriceTick tick) {
        template.convertAndSend("/topic/prices", tick);
    }
}

22.4 Scaling across instances Critical

The enableSimpleBroker in-memory broker keeps subscriptions in the JVM heap — fine for one node, broken across many. If User A is connected to instance 1 and User B to instance 2, a message broadcast on instance 1 never reaches B.

  • External STOMP broker relay — point Spring at RabbitMQ or ActiveMQ (enableStompBrokerRelay("/topic","/queue")). All instances share the broker, so subscriptions and broadcasts span the cluster.
  • Redis pub/sub relay — a lighter option: publish messages to Redis and have every instance fan them out to its local WebSocket sessions.
  • Sticky sessions at the load balancer keep a client pinned to the instance holding its socket; combine with a shared broker for cross-instance delivery.
  • WebSockets are stateful connections — plan for connection limits per node, graceful drain on deploy, and reconnection/heartbeat (STOMP heartbeats) on the client.
// Cluster-ready: replace the simple broker with an external relay
@Override
public void configureMessageBroker(MessageBrokerRegistry registry) {
    registry.setApplicationDestinationPrefixes("/app");
    registry.enableStompBrokerRelay("/topic", "/queue")
            .setRelayHost("rabbitmq").setRelayPort(61613)
            .setClientLogin("guest").setClientPasscode("guest");
}
Why choose STOMP+SockJS over a raw WebSocket?
STOMP gives you a destination-based pub/sub model (subscribe to /topic/..., send to /app/..., per-user /user/queue/...) and integrates with a message broker — so you write almost no routing code. SockJS adds automatic fallback to HTTP streaming/long-polling when proxies or firewalls block WebSockets, improving reach. Use raw WebSocket only for a simple, custom protocol.
How do WebSockets scale beyond one server?
The default in-memory simple broker is per-JVM. Use an external broker relay (RabbitMQ/ActiveMQ) or a Redis pub/sub relay so all instances share subscriptions, and enable sticky sessions so each client stays on the node holding its socket. Broadcasts then reach subscribers on every instance.

23. gRPC with Spring Boot Advanced New ↑ Contents

gRPC is a high-performance RPC framework using Protocol Buffers (protobuf) for a compact binary contract and HTTP/2 for multiplexed, streaming transport. It shines for low-latency, strongly-typed internal service-to-service communication.

23.1 The protobuf contract

You define the service and messages once in a .proto file; the protobuf compiler generates strongly-typed stubs for every language. The contract is the single source of truth.

syntax = "proto3";
package inventory;
option java_package = "com.app.grpc";

service InventoryService {
  rpc GetStock (StockRequest) returns (StockReply);              // unary
  rpc WatchStock (StockRequest) returns (stream StockReply);      // server streaming
}

message StockRequest { string sku = 1; }
message StockReply   { string sku = 1; int32 quantity = 2; }

23.2 grpc-spring-boot-starter

The community grpc-spring-boot-starter auto-configures an embedded gRPC server, registers @GrpcService beans, and lets you inject stubs as clients — so gRPC feels like ordinary Spring.

// Server: implement the generated base class, expose it as a Spring bean
@GrpcService
public class InventoryGrpcService extends InventoryServiceGrpc.InventoryServiceImplBase {

    @Override
    public void getStock(StockRequest req, StreamObserver<StockReply> obs) {
        StockReply reply = StockReply.newBuilder()
            .setSku(req.getSku())
            .setQuantity(lookup(req.getSku()))
            .build();
        obs.onNext(reply);   // send the single response
        obs.onCompleted();   // close the call
    }
}
// Client: inject a generated blocking stub and call it like a local method
@Service
public class StockClient {
    @GrpcClient("inventory")
    private InventoryServiceGrpc.InventoryServiceBlockingStub stub;

    public int stock(String sku) {
        return stub.getStock(StockRequest.newBuilder().setSku(sku).build())
                   .getQuantity();
    }
}

Server streaming1 request → stream of responsesLive feeds, large result sets, progress updates
Client streamingStream of requests → 1 responseUploads, batching, telemetry ingestion
BidirectionalBoth stream independentlyChat, real-time sync, long-lived sessions

23.4 gRPC vs REST

gRPCREST / JSON
PayloadProtobuf (binary, small, fast)JSON (text, human-readable)
TransportHTTP/2 (multiplexed, streaming)Usually HTTP/1.1
ContractStrict .proto (codegen, versioned)OpenAPI (looser, optional)
StreamingFirst-class (4 modes)Awkward (SSE/chunked)
Browser supportNeeds gRPC-Web proxyNative
Best forInternal microservice calls, low latency, polyglotPublic APIs, browser clients, caching, simplicity
Rule of thumb: gRPC for east-west (service-to-service) traffic where latency and strong contracts matter; REST for north-south (public/browser-facing) APIs where readability, caching, and ubiquity win. Many systems use both — REST at the edge, gRPC between services.
When would you pick gRPC over REST?
For internal, high-throughput, low-latency service-to-service calls with a strict versioned contract and/or streaming needs. Protobuf over HTTP/2 is smaller and faster than JSON, codegen keeps client/server in lock-step, and streaming is first-class. Keep REST for public and browser-facing APIs where human-readability, caching, and native browser support matter.

24.3 Resilience patterns with Resilience4j

Resilience4j is a lightweight, composable fault-tolerance library. The four core decorators each guard a different failure mode — and they compose.

PatternGuards againstKey config
Circuit BreakerCascading failure from a sick dependencyfailure-rate-threshold, wait-duration, sliding window (CLOSED → OPEN → HALF-OPEN)
RetryTransient blips (only for idempotent ops)max-attempts, exponential backoff + jitter
BulkheadOne slow dependency exhausting all threadsmax-concurrent-calls (isolate resource pools)
TimeLimiterSlow calls hanging indefinitelytimeout-duration; cancels the running future
Rate LimiterOverloading a dependency / self-throttlinglimit-for-period, refresh-period

Composed example (TimeLimiter + CircuitBreaker + Retry + Bulkhead)

TimeLimiter works on a CompletableFuture, so the method returns one. Order matters: Retry wraps CircuitBreaker wraps TimeLimiter wraps Bulkhead wraps the call — a timed-out or failed call trips the breaker and can be retried.

@Service
public class InventoryClient {

    @TimeLimiter(name = "inventory")                          // cancel if too slow
    @CircuitBreaker(name = "inventory", fallbackMethod = "fallback")
    @Retry(name = "inventory")                                // retry transient failures
    @Bulkhead(name = "inventory", type = Bulkhead.Type.SEMAPHORE)
    public CompletableFuture<Stock> check(String sku) {
        return CompletableFuture.supplyAsync(() -> client.getStock(sku));
    }

    // Fallback signature: original args + the Throwable; must return the same type.
    private CompletableFuture<Stock> fallback(String sku, Throwable t) {
        return CompletableFuture.completedFuture(Stock.unknown(sku));
    }
}
# application.yml
resilience4j:
  timelimiter:
    instances:
      inventory:
        timeout-duration: 2s
        cancel-running-future: true
  circuitbreaker:
    instances:
      inventory:
        sliding-window-size: 20
        failure-rate-threshold: 50        # open when >=50% of last 20 calls fail
        wait-duration-in-open-state: 10s
        permitted-number-of-calls-in-half-open-state: 3
  retry:
    instances:
      inventory:
        max-attempts: 3
        wait-duration: 200ms
        enable-exponential-backoff: true
  bulkhead:
    instances:
      inventory:
        max-concurrent-calls: 25
TimeLimiter vs a plain timeout: a bare future.get(2, SECONDS) throws on the caller but leaves the underlying work running. The Resilience4j TimeLimiter can cancel the running future, freeing the thread — and because it emits a failure, that timeout counts toward the circuit breaker's failure rate. Only retry idempotent operations, and add jitter so retries don't synchronize into a thundering herd.

24.4 Distributed data patterns

  • Saga — manage distributed transactions via a sequence of local transactions + compensating actions (choreography or orchestration).
  • CQRS — separate read & write models.
  • Event Sourcing — store state as a log of events.
  • Outbox pattern — reliably publish events with DB writes (avoids dual-write problem).
  • API Composition / BFF — aggregate data for clients.

24.5 The CAP theorem

A distributed store can guarantee only two of Consistency, Availability, Partition tolerance. Since partitions are unavoidable, you choose CP or AP. Many microservice systems favour AP + eventual consistency.

Distributed pitfalls (fallacies): network is reliable, latency is zero, bandwidth is infinite, topology never changes. Design for failure, timeouts, idempotency, and eventual consistency.
How do services find each other?
Via a service registry (Eureka/Consul) or platform DNS (Kubernetes). The client (or a load balancer/gateway) resolves a logical service name to one of the healthy instances.

25. Caching Intermediate ↑ Contents

Caching stores expensive results to cut latency & load. Spring's cache abstraction is provider-agnostic.

@EnableCaching
@Service
public class ProductService {
    @Cacheable(value="products", key="#id")
    public Product get(Long id){ /* slow DB call */ }

    @CachePut(value="products", key="#p.id")     // update cache
    public Product save(Product p){ ... }

    @CacheEvict(value="products", key="#id")      // remove on delete
    public void delete(Long id){ ... }
}
AnnotationEffect
@CacheableReturn cached value if present, else compute & store
@CachePutAlways execute & update cache
@CacheEvictRemove entry (or allEntries=true)

Strategies & concerns

PatternHow
Cache-asideApp checks cache, loads DB on miss (most common)
Read-through / Write-throughCache layer handles DB sync
Write-behindAsync write to DB
Cache problems: stampede (many misses at once → lock/early refresh), penetration (queries for nonexistent keys → cache nulls), avalanche (mass simultaneous expiry → jittered TTLs). Always set TTLs & an eviction policy (LRU/LFU).
Redis is the typical distributed cache for Spring (also used for sessions, rate limiting, locks, leaderboards). Local cache: Caffeine.

26.3 Kafka core concepts

  • Topic → split into partitions (unit of parallelism & ordering).
  • Producer writes; consumer groups read — each partition consumed by one consumer in a group.
  • Offset — consumer's position; commit it to track progress.
  • Replication factor — copies of a partition for fault tolerance.
@KafkaListener(topics = "orders", groupId = "billing")
public void consume(OrderEvent event){ billingService.process(event); }

kafkaTemplate.send("orders", order.getId(), event);  // key -> same partition

26.4 Delivery semantics & reliability

GuaranteeMeaning
At-most-onceMay lose, never duplicate
At-least-onceNever lose, may duplicate (most common)
Exactly-onceNo loss, no dup (Kafka transactions/idempotent producer)
Make consumers idempotent (dedup by event ID) since at-least-once delivery can replay messages. Use a dead-letter queue/topic (DLQ) for poison messages, and the outbox pattern to avoid the dual-write problem.
🐛 Production Gotchas — Kafka. Recurring pain: (1) consumer lag creeping up because processing is slower than production — scale partitions/consumers or speed up the handler; (2) rebalancing storms when max.poll.interval.ms is exceeded by slow processing, kicking consumers out of the group; (3) duplicate side effects from at-least-once redelivery with a non-idempotent consumer; (4) ordering broken by using the wrong (or null) partition key; (5) poison messages retried forever with no DLQ. 30. Common Interview Scenarios Advanced ↑ Contents

30.1 System / API design

Design a URL shortener / rate limiter / notification service.
Talk through: requirements → API contract → data model → ID generation (base62, Snowflake) → storage (SQL vs NoSQL) → caching (Redis) → scaling (sharding, replication) → rate limiting (token bucket) → bottlenecks & trade-offs. Always state assumptions and capacity estimates.
How would you make an endpoint idempotent?
Accept an Idempotency-Key header, store its result keyed by that ID, and on retry return the stored response instead of reprocessing. Use unique DB constraints to prevent duplicate side effects. See the two-layer pattern (Redis SETNX + DB unique constraint) in section 16.6.

30.2 Performance & debugging

An API is slow in production — how do you diagnose it?
Check metrics/traces (Actuator, APM) to localize: DB (slow queries, N+1, missing index), external calls (timeouts), GC pauses (heap), thread pool exhaustion, locks. Reproduce, profile (async-profiler), fix the actual bottleneck, add caching/pagination where appropriate.
App throws OutOfMemoryError — steps?
Enable -XX:+HeapDumpOnOutOfMemoryError, analyze the dump (Eclipse MAT) for dominator/retained sets, find the leak (unbounded cache/collection, ThreadLocal, listener). Fix the leak or right-size the heap.

30.3 Concurrency scenarios

Two users update the same record simultaneously — how do you handle it?
Optimistic locking (JPA @Version) — the second commit fails with OptimisticLockException, prompting retry; good for low contention. Pessimistic locking (SELECT ... FOR UPDATE) — lock the row up front; good for high contention but reduces concurrency. See section 20.5 for the full comparison and retry strategy.
Implement a thread-safe singleton cache that loads lazily.
Use the initialization-on-demand holder idiom, or a ConcurrentHashMap with computeIfAbsent for per-key lazy loading without locking the whole map.
