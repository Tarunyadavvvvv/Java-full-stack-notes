01 Foundations

Core Concepts & the Commit Log

Kafka isn't a message queue that happens to be fast, and it isn't a database that happens to stream — it's a distributed, append-only, replicated commit log, and almost every one of its odd-looking design decisions falls out of taking that one sentence seriously.

9 min read Start here

Picture a notebook that you're only ever allowed to add to — never erase, never edit a line once it's written. Now copy that same notebook, page for page, onto two or three other machines the moment anything gets written, so a single lost or burned notebook doesn't lose the record. Finally, give every person who reads from it their own personal bookmark, so ten different readers can all be at completely different pages of the exact same notebook at once, each moving forward at their own pace. That's Kafka. The notebook is a partition — an ordered, append-only log — replicated across brokers for durability, with each consumer tracking its own offset (its bookmark) independently. It is explicitly not a traditional message queue, where a message is typically consumed once and then gone, and it is explicitly not a database, since it has no query language, no indexes on arbitrary fields, and no update-in-place — it only ever appends. Kafka occupies a third category: a durable, replayable, distributed commit log that a message queue and a database both happen to resemble from certain angles.

The problem Kafka actually solves

Before an event bus like Kafka enters the picture, a system with several data-producing services and several systems that want to react to that data tends to grow point-to-point integrations — every producer wiring a direct connection to every consumer that needs its data. That relationship grows quadratically: N producers times M consumers means N×M individual integrations to build, test, and keep working as either side changes. Kafka collapses that by sitting in the middle as a shared, durable buffer — producers only need to know about the topic they're writing to, and consumers only need to know about the topic they're reading from, dropping the integration count from N×M to N+M.

Before Kafka — N×M

  • Every producer maintains a direct connection to every consumer that needs its data
  • 3 producers × 4 consumers = 12 separate point-to-point integrations to build and maintain
  • Adding one new consumer means touching every existing producer
  • A producer going down can directly break every consumer wired to it

After Kafka — N+M

  • Producers write to a topic; consumers read from a topic — neither knows about the other
  • 3 producers + 4 consumers = 7 total integration points, each with just the topic
  • Adding a new consumer means subscribing it to the topic — zero changes to any producer
  • The topic buffers and persists the data, so a slow or offline consumer doesn't touch producers at all

Any number of independent consumer groups can attach to the same topic — each one gets its own full copy of the stream, at its own pace, without affecting any other group.

Queue and pub/sub — Kafka is both, depending on grouping

This is one of the most commonly confused points about Kafka, and it comes down to a single rule: whether two consumers are in the same consumer group or different ones.

Queue-style (same group)

  • Consumers sharing one group.id split a topic's partitions between them
  • Each record is delivered to exactly one consumer in that group
  • Adding consumers to the group spreads the work out further — classic worker-pool behavior

Pub/sub-style (different groups)

  • Each consumer group is tracked independently, with its own offsets
  • Every group gets a full, independent copy of every record on the topic
  • A billing group and an analytics group can both consume the same order-events topic in full, unaware of each other

Commit log storage internals

Each partition is physically just a directory on disk containing a sequence of immutable segment files. Only the newest segment — the "active" one — is ever being appended to; every older segment is closed and never touched again. That single design choice is what makes two things cheap: sequential writes (always appending to one open file) and bulk deletion (an entire old segment can be dropped as one filesystem operation once it's past its retention limit, rather than deleting records one at a time).

  • Partition directory (orders-0)an ordered sequence of segment files on disk
    • 00000000000000000000.logclosed segment — immutable, eligible for whole-segment deletion once past the retention limit
    • 00000000000000000000.indexmaps offsets to physical byte positions within the matching .log file
    • 00000000000000000000.timeindexmaps timestamps to offsets, for time-based lookups
    • 00000000000000170243.logthe current active segment — the only file anything is being appended to right now

A new segment is rolled over once log.segment.bytes (default 1GB) or log.segment.ms is reached — the old one closes for good and a fresh active segment opens.

The operational implication

Because so much of Kafka's read performance comes from the OS page cache rather than the JVM heap, the standard broker-tuning advice is almost the opposite of what you'd expect from a JVM application: leave the majority of a broker's RAM free for the operating system's page cache, and keep the JVM heap itself deliberately modest (commonly in the single-digit gigabytes). An oversized heap doesn't make Kafka faster — it just shrinks the page cache and invites longer GC pauses.

Is Kafka a message queue or a database?
Neither, exactly — and that's the point. It has queue-like properties (producers and consumers, at-least-once delivery, consumer groups that split work like workers off a queue) and database-like properties (durable storage on disk, replication, records that can be replayed long after they were written). But it has no query language, no arbitrary indexing, no update-in-place, and no transactions in the SQL sense. The cleanest description is the one this chapter opened with: a distributed, append-only, replicated commit log — a category of its own that a queue and a database both partially resemble.
Chapter summary
  • Kafka is a distributed, append-only, replicated commit log — not a traditional queue, not a database.
  • It collapses N×M point-to-point integrations between producers and consumers down to N+M.

  • Kafka's speed comes from sequential I/O, the OS page cache, zero-copy transfer, batching, and compression — which is why brokers are tuned to favor page cache over JVM heap.

02 Foundations

Partitioning Strategy & Ordering

A partition is Kafka's unit of parallelism and its unit of ordering, and those two jobs are in permanent tension — more partitions buys more parallel throughput, but ordering only ever holds within one partition, never across them.

8 min read

Think of a topic's partitions as lanes on a highway. Traffic within a single lane stays strictly in order — cars can't pass each other. But there's no ordering relationship between lanes at all; a car in lane 3 might arrive well before a car that entered lane 1 first. Splitting a topic into more partitions is exactly like adding more lanes: total throughput goes up because more cars can move in parallel, but you give up any guarantee about the relative order of cars in different lanes. Kafka never tries to hide this trade-off — it hands it to you directly through how records get assigned to partitions.

Keyed records for the same key (user-42) always land in the same partition — hash("user-42") % 4 resolves to partition 1 every time, so both of that user's events stay in order relative to each other.

Adding partitions later remaps every key

Because the formula is hash(key) % numPartitions, changing numPartitions changes the result of that formula for essentially every key — a key that used to land on partition 2 might now land on partition 5. Existing, already-written records don't move, but new records for that same key start landing somewhere else, breaking the "same key always in the same partition" guarantee that per-key ordering depends on. The fix isn't a fix at all — it's planning: decide on a partition count that will hold up for expected future scale before a topic goes into production, since growing it later is disruptive in a way that's easy to miss until it bites.

Choosing a partition count

More partitions mean more parallelism and higher aggregate throughput, but they aren't free: each one costs an open file handle and memory on every broker, and a broker failure takes longer to recover from when there are more partition leaders to re-elect. A practical rule of thumb is to divide a target total throughput by the throughput a single partition can sustain, and separately, to make sure the partition count is at least as large as the maximum number of consumers you ever expect to run in one consumer group at once.

Max useful consumers in a group = number of partitions

This is a frequently tested fact precisely because it's easy to get backwards: a consumer group can never usefully run more active consumers than the topic has partitions, because each partition is assigned to exactly one consumer within a group at a time. A 6th consumer added to a group reading a 6-partition topic simply sits idle — there's nothing left to hand it. If more consuming capacity is genuinely needed, the partition count itself has to grow (with all the remapping consequences above), not just the consumer count.

Ordering guarantees, precisely

Kafka guarantees ordering within a single partition, and only within a single partition — never across partitions, even within the same topic. Sending records with the same key to the same partition is what preserves order for events that need to stay in sequence relative to each other (a given order's created/updated/cancelled events, for instance). True global ordering across an entire topic is achievable, but only by using a single partition for that topic — which throws away every bit of the parallelism partitioning exists to provide. In practice, the design question is almost never "how do I get global ordering" but "what's the right key to partition on so that everything that needs to stay ordered relative to each other ends up on the same partition."

What can silently break ordering, even with a stable key:

  • Increasing the partition count remaps keys to different partitions going forward (covered above)
  • A producer retrying a failed batch while multiple requests are in flight at once can let a later batch land on disk before an earlier one — unless idempotence is enabled (covered fully in the next chapter)
If I need strict ordering across an entire topic, is a single partition really the only option?
Yes, if "strict ordering across every record on the topic, no exceptions" is a hard requirement — a single partition is the only way Kafka can offer that, since ordering is a partition-local property. In practice, almost no system actually needs global ordering; it needs ordering among a related subset of events (all events for one order, one user, one account). Picking a key that groups exactly those related events onto the same partition gets you the ordering that actually matters while still spreading unrelated work — different orders, different users — across many partitions in parallel.
Chapter summary
  • Partitions are the unit of both parallelism and ordering — ordered strictly within a partition, unordered across partitions.
  • Keyed records hash to a stable partition; keyless records use a sticky partitioner that batches then rotates.
  • Increasing partition count later remaps keys and breaks existing per-key ordering — plan partition count up front.
  • Partition count should be sized to target throughput and must be at least the maximum number of consumers ever expected in one group — extra consumers beyond the partition count simply idle.
  • Global ordering requires collapsing to a single partition, which eliminates parallelism — the real design lever is choosing the right partition key.

The modulus in the hashing formula depends directly on the partition count, so growing that count changes where a given key's future records get routed — old records stay put, but the ordering guarantee going forward is now split across two partitions instead of one.
03 Reliability & Delivery

Replication, ISR & Durability

Durability in Kafka isn't one setting — it's an interaction between how many copies of a partition exist, how many of those copies have to be caught up before they're trusted, and how many of those have to confirm a write before the producer hears "yes." Get the interaction right and Kafka survives real failures without losing a single record.

11 min read Detailed walkthrough

Every partition has a replication factor (RF) — the total number of copies of that partition's data spread across different brokers, commonly 3 in production. Exactly one of those copies is the leader: every single read and write for that partition goes through the leader, full stop. The rest are followers, continuously fetching new records from the leader to replicate them. If the leader broker dies, one of the followers is promoted to take its place. It helps to think of it like a photocopier chain: one master original (the leader) that everything is written onto first, with photocopies (the followers) being made continuously so that if the original is destroyed, a copy is ready to become the new original.

Producerwrites only ever go here first
B1 — Leaderall reads & writes for this partition
B2 & B3 — Followerscontinuously fetch & replicate

Replication factor 3 for partition orders-0 — one leader, two followers, all three physically holding a copy of the data.

In-Sync Replicas (ISR)

Not every follower is automatically trusted at every moment — a follower that's fallen behind (network blip, GC pause, a slow disk) is still a replica, but it isn't necessarily caught up. The ISR (in-sync replicas) is the subset of replicas that are confirmed caught up within replica.lag.time.max.ms. This distinction matters enormously for acks=all: that setting requires acknowledgment from every member of the ISR specifically — not literally every replica that happens to exist. A replica that's lagging behind isn't waited on; it's excluded from the ISR until it catches back up.

min.insync.replicas is the other half of the equation: it's the minimum ISR size required for a write to succeed at all. If the ISR ever shrinks below that number, an acks=all producer doesn't get a slow write — it gets a hard, immediate error. Kafka would rather refuse a write outright than accept it with too few confirmed copies backing it up. This is a deliberate fail-closed design: silently accepting a write with insufficient durability, only to lose it later in a failure, is judged worse than rejecting it up front.

Then the situation gets worse: Broker1 — the leader itself — also dies. Kafka runs a clean leader election (covered next) from the remaining ISR, and B2 is promoted to the new leader. Record R survives this without any loss whatsoever, because it was guaranteed to exist on every member of the ISR at the moment it committed — and B2 was one of those members. But now look at what the ISR has become: it's just {B2}, size 1. That's below min.insync.replicas=2. So while every previously committed record (including R) is intact and readable, new acks=all writes are now rejected outright with a NotEnoughReplicas error, and they'll keep being rejected until at least one more replica catches back up and rejoins the ISR.

The overall shape of this story is the whole point of the durability formula: RF=3 + min.insync.replicas=2 + acks=all tolerates exactly one broker failure with zero data loss and zero availability impact. A second, overlapping failure doesn't lose anything that was already committed — that's still guaranteed — but it does pause new writes rather than risk accepting them with too thin a safety margin. Kafka would rather stop taking writes for a while than quietly accept ones it can't actually back up.

Clean vs. unclean leader election

Clean election picks the new leader only from the current ISR — guaranteed no data loss, but if the entire ISR is unreachable, the partition simply becomes unavailable until one comes back. Unclean election allows promoting any replica, even one that's badly out of sync — it keeps the partition available, but at the risk of silently losing any records the promoted replica never caught up on. unclean.leader.election.enable defaults to false — Kafka ships favoring correctness over availability here, on the reasoning that surprising data loss is usually worse than a temporary outage.

The high watermark

The high watermark (HW) is the highest offset that has been replicated to every member of the ISR. Consumers are only ever allowed to read up to the high watermark — never past it, even if the leader itself has already physically written records beyond that point. This is what guarantees a consumer can never read a record that might vanish later: if a record hasn't been confirmed by the full ISR yet, and the leader that holds it dies before it's replicated, that record can disappear during the resulting leader election. Capping consumer reads at the high watermark means a consumer is only ever shown data that's already safely durable everywhere it needs to be.

Why does acks=all only wait on the ISR instead of literally every replica?
Because waiting on literally every replica would mean a single slow or dead follower — even one that's temporarily unreachable for a completely mundane reason — could block every future write indefinitely. The ISR mechanism separates "replicas that exist" from "replicas that are currently trustworthy and caught up," and acks=all only depends on the latter. A follower drops out of the ISR (and stops being waited on) the moment it falls behind by more than replica.lag.time.max.ms, and rejoins automatically once it catches back up — this is what lets Kafka keep accepting durable writes through ordinary transient follower slowness, rather than treating every replica hiccup as a full outage.

"At-least-once," "exactly-once," and "idempotent" get used loosely enough in casual conversation that it's worth being exact: each solves a specific, narrow problem, and none of them alone is the whole story of not losing or duplicating data.

The idempotent producer

When a producer's request times out or the connection drops, the producer's natural response is to retry — but a retry is dangerous if the original write actually succeeded and only the acknowledgment got lost in transit; that retry would duplicate the record. The idempotent producer (enable.idempotence=true, on by default in modern Kafka) closes this gap: each producer instance is assigned a unique Producer ID (PID), and every record it sends carries a per-partition, strictly increasing sequence number. The broker tracks the last sequence number it accepted for each (PID, partition) pair, and if a retried batch arrives with a sequence number it's already seen, the broker recognizes it as a duplicate and discards it rather than appending it again — giving exactly-once-per-partition writes without sacrificing ordering, and without the application doing anything differently.

Worked example: retries under multiple in-flight requests

This is one of the sharpest illustrations of why idempotence matters even when a producer isn't obviously duplicating anything. Suppose max.in.flight.requests.per.connection=5, meaning up to five batches can be outstanding to the broker at once before waiting for acknowledgments — good for throughput, but it opens a window where ordering can silently flip.

Without idempotence — order can flip

  • Batch B1 is sent, intended for offsets 100-102
  • Batch B2 is sent concurrently (5 requests can be in flight at once), intended for the following offsets, 103-105
  • B1 hits a transient network failure and has to be retried
  • B2, unaffected, reaches the broker successfully and is written first
  • B1's retry then succeeds and is appended after B2
  • Result: on-disk order becomes [B2][B1] — the batch meant to come second is now first

With idempotence — order is enforced

  • Every batch carries the producer's PID plus a strictly increasing per-partition sequence number
  • The broker only accepts the next expected sequence number for that PID+partition — nothing else
  • If B2 (a later sequence) arrives before B1 (an earlier sequence), the broker rejects B2's out-of-order arrival
  • B1's retry is accepted first, then B2's sequence becomes valid and is accepted
  • Result: on-disk order stays [B1][B2], correctly ordered, even with 5 requests in flight
B1 sent (offsets 100-102)first batch, intended to land first
Transient failure, B1 retriesoriginal attempt fails in flight
B2 sent (offsets 103-105) lands firstconcurrent batch succeeds while B1 is retrying
B1 retry lands afterarrives once B2 is already on disk

Five in-flight requests, no idempotence: a retried batch can land after a later one that succeeded first, flipping order on disk.

Without idempotence, only one other fix exists

If idempotence is disabled for some reason, the only way to guarantee ordering under retries is max.in.flight.requests.per.connection=1 — allowing just one outstanding request at a time so a retry can never be overtaken by a later batch. That guarantees order, but throttles throughput back to one request at a time. Idempotence is strictly better here: it preserves ordering and keeps multiple requests in flight, which is exactly why it's on by default in modern Kafka.

At-most-onceA record may be lost, but is never duplicated — offset committed before processing, typically acks=0/1
At-least-onceA record is never lost, but may be reprocessed/duplicated — process first, then commit; retries enabled. The most common real-world default.
Exactly-once (EOS)No loss, no duplication — requires the idempotent producer plus transactions

Duplicate messages have two genuinely separate sources, and it's easy to conflate them. Producer-side duplication happens when an acknowledgment is lost in transit even though the write actually succeeded — the producer, seeing no ack, retries a write that already landed. Consumer-side duplication happens independently of any producer behavior at all: a consumer processes a record, then crashes before it commits its offset — on restart, it re-reads and reprocesses that same record, because as far as the group's committed offsets are concerned, it was never handled. The idempotent producer only fixes the first kind. It does nothing whatsoever for consumer-side duplication, and nothing for atomically writing to multiple partitions or topics as one unit — those require transactions.

A Kafka transaction bundles multiple actions — writes to several partitions or topics, plus committing the consumer's own input offset — into one atomic unit that either fully lands or fully doesn't. Consumers that need to see only fully-committed transactional writes set isolation.level=read_committed, which hides any records from a transaction that was aborted rather than committed.

TransactionalProducer.java
producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("payments", key, value));
    producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata); // commits input offset atomically too
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction(); // all-or-nothing — nothing partially lands
}
Exactly-once is Kafka-to-Kafka only

Kafka's exactly-once guarantees stop at Kafka's own boundary. If a consumer writes to an external database, sends an email, or calls a third-party REST API as part of processing a record, that external side effect needs its own idempotency mechanism — Kafka's transactions can't reach into it. The standard approaches: making the external write itself idempotent (an upsert keyed by the record's identity), the transactional outbox pattern (write the outbound event to a table in the same database transaction as the business write, then relay it separately), or storing the last-processed offset in that same external database transaction so a reprocessed record can be recognized and skipped.

If enable.idempotence=true is on, do I already have exactly-once processing?
No — and this is a very common misconception. The idempotent producer solves exactly one problem: a single producer's own retries no longer duplicate writes to a single partition. It says nothing about a consumer crashing after processing but before committing its offset (still a duplicate, just on the consumer side), nothing about atomically writing to more than one partition or topic together, and nothing about any external system a consumer talks to along the way. Full exactly-once processing needs idempotence plus transactions, and even then, the guarantee only extends as far as Kafka itself.
Chapter summary
  • The write path is send() → Serializer → Partitioner → RecordAccumulator → Sender thread → broker leader → ack.
  • acks=0/1/all trade off throughput against durability — acks=all is the only one that survives a leader crash with zero loss.
  • The idempotent producer (PID + per-partition sequence number) deduplicates a producer's own retries without sacrificing ordering, and is on by default.
  • With multiple in-flight requests and no idempotence, a retried batch can land out of order on disk; idempotence fixes this while still allowing high in-flight concurrency.
  • Duplicates come from either the producer side (lost ack, retry) or the consumer side (crash before offset commit) — idempotence only fixes the former.
  • Transactions bundle multi-partition writes and offset commits atomically; exactly-once is a Kafka-to-Kafka guarantee only — external side effects need their own idempotency mechanism.

Consumer Groups & Rebalancing

A consumer group is how Kafka turns "many consumers" into "one coordinated team splitting the work" — and rebalancing is the mechanism that keeps that split fair every time a consumer joins, leaves, or crashes.

9 min read

Think of it like a team splitting a shared to-do list: everyone on the team picks up different items so nothing gets done twice, but a different team working from a copy of the same list works through all of it independently, unaware of the first team's progress.

The pull model

Consumers don't have data pushed at them — they call consumer.poll() whenever they're ready for more. That single design choice makes Kafka naturally back-pressure friendly: a consumer that's temporarily slow (a heavier-than-usual batch to process, a downstream dependency under load) simply calls poll() less often, and nothing on the broker side needs to know or react — there's no queue building up on the broker forcing a decision about what to drop.

Cooperative / incremental

  • Only the specific partitions that actually need to move are revoked

  • The modern default (CooperativeStickyAssignor)
  • Static membership (group.instance.id) goes further — a consumer restarting briefly doesn't trigger a rebalance at all, since the group recognizes it as the same member returning

Contrast this against what the old eager protocol would have done for this exact same single-consumer-joining event: every consumer in the group — A and B both, even though neither of them individually needed to give up anything — would revoke all of their partitions and stop entirely, waiting for the coordinator to compute and hand out a brand-new assignment from scratch. Six partitions' worth of processing would pause, group-wide, to accommodate a change that cooperative rebalancing handles by pausing exactly one.

Rebalance and reassignment are not the same thing

A consumer-group rebalance is entirely client-side: it moves partition ownership between consumers within a group, and no data is physically copied anywhere — the partition's replicas stay exactly where they are on their brokers. A partition reassignment, triggered via the admin tool kafka-reassign-partitions, is a completely different, server-side operation: it's an admin-initiated action that physically copies a partition's replica data from one broker to another (often to rebalance disk usage or move load off a broker being decommissioned). Same-sounding word, completely different mechanism — confusing the two is a classic trap, since one is a lightweight client protocol event and the other is a heavyweight data-copying operation between brokers.

Why can't two consumers in the same group read the same partition?
Because that's the entire mechanism that makes queue-style, work-splitting consumption possible — if two consumers in the same group could both read the same partition, each record would potentially be double-processed by both of them, which defeats the point of having a group divide work up in the first place. Two different consumer groups, on the other hand, can absolutely both read the same partition — that's exactly the pub/sub-style behavior from the core-concepts chapter, since each group tracks its own independent offsets.

  • Eager rebalancing pauses the entire group for any membership change; cooperative/incremental rebalancing (the modern default) moves only the affected partitions.
  • In the billing example, only P5 ever paused when C joined — A and B kept processing their other partitions uninterrupted throughout.
  • Static membership (group.instance.id) avoids triggering a rebalance at all for a transient consumer restart.
  • A client-side rebalance (partition ownership change, no data movement) is a completely different mechanism from a server-side kafka-reassign-partitions (physical replica data movement between brokers).

Offset Management & Consumer Lag

An offset is just a position in a log — but tracking four subtly different kinds of "position" at once (what's been written, what's safe to read, what's been acknowledged, and where you personally are) is what makes lag, reprocessing, and rebalance bugs make sense.

8 min read

It helps to picture a partition as a book being written live, one page at a time, while people are already reading it. Several different "how far along" markers matter simultaneously, and they're easy to conflate.

TermMeaning
Log-End-Offset (LEO)The offset of the next record that will be written — the very end of the log as it currently stands
High Watermark (HW)The highest offset replicated to every ISR member — consumers can only read up to here
Committed offsetThe last offset the consumer group has explicitly acknowledged as processed
Current positionThe next offset this particular consumer instance will read on its next poll()

Consumer offsets aren't stored client-side in some config file — they live in an internal, Kafka-managed, compacted topic called __consumer_offsets, keyed by (group, topic, partition), so only the latest committed offset per group/partition is retained (compaction is covered in full in the next chapter).

Heartbeats, liveness, and the classic poll-loop bug

A consumer's membership in a group depends on staying alive by two related mechanisms: a background heartbeat sent every heartbeat.interval.ms, and an overall session.timeout.ms — if no heartbeat arrives within that window, the consumer is presumed dead. Separately, and this is the one that catches people off guard, max.poll.interval.ms caps the maximum allowed gap between successive calls to poll() itself — not just heartbeats.

The classic max.poll.interval.ms bug

If processing the records from one poll() call takes longer than max.poll.interval.ms, the consumer is treated as dead and removed from the group — even though its process is still very much alive and working — triggering a rebalance and handing its partitions to someone else. When it eventually finishes and calls poll() again, it discovers it's no longer a group member, and whatever it just finished processing gets reprocessed by whichever consumer picked up its partitions, creating duplicates. The fix is not to blindly raise the timeout — that just delays detecting a genuinely stuck consumer. The real fix is lowering max.poll.records so each batch is smaller and faster to finish, or offloading slow work (a slow downstream call, heavy computation) so poll() gets called again promptly.

Worked example: computing consumer lag

Per-partition lag is simply LEO − committed offset — how far behind the group's acknowledged position is from the actual end of the log.

On its own, 150 records of lag could mean almost anything — a momentarily busy consumer, or the very early sign of a consumer that's falling permanently behind. What actually matters for diagnosis is the trend over time, not any single snapshot: lag that's stable or shrinking is healthy; lag that climbs steadily poll after poll means the consumer genuinely can't keep up with the incoming rate, and that's the signal worth acting on.

Why does auto-commit risk both losing and duplicating records, not just one or the other?
Because it commits on a fixed timer, entirely decoupled from actual processing progress. If the timer fires and commits an offset for records that are still being processed, and the consumer then crashes before finishing them, those records are marked as committed but were never actually completed — effectively lost. Conversely, if processing finishes but the timer hasn't fired yet when the consumer crashes, those already-processed records get reprocessed on restart, since the commit never happened. Auto-commit's timing is independent of the real unit of work, which is exactly why manual commits, tied explicitly to "processing is actually done," are the standard choice when correctness matters.

  • Consumer offsets live in the internal compacted topic __consumer_offsets, not client-side.
  • Auto-commit can lose or duplicate depending on timing; commitSync() is the reliable standard for at-least-once; commitAsync() is faster but needs care on failure.
  • max.poll.interval.ms — not just the heartbeat — governs liveness; exceeding it triggers a rebalance and reprocessing, and the fix is faster/smaller processing, not a blindly raised timeout.

Retention, Compaction & Schema Evolution

Kafka gives you two entirely different answers to "how long does data live here" — one for pure event streams, one for anything that behaves like a changing piece of state — plus a separate answer to "what happens when the shape of that data changes underneath you."

8 min read

Two cleanup policies

PolicyBehaviorBest for
delete (default)Drops whole old segments once they're past a configured time or size limitPure event streams — logs, clickstreams, telemetry — where only recent history matters
compactKeeps only the latest value written for each key, foreverChangelogs and state snapshots — anything representing "current state per key"
compact,deleteBoth combined — compacts by key, and additionally still drops data past a time/size limitState that should compact but also shouldn't be retained indefinitely

The relevant configs are retention.ms (defaulting to 7 days) and retention.bytes. Critically, cleanup under the delete policy happens at the segment level, not the individual record level — an entire segment only becomes eligible for deletion once every record inside it is past the retention limit, and this happens regardless of whether any consumer has actually read that data yet. A consumer that's fallen far enough behind can lose access to records it never got to, simply because their segment aged out.

Worked example: log compaction

Think of a compacted topic like a contacts app: you don't care about every previous phone number someone has ever had, only their current one. Compaction guarantees at least the latest value per key survives, regardless of how many times that key was overwritten in between.

Every earlier value for k1 and k2 (A, B, X) is dropped — only the latest value per key survives.

A record with a null value is a special marker called a tombstone — it signals that the corresponding key should eventually be removed entirely, rather than just superseded by a newer value. Both __consumer_offsets (from the previous chapter) and Kafka Streams' internal state-store changelog topics rely on exactly this compaction behavior — they only ever need the latest value per key, never the full history of how it got there.

Kafka doesn't know or care what's in your bytes

Kafka itself stores and moves raw bytes — it enforces absolutely no schema of its own on a record's key or value. That's deliberate flexibility, but it means nothing stops a producer from evolving its data shape in a way that silently breaks every consumer relying on the old shape. A Schema Registry (the Confluent-style version being the common one) exists specifically to close that gap: it's a central service that stores Avro/Protobuf/JSON schemas and enforces compatibility rules as producers and consumers evolve independently of each other, over time.

The mechanics are simple and deliberately lightweight: a producer registers a new schema (or looks up an existing, already-registered one) with the registry, then writes each record as [magic byte][schema ID][payload] — meaning only a small integer schema ID travels with every single message, not the schema itself. A consumer reads that schema ID out of the record, fetches the matching schema definition from the registry (typically cached locally after the first fetch), and uses it to correctly deserialize the payload.

The safest schema evolution pattern under BACKWARD compatibility is to only ever add new fields with sensible defaults, so older data missing that field still deserializes cleanly. Renaming a field in place, or changing its type, is effectively a breaking change dressed up as a small edit — consumers reading old data with the new schema (or vice versa) will misinterpret or fail to parse it. If a field genuinely needs to change shape, the safer path is adding a brand-new field alongside the old one and migrating consumers over deliberately, rather than mutating the existing field's meaning.

Can a compacted topic ever lose the latest value for a key?
No — that's the one guarantee compaction never breaks. It can and does remove every superseded, older value for a key, but the most recent value for any key that hasn't been explicitly tombstoned is always preserved. What compaction cannot promise is retaining the full history of how a key's value changed over time — if that history matters for auditing or replay purposes, compaction alone is the wrong tool, and a delete-policy (or compact,delete) topic retaining the raw event history is a better fit.

Kafka Ecosystem & Operations

Kafka rarely stands alone in production — Streams and ksqlDB process what's already flowing through it, Connect moves data across its boundary, KRaft runs the cluster itself, and a handful of metrics tell you whether all of it is actually healthy.

8 min read

Kafka Streams & ksqlDB

Kafka Streams

  • KStream — an unbounded stream of individual events
  • KTable — a changelog representing the latest value per key, table-like
  • Stateful operations (aggregations, joins) are backed by a local RocksDB store plus a changelog topic, so state survives a crash and restart
  • Windowing comes in four flavors: tumbling, hopping, sliding, and session windows

ksqlDB

  • A streaming SQL engine built directly on top of Kafka Streams
  • Push queries (EMIT CHANGES) run continuously, streaming new results as data arrives
  • Pull queries fetch a point-in-time snapshot of current state, like a normal SQL query
  • Lets teams express stream processing logic in SQL instead of writing a Streams application in code

Kafka Connect

Kafka Connect is the standard way to move data across Kafka's boundary without hand-writing producer/consumer glue code for every integration. Source connectors pull data from an external system into Kafka (a JDBC source polling a database, a file source tailing logs); sink connectors push data out of Kafka into an external system (writing to Elasticsearch, S3, or a data warehouse). The most common source-connector use case in modern architectures is change-data-capture (CDC) — Debezium, for instance, tails a database's own write-ahead/binlog and streams every row-level change into Kafka as it happens, without the source application needing to publish anything itself.

KRaft

Kafka historically depended on an entirely separate system, ZooKeeper, to handle cluster consensus — electing the controller, storing metadata, tracking broker liveness. That meant operating two distributed systems to run one Kafka cluster. KRaft (KIP-500) removed that external dependency by implementing an internal Raft-based controller quorum directly inside Kafka itself, storing cluster metadata in its own internal log. KRaft is the current, production-default mode in modern Kafka — ZooKeeper support was fully removed as of Kafka 4.0, making KRaft not an emerging alternative but the only supported path going forward.

When you'd actually pick RabbitMQ instead

Kafka isn't a universal replacement for a traditional broker. Why does KRaft scale to more partitions than ZooKeeper-based Kafka did?
ZooKeeper-based clusters kept every bit of partition metadata replicated through ZooKeeper's own consensus protocol, which becomes a bottleneck as the number of partitions climbs into the hundreds of thousands — metadata propagation and controller failover both got slower. KRaft stores metadata as a Kafka-native log, replicated via Kafka's own Raft implementation, tightly integrated with the rest of the system rather than bolted on as an external dependency. That integration is what lets modern Kafka clusters scale to significantly higher partition counts and recover a failed controller considerably faster than the old ZooKeeper-based design could.

09 Interview Room

Interview Questions

Sixteen deep-dive questions across internals, trade-offs, traps, and scenarios — try answering each before revealing.

16 questions
Internals & Why
01
InternalsWhy does acks=all wait on the ISR specifically, rather than requiring an acknowledgment from literally every replica of the partition?

Waiting on every replica that exists — rather than every replica that's currently trustworthy — would mean a single slow, GC-paused, or network-partitioned follower could stall every future write on that partition indefinitely, since it would never be able to catch up while blocking new writes at the same time. The ISR mechanism separates "replicas that physically exist" from "replicas confirmed caught up within replica.lag.time.max.ms," and acks=all only depends on the latter set. A lagging follower simply drops out of the ISR (and out of what acks=all waits on) rather than blocking progress, and rejoins automatically once it catches back up. This is precisely what lets Kafka absorb ordinary transient follower slowness without treating it as a full outage, while min.insync.replicas still guards against the ISR shrinking too far to trust.

02
InternalsWhy is Kafka able to sustain very high throughput despite persisting every single record to disk before it's considered written?

Several design choices stack together here. Writes are purely sequential appends to the currently active segment file, which run at speeds close to memory even on spinning disks — Kafka never does random-access writes. Reads are served from the operating system's page cache far more often than from the physical disk, and when data does need to move to a consumer, Kafka uses zero-copy transfer (sendfile) straight from the page cache to the network socket, skipping an extra copy through application memory entirely. On top of that, producers batch many records per request and typically compress those batches, trading a little CPU for dramatically less network and disk I/O. None of these individually would be enough, but together they let Kafka treat "durable" and "fast" as compatible rather than opposing goals.

03
InternalsWhy does the high watermark exist at all — why not just let consumers read whatever the leader has most recently appended?

A record the leader has written but hasn't yet replicated to the full ISR is not yet safe — if the leader dies before that replication completes, a newly elected leader (promoted from the ISR) might never have received that record at all, and it would simply vanish. If consumers were allowed to read that record before it was safely replicated, they could observe data that a failover then makes disappear, which is a much harder inconsistency for downstream systems to reason about than "the data just hasn't arrived yet." The high watermark — the highest offset replicated to every ISR member — is the boundary past which a record is guaranteed durable even through a leader failure, so capping consumer reads there guarantees consumers never observe something that could later un-happen.

04
InternalsWhy does the idempotent producer need both a Producer ID (PID) and a per-partition sequence number, instead of just tagging each message with a random unique ID?

A random unique ID per message would let the broker detect an exact duplicate, but it wouldn't let the broker enforce anything about order — it would only know "have I seen this exact ID before," not "is this the next thing I should accept from this producer." A strictly increasing, per-(PID, partition) sequence number gives the broker both pieces of information at once: it can reject an already-seen sequence number as a duplicate, and it can reject an out-of-order sequence number arriving too early, forcing retries to land in the correct order even when several requests are in flight simultaneously. The PID scopes that sequence space to one producer session, so two independent producers' sequence numbers never collide or interfere with each other's ordering.

Trade-offs
05
Trade-offHow would you go about choosing a topic's partition count, and what do you actually give up by simply over-provisioning it "to be safe"?

A reasonable starting point is target throughput divided by the throughput a single partition can realistically sustain, then rounded up to at least the maximum number of consumers you'd ever expect running in one group at once, since useful parallelism caps out exactly at the partition count. Over-provisioning isn't free, though: every partition costs an open file handle and some memory on every broker holding a replica of it, and a broker failure takes longer to recover from the more partition leaders it's responsible for re-electing — so a topic with far more partitions than it needs quietly adds operational overhead and slower failover, in exchange for parallelism headroom that may never actually get used. And because growing partition count later remaps keys and can break existing ordering guarantees, the practical answer is sizing deliberately up front rather than defaulting to "as many as possible."

06
Trade-offacks=all gives the strongest durability guarantee Kafka offers. Why wouldn't every producer simply always use it?

acks=all trades latency for durability — every write has to wait for every current ISR member to confirm replication before the producer is told it succeeded, which is strictly slower than acks=1 (leader-only) or acks=0 (fire-and-forget). For genuinely high-volume, loss-tolerant data — metrics samples, non-critical telemetry, certain kinds of logs — that extra latency, multiplied across enormous message volume, can be a real cost with limited actual benefit, since losing an occasional sample doesn't meaningfully hurt the aggregate picture. The right acks setting is a direct reflection of how much a specific data stream's individual records actually matter, not a single universal best answer.

07
Trade-offCooperative/incremental rebalancing is clearly less disruptive than eager rebalancing. Why wasn't it the default from the very beginning?

Cooperative rebalancing is genuinely more complex to implement correctly — computing the minimal set of partitions that actually need to move, coordinating a two-phase revoke-then-assign protocol, and handling all the edge cases where that minimal-change computation itself needs to be safe under concurrent membership changes, is a harder problem than "stop everyone, recompute from scratch, restart everyone." The simpler eager protocol was a reasonable, correct starting point while the ecosystem matured; cooperative rebalancing arrived once the added complexity had been proven out, and eventually became the default once it was clearly the better trade-off for the vast majority of real workloads, where minimizing processing interruption matters far more than protocol simplicity.

08
Trade-offWhen would you choose a compacted topic over a plain delete-policy topic with a long retention period, given compaction seems to throw away more historical detail?

Compaction is the right choice when what you actually care about is "current state per key" rather than "the full history of how that state changed" — a changelog of a user's current profile fields, or a Kafka Streams state store, doesn't need every past value, only the latest one, and compaction lets that topic stay bounded in size indefinitely regardless of how many updates occur. A long-retention delete-policy topic is the better fit when the history itself is the point — an audit trail, an event-sourced ledger, anything that needs to be replayed in full to reconstruct how state arrived where it is. The trade-off is bounded size and instant "current value" lookups (compaction) versus complete historical fidelity (delete with long retention) — and compact,delete exists specifically for cases that want compaction's bounded-size property without retaining data truly forever.

Traps
09
TrapA producer with max.in.flight.requests.per.connection=5 and enable.idempotence=false notices that records occasionally land out of order on disk after a transient network failure. Diagnose exactly what's happening.

With 5 requests allowed in flight at once, several batches can be outstanding to the broker simultaneously. If an earlier batch (say, B1, meant for offsets 100-102) hits a transient failure and needs to be retried, while a later batch sent concurrently (B2, meant for 103-105) succeeds on its first attempt, B2 lands on disk before B1's retry does — flipping the on-disk order to [B2][B1] even though B1 was logically supposed to come first. Without idempotence, the broker has no concept of "which batch was supposed to come first," so it simply appends whatever arrives, in arrival order. The fix is enabling the idempotent producer, which tags every batch with a producer ID and a strictly increasing per-partition sequence number, so the broker can reject an out-of-order arrival and force the correct order — without needing to fall back to max.in.flight.requests.per.connection=1, which would fix ordering too, but at a real throughput cost.

10
TrapA team assumes a consumer-group "rebalance" and a "partition reassignment" (via kafka-reassign-partitions) are just two names for the same operation. Where does this assumption break down, and what actually goes wrong if it's acted on?

A rebalance is a lightweight, client-side event that only changes which consumer within a group owns which partition — no data moves anywhere, since the partition's replicas stay exactly where they are on their brokers. A reassignment triggered via kafka-reassign-partitions is a heavyweight, server-side, admin-initiated operation that physically copies a partition's replica data from one broker to another. If a team treats these as interchangeable — say, expecting a reassignment to complete as fast as a rebalance, or expecting a rebalance to actually rebalance disk usage across brokers — they'll be caught off guard: a reassignment of any real size can take significant time and consume meaningful network/disk bandwidth while it copies data, and a plain rebalance does absolutely nothing to address uneven broker-level storage or replica placement.

11
TrapA team enables enable.idempotence=true and tells stakeholders the pipeline now has full exactly-once processing, end to end, including its final database write. What's the gap in that claim?

The idempotent producer only deduplicates one specific thing: a single producer's own retries writing to a single partition. It does nothing about a consumer crashing after processing a record but before committing its offset, which still causes reprocessing and duplicate handling on the consumer side. It also does nothing about atomically writing to multiple partitions or topics as one unit — that requires transactions on top of idempotence. And critically, it says nothing at all about the final database write, or any other external side effect — Kafka's exactly-once guarantees stop at Kafka's own boundary, so the database write needs its own idempotency mechanism (an idempotent upsert, a transactional outbox, or storing the processed offset in the same database transaction) to actually be safe against duplicates.

12
TrapA consumer occasionally takes longer than max.poll.interval.ms to process a batch, gets kicked from its group, and the team's fix is simply raising max.poll.interval.ms to a very large value. What's wrong with that fix?

Raising the timeout doesn't fix the underlying reason processing is slow — it just gives slow processing more room to hide, and it directly delays how quickly Kafka can detect a consumer that's genuinely stuck (deadlocked, crashed, or otherwise never coming back), since the group now has to wait much longer before deciding to reassign that consumer's partitions. The more durable fix addresses the actual cause: reducing max.poll.records so each batch is smaller and finishes faster, or moving genuinely slow work (an external API call, heavy computation) off the poll loop entirely so poll() gets called again promptly. Raising the timeout is sometimes a reasonable stopgap, but treating it as the actual solution just trades a visible rebalance-and-reprocess problem for a much slower failure-detection problem.

Scenario
13
ScenarioConsumer lag on a critical topic has been climbing steadily for the last hour. Walk through how you'd diagnose it.

Start by confirming this is a real trend and not noise — check the lag graph over the full hour rather than a single snapshot, and compare it against the topic's incoming write rate over the same window, since lag climbing because writes suddenly doubled is a very different problem than lag climbing because processing quietly got slower. If the write rate is steady but lag still climbs, look at per-partition lag specifically — even lag concentrated on one or two partitions (a hot key, uneven partitioning) looks different from lag spread evenly across all of them (a genuine processing slowdown or too few partitions for the current load). Check whether rebalances have been happening frequently around the same window, since a rebalance storm (often caused by processing exceeding max.poll.interval.ms) directly causes lag to climb by repeatedly pausing and reassigning partitions. Finally, look at what the consumer is actually doing per record — a downstream dependency (database, external API) that's gotten slower is one of the most common root causes, and it shows up as increased per-record processing time rather than anything visible in Kafka's own metrics.

14
ScenarioOn a topic with RF=3 and min.insync.replicas=2, a follower broker fails, and some time later the leader broker also fails. Walk through what happens to reads, writes, and the data at each stage.

When the follower fails, the ISR shrinks from 3 down to 2 — still at or above min.insync.replicas, so nothing changes for producers or consumers: writes continue succeeding under acks=all, reads continue normally, and there's zero data loss. When the leader then fails too, Kafka runs a clean leader election from the remaining ISR, promoting the surviving replica — every record that was ever committed survives this, since committing required replication to every ISR member at the time, including the one now being promoted. But the ISR is now down to just that one promoted broker, size 1, which is below min.insync.replicas=2 — so while reads of existing data continue working fine, new acks=all writes are rejected outright with a NotEnoughReplicas-style error until at least one more replica catches up and rejoins the ISR. The system fails closed rather than silently accepting writes it can't back up to the configured durability level, and full write availability only returns once the ISR grows back to meet the minimum.

15
ScenarioYou need to remove a field from a topic's schema that's no longer populated by any producer. What compatibility mode could block this, and how would you make the change safely?

Removing a field is actually a safe change under BACKWARD compatibility (the default) — a new schema without the field can still read old records that happen to contain it, since it simply ignores the extra data. It's FORWARD compatibility that this could threaten: an old schema expecting that field to be present, reading a new record that no longer has it, may fail or need a sensible default depending on the exact schema language's rules. Practically, the safe path is checking whether any still-running consumer is pinned to an old schema version expecting that field, deploying all consumers to a version that no longer requires it first, confirming no producers are actively writing under the old schema anymore, and only then registering the new schema without the field — letting the registry's compatibility check itself be the final guardrail rather than assuming the removal is risk-free just because BACKWARD compatibility technically permits it.

16
ScenarioA financial ledger service needs to consume an event, write a row to its own database, and produce a confirmation event to another topic — with a hard requirement that all three either happen together or not at all. How would you build this on Kafka?

The Kafka-to-Kafka half of this — consuming the input event and atomically producing the confirmation event, together with committing the input offset — is exactly what Kafka transactions provide: wrapping the produce calls and sendOffsetsToTransaction in a single beginTransaction/commitTransaction block guarantees they land together or not at all, and downstream consumers reading with isolation.level=read_committed never see a partially-committed transaction. The database write is the part transactions can't reach, since it's an entirely external system — the standard pattern there is the transactional outbox: write the ledger row and an "outbox" record representing the confirmation event in one single database transaction, then have a separate relay (or Debezium-style CDC connector) pick up that outbox row and publish it to Kafka. That turns the true atomic unit into "database write + outbox row," with Kafka publication happening reliably afterward — rather than trying to make one distributed transaction span both a database and Kafka directly, which neither system is really built to do.

Interview delivery tips

(1) For any acks/durability question, name the specific interaction — RF, ISR, min.insync.replicas, acks — rather than a single setting in isolation; that's what actually signals real depth. (2) When asked about ordering, immediately mention "within a partition only" before anything else — it's the single most commonly tested precision point in this whole topic. (3) For any "is this exactly-once" question, reflexively check whether the claim covers the consumer side and any external system, not just the producer — that's where most exactly-once claims quietly fall apart. (4) Distinguish rebalance from reassignment explicitly whenever either comes up — it's a favorite trap precisely because the names sound identical. (5) For lag or rebalance-storm scenarios, lead with "is this a trend or a snapshot" before reaching for a specific root cause.
