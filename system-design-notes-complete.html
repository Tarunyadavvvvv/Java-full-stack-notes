01 Foundations

Scalability Fundamentals & Standard Architecture

Every system design conversation, no matter what you're actually asked to build, eventually comes back to the same question: what happens when this gets ten times more traffic? The answer starts here.

9 min read

Vertical vs horizontal scaling

Vertical scaling (scale up)

  • Add more CPU, RAM, or faster disks to the same machine
  • Simple — no architecture or code changes required
  • Hits a hardware ceiling, and the machine stays a single point of failure

Horizontal scaling (scale out)

  • Add more machines and spread load across them
  • Near-unlimited headroom, and no single box failing takes the system down
  • Requires a load balancer and — the hard part — a plan for shared state

Stateless vs stateful services

Horizontal scaling only works cleanly if any instance can handle any request. That's trivial for a service that keeps no memory of previous requests (stateless) — a load balancer can send request #1 to server A and request #2 to server B without either server needing to know about the other. It breaks the moment a service keeps session data, in-progress uploads, or cached per-user state in its own process memory (stateful) — now a user has to keep hitting the same server, which quietly reintroduces the single-machine ceiling you were trying to escape.

The fix is moving that state somewhere shared — Redis, a database, a distributed cache — so the app server itself holds nothing that can't be reconstructed from a shared store. That single decision is what makes both horizontal scaling and zero-downtime deploys possible: you can kill an instance, spin up a new one, or route around a crash, and no user session is lost, because the session was never actually tied to that instance in the first place.

Default to stateless, even when sticky sessions look tempting

Pinning a user to "their" server is often reached for as a shortcut around building shared state — but it caps how evenly you can load-balance, and a server crash loses every session pinned to it. Push session/user state into Redis or a database from day one; it costs a network hop, but it buys you the ability to scale and deploy without ceremony.

The shape you'll draw in almost every interview: static content served from the edge, dynamic requests hitting stateless compute that fans out to whichever backing services the request needs, with the database itself scaled independently underneath — replicated for reads, sharded for writes.

RAM (~100 ns) vs. an HDD seek (~10 ms) is a five-order-of-magnitude gap — the entire reason caching exists as a discipline. Two more relationships worth memorizing: an SSD is roughly 20× faster than an HDD for random reads, and a same-datacenter round trip (~500 µs) is already ~5,000× slower than a single memory access — and sequential access beats random access at every layer of this hierarchy, not just on disk.

Why does an interviewer care about p99 latency instead of just the average?
Averages hide exactly the users you should worry about most. If 99% of requests take 20ms but 1% take 4 seconds (a GC pause, lock contention, a slow downstream call), the average might still look fine — maybe 60ms — while a meaningful slice of real users are having a bad time on every page load. At scale, "1% of requests" is never a rounding error: at 10,000 QPS, that's 100 slow requests every single second. p95/p99 make that tail visible instead of averaging it away.
Chapter summary
  • Vertical scaling is simple but ceiling-limited and a single point of failure; horizontal scaling is near-unlimited but requires shared state.
  • Statelessness — keeping session/user state in a shared store, not app-server memory — is what makes horizontal scaling and zero-downtime deploys possible.
  • The standard architecture: CDN for static content, a load balancer in front of stateless app servers, which fan out to cache/queue/search/DB, with the DB scaled via replicas and shards.
  • Know your metrics vocabulary — QPS, p50/p95/p99 latency, availability, error rate — you'll use it to size every system you design.
  • Memory beats disk by ~100,000×; that single fact justifies almost every caching decision in this file.

Load Balancing

A load balancer is the traffic cop standing between your clients and a fleet of servers — and, if you're not careful, the one thing standing between you and an outage when it falls over itself.

7 min read

Load balancing algorithms

AlgorithmHow it picks a serverGood for
Round robinCycles through servers in orderUniform servers, uniform request cost
Weighted round robinCycles, but sends more requests to higher-capacity serversA mixed fleet of different instance sizes
Least connectionsSends the next request to whichever server has the fewest active connectionsRequests with widely varying processing time

L4 vs L7 load balancing

L4 — transport layer

  • Routes on IP address and port only — never opens the payload
  • Very fast, protocol-agnostic (works for anything over TCP/UDP)
  • Can't route by URL path, header, or do SSL termination

L7 — application layer

  • Understands HTTP — reads the URL path, headers, cookies
  • Can do content-based routing, SSL termination, per-route rules
  • Slightly higher cost per request from actually parsing the payload
ClientGET /api/orders/42
L7 load balancerinspects path + host header
Orders service poolone of several backend pools

The same load balancer might send /api/orders/* to one backend pool and /api/search/* to a completely different one — L7's whole value proposition is that this routing decision happens at the LB, not scattered across application code.

Don't let the load balancer become the single point of failure it was meant to remove

A load balancer fanning traffic across ten redundant app servers has done nothing for your availability if it's itself one box. Always pair it with health checks (so it stops routing to dead backends within seconds, not minutes), and run the LB layer redundantly too — active-passive with a floating IP, or DNS-based/anycast routing across multiple LB instances — so no single machine stands between every client and your entire fleet.

If L7 can do everything L4 can plus more, why would anyone still choose L4?
Raw speed and protocol flexibility. L4 never buffers or parses the payload, so it adds negligible latency and works identically for HTTP, raw TCP, gRPC, or any other protocol over TCP/UDP — useful for non-HTTP traffic or when every microsecond and CPU cycle at the LB tier matters. L7 is almost always the right default for HTTP APIs because content-based routing is so useful, but L4 still shows up underneath L7 (as the outer entry point to a cluster) or for protocols L7 rules don't understand.
Chapter summary
  • Round robin, weighted round robin, least connections, and IP/consistent hash cover most real load-balancing needs — pick based on fleet uniformity and whether you need stickiness.
  • L4 routes on IP/port only — fast and protocol-agnostic; L7 understands HTTP and can route by path/header, terminate SSL, and do content-based routing at a small latency cost.
  • Always pair a load balancer with health checks, and never run it as a single instance — it exists to remove a single point of failure, not become one.

Every request passes through the LB — if it goes down, all backend redundancy is unreachable. Health checks and a redundant LB layer close this gap.

Database Scaling

The database is almost always the first thing to fall over under real load — because unlike a stateless app server, you can't just add another identical copy and call it done. Every technique here is really a way of answering "who owns which piece of the data."

11 min read

Replication: primary-replica vs multi-primary

Writesfrom app servers
Primarythe only node accepting writes
Replicasreads load-balanced across these

Primary-replica: every write goes through one node, which asynchronously ships changes to replicas that only serve reads — scales read throughput and gives you a failover target, at the cost of replica lag.

Forgetting replica lag exists

A write hits the primary and returns success — but the read replica your very next request lands on may not have replicated it yet. Write a user's profile and immediately read it back from a replica, and you can see the old value. This is the single most common source of confusing "it worked, but then it didn't" bug reports in systems that scale reads via replicas — either read your own writes from the primary, or design the UI to tolerate a brief staleness window.

Multi-primary replication flips this: more than one node accepts writes, removing the single-writer bottleneck but reintroducing a much harder problem — two primaries can accept conflicting writes to the same row at nearly the same time, and something has to reconcile them (last-write-wins, vector clocks, or application-level merge logic). Most systems default to primary-replica specifically to avoid this class of problem, and only reach for multi-primary when write throughput or multi-region write latency genuinely demands it.

Sharding strategies

StrategyHow keys map to shardsFailure mode
RangeContiguous key ranges (A–M on shard 1, N–Z on shard 2)Hotspots if data or traffic is unevenly distributed across ranges
Hashhash(key) % NResharding (changing N) remaps almost every key — very expensive

What makes a good shard key

A good shard key has high cardinality (many distinct values, so it actually spreads across shards), an even distribution (no value dominates the dataset), and matches your most common query pattern (so most queries hit one shard, not all of them). user_id is a near-ideal shard key for a per-user product — high cardinality, roughly even, and most queries are already scoped to one user. country or a raw timestamp are classic anti-patterns: a handful of countries or a narrow recent-time window absorb a disproportionate share of traffic, creating exactly the hotspot sharding was supposed to prevent.

Cross-shard joins and transactions are the real cost

Sharding solves the "one machine can't hold it all" problem, but creates a new one: a query needing data from two different shards can no longer be a single fast local join — it now needs an application-level fan-out-and-merge, and a transaction spanning two shards needs a distributed-transaction pattern (see the outbox/saga discussion in ch. 6) instead of a normal database transaction. Choose a shard key that keeps related data together specifically to minimize how often this comes up.

Why does a B+ tree index turn an O(n) scan into an O(log n) lookup?
A B+ tree keeps keys sorted and organizes them into a shallow, wide tree — each internal node holds many keys and pointers, so even a table with millions of rows typically needs only a handful of node reads to find a match, instead of scanning every row. The trade-off is that every write now also has to keep the tree balanced and sorted, which is why indexes speed up reads but slow down writes — a cost worth paying on columns you actually query by, and worth avoiding on ones you don't.
Chapter summary
  • SQL gives you ACID and joins at the cost of harder horizontal scaling; NoSQL trades some of that consistency/flexibility for scale built in from the start.
  • Primary-replica replication scales reads and gives failover, but replica lag means reads can be stale — a frequent source of confusing bugs.
  • Sharding strategies trade off hotspot risk, resharding cost, and lookup overhead differently — range, hash, consistent-hash, and directory-based each fail in their own characteristic way.
  • A good shard key has high cardinality, even distribution, and matches your query pattern — user_id is usually good, country/timestamp usually isn't.
  • Sharding's real cost shows up in cross-shard joins and transactions, not in the sharding mechanism itself.

A user updates their profile and immediately reloads the page, but sees the old data. What's the most likely cause in a primary-replica setup?
Primary-replica replication is asynchronous by default — a write can succeed on the primary before it's propagated to every replica, so a read immediately after can hit a not-yet-updated replica.
Why is country usually a poor choice of shard key for a global consumer app?
Low cardinality plus skewed distribution (a few countries holding most of the users) concentrates load onto a small number of shards — exactly the hotspot problem a good shard key is supposed to avoid.

CAP Theorem & Consistency Models

CAP gets misquoted in almost every interview as "pick any two of three" — which is wrong in a way that matters. Get this one right and you've separated yourself from most candidates before you've said anything else.

8 min read

The theorem, stated correctly

CAP theorem says a distributed data store can guarantee at most two of Consistency (every read sees the latest write), Availability (every request gets a response), and Partition tolerance (the system keeps working when network messages between nodes are lost or delayed). The common "pick any two" framing is misleading because partitions aren't optional in any real distributed system running over an actual network — they will happen. Partition tolerance isn't a choice you get to opt out of; it's a fact of life. So the only live decision CAP actually hands you is what happens during a partition: do you sacrifice consistency (keep serving, maybe with stale data) or sacrifice availability (refuse to answer until you can be sure you're correct)?

CP — consistency over availability

  • During a partition, refuses (or blocks) requests it can't answer correctly
  • Examples: HBase, MongoDB (default config), ZooKeeper, traditional RDBMS
  • Right when a wrong answer is worse than no answer (inventory counts, financial ledgers)

AP — availability over consistency

  • During a partition, keeps answering — possibly with stale or conflicting data
  • Examples: Cassandra, DynamoDB, Riak
  • Right when staying up matters more than every reader seeing the same value instantly (social feeds, shopping carts)
Partition detectednetwork split
Choose Creject the request
Consistentbut unavailable
Partition detectednetwork split
Choose Aanswer anyway
Availablebut possibly stale

This is the only fork CAP actually hands you — partition tolerance was never on the table, so everything comes down to which branch a node takes the instant it can't reach its peers.

PACELC — the trade-off CAP leaves out

CAP only describes behavior during a partition. PACELC extends it: if Partitioned, choose Availability or Consistency (the "PAC" part) — else (normal operation, no partition), choose Latency or Consistency (the "ELC" part). Even when nothing is broken, a system that wants strong consistency has to pay for it with coordination latency; a system willing to accept eventual consistency can answer faster. This is why Cassandra and DynamoDB feel fast even outside failure scenarios — they're PA/EL systems by design, not just AP ones.

Consistency models

ModelGuarantee
StrongEvery read sees the most recent write, everywhere, immediately
EventualReplicas converge given enough time — a read may briefly return stale data
Read-your-writesA client always sees its own prior writes, even if others might see something stale
CausalOperations that are causally related are seen by everyone in the same order (unrelated ones may reorder)

ACID vs BASE

ACID (SQL default)

  • Atomicity, Consistency, Isolation, Durability
  • Transactions either fully happen or don't happen at all
  • The usual choice for CP-leaning systems

BASE (NoSQL default)

  • Basically Available, Soft state, Eventually consistent
  • Prioritizes uptime and throughput over immediate consistency
  • The usual choice for AP-leaning systems

Tunable consistency: the quorum formula

quorum.txt
// N = total replicas, W = replicas that must ack a write, R = replicas read from
if (W + R > N) {
    // every read set and every write set overlap by at least one node
    // -> a read is guaranteed to see the most recent write -> strong consistency
}
// e.g. N=3, W=2, R=2  ->  W+R=4 > 3  ->  strong
// e.g. N=3, W=1, R=1  ->  W+R=2 < 3  ->  fast, but eventually consistent

Cassandra and DynamoDB expose W and R as per-query knobs precisely so you can dial this trade-off yourself — a critical write can ask for QUORUM on both sides, while a low-stakes read can ask for ONE and accept a small risk of staleness in exchange for lower latency. This is the practical, tunable version of the CAP/PACELC trade-off, not an abstract theorem — it's a config value you set per query.

Is CAP really "pick any 2 of 3," as it's so often summarized?
Not quite, and this is worth saying precisely in an interview: partition tolerance isn't optional for any system running across more than one machine over a real network, so you don't get to "choose" it the way you choose consistency or availability. The actual choice CAP forces on you only exists during a partition — and it's a choice between consistency and availability at that moment, not a permanent architecture-wide trade-off. PACELC then adds the trade-off that exists the rest of the time, between latency and consistency, which is arguably the more practically relevant one, since partitions are rare but every single request pays the latency/consistency cost.
Chapter summary
  • CAP's real choice is C vs A during a partition, not "pick any 2 of 3" — partition tolerance is mandatory in any real distributed system.
  • CP systems (HBase, MongoDB, ZooKeeper, RDBMS) refuse to answer rather than answer wrong; AP systems (Cassandra, DynamoDB, Riak) keep answering, possibly with stale data.
  • PACELC extends the theorem to normal operation: absent a partition, you're still trading latency against consistency.
  • Consistency models range from strong to eventual, with read-your-writes and causal consistency as useful middle grounds.
  • W + R > N gives tunable strong consistency in quorum-based systems like Cassandra and DynamoDB — a per-query dial, not a fixed architectural choice.

CDN & Caching at the System Level

This chapter deliberately stays at 30,000 feet. Cache-aside, eviction policies, and Redis internals get a full dedicated treatment in the Caching & Redis module — here, the only question is where caching sits in the overall architecture, and when it actually helps.

6 min read

The cache location chain

Browserlocal cache
CDNedge, near the user
Load balancerroutes to app tier
App-local cachein-process, e.g. Caffeine
Distributed cacheshared Redis
Databasesource of truth

A request that misses every layer above pays the full cost of the layer below it — which is exactly why each layer exists: to intercept as much traffic as possible before it reaches something slower.

What a CDN actually does

A CDN is a network of edge servers, physically distributed close to users, that cache static and semi-static content — images, video, JS/CSS bundles, and increasingly whole cacheable API responses — so a user in Mumbai doesn't have to round-trip to an origin server in Virginia for every asset on a page. Two effects compound here: latency drops (a nearby edge server responds far faster than a distant origin), and origin load drops (the origin server never even sees the requests the CDN served from cache).

CDN helps

  • Static assets: images, video, fonts, JS/CSS bundles
  • Content that's the same for every user (or cacheable per a small set of variants)
  • Read-heavy, rarely-changing data

CDN doesn't help

  • Highly personalized, per-user dynamic data (a live account balance, a private feed)
  • Data that changes faster than any reasonable cache TTL
  • Write traffic — a CDN caches responses, it doesn't accelerate writes

Cache-aside vs. read/write-through vs. write-behind, LRU/LFU eviction, and the mechanics behind each failure mode above are covered in genuine depth in the dedicated Caching & Redis module. This chapter is intentionally the "where does this sit in the system" view, not the "how does it work" view.

Why does a CDN help even for content that technically changes sometimes?
Because "changes sometimes" is different from "changes every request." A product image, a JS bundle, or a blog post can carry a cache TTL of minutes to hours and still be correct the overwhelming majority of the time it's served — the rare staleness window is a fine trade for removing nearly all of that traffic from the origin. The line CDNs actually can't cross is per-user personalization: two different users hitting the same URL who must see two different responses defeats the entire premise of a shared edge cache.
Chapter summary
  • Caching exists at multiple layers — browser, CDN, load balancer, app-local, distributed — and each layer's job is to intercept traffic before it reaches something slower.
  • A CDN caches static/cacheable content at edge servers near users, cutting both latency and origin load.
  • CDNs help for static or rarely-changing, non-personalized content; they don't help for highly dynamic per-user data or writes.
  • Stampede, penetration, and avalanche are the three named cache failure modes — the mechanics and fixes get full depth in the Caching & Redis module.

Async Processing & Message Queues

Kafka's internals — partitions, consumer groups, ISR, exactly-once semantics — get an entire dedicated module. What belongs here is the decision one level up: when do you reach for "async" at all, and what does it actually buy you?

8 min read

Why go async at all

Clientfires a request
APIwrites to a queue, returns immediately
Queuebuffers the work
Worker poolprocesses at its own pace

The producer and consumer are now decoupled — a traffic spike fills the queue instead of overwhelming the workers, and each side can be scaled independently based on its own bottleneck.

Three separate benefits fall out of that one architectural move: decoupling (the API doesn't need to know or care how the work gets done, or by what), buffering (a burst of traffic queues up instead of taking the system down), and independent scaling (you can run 2 API instances and 50 worker instances, or vice versa, based on where the actual bottleneck is).

Queue vs pub/sub

Queue (point-to-point)

  • Each message is consumed by exactly one consumer
  • Examples: RabbitMQ, Amazon SQS
  • Right for distributing units of work across a worker pool

Pub/sub

  • Every subscriber receives every message independently
  • Examples: Kafka (via separate consumer groups), Amazon SNS
  • Right for broadcasting an event to multiple independent downstream systems

The outbox pattern

Say a service needs to update its own database and publish an event about that change — for example, "order placed" needs to both write the order row and notify a shipping service. These are two separate operations against two separate systems, and they can fail independently: the DB write succeeds but the publish fails (or vice versa), leaving the two systems permanently disagreeing about what happened. This is the dual-write problem, and it shows up anywhere a service talks to a database and a message broker in the same logical operation.

Serviceone DB transaction
State table + outbox tablewritten together, atomically
Relay processreads outbox, publishes reliably
Message brokerevent delivered downstream

Because the state change and the outbox row are written in the same database transaction, they either both commit or both roll back — there's no window where one happened and the other didn't. A separate relay process (polling the outbox, or CDC-based like Debezium) then does the actual publish, retrying until it succeeds, since the outbox row itself is durable proof the event still needs to go out.

The outbox turns an unreliable dual-write into a reliable single-write

The trick isn't making the publish itself atomic with the DB write — that's not achievable across two different systems. It's converting the publish into data (a row in your own database) so it can share a transaction with the state change, then handling the actual cross-system hop separately, with retries, as an already-solved "reliably deliver a message" problem instead of an unsolvable "atomically commit across two systems" problem.

Doesn't the outbox pattern just move the reliability problem to the relay process?
It moves it somewhere much easier to solve. The relay process only needs to guarantee "eventually publish every row that exists in the outbox table, at least once" — a much simpler property than atomically coordinating a database transaction with a network publish. If the relay crashes mid-publish, it just resumes from the last unprocessed outbox row on restart; consumers on the other end are expected to handle at-least-once delivery (duplicate messages) with idempotent processing, which is a well-understood, solvable problem — unlike trying to make two unrelated systems commit atomically.

  • Queues give each message to exactly one consumer (work distribution); pub/sub gives every message to every subscriber (broadcast).
  • The dual-write problem: a DB write and an event publish are separate operations that can fail independently, leaving systems inconsistent.

Consistent Hashing, Distributed IDs & Bloom Filters

Three small ideas that show up in almost every "design X at scale" answer: how to spread keys across nodes without a reshuffle, how to generate IDs without a central coordinator, and how to say "definitely not here" without actually looking.

Consistent hashing

Both nodes and keys get hashed onto the same circular space — a ring spanning 0 to 2³². A key belongs to whichever node is the first one found going clockwise from that key's position. Look up, insert, or route a key by hashing it and walking clockwise to the nearest node — no lookup table required.

Why this beats plain hash(key) % N — the single most-asked question here

Plain hash % N

  • A key's owner is hash(key) % N
  • Change N by even one node (add or remove) and almost every key's assigned node changes
  • Every node addition/removal forces a near-total data reshuffle

Consistent hashing

  • A key's owner is "the first node clockwise" on a fixed-size ring
  • Adding or removing one node only affects the keys between it and its clockwise neighbor
  • Only ~1/N of all keys move, not nearly all of them

With % N, N is baked directly into the formula — change it, and the entire mapping shifts, because hash(key) % 4 and hash(key) % 5 agree on almost nothing. Consistent hashing removes N from the formula entirely; a node's position on the ring is fixed regardless of how many other nodes exist, so adding or removing one node only ever disturbs the small arc of keys immediately next to it.

Virtual nodes fix the uneven-load problem

With only one point per physical node on the ring, a small number of nodes can end up with wildly uneven arcs (bad luck in hash placement) — one node's arc might be 3x another's. The fix is giving each physical node many points on the ring (hundreds of "virtual nodes"), so its total owned arc is an average over many small pieces rather than one lucky or unlucky big one — load evens out across the cluster almost regardless of raw node count.

Snowflake IDs — unique, roughly-ordered, no coordination

Generating unique IDs across many machines without a central counter (which would itself be a bottleneck and a SPOF) is a recurring need — Twitter's Snowflake scheme is the standard answer. A 64-bit ID is built entirely from local information, no network round-trip required:

Why "roughly" time-ordered matters

Because the timestamp occupies the highest bits, IDs generated later almost always sort after IDs generated earlier — useful for keeping database indexes append-friendly and for sorting-by-ID as a cheap proxy for sorting-by-time. It's only "roughly" ordered because two machines can generate IDs in the same millisecond in either order relative to each other — if you need a global, exact order, Snowflake alone isn't enough.

Bloom filters

A Bloom filter answers one narrow question extremely cheaply: is this item definitely not in the set, or maybe in it? It's a fixed-size bit array with a handful of hash functions — checking an item hashes it through each function and checks whether all the resulting bits are set; if even one isn't, the item is guaranteed absent (no false negatives), but a "yes" can occasionally be a false positive, since bits get shared across items. That asymmetry is exactly what makes it useful: it lets you skip an expensive lookup (disk read, network call, database query) for the vast majority of cases where the answer is a fast, confident "definitely not," at the cost of occasionally still doing the expensive check for a false positive.

Concrete use: killing cache penetration

Before hitting the database for a cache miss, check a Bloom filter of all known-valid keys first. If the filter says "definitely not present," reject the lookup immediately — no wasted database round-trip for keys that were never going to exist (the exact attack pattern behind cache penetration). Cassandra uses the same trick internally: a per-SSTable Bloom filter lets it skip a disk read entirely for the majority of SSTables that provably don't contain a given key.

Can a Bloom filter ever tell you an item is definitely present?
No — that's the one guarantee it never makes. A "maybe present" result just means every relevant bit happened to be set, which could be a true positive or an unlucky collision from other items sharing those same bits. Every positive result still needs a real lookup to confirm; the filter's entire value is in how confidently and cheaply it rules items out, not in confirming them.

09 Reliability & Operations

Distributed Locks & Consensus

A lock inside one process is a solved problem. A lock across machines that can independently crash, pause, or lose network connectivity at any moment is a genuinely different — and genuinely harder — problem, and it's the one this chapter earns its keep on.

10 min read

What a distributed lock actually has to guarantee

A distributed lock needs to guarantee mutual exclusion across machines: at most one process, anywhere in the system, believes it holds the lock at any given moment — and, critically, that belief has to stay correct even when a machine crashes mid-operation, a network link drops, or a process pauses for an unpredictable amount of time (a GC pause, a slow disk, a scheduler hiccup). A single database row used naively as a lock ("acquire by inserting a row, release by deleting it") fails exactly at that seam: if the process holding the lock crashes before deleting its row, the lock is held forever — nobody else can ever acquire it, and there's no built-in mechanism to detect the holder is gone and recover.

Redis-based locking — and its sharp edge

The standard fix is SETNX lock:resource holderId with a TTL — set atomically in one call (e.g. Redis's SET key value NX PX ttl), since doing the set and the expiry as two separate commands leaves a crash window where the lock has no TTL at all: the lock auto-expires if its holder crashes and never releases it. That solves the "crashed forever" case, but introduces a subtler one — a paused, not crashed client. Say a client acquires the lock, then stalls (a long GC pause, a slow network call) for longer than the TTL. The lock expires and a second client acquires it and starts working. The first client eventually wakes up, has no idea time has passed, still believes it holds the lock, and writes to the protected resource anyway — now two clients have modified the same resource, exactly the outcome the lock existed to prevent.

A TTL alone doesn't make a lock safe — it just bounds how long it's unsafe for

Adding a TTL to a Redis lock fixes the "holder crashed and never released it" failure, but it does not fix the "holder is still alive and still writing after its lock silently expired" failure. These are two different bugs with two different fixes — don't let a TTL give you false confidence about the second one.

The fix for that second failure is a fencing token: every time the lock is granted, hand out a monotonically increasing number along with it (token 1, then 2, then 3...). The resource being protected — not the lock service — checks that token on every write, and rejects any write carrying a token lower than the highest one it's already seen. Now the stale first client's late write arrives with an old token, gets rejected by the resource itself, and the corruption never happens — the lock service doesn't need to somehow know the first client is "really" dead; the resource just refuses to honor stale authority.

FencingToken.pseudo
// resource-side check, not lock-service-side
function handleWrite(request) {
    if (request.fencingToken < highestTokenSeen) {
        return "reject: stale lock holder";
    }
    highestTokenSeen = request.fencingToken;
    applyWrite(request);
    return "ok";
}

ZooKeeper / etcd-style locks

An alternative that sidesteps TTL-tuning entirely: each client trying to acquire the lock creates an ephemeral sequential node (e.g. /locks/resource/lock-0000000007). Whoever created the lowest-numbered node holds the lock; everyone else watches the node just ahead of them in sequence and wakes up when it disappears. Because the node is ephemeral, it's automatically deleted the moment its owning client's session dies (crash, or the client simply stops heartbeating) — no manual TTL to tune, and no ambiguity about whether the holder is still alive, since liveness is tied directly to an active session with the coordination service itself.

Consensus: how a cluster agrees on one thing

Locks solve "who gets to act." Consensus solves a related but harder problem: how does a cluster of machines, any of which might crash or become unreachable at any moment, agree on a single sequence of facts (who's the leader, what got written and in what order) without a human or a single trusted coordinator making the call? Raft is the algorithm most modern systems reach for, and it's built from two mechanisms worth actually understanding rather than just naming:

Leader election and log replication both reduce to the exact same primitive: a majority of the cluster has to agree before anything becomes official. A minority partition can never independently elect a leader or commit an entry, which is precisely what keeps the cluster from splitting into two disagreeing halves.

Leader election: every election is tagged with a strictly increasing term number. A node that hasn't heard from a leader recently declares itself a candidate, bumps the term, and asks every other node for its vote. A node grants at most one vote per term, first-come-first-served — so a candidate needs votes from a strict majority of the cluster to win. That majority requirement is exactly what prevents two leaders from both existing in the same term: two candidates can't both win a majority of the same fixed set of voters. Log replication: once elected, the leader is the only node that accepts new writes; it appends each one to its own log and pushes it to every follower. An entry only becomes committed — safe to act on, safe to tell the client "yes, this happened" — once a majority of nodes (leader included) have it durably in their log. If the leader crashes right after, whoever gets elected next is guaranteed (by the same majority-vote mechanism) to have that committed entry, because winning an election also requires a majority overlap with whoever had the most up-to-date log.

This is the exact same idea as Kafka's ISR and min.insync.replicas

Raft committing a log entry only once a majority of nodes have it, and Kafka only acknowledging an acks=all write once every in-sync replica (governed by min.insync.replicas) has it, share the same broader quorum intuition — commit only once enough replicas agree — though the mechanisms and exact guarantees aren't identical: Raft's safety specifically depends on majority overlap, while Kafka's ISR is a dynamic set where acks=all only requires current members, not necessarily a majority, to acknowledge. If min.insync.replicas is set below a majority, Kafka's guarantee is weaker than Raft's.

Paxos is the older, foundational algorithm solving this same problem — it's provably correct and Raft's conceptual ancestor, but it's notoriously difficult to explain and implement correctly (Raft was explicitly designed in response, prioritizing understandability while preserving the same guarantees). In an interview, it's enough to know Paxos exists, that Raft is the more approachable and far more commonly implemented descendant of the same idea, and that both are solving "how does a cluster agree on one truth without a single trusted coordinator."

Why does Raft require a strict majority instead of, say, "more than half of the nodes that happen to respond"?
Because a majority of the total configured cluster size is the only threshold that guarantees any two majorities must overlap by at least one node. That overlap is the whole safety argument: whoever wins the next election is guaranteed to overlap with whoever committed the last entry, so the new leader can't "forget" already-committed data. If you instead only required a majority of whoever responds, two disjoint groups of nodes could each independently believe they have a majority during a network partition, and you'd lose the single-truth guarantee entirely.

  • Redis SETNX+TTL fixes the crash case but introduces a new risk: a paused (not crashed) client whose lock silently expires while it still believes it holds it.
  • Fencing tokens fix this properly — a monotonically increasing number checked by the resource itself rejects any write from a stale lock holder.
  • ZooKeeper/etcd ephemeral sequential nodes tie lock ownership directly to an active session, avoiding manual TTL tuning altogether.
  • Raft's leader election (majority votes, term numbers) and log replication (majority acks to commit) both rest on the same quorum idea as Kafka's ISR/min.insync.replicas — a majority of independent copies agreeing is what makes something durable.
  • Paxos is the harder-to-explain ancestor of the same idea; Raft was designed specifically to be more understandable while keeping the same guarantees.

Designing for Failure & Observability

Everything fails eventually — disks, networks, whole datacenters. The systems that stay up aren't the ones that never fail; they're the ones built assuming failure is normal, with enough visibility to know exactly what broke the moment it does.

11 min read

Designing for failure — the system-level view

At the architecture level, resilience comes down to a short list of ideas repeated everywhere in this file: redundancy (no single instance of anything critical — multiple app servers, multiple DB replicas, multiple load balancers), failover (a standby or replica automatically takes over when the primary disappears), and timeouts (never wait forever on a dependency — a slow downstream call should fail fast rather than hang the caller indefinitely and let the failure cascade upstream).

Retries, circuit breakers, and bulkheads exist — full depth is in the Microservices module

Three more resilience patterns are worth knowing exist, even without re-deriving them here: retry with backoff+jitter (retrying a failed call, spacing attempts out to avoid amplifying an outage), the circuit breaker (stop calling a dependency that's clearly failing, so you fail fast instead of piling up timeouts), and the bulkhead pattern (isolate resources per-dependency so one slow/failing dependency can't exhaust the thread pool or connections shared by everything else). The state machines, thresholds, and implementation details behind each of these get a full dedicated treatment in the Microservices module — this file only needs you to recognize them by name and know roughly what problem each solves.

Case Study: Real-Time Chat & Ride-Sharing

Two systems built around the same underlying need — knowing, at any instant, exactly where something is (a connected user, a moving driver) — solved with two different flavors of the same idea: a fast, purpose-built index instead of a linear scan.

11 min read

Real-time chat — why WebSockets replace polling

Polling ("ask the server every 2 seconds if there's a new message") wastes most of its requests on "no, nothing new" and still adds up to 2 seconds of delivery lag in the best case. A persistent WebSocket connection flips the direction: the client opens one long-lived connection, and the server pushes a message down it the instant one arrives — no polling interval, no wasted requests, genuinely real-time delivery.

The presence problem: which server is this user on?

A single chat server can only hold so many concurrent WebSocket connections, so any real deployment needs many chat servers behind a connection-aware layer — which immediately raises a routing question: if user A is connected to chat-server-7 and user B (connected to chat-server-3) sends A a message, how does server 3 know to forward it to server 7? The answer is a shared presence/session registry — typically Redis, mapping userId → serverId — that any chat server can query to find out where to route a message for any recipient, regardless of which physical server the sender or recipient happens to be attached to.

Client AWebSocket → chat server 3
Presence service (Redis)userId → server mapping
Message busroutes to server 7
Client BWebSocket → chat server 7

Every message write also lands in a durable message store (partitioned by conversation, ordered by time) so history survives independent of any single chat server's uptime.

Offline delivery — persist first, push second

If the presence lookup finds no server for the recipient (they're offline), the message is still persisted to the message store as undelivered. Once the recipient reconnects, undelivered messages are flushed to them over the freshly (re)established WebSocket; while they're fully offline (app closed, no connection at all), a push notification (FCM/APNs) is what actually gets their attention, with the full message delivered once they open the app and reconnect.

Ride-sharing — finding nearby drivers fast

"Find every driver within 2km" is a spatial query, and a naive answer (scan every driver's coordinates, compute distance, filter) doesn't scale past a trivial number of drivers. The standard fix — whether it's a Geohash, a Quadtree, or Uber's own H3 hexagonal grid — is the same core idea: encode a location so that spatially nearby points share a common prefix. "Nearest drivers" then stops being a full scan and becomes a prefix lookup: find every driver whose location code shares your prefix, which by construction means they're nearby.

Why doesn't a plain database index (like a B-tree on latitude/longitude) solve "find nearby drivers" efficiently?
A B-tree index sorts by one dimension at a time — indexing latitude and longitude separately means a "nearby" query still has to intersect two large range scans (or scan one dimension fully and filter the other in memory), and neither range naturally captures "physically close" the way a single combined key does. Geohash/Quadtree/H3 solve this by encoding both dimensions into one key that preserves spatial locality — points that are physically close end up with keys that are also close (sharing a prefix), which a normal single-dimension index can't give you.

Drawing boxes before sizing the problem

14 Interview Room

Interview Questions

Sixteen questions pulled from across every chapter in this file, organized by what they're actually testing. Try to answer each one yourself, out loud, before expanding it — the exercise is worth more than the reading.

Read before the interview, not during it
Internals & Why
01
InternalsWhy does consistent hashing beat plain hash(key) % N when the cluster resizes?

With hash(key) % N, N is baked directly into the formula, so changing it — adding or removing even one node — changes the result for almost every key, forcing a near-total data reshuffle. Consistent hashing removes N from the formula entirely by placing nodes and keys on a fixed-size ring instead — a key belongs to whichever node is first found going clockwise, so adding or removing one node only ever disturbs the small arc of keys immediately next to it, roughly 1/N of the total. Virtual nodes (many ring positions per physical node) further smooth out the uneven-arc problem a single point per node would otherwise create. This is why it's the default answer any time "nodes come and go" is part of the problem.

02
InternalsWhy does Raft require a majority of the cluster's total configured nodes to elect a leader, rather than a majority of whichever nodes happen to respond?

Using the total cluster size as the denominator guarantees that any two majorities must overlap by at least one node — that overlap is the entire safety argument, since it means whoever wins the next election is guaranteed to already hold the most recently committed log entry. If a majority of responders were enough instead, a network partition could let two disjoint groups each independently believe they have a majority, electing two leaders in the same term and breaking the single-truth guarantee consensus exists to provide. It's the same underlying idea as Kafka only acknowledging an acks=all write once every in-sync replica has it — durability comes from a quorum of independent copies agreeing, not any one node's say-so.

03
InternalsWhy does a Bloom filter never produce a false negative, but can produce a false positive?

Checking a key hashes it through several hash functions and checks whether all the resulting bits are set — if even one isn't set, the key is guaranteed to have never been inserted, since insertion always sets every one of those bits. A "yes" is less certain, because those same bits are shared across every other key ever inserted — a different key, or combination of keys, could coincidentally have set all the same bits. That asymmetry is exactly what makes it useful: a fast, trustworthy "definitely not here" lets you skip an expensive lookup for the vast majority of cases, at the cost of occasionally still doing the real lookup for a false positive.

04
InternalsWhy does the outbox pattern solve the dual-write problem by adding a database table, instead of trying to make the publish itself atomic with the write?

Atomically committing across two genuinely different systems — a database and a message broker — isn't achievable; there's no shared transaction spanning both. The outbox pattern sidesteps that by converting the publish into data: a row written to an outbox table in the exact same transaction as the state change, so both commit or both roll back together. A separate relay process then does the actual cross-system hop, retrying until it succeeds — turning an unsolvable "atomic commit across two systems" problem into an easy "eventually deliver every row at least once" problem that already has well-understood solutions.

Trade-offs
05
Trade-offYou're designing seat inventory for a ticketing platform where two people must never be sold the same seat. CP or AP?

CP. A wrong answer here — telling two different customers they both successfully bought the same seat — is strictly worse than a request briefly failing or timing out during a partition, so refusing to answer until the system can be sure it's correct is the right default. This sits in the same category as financial ledgers and inventory counts: cases where staying silently wrong is more damaging than staying briefly unavailable. Contrast with a social media like-count or comment feed, where staying up with slightly stale data is clearly the better trade — that's the AP end of the exact same decision.

06
Trade-offPrimary-replica replication is the default almost everywhere. When would you actually take on multi-primary's write-conflict complexity instead?

When the single-writer bottleneck itself becomes the limiting factor — either write throughput has outgrown what one primary can absorb, or the system genuinely needs low-latency local writes in multiple regions and routing every write back to one region's primary would add too much latency. The trade being accepted is real: two primaries can now accept conflicting writes to the same row nearly simultaneously, requiring last-write-wins, vector clocks, or application-level merge logic to reconcile. Most systems avoid this entirely and only reach for it once primary-replica's constraints are demonstrably the actual bottleneck, not a theoretical one.

07
Trade-offFor a messaging-style feed where most users follow a small, roughly even number of accounts, would you lean fan-out-on-write or fan-out-on-read?

Fan-out-on-write, and it's not close. Feed reads happen far more often than posts get written, so precomputing each follower's feed at write time keeps every read fast and cheap, while the write cost per post stays small and manageable when follower counts are modest and even. Fan-out-on-read only starts winning at the extreme tail — accounts with such enormous follower counts that pushing to everyone at once becomes a write storm — which is exactly why real systems use fan-out-on-write as the default and carve out fan-out-on-read as a per-account exception, not a global choice.

08
Trade-offL7 load balancing can do almost everything L4 can, plus more. When would you actually choose raw L4?

When raw speed and protocol flexibility matter more than content-based routing — L4 never buffers or parses the payload, so it adds negligible latency and works identically for HTTP, raw TCP, gRPC, or anything else riding over TCP/UDP. That makes it the right choice for non-HTTP traffic, or as the outer entry point in front of an L7 layer, where every microsecond and CPU cycle at that outermost tier counts. For a typical HTTP API where path- or header-based routing is valuable, L7 is still the right default — L4 wins specifically when that value doesn't apply.

Traps
09
TrapA candidate adds read replicas to scale reads, then calls "the user sees stale data right after writing" a load-balancer bug. What did they get wrong?

This isn't a load-balancer problem at all — it's replica lag, the normal, expected delay between a write landing on the primary and that write propagating to replicas. Routing the very next read to a different, not-yet-caught-up replica will surface the old value no matter how the load balancer happens to pick which replica to hit. The actual fixes are reading your own writes from the primary (or a replica known to be caught up) right after a write, or designing the UI to tolerate a brief staleness window — not touching load-balancing logic, which was never the source of the problem.

10
TrapA candidate says a Redis lock with a TTL is now completely safe from race conditions. What's wrong with that claim?

A TTL only fixes one failure mode — a holder that crashed and never released the lock. It does nothing for a holder that merely paused (a long GC pause, a slow network call) past the TTL: the lock silently expires, a second client acquires it and starts working, and the first client eventually wakes up with no idea time has passed, still believing it holds the lock, and can write to the resource anyway. Now two clients have modified the same resource — exactly what the lock was supposed to prevent. The real fix is a fencing token, checked by the protected resource itself, which rejects any write carrying a token older than the highest one already seen.

11
TrapA candidate designs a rate limiter with a fixed window counter that resets every 60 seconds and calls the design complete. What did they miss?

A fixed window resets sharply at a boundary rather than sliding continuously, so a client can send a full window's worth of requests in the last instant of one window and another full window's worth in the first instant of the next — up to double the intended rate compressed into a much shorter real time span. The fix is either a sliding window (log or counter) that has no hard reset point, or token bucket, which enforces a true average rate over time regardless of where a burst happens to land relative to any window boundary.

12
TrapA candidate proposes caching a logged-in user's personalized dashboard at the CDN edge to cut latency. What's wrong with this plan?

A CDN's edge cache is shared across every user hitting the same URL — its entire value proposition depends on the response being the same (or one of a small set of variants) for everyone requesting it. A personalized dashboard is, by definition, different per user, so caching it at a shared edge either risks serving one user's private data to another or forces the CDN to effectively bypass its cache per user, gaining nothing. CDNs help static or rarely-changing, non-personalized content; personalized dynamic data needs a different layer — an app-local or distributed cache keyed per user, not the edge.

Scenario
13
ScenarioWalk through what happens when an account with 50 million followers posts, in a system that only does fan-out-on-write. Where exactly does it break, and what's the fix?

At post time, the system tries to push the new post into 50 million individual precomputed feed caches essentially all at once — a write storm at a scale fan-out-on-write was never built to absorb, likely saturating whatever store holds those feed caches and delaying the post's visibility for everyone. The fix is a per-account threshold: past some follower count, skip write-time fan-out entirely for that account, and instead merge its posts in at read time — fetched live and blended alongside each follower's normal precomputed feed. This makes fan-out strategy a per-account decision based on follower count, not a single global architectural choice.

14
ScenarioIn the last 10 minutes of an interview, you're asked to add "read receipts" to the chat design (WebSockets + presence registry + durable message store). Sketch the minimum viable approach.

Reuse the exact delivery path already built: when a client renders a received message, it sends a small "read" event back over its own WebSocket connection, tagged with the message ID and reader's userId. That event is looked up in the same presence registry used for normal messages to find the sender's current server — or queued for later delivery if the sender is offline, exactly like a regular message — and the sender's client updates the message's status on receipt. The read state itself is persisted alongside the message in the durable message store, so it survives reconnects. No new infrastructure — just a second, smaller message type riding the same rails as everything else.

15
ScenarioDriver-location writes happen roughly 100x more often than ride requests. Where would you focus your scaling effort first, and why?

The location-write path, since it dominates traffic by a wide margin and any inefficiency there is multiplied across every driver, every few seconds, continuously — while ride requests are comparatively rare, bursty events. That means the geo-index needs to be write-optimized (in-memory, partitioned by region) rather than optimized around the matching service's read pattern, since the read side only ever touches a small, geographically-scoped slice of the index per request. Optimizing ride-matching logic first, while leaving the far higher-volume location-write path as an afterthought, would be solving the smaller of the two problems.

16
ScenarioTwo customers try to book the last seat on a flight at the exact same instant. Walk through how you'd prevent a double-booking end to end.

The seat-selection step needs mutual exclusion across whichever app servers both requests land on — a distributed lock (or a single-row optimistic version check) scoped to that specific seat, not the whole flight. With a lock, pair it with a fencing token so a request that stalls past any TTL can't apply a stale write after losing the lock to someone else; with optimistic versioning instead, both requests read the seat's current version, and only the write that still matches that version on commit succeeds, while the other is rejected and retried against the now-updated state. Either way, this is a CP-leaning decision for this one seat: refusing to let both writes succeed is worth the brief cost of one customer seeing "sorry, just booked."

1. Narrate the framework step you're on ("I'll do a quick estimation pass before I draw anything") — it signals structure even before the content is good.
2. When you name a technique (consistent hashing, outbox, fencing token), immediately say what problem it solves in one clause — don't just drop the term and move on.
3. Volunteer trade-offs unprompted, especially CP vs AP and cost/complexity — interviewers give real credit for stating what you gave up, not just what you built.
4. If you don't know something, say what you'd check or who you'd ask rather than guessing confidently — a wrong confident answer reads worse than an honest "I'd verify this against X."

Centralized rate-limit countersA distributed rate limiter needs one shared counter (Redis, atomic ops) — per-node in-memory counters undercount the true rate.
Consistent hashingNodes and keys on a ring; adding/removing a node moves only ~1/N of keys, unlike hash(key)%N which remaps almost everything. Virtual nodes even out load.
Snowflake ID64-bit ID (41-bit timestamp + 10-bit machine ID + 12-bit sequence): unique, roughly time-ordered, zero coordination.
Bloom filterProbabilistic "definitely not present" / "maybe present" check — no false negatives, occasional false positives; kills cache penetration cheaply.
Fencing tokenA monotonically increasing number checked by the protected resource itself, rejecting writes from a stale, previously-expired lock holder.
ZooKeeper/etcd ephemeral sequential nodeLock ownership tied to an active session — automatically released when the holder's session dies, no TTL tuning needed.
Raft consensusLeader election (majority vote per term) and log replication (majority ack to commit) both rest on quorum overlap; Paxos is its harder-to-explain ancestor.
Three pillars of observabilityMetrics ("is it healthy"), logs ("what happened at time T"), traces ("where did the time go across services").
Correlation IDOne ID propagated through metrics, logs, and traces for a request, letting you pivot between all three during an incident.
SLI / SLO / SLA / error budgetMeasured signal / internal target / contractual promise / (1 − SLO) — the spendable amount of allowed failure before missing the objective.
Four golden signalsLatency, traffic, errors, saturation — the minimum viable dashboard for any service.
Symptom vs cause alertingAlert on user-facing symptoms (error rate) rather than every possible cause (CPU) to avoid noisy, ignorable pages.
Resilience patterns (named)Retry with backoff+jitter, circuit breaker, bulkhead isolation — recognize them by name; full depth lives in the Microservices module.
Base62 short codes & 301 vs 302A 7-char Base62 code holds ~3.5 trillion values; 301 is browser-cached (fewer hits, no analytics), 302 hits the origin every time (full analytics).
Fan-out on write vs read (celebrity problem)Push at post time (fast reads, breaks at celebrity scale) vs pull at read time — real systems hybridize by follower-count threshold.
WebSocket vs pollingA persistent connection lets the server push instantly, eliminating wasted "nothing new" requests and polling-interval lag.
Presence registryA shared mapping (e.g. Redis: userId → server) letting any server route a message to any recipient regardless of connection location.
Geohash / Quadtree / H3Encode location so spatially nearby points share a prefix, turning "find nearby" into a fast prefix lookup instead of a full scan.
HLD interview frameworkRequirements → estimation → API → data model → architecture → deep dive → scale → trade-offs.
Idempotency keys & optimistic versioningA client-supplied key lets a retried request safely no-op; a version check on write rejects a stale concurrent update without holding a lock.
JWT + OAuth2A signed, stateless token plus a delegated-authorization protocol — the standard authn/authz pair, usually checked once at the gateway.
Trie & inverted indexTrie: prefix-based autocomplete lookup. Inverted index: term → document-list mapping that powers full-text search.
