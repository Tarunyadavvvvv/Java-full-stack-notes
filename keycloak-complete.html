01 Foundations

The Login System You Stop Reinventing

Every application needs a login screen, a password store, and a way to handle MFA — and building all three from scratch is how security incidents happen. This chapter frames Keycloak as the alternative: a dedicated, audited identity layer that apps plug into instead of owning that risk themselves.

6 min read Beginner-friendly

Keycloak is an open-source Identity and Access Management (IAM) system — originally built at Red Hat, now a CNCF project. Its job is to sit in front of your applications and services and handle authentication and authorization on their behalf, so those apps can externalize identity rather than writing their own login logic.

This chapter stays at the product level: what problem Keycloak exists to solve, and how it compares to buying identity as a managed service. The protocol mechanics underneath it — OAuth2, OIDC, JWTs — are covered in depth in the companion Security & Auth module; this module takes those concepts as given and applies them to one concrete, production-grade product.

The problem: everyone reinvents login

Without a shared identity system, every app on a team's roster ends up building the same thing badly: its own password hashing, its own session handling, its own "forgot password" flow, its own half-finished MFA. The logic is duplicated across codebases, drifts out of sync, and each copy is a separate place for a security mistake to hide.

Without a shared IdP

  • App 1, App 2 and App 3 each store and hash their own passwords
  • Each team re-implements session handling, password reset and MFA from scratch
  • Logging into App 1 does nothing for App 2 — no SSO, re-enter credentials everywhere
  • The weakest app's auth code becomes the whole organization's weak point

With Keycloak in front

  • One realm holds every user; one login screen issues one token
  • Signing into App 1 quietly grants access to App 2 and App 3 — true SSO
  • MFA, password policy and social login are configured once, enforced everywhere
  • LDAP/AD and external identity providers federate in without any app touching that code
App 1 / App 2 / App 3each redirects to sign-in instead of rendering its own
KeycloakSSO, token issuance, MFA enforcement
LDAP / Social / DBthe actual identity sources it federates

Keycloak sits in the middle exactly once, so every app behind it inherits SSO, MFA and federation without writing a line of auth code.

What's actually in the box

"IAM system" covers a lot of ground. In practice Keycloak's feature set splits into what users experience when signing in, and what operators use to run the thing day to day.

Protocols & sign-in

  • OAuth2 / OIDC for modern app and API authentication
  • SAML 2.0 for integrating with legacy enterprise SSO
  • Social login (Google, GitHub, etc.) without wiring each provider's SDK per app
  • MFA and WebAuthn/passkeys as configurable step-up options
  • Customizable login themes so the flow doesn't look bolted-on

Operations & admin

  • LDAP / Active Directory federation for existing corporate directories
  • An admin console for managing realms, clients, users and roles by hand
  • Fine-grained authorization down to resource and permission level
  • An admin REST API for scripting provisioning, rotation and automation

The vocabulary you need first

A handful of IAM terms recur constantly once Keycloak enters the picture. Nailing these down now saves confusion later.

TermWhat it actually means
Authentication (AuthN)Verifying who you are — the login step itself
Authorization (AuthZ)Deciding what you're allowed to do, once you're identified
Single Sign-On (SSO)Log in once, get access to many apps without re-entering credentials

Why not just build it yourself?

Externalize the risk, not just the code

Login, password storage, token issuance and MFA are high-stakes, well-studied problems. Keycloak ships standards-compliant SSO, token handling, MFA and social/federated login as tested defaults, so a team gets this for free instead of spending months building — and later re-hardening — it themselves. The point isn't saving typing; it's moving a high-risk concern out of your codebase and into a dedicated, scrutinized system.

Keycloak vs Okta/Auth0

Keycloak isn't the only option — it's one end of a build-vs-host spectrum, with managed IDaaS platforms like Okta and Auth0 at the other end.

Keycloak (self-hosted, open-source)

  • Full control over the deployment; data stays in-house
  • No per-user licensing cost — you pay in infrastructure and ops time instead
  • Deep customization: themes, extensions, custom flows
  • Strong fit for cost-sensitive, on-prem or regulated environments

Okta / Auth0 (managed SaaS)

  • Someone else runs, patches and scales the identity service
  • Polished UX and integrations available out of the box
  • Ongoing per-user pricing instead of infrastructure cost
  • Strong fit when minimizing operational burden outweighs owning the stack

Neither is universally correct — it's the same build-vs-buy trade-off as any other piece of infrastructure. Data-residency and regulatory requirements often settle it in Keycloak's favor; a small team without spare ops capacity often leans toward the SaaS option instead.

In IAM terms, when an app redirects users to Keycloak to sign in and trusts the result, what role is that app playing?
The app relies on Keycloak's authentication decision instead of performing it itself — that's exactly the Service Provider / Relying Party role. Keycloak is the Identity Provider.
What's the core argument for centralizing login behind Keycloak instead of each app building its own?
Centralizing auth isn't a protocol requirement — it's a risk-and-effort trade-off. One audited system replaces N homegrown, duplicated, inconsistent implementations of the same high-stakes logic.
Quick summary
  • Keycloak is an open-source IAM system (Red Hat origin, now CNCF) that centralizes authentication and authorization so apps don't build their own login.
  • The problem it solves is duplication: without it, every app reimplements password storage, sessions, MFA and reset flows — inconsistently and insecurely.
  • Its feature set spans sign-in protocols (OAuth2/OIDC, SAML 2.0, social login, WebAuthn/passkeys) and operations (LDAP/AD federation, admin console, fine-grained authorization, admin REST API).
  • Core vocabulary: AuthN (who you are), AuthZ (what you can do), SSO (log in once), IdP (Keycloak's role), SP/RP (the app's role), federation (trusting external identity sources).
  • Keycloak (self-hosted) trades ops effort for control and cost savings; Okta/Auth0 (managed SaaS) trade cost for reduced operational burden — the right choice depends on regulatory, cost and staffing constraints.
02 Foundations

Core Concepts

Before touching a single screen in the admin console, you need the vocabulary straight — realm, client, role, group mean specific, non-interchangeable things in Keycloak, and mixing them up is where most misconfigurations start.

7 min read Beginner-friendly

The object model, nested

A single Keycloak server can run many completely independent tenants at once. That isolation happens one level down, at the realm, and everything else you configure — clients, users, roles — lives inside one realm and is invisible to every other realm.

Keycloak Server

One running instance, many tenants hosted side by side.

Realm — e.g. myapp

A sealed security domain with its own users, clients, roles, and signing keys.

Client — e.g. web-app

One application or API registered to authenticate through this realm.

Sitting alongside clients inside that same realm are Users (people and service accounts), Roles (realm-wide or client-specific permissions), Groups (collections of users with shared roles), Identity Providers (brokered logins to Google, an LDAP directory, or a SAML IdP), and the supporting machinery — client scopes, protocol mappers, authentication flows, and sessions. All of it is scoped to the realm; none of it leaks across the boundary.

TermWhat it actually is
RealmAn isolated security domain — a tenant. Users, clients, and roles in one realm are invisible to another. The built-in master realm is reserved for administering Keycloak itself, not for your application's users.
ClientAn app or service that wants Keycloak to handle authentication and authorization for it. Every application you protect is registered as its own client.
UserAn entity that can log in — a human, or a service account acting on behalf of a client.
RoleA named permission grouping, defined at realm level or scoped to one client. Roles can be composite, bundling other roles together.
GroupA set of users that share roles and attributes. Groups can be nested to mirror an org chart.
Client scopeA reusable bundle of protocol mappers and role scope that several clients can share instead of redefining.
Protocol mapperDefines which piece of user data becomes which claim in the issued token.
Identity provider (broker)An external identity source Keycloak delegates the actual login to, then wraps in its own tokens.

Public vs confidential clients

Every client falls into one of two trust categories, and the category dictates which OAuth2 flow you're allowed to use safely — the same PKCE and Authorization Code mechanics covered in the Security & Auth module apply here, Keycloak just gives you a client setting that enforces the right one.

AttributeConfidentialPublic
Can it keep a secret?YesNo
Typical exampleServer-side web app, backend serviceSingle-page app, mobile app
Client authenticationclient_id + secret (or mTLS / signed JWT)client_id only, protected by PKCE
Recommended flowAuthorization CodeAuthorization Code + PKCE
Bearer-only is not a login client

The legacy "bearer-only" client type never initiates a login — it only validates tokens handed to it, which is exactly what a plain API or resource server needs. Newer Keycloak versions no longer expose it as a distinct client type; you get the same behavior through client settings (no standard flows enabled, token validation only). Don't wire it up expecting a login screen — it doesn't have one.

Why are realms important?

Because the isolation is total: a realm has its own users, clients, roles, signing keys, and configuration, with zero visibility into any other realm. That makes realms the right tool for multi-tenancy or strict environment separation — one realm per customer, or one per environment, when tenants must never see each other's data even by accident. If you're instead running one organization's many internal apps, you usually want a single realm with groups doing the separating, not a realm per app — splitting too early just multiplies admin overhead for no isolation benefit.

Roles come in three flavors

A role is just a name until you decide its scope. That scope — and whether it bundles other roles — is the whole design decision.

Realm role

  • Global within the realm — visible to every client in it
  • Good for broad categories, e.g. admin, user
  • Assign it once, it applies wherever the realm's clients check for it

Client role

  • Scoped to a single client's own permission set
  • Fine-grained, e.g. orders-service:manage-orders
  • Keeps one app's internal permissions out of every other app's namespace

Composite role

  • A role that bundles other roles underneath it
  • E.g. super-admin composed of admin + audit + billing
  • One assignment grants everything the bundle contains

Groups vs roles — don't conflate them

Roles and groups solve different problems and get confused constantly because both end up on a user's token. A role answers "what can this identity do." A group answers "who is this identity, organizationally" — and happens to be a convenient place to hang roles off of.

AttributeRoleGroup
RepresentsA permissionA collection of users
HierarchyVia composite rolesVia nested subgroups
Best used forDefining what an identity can doMirroring org structure, bulk-assigning roles and attributes
Assign roles to groups, not to people

The scalable pattern is: attach roles and attributes to a group, then manage membership by moving users in and out of it. When someone changes teams, you move one group membership instead of hunting down and re-assigning a dozen individual role grants.

Attributes, required actions, and machine identities

Attributes & required actions

  • Attributes are custom key-value data on a user, e.g. department, tenant_id
  • They can be mapped into token claims via protocol mappers
  • Required actions are tasks forced at next login — verify email, update password, configure OTP

Service accounts

  • A confidential client can have its own dedicated user identity
  • Used for machine-to-machine calls via the client credentials flow
  • No human ever logs in as it — the client authenticates as itself

Client scopes and the audience claim

A client scope is a named, reusable bundle of protocol mappers and role scope. Default scopes attach to every token a client requests automatically; optional scopes only get added when explicitly requested via the scope parameter. This is what lets several clients share the same claim definitions instead of each one redefining them from scratch.

Client requests a tokendefault scopes attach automatically
Optional scopes addedvia the scope parameter
Protocol mappers runshape user data into claims
Resource server checks audrejects tokens not meant for it

The audience mapper is what stops a token issued for one API from being replayed against another — the receiving service must actually check aud, not just trust that the token is valid.

When would you actually use a composite role?

Whenever several roles are consistently granted as a set. A "manager" role that always implies view-reports, approve-leave, and edit-team is a good candidate for a composite — one assignment grants all three, and admins stop having to remember the full list every time they onboard a new manager.

Which object gives you total isolation of users, clients, and roles from every other tenant?
Realms are the isolation boundary — everything inside one (users, clients, roles, keys) is invisible to every other realm.
Fifty users all need the same three roles. What's the maintainable way to grant them?
Assigning roles to a group and managing membership means a team change is one group edit, not fifty individual role reassignments.
Quick summary
  • The object hierarchy nests: Keycloak Server → Realm (isolated tenant) → Clients, Users, Roles, Groups, Identity Providers, Client Scopes.
  • Confidential clients can hold a secret and use Authorization Code; public clients (SPAs, mobile) can't, so they rely on PKCE instead.
  • Roles say what an identity can do (realm, client, or composite); groups say who the identity is organizationally — assign roles to groups, not to individual users.
  • Client scopes bundle protocol mappers so several clients share claim definitions, and the resource server must validate the aud claim itself.
03 Foundations

Architecture & Internals

Keycloak looks like a single login box from the outside, but underneath it's a layered server with its own cache, its own extension points, and its own rules about where session state actually lives. Knowing the layers is what lets you reason about scaling, failover, and "why did my session vanish."

7 min readIntermediate

Every Keycloak deployment is the same stack wearing different clothes: a UI layer for humans, a protocol layer for tokens and admin calls, an SPI layer for customisation, and a runtime underneath all of it. The request path below shows how a login actually travels through those layers before it ever touches a database or an external identity provider.

UI layerAdmin Console, Account Console, login themes (Freemarker)
Protocol & API layerOIDC/SAML endpoints, Token Service, Admin REST API
Extension layer (SPIs)Authentication, User Storage, Event and Mapper SPIs
External systemsDatabase, LDAP/AD federation, external IdPs (Google, SAML partners)

All four layers run inside the same Quarkus process (WildFly on legacy installs) — the SPI layer is the seam that lets you swap in a different user store or authentication flow without touching anything above it.

Key internal components

Five pieces do almost all of the work. Knowing which one owns which job stops a lot of guesswork during troubleshooting.

ComponentRole
RuntimeQuarkus-based since Keycloak 17+; previously ran on WildFly/JBoss.
DatabasePersists realms, clients, users, roles, and offline sessions. PostgreSQL is the recommended production choice.
Infinispan cacheIn-memory caching of sessions, auth state, and realm config, distributed across cluster nodes.
SPIsService Provider Interfaces — extension points for custom authentication, user storage, and mappers.
ThemesCustomisable login, account, and admin UI, built with Freemarker templates and CSS.

Where sessions actually live

User sessions and client sessions are not primarily a database concern — they live in Infinispan, an in-memory cache, precisely because sessions are read and touched constantly and a database round trip on every request would be slow. The database only re-enters the picture for offline sessions, which need to outlive a restart.

Login succeedssession created for the authenticated user
Written to Infinispanfast, in-memory, no disk round trip
Replicated cluster-wideany node can now serve the next request

This is the mechanism that makes horizontal scaling possible: because Infinispan distributes session data across every node, a request doesn't have to land back on the node that created the session.

Offline sessions are the exception

Offline sessions back offline refresh tokens and are persisted to the database, not just cached — that's what lets them survive a Keycloak restart for genuinely offline access.

Token signing keys and discovery

Each realm has its own signing keys (RSA or EC) and its own key rotation schedule. Resource servers never have to trust those keys blindly — they can discover and verify them through two well-known endpoints:

GET /realms/{realm}/.well-known/openid-configurationthis realm's own metadata document
Returns endpoint mapauthorization_endpoint, token_endpoint, jwks_uri…
GET /realms/{realm}/protocol/openid-connect/certsthe JWKS — this realm's public signing keys
Signature verified locallyno call back to Keycloak needed per request

A resource server fetches the JWKS once, caches it, and from then on verifies tokens with pure cryptography — Keycloak doesn't need to be in the hot path of every API call.

The full mechanics of key rotation (the kid header, when to refetch JWKS) and the trade-off between this local validation and calling the introspection endpoint are covered in depth in the companion Security & Auth module's OpenID Connect & JWT chapter. This is the Keycloak-concrete version of that same theory — the endpoints above are real, per-realm URLs, not abstractions.

Don't build in the master realm

The master realm exists to administer Keycloak itself — it is not a template for your application. Always create a dedicated realm for your app's users and clients; mixing them into master conflates who manages the server with who logs into your product.

Scaling and high availability

How does Keycloak scale and stay highly available? Run multiple stateless Keycloak nodes behind a load balancer, all sharing one database and one distributed Infinispan cache so session state is available cluster-wide rather than pinned to a single node. Sticky sessions or distributed caching keep routing sane, database replicas absorb read load, and health endpoints let orchestrators like Kubernetes make restart and scaling decisions automatically.

Does the Quarkus-vs-WildFly runtime choice actually matter day to day?

Mostly it's transparent to how you use Keycloak — realms, clients, and the REST API behave the same either way. The practical difference shows up in startup time, configuration style, and packaging: Quarkus (the default since Keycloak 17+) is the actively developed target, so new deployments should assume Quarkus rather than the legacy WildFly distribution.

What is Infinispan primarily responsible for in Keycloak's architecture?
Infinispan is the fast in-memory cache for sessions, auth state, and realm config, replicated across cluster nodes. Persistent storage — realms, users, offline sessions — is the database's job.
Why shouldn't application users and clients live in the master realm?
Master is the control-plane realm for managing the Keycloak server. Application users and clients belong in their own dedicated realm, keeping "who runs Keycloak" separate from "who logs into your app."
Quick summary
  • Keycloak layers UI, protocol/API, and SPI extension points on top of a Quarkus (or legacy WildFly) runtime, connecting out to a database, LDAP/AD, and external IdPs.
  • Sessions live in the Infinispan cache for speed and are replicated cluster-wide, so any node can serve any request — offline sessions are the one type persisted to the database to survive restarts.
  • Each realm signs tokens with its own keys; resource servers discover endpoints via /realms/{realm}/.well-known/openid-configuration and fetch public keys via the JWKS at /realms/{realm}/protocol/openid-connect/certs to verify signatures locally.
  • Never put application users or clients in the master realm — it's reserved for managing Keycloak itself.
  • High availability comes from stateless nodes behind a load balancer, sharing one database and one distributed cache, with health endpoints supporting orchestration.
04 Protocols & Flows

OAuth2 & OIDC in Keycloak

Keycloak speaks OAuth2 fluently, but OAuth2 alone can't tell you who logged in — that's what OIDC bolts on top. Get the two straight, and every login screen, token, and grant-type choice in Keycloak stops looking like magic.

9 min readAdvanced

Keycloak is technically an OAuth2 Authorization Server first, an OpenID Connect Provider second. That order matters: OIDC isn't a separate protocol living next to OAuth2, it's a thin identity layer standardised on top of it. Almost every confusing default in Keycloak — why a token response includes an id_token, why there's a /userinfo endpoint, why openid is a scope you have to request — falls out of that one fact.

OAuth2 vs OIDC: two different questions

OAuth2 was built to answer "what is this app allowed to access?" — delegated authorization, nothing more. OIDC was layered on to answer a question OAuth2 was never designed for: "who is the person sitting at the keyboard?"

AspectOAuth2OIDC
PurposeAuthorization — delegated accessAuthentication — identity, built on OAuth2
Answers"What can this app access?""Who is the user?"
Key outputAccess tokenID token (plus an access token)
AnalogyA valet key — limited access, no identity checkA passport — proves who you are
OIDC = OAuth2 + an identity layer

It adds the ID token (a JWT that proves who logged in and when), the /userinfo endpoint (fetch profile claims with an access token), and standard scopes like openid, profile, and email. Keycloak's default protocol is OIDC, so unless you specifically configure a client otherwise, this identity layer is already there — not something bolted on later.

The four roles, in Keycloak's terms

Every OAuth2/OIDC exchange has the same four actors. Mapping them onto Keycloak concretely removes most of the ambiguity in the spec's abstract language.

RoleWho it is in Keycloak
Resource OwnerThe user — the human granting access to their own data
ClientThe application requesting access (your SPA, mobile app, backend service)
Authorization ServerKeycloak itself — it authenticates the owner and issues tokens
Resource ServerThe API holding the protected resources the client wants to call

The OIDC endpoints you'll actually use

Everything a client does against Keycloak funnels through a small, fixed set of endpoints. Knowing which one does what is most of the battle when debugging a broken flow.

EndpointPurpose
/authAuthorization endpoint — login and consent happen here
/tokenExchange an authorization code or credentials for tokens
/userinfoFetch user claims using a valid access token
/logoutEnd the session — supports single logout (SLO)
/certs (JWKS)Public keys used to verify a token's signature
/token/introspectAsk Keycloak directly whether a token is valid — needed for opaque tokens
"Is OAuth2 for authentication?"

No. OAuth2 is for authorization — granting an app access to resources. Treating a bare access token as proof of identity is one of the most common mistakes teams make with it. OIDC exists precisely to fix this, by adding the ID token as a dedicated authentication artifact.

The Authorization Code flow (with PKCE)

This is the standard flow — the one Keycloak expects for essentially every user-facing login, whether the client is a traditional web app, a single-page app, or a mobile client. The general mechanics of why it's secure are covered in the Security & Auth module's "OAuth 2.0 Deep Dive" chapter; here's how it maps onto Keycloak's actual endpoints.

Redirect to Keycloak/auth?response_type=code&client_id=...&redirect_uri=...&scope=openid
User authenticatesLogin form is rendered and handled entirely by Keycloak
Redirect back with a code?code=ABC — a short-lived authorization code, not a token
App exchanges the codeBack-channel POST to /token: code + client_secret (or PKCE verifier)
Tokens issuedaccess_token + id_token + refresh_token

The authorization code itself is worthless without the follow-up secret or PKCE verifier — that's what makes it safe to expose in a browser redirect, unlike a token.

PKCE, in one line

The client sends a hashed code_challenge up front, then reveals the original code_verifier at token exchange. If an attacker intercepts the authorization code mid-redirect, they still can't redeem it without the verifier. It's mandatory for public clients — SPAs and mobile apps — that have no secret to keep secret in the first place.

Choosing a grant type

Keycloak supports several grant types, but in practice only a handful are worth reaching for. The rest exist mostly to explain what not to do.

Grant typeBest forVerdict

Refresh TokenGetting a new access token without re-loginRecommended

Machine-to-machine: Client Credentials

Not every call to Keycloak has a human behind it. When Service A needs to call Service B with no user in the loop, there's no login to redirect to — the service authenticates as itself.

Service A requests a tokenPOST /realms/myrealm/protocol/openid-connect/token
Sends its own credentialsgrant_type=client_credentials, client_id=orders-service, client_secret=xxxxx
Access token returnedNo user context — the service itself is the identity

There's no id_token here, deliberately — there's no user to authenticate. The token simply says "orders-service is calling," which is all Service B needs to authorize the request.

Why Implicit and ROPC are on the way out

Implicit returns tokens directly in the browser URL — they end up in history and referrer headers, and the flow can't issue refresh tokens safely. ROPC has the app collect the raw username and password itself, which quietly defeats SSO, MFA, and every centralised control Keycloak exists to provide. Authorization Code + PKCE replaces both, with no real downside. The full reasoning behind these deprecations is in the Security & Auth module's OAuth 2.0 deep dive.

Which flow for a React SPA?

  • Authorization Code flow with PKCE
  • Configured as a public client in Keycloak — no client secret
  • PKCE secures the code exchange without a secret the browser can't keep safe anyway

Service A calling Service B, no user?

  • Use the Client Credentials grant
  • Service A authenticates with its own client_id + secret (or service account)
  • The resulting access token represents the service, not a person
A single-page app needs to log users in. Which grant type and client type should it use?
An SPA can't keep a client secret, so it must be a public client — and PKCE is what secures the authorization code exchange in place of that secret. Implicit is deprecated precisely because it skips this protection.
What does an ID token prove that an access token alone does not?
Access tokens are about authorization — what the app can access. The ID token is the piece OIDC adds specifically to answer "who logged in," which is why treating a bare access token as identity proof is a common mistake.
Quick summary
  • OAuth2 answers "what can this app access?"; OIDC layers identity on top to answer "who is the user?" — Keycloak defaults to OIDC.
  • The four roles map directly: user = Resource Owner, app = Client, Keycloak = Authorization Server, API = Resource Server.
  • Six endpoints cover almost everything: /auth, /token, /userinfo, /logout, /certs, and /token/introspect.
  • Authorization Code + PKCE is the default choice for any user-facing login, web or SPA; Client Credentials is the default for service-to-service calls with no user present.
  • Implicit and ROPC are deprecated/discouraged — both exist only for legacy compatibility, not new integrations.
05 Protocols & Flows

Tokens in Keycloak

A single login hands you three different JWTs, not one — and mixing them up is the most common Keycloak integration bug. This chapter is about telling them apart and reading the Keycloak-specific claims correctly.

8 min read Advanced

Every successful authentication against Keycloak produces three tokens, and each one answers a different question. Treating them as interchangeable — because they're all JWTs, all signed by the same realm — is exactly how authorization bugs sneak into production.

TokenAnswersAudienceLifespan
Access tokenAm I allowed to call this API? (sent as a Bearer token)Resource serverShort, ~5 min
ID tokenWho just logged in? (OIDC identity)The client appShort
Refresh tokenCan I get a new access token without re-login?Authorization serverLonger, session-length
Access token and ID token are not interchangeable

The ID token authenticates the user to the client application — it should never be sent to an API. The access token authorizes calls to resource servers. An API that validates an ID token instead of an access token is validating the wrong claim set entirely; its aud names the client, not the service.

What's inside the JWT — the Keycloak-specific parts

The general shape of a JWT — three Base64URL parts, header/payload/signature, and how to verify one — is covered in the Security & Auth module's OpenID Connect & JWT chapter, along with the full validation checklist and key-rotation mechanics. scope, azpGranted OAuth2 scopes; authorized party (the client that requested the token)

The realm_access / resource_access gotcha

Keycloak splits roles into two separate claims, and this is where authorization checks quietly go wrong. realm_access.roles lists roles that apply across the whole realm — every client sees the same list. resource_access is keyed by client ID, and each client only sees its own roles nested underneath. A role called admin assigned at the client level for billing-service will never show up in realm_access.roles — a resource server checking the wrong claim will silently deny (or worse, silently allow) access based on a role that was never actually granted for it.

Know which claim you're supposed to be reading

Before writing an authorization check against a Keycloak token, confirm whether the role was assigned as a realm role or a client role in the admin console — that decides whether your code should look under realm_access.roles or resource_access.<your-client-id>.roles.

Validating the access token

The general checklist — signature, expiry, issuer, audience — is the same one from the Security & Auth module. Keycloak gives resource servers two ways to run it:

MethodHow it worksWhen to use it
Local (JWT) validationVerify the signature offline using Keycloak's public key (JWKS)Fast, no network call — the most common choice
IntrospectionCall Keycloak's /introspect endpoint on every requestNeeded for opaque tokens, or when live revocation status matters

Local validation is fast because it trades away real-time truth: if a session is revoked mid-lifespan, the API won't know until the access token naturally expires.

Introspection buys real-time revocation truth at the cost of a network call per request — worth it for opaque tokens or high-security paths, overkill for everything else.

Refresh tokens: renewing without re-login

Short access-token lifespans only work because clients don't need the user to log in again every five minutes. When the access token expires, the client sends the refresh token to Keycloak's token endpoint with grant_type=refresh_token and gets a fresh access token back — silently, in the background.

Access token expires~5 min lifespan runs out
Client POSTs to /tokengrant_type=refresh_token, no user prompt
New access + rotated refresh token issuedold refresh token invalidated immediately

Refresh token rotation means each renewal invalidates the previous refresh token — so if a stolen refresh token ever gets reused after the legitimate client already rotated it, that reuse itself is the theft signal.

For background jobs and offline processing that can't rely on a live user session, Keycloak supports offline tokens — long-lived refresh tokens requested with the offline_access scope, which survive Keycloak restarts instead of expiring with the session.

Three pitfalls that show up together

Issuing long-lived access tokens makes revocation nearly impossible — keep them short and lean on refresh tokens instead. Skipping aud validation means a token minted for one service can be replayed against another. And storing tokens in localStorage exposes them to XSS; prefer secure HttpOnly cookies or an in-memory token held by a backend-for-frontend.

How do you revoke a JWT before it expires?

You don't, not directly — JWTs are stateless, so there's no "delete this token" operation. Instead: keep access tokens short-lived so any leak has a small blast radius; revoke the refresh token or end the session in Keycloak, which stops new access tokens from being minted; use introspection or a revocation list where immediate effect matters; or bump the realm's "not-before" policy to invalidate every token issued before that moment.

A resource server needs to check if the caller has the "admin" role for that specific client, not realm-wide. Which claim should it read?
realm_access.roles holds roles shared across the whole realm. Client-specific roles live nested under resource_access, keyed by client ID — checking the wrong one silently breaks authorization.
A client mistakenly sends its ID token as the Bearer token to a microservice. What should a correctly implemented API do?
ID tokens authenticate the user to the client application; their aud claim reflects that. A resource server validating audience correctly will reject an ID token outright, even though it's a legitimately signed JWT.
Quick summary
  • Keycloak issues three tokens per login — access (for APIs), ID (for the client app), and refresh (for silent renewal) — each with its own audience and lifespan.
  • realm_access.roles carries realm-wide roles; resource_access.<client>.roles carries client-specific ones — reading the wrong claim is a common, silent authorization bug.
  • Most resource servers validate access tokens locally against Keycloak's JWKS; introspection trades that speed for live revocation truth.
  • Refresh token rotation invalidates the previous refresh token on every renewal, turning any reuse of an old one into a theft signal.
  • JWTs can't be deleted early — shorten access token lifespans, revoke sessions or refresh tokens in Keycloak, or bump a not-before policy instead.

Authorization Services & RBAC/ABAC

Authentication answers "who is this?" — authorization answers "can they do this?" Keycloak gives you two structurally different ways to answer that second question, and the one you pick shapes every request your app makes for the rest of its life.

7 min read Advanced

Every protected action in an app needs a yes/no answer, and Keycloak lets that answer come from two very different places. The distinction is not cosmetic — it decides whether an authorization check costs a network round trip or a few nanoseconds reading a claim.

LevelWhere it's decidedHow it worksCharacter
Role-based (token claims)In the app / APIApp reads realm_access.roles from the token and enforces the rule itselfSimple, common, decentralized
Keycloak Authorization ServicesIn Keycloak (centralized)Fine-grained policies live in Keycloak; the app asks "can this user do X?" instead of deciding itselfCentralized, fine-grained, adds a call

Most apps only ever need the first row. The second exists for the cases where "does this role allow this action" stops being a question your code can answer on its own.

RBAC, ABAC, ReBAC — Keycloak's names for the same three models

The general theory of these three authorization models, and the "role explosion" problem that pushes teams from RBAC toward ABAC, is covered in depth in the companion Security & Auth module's Authorization Models chapter. Keycloak implements all three; what matters here is how it frames and names them.

RBAC — Roles

  • Access tied to a named role, checked as a token claim
  • Example: "admins can delete"
  • Fast, cacheable, easy to reason about

ABAC — Attributes

  • Access depends on user, resource, and environment attributes
  • Example: "managers in the same department, during work hours"
  • Needs a policy evaluator, not just a claim check

ReBAC — Relationships

  • Access derived from a relationship between subject and resource
  • Example: "owner of this document"
  • Ties permission to data, not identity alone

Inside Authorization Services: Resource, Scope, Policy, Permission

When role claims aren't enough, Keycloak's Authorization Services give you a vocabulary for describing access rules centrally, so the app never has to hardcode them. The app becomes a Policy Enforcement Point (PEP) — it asks a question — and Keycloak becomes the Policy Decision Point (PDP) — it answers.

ConceptWhat it means
ResourceA protected item — e.g. "Invoice #42", /api/orders
ScopeAn action on a resource — read, write, delete
PolicyA condition: role-based, user-based, time-based, JS/Rego rule, or an aggregate of other policies
PermissionLinks resources and scopes to the policies that govern them
PEP / PDPThe app (PEP) asks; Keycloak (PDP) decides
App holds an access tokenuser already authenticated
App requests an RPTUMA 2.0 grant, exchanging the access token
Keycloak evaluates policiesPDP checks resource + scope against configured rules
RPT issuedcarries the permissions actually granted

The app never encodes the rule itself — it hands over a token and gets back a Requesting Party Token (RPT) listing exactly what's allowed. The decision logic lives entirely in Keycloak, not scattered across services.

Default to the simple thing

Use plain role-based checks in the token for most apps — they're fast and need no round trip to Keycloak. Reserve Authorization Services for permissions that are genuinely fine-grained, centrally managed, and change often; the centralization is worth its cost only when the alternative is chasing rule changes across every service.

It's not free

Every Authorization Services check is a per-request call out to Keycloak's PDP, plus the ongoing work of maintaining resources, scopes, policies, and permissions as separate objects. Reach for it deliberately, not by default.

RBAC vs ABAC — when do you actually need ABAC?

RBAC is simple and sufficient whenever access maps cleanly onto roles — "admins can delete" needs nothing more. ABAC earns its complexity when rules depend on dynamic, contextual attributes — department, ownership, time of day, location — that would otherwise force you into a role for every combination, the "role explosion" problem detailed in the Security & Auth module's Authorization Models chapter. If you're naming roles like manager-finance-daytime, that's the signal to move to ABAC.

In Keycloak's UMA 2.0 flow, what is an RPT?
The RPT (Requesting Party Token) is what the app gets back after asking Keycloak's PDP to evaluate its policies against a resource and scope — it lists what was actually granted.
A system needs permissions that shift by department, document ownership, and time of day. What's the better fit?
Rules this dynamic and context-dependent would explode into an unmanageable number of roles under pure RBAC — this is exactly the fine-grained, centrally-managed case Authorization Services is built for.
Quick summary
  • Two levels of authorization: role claims checked in the app (fast, decentralized) versus Keycloak Authorization Services (centralized, fine-grained, but an extra call).
  • Keycloak's vocabulary: Resource (protected item), Scope (action on it), Policy (a condition), Permission (links resources + scopes to policies).
  • The app is the Policy Enforcement Point asking a question; Keycloak is the Policy Decision Point answering it.
  • Under the UMA 2.0 grant, the app exchanges its access token for an RPT that carries the granted permissions.
  • Default to simple role-based checks; reserve Authorization Services for permissions that are genuinely fine-grained and frequently changing.

Identity Brokering & Federation

Not every user should have to create yet another password. Brokering and federation are Keycloak's two answers to "let someone else handle the login" — but they solve very different problems, and mixing them up leads to the wrong architecture.

6 min readIntermediate

Delegating login: how brokering works

Identity brokering lets Keycloak hand off authentication to an external identity provider — Google, GitHub, Microsoft, or any other OIDC or SAML provider — instead of checking a password itself. The user still ends up with a Keycloak-issued token; they just never typed a Keycloak password to get it.

User hits the appTries to access a protected resource
Keycloak redirectsTo the configured external IdP, e.g. Google
Google authenticates the userKeycloak never sees the password
Keycloak links the identityCreates or matches a local user record
Keycloak issues its own tokensThe app only ever trusts Keycloak

The app and Keycloak never need to know or care which upstream provider the user actually authenticated with — that detail is absorbed at the redirect step.

That "links the identity" step is where the interesting decisions happen. On a user's first login through an external provider, Keycloak can auto-create a brand-new local user, link the login to an existing account (matching on email, say), or require review before the account is activated. Which one you pick depends on whether you already have users in Keycloak that might collide with incoming external identities.

Once the identity is linked, Identity Provider Mappers take over: they translate claims coming from the external provider — a Google Workspace group, a SAML attribute — into Keycloak roles and user attributes. This is what turns "logged in via Google" into "logged in via Google and automatically has the editor role because they're in the right Google group."

Where brokering earns its keep

Three recurring use cases: social login for consumer apps, B2B single sign-on where a partner company brings its own IdP, and gradual migration — letting an old identity system keep authenticating users while Keycloak takes over everything downstream.

Brokering vs. federation — same goal, opposite mechanics

Both features exist to avoid asking users for a brand-new password, but they sit on opposite sides of the authentication moment. Brokering hands the login off at runtime, via a redirect, to a system that authenticates the user itself. Federation has Keycloak do the authenticating, directly against an external store it's connected to.

Identity Brokering

  • Delegates the login itself to another IdP via redirect
  • The external provider authenticates; Keycloak just relays and re-issues tokens
  • Fits social login, partner SSO, and phased migrations

User Federation

  • Keycloak authenticates directly against an external store like LDAP or AD
  • Users can be imported into Keycloak's database or checked read-through, live
  • Fits an existing corporate directory you don't want to duplicate

User federation: plugging in LDAP or Active Directory

Federation connects Keycloak to a store that already holds your users, so nobody has to be migrated or re-registered. Existing corporate credentials just keep working — Keycloak becomes the front door, the directory stays the source of truth.

SettingOptions
ProvidersLDAP, Active Directory, Kerberos, or a custom store via the User Storage SPI
Sync modeImport — copies users into Keycloak's own database, refreshed on a periodic sync — or read-through, checking the external store each time
Edit modeREAD_ONLY, WRITABLE (changes made in Keycloak get pushed back to LDAP), or UNSYNCED
MappersMap LDAP attributes and group memberships onto Keycloak user attributes and roles
WRITABLE mode plus import sync is where sync jobs break

Conflicting edits or schema mismatches between Keycloak and LDAP show up as sync failures. Map attributes carefully and test the sync direction before relying on it. For very large directories, prefer on-demand import over a full periodic sync — hammering the whole directory on a schedule scales badly.

A partner company wants its employees to log into your app using their own Okta instance, and you'd rather not manage their passwords at all. Which feature fits?
This is a partner IdP authenticating its own users at runtime — that's brokering. Federation would mean importing or directly querying their directory, which usually isn't something a partner company will grant access to.
Your LDAP directory holds tens of thousands of users and you're worried about load. What's the safer federation sync approach?
A full periodic sync re-pulls the whole directory on a schedule, which scales poorly for huge directories. On-demand import only pulls users as they're needed, avoiding that load.
Quick summary
  • Identity brokering delegates the login to an external IdP via redirect — the app still only ever trusts tokens Keycloak issues.
  • First-login behavior (auto-create, link, or require review) plus Identity Provider Mappers control how external claims become local users, roles, and attributes.
  • User federation is the opposite direction: Keycloak authenticates directly against an external store like LDAP or AD, either importing users or checking read-through.
  • Use brokering for social login and partner SSO; use federation for an existing corporate directory you don't want to duplicate.
  • WRITABLE edit mode and full periodic sync are convenient but fragile at scale — test the sync direction and prefer on-demand import for large directories.

Sessions, SSO & MFA

One login should carry you across every connected app — until the moment you need to log out everywhere, or prove you're really you before touching something sensitive. This is where Keycloak's session model and authentication flows turn a single credential check into a full security posture.

8 min readAdvanced

How SSO Actually Works

The trick behind single sign-on isn't magic — it's a cookie in the right place. When a user logs into the first app, Keycloak doesn't just hand back tokens; it also sets an SSO session cookie on its own domain. When the user later opens a second app and gets redirected to Keycloak for authentication, Keycloak checks for that cookie first. If a valid session exists, it issues new tokens immediately — no login form, no re-entered password.

Login to App 1credentials verified once
Keycloak creates SSO sessioncookie set on Keycloak's domain
User opens App 2redirected to Keycloak to authenticate
Existing session foundtokens issued silently, no login form

The cookie lives on Keycloak's domain, not the app's — that's exactly what lets any number of unrelated apps piggyback on one login.

Sessions Have Layers, Not One Timeout

"How long does a login last" isn't a single answer in Keycloak — it's several independent knobs, each governing a different scope. Get them confused and you'll either force people to re-authenticate constantly or leave sessions alive far longer than intended.

SettingWhat it controls
SSO Session IdleLogs the session out after a period of inactivity
SSO Session MaxAbsolute lifetime of the session, active or not
Access Token LifespanHow long a single access token is valid — typically short, around 5 minutes
Client Session Idle / MaxPer-client session limits, layered on top of the SSO session
Offline Session Idle / MaxLifetime rules for offline tokens (long-lived, refresh-only access)

Single Logout (SLO): Ending It Everywhere

Logging out of Keycloak ends the central SSO session — but that only matters if the connected apps actually find out about it. Keycloak propagates that logout to every client through one of two mechanisms.

Front-channel logout

  • The browser is redirected to each client's logout URL in turn, often via hidden iframes
  • Depends on the browser actually loading every redirect
  • Can silently fail — blocked third-party cookies, closed tabs, or iframe restrictions all break the chain

Back-channel logout

  • Keycloak notifies each client directly, server-to-server
  • Doesn't depend on the user's browser cooperating
  • More reliable, and the recommended approach in production
"I logged out of one app, but I'm still logged into the others"

The app only cleared its own local session — it never touched the Keycloak SSO session. To log out everywhere, the app must call Keycloak's end-session endpoint (OIDC RP-initiated logout). That ends the central session, which then triggers back-channel logout to notify every other connected client.

Authentication Flows: The Login Sequence Is Configurable

A Keycloak authentication flow is a sequence of steps — called executions — that a user walks through to log in. Each step is marked Required, Alternative, Conditional, or Disabled, and that marking decides whether it runs, whether it can be skipped, and whether success anywhere else in the flow makes it redundant.

Cookie checkAlternative — auto SSO if a valid session cookie exists
Identity Provider RedirectorAlternative — hands off to an external IdP if configured
Username & Password FormRequired
Conditional OTPConditional — becomes Required only if the user has OTP configured

This is Keycloak's default Browser Flow. Alternative steps race to the first success — that's exactly why a valid cookie can skip the password form entirely, rather than the flow running every step regardless.

Because flows are just configurable step sequences, you're not limited to the defaults. Copy a built-in flow and customize it to force MFA for specific users, plug in a custom authenticator via the SPI, or insert a terms-and-conditions step before login completes.

Multi-Factor Authentication

MFA in Keycloak is just another set of steps in the flow — the question is which factor, and for whom. The theory behind knowledge/possession/inherence factors and step-up authentication is covered in the companion Security & Auth module's Authentication Mechanisms chapter; here's how it's actually wired up in Keycloak.

MethodExamples
OTP / TOTPGoogle Authenticator, FreeOTP — built in
WebAuthn / PasskeysHardware security keys, biometrics, FIDO2
Email / SMS OTPVia extensions or custom authenticators
Recovery codesBackup codes for when the primary factor is unavailable

There are two ways to switch MFA on. A required action like Configure OTP forces enrollment the next time a specific user logs in. A conditional step in the flow targets a whole population — admins only, or logins flagged as risky — without touching everyone else's experience.

Step-up authentication

Not every action deserves the same bar. Step-up auth means requiring a stronger factor (a higher ACR/LoA) only for sensitive operations — say, changing a password or approving a payment — while ordinary browsing stays on the lighter flow. It's the same conditional-flow mechanism, just triggered by the operation instead of the role.

How would you force MFA only for admin users?

Customize the Browser Flow and add a conditional sub-flow using the "Condition - User Role" authenticator, set to the admin role. Inside that sub-flow, add a Required OTP step. Admins hit the condition, match the role, and must complete OTP. Everyone else fails the condition check and skips the sub-flow entirely — no extra friction for regular users.

What actually makes cross-app SSO possible in Keycloak?
The cookie lives on Keycloak's domain, not the app's. Any app that redirects to Keycloak for auth will hit that existing session and get tokens without a login prompt.
Which logout mechanism is recommended for production because it doesn't depend on the browser cooperating?
Back-channel logout has Keycloak notify each client directly, server-to-server — no reliance on iframes, redirects, or third-party cookies surviving the round trip.
Quick summary
  • SSO works because Keycloak sets a session cookie on its own domain — any app that redirects there finds the existing session and skips the login form.
  • Session timeouts are layered, not singular: SSO Session Idle/Max, Access Token Lifespan, Client Session limits, and Offline Session limits all govern different scopes.
  • Back-channel logout (server-to-server) is more reliable than front-channel logout (browser redirect chain) for propagating Single Logout to every client.
  • A logout that only clears an app's local session leaves the central SSO session alive — full logout requires calling Keycloak's end-session endpoint.
  • Authentication flows are configurable step sequences (Required/Alternative/Conditional/Disabled); the default Browser Flow's Alternative steps are why a valid cookie can bypass the password form.
  • MFA is enforced via required actions (per-user enrollment) or conditional flow steps (per-population, e.g. admins-only via the Condition - User Role authenticator).

Integrating Applications

Keycloak only earns its keep once real applications trust it — a Spring Boot API, a browser SPA, a gateway sitting in front of a dozen microservices. Each integration shape has its own failure mode, and most of them come from treating Keycloak's tokens like generic OAuth2 tokens instead of reading what's actually inside them.

8 min read Advanced

Spring Boot as a resource server

Older Keycloak-specific adapters for Spring are deprecated. The current path is plain Spring Security OAuth2 Resource Server support, which treats Keycloak as just another OIDC-compliant issuer. Point it at the realm's issuer URL and Spring auto-discovers the JWKS endpoint, fetches the public keys, and validates every incoming JWT's signature and expiry — no manual key management.

application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://kc.example.com/realms/myrealm
SecurityConfig.java
@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain chain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(a -> a
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .oauth2ResourceServer(o -> o
                .jwt(j -> j.jwtAuthenticationConverter(keycloakRolesConverter())));
        return http.build();
    }
}
Roles aren't where Spring expects them

Spring Security's default JWT authorities converter looks for a scope claim. Keycloak instead nests roles under realm_access.roles (realm-level) and resource_access.{client}.roles (client-level). Without a custom JwtAuthenticationConverter that reads these claims and prefixes each one with ROLE_, every hasRole(...) check silently fails — the token is valid, the user is authenticated, but nothing ever matches.

This is exactly the kind of wiring the companion Spring Boot module covers in depth — its IoC & Dependency Injection chapter explains how a @Bean like keycloakRolesConverter() gets discovered and injected, and its general Spring Security configuration patterns apply here without modification. Keycloak just supplies the token; Spring's own security model does the rest.

Request arrivesBearer JWT in Authorization header
JWKS fetchedfrom issuer-uri, cached
Signature verifiedexpiry & issuer checked
Custom converter runsrealm_access.roles → ROLE_*

Signature validation is generic OAuth2 — any library does it. The last step is the one only Keycloak needs, and it's the one teams forget.

SPAs and the token-in-the-browser problem

Browser-based apps talk to Keycloak using keycloak-js or a generic OIDC library, running Authorization Code + PKCE as a public client (no client secret, since anything shipped to a browser can be read). The client's valid redirect URIs and web origins must be configured on the Keycloak client, or CORS and redirect validation reject the flow outright.

Browser redirectsto Keycloak login
User authenticatescredentials stay on Keycloak's page
Code returnedto registered redirect URI
Code exchangedwith PKCE verifier, for tokens

PKCE replaces the client secret a public SPA can't safely hold — the verifier proves the code exchange comes from the same browser session that started the flow.

Tokens in the browser

  • SPA holds access/refresh tokens directly (memory or storage)
  • Simple to wire up with keycloak-js
  • Any XSS in the app can exfiltrate the tokens

BFF (Backend-for-Frontend)

  • A server-side component holds the tokens, never the browser
  • Browser only ever sees a secure, httpOnly session cookie
  • An XSS bug leaks page data, not a bearer token an attacker can replay
Prefer the BFF where you can

This is the same trade-off the Security & Auth module's Authentication Mechanisms chapter walks through when discussing where session state should live. Keycloak doesn't force either shape on you — but pushing token storage server-side removes an entire class of browser-based attacks for a modest architectural cost.

Gateways: validating once instead of everywhere

In a microservices layout, repeating JWT validation logic in every service is wasted effort and a consistency risk. API gateways and reverse proxies — Spring Cloud Gateway, Kong, NGINX, oauth2-proxy — can sit at the edge, validate the Keycloak-issued token once, and forward a verified identity downstream, so individual services trust the gateway instead of re-implementing auth.

Client requestBearer JWT
Gateway validatessignature, issuer, expiry
Identity forwardedas headers to downstream services

Downstream services get a smaller, cheaper job: trust the gateway's headers instead of re-verifying a token on every hop.

Managing Keycloak as code

Clicking through the admin console works for one realm, once. For anything reproducible — staging, production, a second environment — drive Keycloak through its Admin REST API, the bundled kcadm.sh CLI, or the Terraform keycloak provider.

create-user.sh

  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","enabled":true,"email":"a@x.com"}'
Realms-as-code

Whether you script it directly against the Admin REST API, use kcadm.sh, or manage it declaratively with Terraform, the goal is the same: a realm's clients, roles, and mappers should be reproducible from a file, not remembered as a sequence of console clicks.

Why does a Spring Boot resource server need a custom JwtAuthenticationConverter to enforce Keycloak roles?
Spring's default converter reads the scope claim. Keycloak puts roles in realm_access.roles and resource_access.{client}.roles, so without a custom converter, hasRole(...) checks fail even against a perfectly valid, signed token.
What problem does the BFF pattern address for a Keycloak-backed SPA?
A BFF holds access and refresh tokens on the server; the browser only ever sees a secure session cookie. An XSS vulnerability in the SPA then leaks page data rather than a bearer token an attacker could replay directly against the API.

Keycloak sees http://10.0.1.5:8080and issues URLs from that, unless told otherwise

Without proxy-headers and hostname configured, the discovery document, issuer, and redirect URLs all point at the private address — clients outside the network can never complete the flow.

How do you run Keycloak behind a reverse proxy or load balancer?

Set the proxy-headers option (e.g. xforwarded) along with the hostname setting, so Keycloak trusts the forwarded headers and generates every external URL — issuer, redirect, token endpoints — as the public address, not the internal one it actually received the request on.

Security checklist for a live realm

None of this is exotic — it's the same OAuth2/OIDC hardening covered conceptually in the Security & Auth module, applied as concrete Keycloak settings.

Harden the protocol flow

  • HTTPS everywhere — no exceptions for internal traffic
  • Short access-token lifespans, with refresh token rotation and reuse detection enabled
  • PKCE for every public client; avoid the Implicit and Resource Owner Password grants entirely
  • Every resource server validates aud and iss — not just the signature
  • Strict, exact redirect URIs — no wildcards, a top real-world OAuth attack vector

Harden the realm & admin surface

  • Confidential clients (with rotated secrets) for anything that can actually keep one
  • Least-privilege role design; never hand out more than a client needs
  • Lock down and restrict access to the master realm and admin console
  • Built-in brute-force detection and account lockout on; MFA required for privileged users
  • Keep Keycloak patched, audit login/admin events, and rotate signing keys periodically
Where the client stores the token matters too

Avoid localStorage — any injected script can read it, turning a single XSS bug into full account takeover. Prefer HttpOnly, secure cookies, or better, a Backend-for-Frontend that keeps tokens off the browser entirely. Set SameSite on cookies to mitigate CSRF as a bonus layer.

Core Concepts & Architecture
01
TrapWhy is putting application end users in the master realm a mistake, even though it would technically work?

The master realm exists to administer Keycloak itself — it holds the super-admin account and controls access to every other realm. Treating it as "just another realm" for a product's customers means a compromised or over-permissioned app user could pivot into managing the entire Keycloak instance, not just their own tenant.

In practice this shows up during access reviews: master realm role mappings should be tiny and tightly held, a handful of operations accounts at most. Seeing thousands of ordinary user accounts in master is itself a sign something was set up wrong. Every real application or tenant gets its own dedicated realm, keeping the admin boundary separate from any user population.

02
Trade-offPKCE is recommended for every OAuth2 client today, confidential or not. So why does Keycloak still draw a hard line requiring it specifically for public clients?

A confidential client holds a client secret it presents at the token endpoint, so even if an authorization code is intercepted in transit, an attacker without that secret can't redeem it. A public client — a single-page app or mobile app — has no secret it can actually protect, since anything shipped to the browser or device is extractable. Without something else binding the code to the legitimate requester, an intercepted code alone would be redeemable by whoever grabbed it.

PKCE closes that gap with a per-request verifier only the real client instance holds. For confidential clients the secret already provides that binding, so PKCE there is defense-in-depth rather than the only thing stopping code interception — which is why it's mandatory for public clients specifically, while still being good hygiene everywhere else.

03
InternalsWhat does Infinispan actually buy Keycloak, and why should you care as the person running it in production?

Keycloak, running on Quarkus, keeps login sessions and related caches in Infinispan, a distributed in-memory data grid, rather than pinning them to whichever process first handled the request. That's what makes horizontal scaling and high availability actually work: any node in the cluster can serve a request tied to a session that started on a different node, because Infinispan replicates or distributes that session data across the cluster instead of keeping it node-local.

The practical consequence is that putting two Keycloak instances behind a load balancer doesn't give you real HA on its own — Infinispan needs to be clustered correctly, with working node discovery and network reachability between instances. Get that wrong and you'll see intermittent "session not found" failures whenever the load balancer happens to route a request to a node that never received that session.

04
InternalsKeycloak exposes a JWKS endpoint. Why does that exist, and what happens when Keycloak rotates its signing key?

Resource servers need Keycloak's public signing key to verify a JWT's signature without calling Keycloak on every request. The JWKS endpoint publishes the current key (and recently retired ones), and each token's header carries a kid identifying exactly which key signed it.

Rotation doesn't invalidate every token in flight — Keycloak starts signing new tokens with a new kid while JWKS keeps publishing the old public key for a while, so tokens signed before rotation still validate. A validator that only fetches JWKS once at startup and never refreshes will eventually reject perfectly valid tokens signed with a kid it's never seen, which is why clients should refresh their cache periodically and specifically whenever they meet an unrecognised kid.

OAuth2, OIDC & Tokens in Keycloak
05
ScenarioTrace what actually happens on the wire during an Authorization Code login against Keycloak.

The app redirects the browser to Keycloak's realm-scoped /auth endpoint with client_id, redirect_uri, response_type=code, and the requested scopes. Keycloak authenticates the user — its own login form, or a broker/federated identity behind the scenes — then redirects back to redirect_uri carrying a short-lived authorization code.

The app's backend then calls Keycloak's /token endpoint directly, server-to-server, exchanging that code — plus a client secret if confidential, or a PKCE code_verifier if public — for an access token, ID token, and refresh token. Because the exchange happens over a back channel, tokens never touch the browser's address bar or history, which is precisely what the deprecated Implicit flow got wrong.

06
ScenarioWhen would you reach for the Client Credentials grant instead of Authorization Code against Keycloak?

Client Credentials is for machine-to-machine calls with no human present to authenticate — a batch job, a scheduled sync, one microservice calling another as itself. The client authenticates directly to Keycloak's /token endpoint with its own credentials and gets back an access token representing the client, not any user.

The trap is reaching for it inside a user-facing flow just because it's simpler to wire up — that throws away any notion of who the user is, and downstream audit logs will only ever show "the service" acted, never which end user actually triggered the action.

07
TrapImplicit and Resource Owner Password Credentials grants are still technically supported. Why would using either be considered a mistake today?

Implicit returned the access token directly in the browser's redirect fragment, with no back-channel exchange — tokens ended up in browser history, referrer headers, and logs, and there was no way to use a client secret since everything happened in the front channel. Authorization Code with PKCE covers the same SPA use case without ever putting a token somewhere it can leak that way.

ROPC has the client itself collect the user's actual username and password and forward them to Keycloak, which trains users to type credentials into arbitrary app UIs instead of only Keycloak's login page, defeats the point of centralising authentication, and leaves no room for redirecting to an external IdP or prompting for MFA mid-flow.

08
TrapA Spring Boot resource server validates Keycloak-issued JWTs fine locally, but every role-based @PreAuthorize check fails once deployed. What's the likely cause?

Spring Security's default JWT authentication converter expects roles as a flat, space-delimited scope claim. Keycloak doesn't emit roles that way — it nests them under realm_access.roles for realm-level roles and resource_access.{client}.roles for client-level roles. The default converter never looks there, so every role check silently resolves to "no authorities," which usually shows up as unexplained 403s rather than an obvious error, since the token itself is perfectly valid.

The fix is a custom JwtAuthenticationConverter that reads those specific claim paths and maps them into GrantedAuthority objects, typically prefixed ROLE_, before Spring's authorization checks run. It's one of the most common real integration gotchas precisely because both sides "work" in isolation — the mismatch is purely about which JSON path the roles live under.

Authorization & Federation
09
Trade-offA resource server can validate a token locally against a cached JWKS key, or call Keycloak's introspection endpoint. When would you choose each?

Local validation — checking the signature against a cached JWKS key, plus exp/iss/aud — is fast and needs no network round trip per request, which matters under load. But it only knows what's inside the token. If a session is killed or a token revoked before it naturally expires, a local validator has no way to find out; it'll accept the token until it expires on its own.

Calling /introspect asks Keycloak directly whether the token is still valid right now, so it reflects revocation immediately, at the cost of a network call — and Keycloak load — on every request. Most systems land on a middle ground: local validation plus short-lived access tokens, so the exposure window for a revoked-but-not-expired token stays small without paying the introspection cost constantly.

10
Trade-offKeycloak's Authorization Services give you Resources, Scopes, Policies, Permissions, and RPT tokens via UMA. When is that worth it over just checking roles embedded in the token?

Simple role checks are cheap to reason about and need nothing beyond what's already in the JWT — fine when authorization decisions are static and few. Authorization Services centralises the actual policy decisions in Keycloak: you define resources and scopes once, and any service can ask "can this user do X to resource Y" via a permission ticket or RPT, with the policy logic — role-based, attribute-based, time-based, whatever — living in one place instead of duplicated across services.

The cost is real: extra complexity, and an extra network dependency for authorization, not just authentication. It earns its keep when rules are numerous, change often, or must stay consistent across many services so you're not reimplementing the same rule five times. It's overkill for an app with two or three static roles.

11
TrapIdentity brokering and User Federation both involve an "external" identity source. What's actually different, and why do people conflate them?

With brokering, Keycloak doesn't authenticate the user itself — it redirects to an external IdP such as Google or another OIDC/SAML provider, lets that IdP do the actual login, and links or creates a local Keycloak account from the resulting token. The user's password never touches Keycloak.

User Federation is the opposite: Keycloak still runs the login screen and the authentication attempt itself, but instead of checking the password against its own database it checks against a federated directory like LDAP or AD. People conflate the two because both involve "another system holding identity," but the redirect-versus-direct-authentication distinction is the load-bearing difference — it changes who owns the login UI and where credentials actually get checked.

12
InternalsFor LDAP/AD federation, what's the practical difference between import and read-through sync, and what does each cost you?

Import mode copies user attributes into Keycloak's own store on first lookup, so Keycloak has a local, fast-to-query copy — but that copy can drift out of sync with the source directory until the next sync cycle, so a user disabled in AD might still look active in Keycloak's local copy for a while.

Read-through (no-import) mode queries LDAP live on each lookup, so it's always current, at the cost of making Keycloak's user operations only as fast and as available as the directory itself. If LDAP is slow or briefly unreachable, that latency or outage shows up directly in your login flow.

SSO, MFA & Integration
13
TrapA user logs out of App A but is surprised to still be logged into App B afterward. What's going on, and how would you actually fix it?

Keycloak's SSO runs on its own browser session cookie. Logging out of App A typically only ends App A's local application session, not the underlying Keycloak SSO session, unless something explicitly tells Keycloak to end that broader session too.

The fix is RP-initiated logout — redirecting the browser through Keycloak's own logout endpoint so it terminates the Keycloak session cookie itself — combined with back-channel logout, where Keycloak notifies every other client holding a session so they can invalidate their own local sessions even without the user's browser visiting them. Skipping this is one of the most common real-world "SSO logout doesn't work" bug reports.

14
InternalsKeycloak lets you build custom authentication flows from Required, Alternative, Conditional, and Disabled steps. What do those settings actually control?

A flow is an ordered sequence of authenticator steps, and each step's requirement setting decides how it combines with the others. Required means the step must succeed for the flow to continue; Alternative means any one sibling succeeding is enough; Disabled skips the step entirely; Conditional gates a sub-flow behind a runtime condition — like the user's role or which client is being used — rather than always running it.

This is what lets one realm serve very different login experiences without spinning up separate realms: username/password Required, then a Conditional sub-flow that only executes an OTP Required step when its condition is true. Regular users breeze through, while whoever matches the condition hits the extra factor.

15
ScenarioYou need MFA enforced for admins only, without touching regular users' login experience. How do you actually build that in Keycloak?

Inside the realm's browser authentication flow, add a Conditional sub-flow gated by the Condition - User Role authenticator, configured to match the admin role. Inside that sub-flow, add an OTP (or WebAuthn) step marked Required.

For a regular user, the condition evaluates false, so the whole sub-flow — OTP prompt included — is skipped, leaving username/password as their only requirement. For an admin, the condition passes and OTP becomes mandatory before the flow can succeed. One flow definition now serves both populations instead of needing separate flows or separate clients per audience.

16
ScenarioInterviewers sometimes ask you to trace a login "from theory to implementation." How would you connect the general OAuth2/OIDC picture to what Keycloak specifically does?

As covered in the Security & Auth module's OAuth2/OIDC chapters, the abstract picture is: a client redirects the resource owner to an authorization server, that server authenticates the user and obtains consent, then returns tokens the client can use against a resource server — with OIDC layering an ID token and identity claims on top of OAuth2's authorization-only model.

Keycloak is a concrete authorization server implementing exactly that shape: its /auth endpoint is the authorization endpoint, /token is the token endpoint, it issues both an OIDC ID token and OAuth2 access/refresh tokens, and it exposes the JWKS endpoint so resource servers can verify signatures. Being able to point at Keycloak's actual endpoints while narrating the generic flow is exactly what separates "knows the theory" from "has actually built on this."

Deployment & Cross-Topic Scenarios
17
TrapWhat are the production mistakes that trip up teams running Keycloak for real, as opposed to a local demo?

The most common is forgetting to configure the hostname/proxy settings correctly behind a load balancer or reverse proxy — Keycloak needs to know its externally visible hostname to generate correct issuer and redirect URLs, and without that, tokens get issued with an issuer that doesn't match what clients expect, breaking validation. Close behind is forgetting to rebuild or restart after changing providers or certain config, since some changes only take effect once Keycloak reprocesses its configuration.

Others: still running on the embedded H2 database in production instead of PostgreSQL, clock skew between servers causing tokens to look already expired or signatures to appear invalid the moment they're issued, and leaving the admin console reachable from the public internet instead of restricting it to an internal network. Each individually is a "worked in the demo" problem that turns into a production incident.

18
ScenarioDesign SSO for five internal apps, add "log in with Google," and require MFA just for admins. What does the Keycloak setup look like?

One realm covering all five apps, not five separate realms — a single realm gives shared SSO for free and is simpler to operate, whereas multiple realms would buy full isolation at the cost of more overhead and no cross-realm SSO, which isn't needed here since these are all internal apps meant to share sessions. Each app still gets its own client: confidential clients for server-side apps that can hold a secret, public clients with PKCE for any SPA.

Google is wired up as an identity provider via brokering, so users authenticate through Google without Keycloak ever owning their Google password. Roles are organised through groups, so promoting someone to admin is a group membership change rather than a per-user edit, and the admin-only MFA requirement is the Conditional-sub-flow-plus-Condition-User-Role setup described earlier, applied once at the realm level.

19
ScenarioA dozen microservices need to trust access tokens on every incoming request without hammering Keycloak. How do you architect that?

Each service validates tokens locally: fetch and cache Keycloak's JWKS public keys, verify the token's signature against the key matching its kid, and check exp, iss, and aud itself, with no call to Keycloak on the request path. This is the local-validation side of the introspection trade-off, chosen here because inter-service request volume makes a per-call round trip to Keycloak both slow and a potential bottleneck or single point of failure.

The cache needs a refresh strategy: periodically on a timer, and immediately whenever a token arrives signed with a kid the service hasn't seen, which signals a key rotation happened. Since this trades away live revocation awareness, teams pair it with reasonably short access-token lifetimes so a compromised or revoked token's blast radius stays time-boxed even without introspection.

20
ScenarioYou're migrating users out of a legacy in-house database into Keycloak. What are the realistic options, and what pushes you toward one?

For a one-time cutover, bulk-import existing users through Keycloak's Admin REST API, typically paired with an "update password" required action since you generally can't recover cleartext passwords from the legacy store to set them directly. If users still need to authenticate against the legacy system during a transition period, a custom User Storage SPI lets Keycloak authenticate directly against that store live, optionally importing the user into Keycloak's own store on their first successful login.

If the legacy system already looks like a directory rather than a bespoke database, LDAP federation is the more natural fit and needs no custom code at all. The deciding factor is whether you can afford a hard cutover: the SPI or federation route buys a gradual migration where old and new coexist, while bulk import assumes you're ready to fully commit on migration day.

Interview delivery tips

1) Name the actual endpoint or claim — /auth, /token, realm_access.roles — instead of speaking only in generic OAuth2 terms; it signals hands-on experience over textbook knowledge. 2) When asked to compare two mechanisms (brokering vs federation, local validation vs introspection), lead with the trade-off, not the definition. 3) Keep one end-to-end scenario ready — SSO across several apps plus an external IdP plus MFA for a subset of users — so you can narrate a full design instead of isolated facts. 4) When a scenario question involves something broken, reach for the small set of usual suspects first — clock skew, hostname/proxy misconfiguration, claim-shape mismatches — before inventing an exotic cause.
