01
EasyYour resume says you "architected Spring Boot microservices for HyperTrack … exposing versioned REST APIs (OpenAPI/Swagger) to 10+ internal services." What does "versioned" actually mean here, and why does it matter with 10+ internal consumers?

Versioning means the API's contract is tagged (commonly in the URI, e.g. /api/v1/timesheets, or via a request header/media type) so that a breaking change can ship as a new version while old consumers keep talking to the version they already integrated against. With 10+ internal services depending on these APIs, a breaking change rolled out without versioning would require coordinating a simultaneous update across every consumer — completely impractical at that scale, and a guaranteed source of production incidents.

In practice: additive changes (a new optional field) can go into the existing version safely, but anything that changes an existing field's meaning or removes something gets a new version, with the old version kept running until every consumer has migrated. OpenAPI/Swagger (via springdoc-openapi) is what documents each version's contract, so consumer teams can see exactly what changed without reading your code.

02
EasyYour resume says HyperTrack was "shipped to Linux servers via Azure ACR, earlier on AWS EC2 and S3." Walk me through how a code change actually reaches production.

The real flow: a scripted Jenkins job pulls the latest code from GitLab, builds the Spring Boot service with Maven, runs the SonarQube analysis, and builds a Docker image. Jenkins then logs in to Azure (with a service principal stored in Jenkins credentials, never hardcoded) and pushes the image, tagged with the build number, to Azure Container Registry (ACR). Finally, the Linux application server (a Utho cloud server) pulls that exact image tag from ACR, stops the old container and starts the new one.

Be precise about the roles: ACR is only the registry, a private store for images, and the app does not run on Azure. Docker is the runtime on the server, not a separate step. For AWS, be honest that it was an earlier, shorter phase: the service ran on an EC2 instance and user-uploaded files were stored in S3. Know the S3 basics (private bucket, object key saved in the database, pre-signed URLs for upload and download) and the EC2 basics (instance type, security group, IAM role instead of hardcoded access keys).

03
EasyYou list JUnit 5 and Mockito. Walk through how you'd unit-test a service class that depends on a repository, using Mockito to isolate it.

Mock the repository dependency with @Mock, inject it into the service under test with @InjectMocks (using @ExtendWith(MockitoExtension.class) in JUnit 5), then use when(repository.findById(id)).thenReturn(Optional.of(entity)) to control exactly what the "database" returns without touching a real one. The test asserts on the service's own logic — the transformation, validation, or business rule it applies — not on whether the repository itself works.

Use verify(repository).save(any()) (or an ArgumentCaptor to inspect exactly what was saved) when the return value alone doesn't prove a side effect happened. That isolation is what makes it a unit test; a real database round-trip belongs in an integration test (@DataJpaTest or @SpringBootTest). Your resume also lists Playwright: be clear that it is for browser/end-to-end tests, a different layer from JUnit.

Useful metrics: pending/failed reconciliation counts, failed batch jobs, request latency percentiles, per-service health status, and recent error rates — the things an ops person needs to decide "is something broken right now, and where." The frontend typically polls a REST endpoint on a short interval (10–30s is common for an ops dashboard), backed by Spring Actuator/Micrometer metrics or a small purpose-built reporting endpoint. A WebSocket push is usually overkill unless the dashboard genuinely needs sub-second updates.

Be ready for "why React on a backend resume?" A good answer: it was a small internal tool that let the ops team see your services' state without asking developers, and it shows you understand how your APIs are consumed.

MediumYou "built multi-level approval workflows in Camunda BPM with RBAC, audit trails … and escalations." How is a multi-level approval modelled in BPMN, and where do RBAC and escalations fit?

Each approval level is a BPMN user task (e.g. manager approval, then project-lead approval), connected by exclusive gateways that route on the decision: approved moves to the next level, rejected ends the process or sends it back to the submitter. Work that needs no human (updating the timesheet status, sending notifications) is done in service tasks backed by Java delegates in your Spring Boot app.

RBAC maps to candidate groups on each user task, so only users with the right role see and can complete that task. Escalations use a timer boundary event on the user task: if nobody acts within, say, 48 hours, the timer fires and reassigns or notifies a higher approver. The audit trail comes largely for free from Camunda's history tables, which record who completed which task and when. Be honest that your Camunda exposure was short, but know this model well.

07
MediumYour pipeline has "SonarQube quality gates." What does the gate check, and what happens when it fails?

After the Maven build, a Jenkins stage runs the analysis inside withSonarQubeEnv('sonar') { sh 'mvn sonar:sonar' }, and the next stage calls waitForQualityGate abortPipeline: true. SonarQube evaluates the gate, and if it fails, the pipeline stops before the Docker image is built or pushed, so bad code never reaches ACR or the server.

The default "Sonar way" gate focuses on new code: no new bugs or vulnerabilities, all security hotspots reviewed, coverage on new code above a threshold (commonly 80%, measured with JaCoCo), and low duplication. Know the categories: bugs, vulnerabilities, code smells and security hotspots. Reminder: add this stage to your real Jenkins job so you can describe it from experience.

08
MediumKafka resumeYou "integrated Apache Kafka for async event processing between services (idempotent consumers, dead-letter topics)." Concretely, how do you make a Kafka consumer idempotent?

Kafka's default delivery guarantee is at-least-once, meaning the same message can legitimately arrive twice (after a rebalance, a retried commit, a consumer restart). Idempotency is what makes processing it twice harmless. Two common mechanisms: track processed event IDs in a dedup store (a table keyed on a unique event ID, checked before processing — if already present, skip), or design the write itself to be naturally idempotent, e.g. an UPSERT keyed on business ID instead of a raw INSERT, or setting an absolute value instead of incrementing a counter.

The dead-letter topic is the complementary mechanism for the opposite problem: a message that can't be processed (bad data, a bug) gets routed there after retries are exhausted — in Spring Kafka via DefaultErrorHandler with a DeadLetterPublishingRecoverer — instead of blocking the partition forever or being silently dropped.

09
MediumYou "applied Resilience4j circuit breakers, retries, and fallbacks to third-party API calls." Walk through the circuit breaker's state machine — what causes it to open, and what causes it to close again?

Closed (normal): calls pass through to the downstream, and failures are tracked over a sliding window. Once the failure rate inside that window crosses a configured threshold, the breaker trips to Open: calls fail immediately without reaching the downstream. That protects the caller (no waiting on a struggling dependency) and the downstream (no pile-up of retries against something already failing). While open, the fallback method returns a cached or degraded response, or a clean error.

After a configured wait duration, the breaker moves to Half-Open and lets a small number of trial calls through. If they succeed, it closes again; if they still fail, it reopens and waits again. This is what lets the system self-heal without a human resetting it. Be ready to name which third-party APIs you protected.

MediumYou "supported Disaster Recovery (DR) activities for production BFSI systems, including failover, post-switchover service validation, and restoration." What exactly did you do during a DR drill?

Set the context first: banks run production in a primary data centre (DC) and keep a standby DR site, and regulators require periodic drills that prove the business can keep running if the primary site is lost. In a drill, traffic and databases are switched to the DR site (failover), the applications are validated there, and later everything is moved back (restoration, or failback).

Your part was post-switchover validation, so describe your checklist concretely: all services up and /actuator/health green on the DR site, database connections pointing at the DR database, a few smoke transactions end-to-end, login/SSO working, third-party banking integrations reachable, scheduled batch and reconciliation jobs running, and logs free of new errors. Know two terms: RPO (how much data loss is acceptable, e.g. last 15 minutes) and RTO (how quickly service must be restored, e.g. within 2 hours). Have one real example of an issue found during a drill and how it was fixed.

MediumYou "handled production support: triaged incidents, performed root-cause analysis (RCA), and shipped permanent fixes." Walk me through how you handle a production incident from alert to RCA.

Triage first: confirm the impact (which users, which API, how bad), set the severity (P1 for a full outage down to P4), and restore service quickly, e.g. restart the container, roll back, or disable the failing feature. Fix the root cause afterwards, not while customers are down.

Then investigate: read the logs around the first error (a correlation ID in MDC lets you follow one request across services), check recent deployments and config changes, and look at the database (slow queries, locks, connection-pool exhaustion) and the JVM (thread dumps for stuck threads, heap dumps for memory problems). The RCA document covers the timeline, impact, root cause (use "5 Whys" to get past the first symptom), the permanent fix, and a prevention step such as a new alert, test or code-review check. Have two real incidents ready in STAR form.

MediumYou "wrote Oracle PL/SQL stored procedures for high-volume batch processing and scheduled reconciliation jobs." Why put that logic in the database, and how does your Spring app call it?

For high-volume batch work, moving millions of rows into Java and back costs a lot of network round-trips. A stored procedure processes the data where it lives, using set-based SQL and BULK COLLECT / FORALL to handle rows in batches, which is far faster. Reconciliation (matching your records against a bank's or a partner's file and flagging mismatches) is a classic fit.

From Spring you call it with SimpleJdbcCall, or with @Procedure on a Spring Data JPA repository. Be ready for the trade-off question: business logic in PL/SQL is harder to unit-test and version than Java, so keep it for heavy data crunching and keep business rules in Java. Also know who commits (inside the procedure, or the calling Spring transaction) and how the job was scheduled (@Scheduled, Quartz, or DBMS_SCHEDULER).

13
HardYou "tuned PostgreSQL dashboard queries (covering/partial indexes, EXPLAIN ANALYZE), lowering average latency by ~35%." Walk through your actual process — how does EXPLAIN ANALYZE tell you a covering index is the right fix?

Run EXPLAIN (ANALYZE, BUFFERS) on the slow query and look for an index scan followed by a heap fetch — the planner used an index to find matching rows, but then still had to go back to the actual table to fetch columns the index didn't contain. That extra heap access, multiplied across many rows, is exactly the cost a covering index removes: by including the needed columns in the index itself (via a composite index or an INCLUDE clause), the query becomes answerable from the index alone — an index-only scan, with the heap fetch gone entirely.

A partial index solves a different, narrower case: when a query only ever filters a small, well-known subset of rows (e.g. WHERE status = 'PENDING' out of a table dominated by completed rows), indexing just that subset keeps the index small and fast instead of indexing (and maintaining) rows the query never touches. The proof either way is the same: re-run EXPLAIN ANALYZE after the change and confirm actual execution time dropped and the plan no longer shows the heap fetch or full scan you started with.

14
HardYour Camunda approval workflows include "compensating transactions." Give a concrete example — what business action needed "undoing," and how did you undo it?

A HyperTrack-style example: when a first-level approver approves a timesheet, a service task locks that timesheet and pushes the hours to a billing or payroll summary so downstream reports can proceed. If a later approver rejects it, that earlier step has already committed and may already be visible in reports, so a database rollback isn't possible. Instead, a compensation handler (a BPMN compensation event attached to that service task) runs an explicit "undo" action: remove the hours from the billing summary, unlock the timesheet and notify the submitter.

That is the core reason compensating transactions exist: once intermediate steps of a multi-day, multi-approver workflow have committed, there is no single database transaction left to roll back. "Undo" has to be a real forward action (reverse, release, notify), which is the same idea as the Saga pattern.

HardYour centralized monitoring service plus Docker containerization "cut environment incidents by ~60%." What kinds of incidents were happening before, and why do these two changes prevent them?

Classic environment drift: a different JDK patch version between servers, a missing system library, config files that diverged between environments, a manual deployment step someone forgot on one box. Docker removes this category structurally, because the image bundles the exact runtime, dependencies and config as one immutable artifact, so the same image behaves the same wherever it runs.

17
HardYour BFSI microservices had "idempotent APIs and explicit transaction boundaries." How do you stop a client retry from debiting a customer twice?

Use an idempotency key: the client sends a unique ID (e.g. an Idempotency-Key header or a transaction reference) with the request. The server saves that key with the result, protected by a unique constraint in the database. If the same key arrives again, the server returns the saved response instead of processing it again. The unique constraint is the final safety net, because it catches even two requests that arrive at exactly the same moment.

Transaction boundaries: keep the balance update, the ledger entry and the idempotency record in one @Transactional method so they all commit or all roll back together. Know the traps: @Transactional works through a proxy, so calling it from another method in the same class skips it; by default it only rolls back on unchecked exceptions; and REQUIRES_NEW is for work that must commit even if the outer transaction fails, such as an audit log. For concurrent updates to the same account, add optimistic locking (@Version) or SELECT … FOR UPDATE.

18
Very HardYou "integrated SSO and RBAC (OAuth2, OpenID Connect, Keycloak, Okta, Azure AD), centralizing JWT validation … across 8+ microservices." If a request carries an Azure AD-issued JWT but reaches a service only configured for Keycloak, how does multi-IdP validation actually work without hardcoding logic per identity provider?

The centralizing move is a shared validation layer — a gateway filter or a common library used by every service — that reads the token's iss (issuer) claim, resolves which identity provider issued it, and fetches that specific IdP's public signing keys from its JWKS endpoint (cached locally, refreshed periodically) to verify the signature. Because this logic is generic over "whichever issuer is in the token," adding a new IdP means registering its JWKS endpoint once in the shared layer — not writing new per-service validation code for every microservice that might see that IdP's tokens. In Spring Security this is exactly what JwtIssuerAuthenticationManagerResolver is for.

This is what "removing duplicated per-service auth logic across 8+ microservices" means concretely: before centralization, each service had to know how to validate at least one IdP's tokens itself; after, every service trusts one shared component instead of re-implementing (and possibly getting subtly wrong) token validation N times.

19
Very HardYou implemented "AES-256 payload encryption for third-party banking integrations." Where do the encryption keys live, how are they rotated, and what's the actual blast radius if a key is compromised?

Keys belong in a dedicated secrets/key-management service (an HSM, HashiCorp Vault, Azure Key Vault, AWS KMS or equivalent) — never in application config or source. A mature approach uses envelope encryption: each payload (or batch) is encrypted with its own data key, and that data key is itself encrypted by a master key held in the key-management service. Rotating the master key doesn't require re-encrypting every historical payload immediately; only newly generated data keys use the new master key, and old data keys remain decryptable via the key version that issued them.

This is what limits blast radius: if a single data key is compromised, only the payloads it encrypted are exposed, not everything the system has ever encrypted. One static key for everything has the opposite property. Also know the mode: AES-256-GCM (encrypts and detects tampering) with a fresh random IV/nonce for every message, never reused. "AES-256" alone is a checkbox; the real security comes from key management, which is what this question is really testing.

20
Very HardYour rental platform project applies "distributed locking to prevent double bookings." Two users click "book" on the same property within milliseconds — walk through exactly what happens, including if the lock-holder crashes mid-transaction.

Both requests attempt to acquire a distributed lock keyed on the property + date range. One acquires it first; it re-checks availability (never trusting data read before the lock), creates the booking, then releases the lock. The second request, waiting on the same key, acquires the lock only after the first releases it — at which point it re-checks availability itself and correctly finds the slot already taken, returning a conflict rather than double-booking.

The crash case is the important part: the lock must carry a lease/TTL, not be held forever — otherwise a crashed process permanently deadlocks that property for every future booking attempt. But a lease alone isn't a full correctness guarantee either: if the crashed process had already written the booking before crashing (just hadn't released the lock yet), the lease expiring and a second process proceeding could still create a conflict unless the actual write itself has a backstop — e.g. a unique database constraint on (property_id, date_range) that makes a genuine double-booking fail at the data layer regardless of what the lock did or didn't prevent. The lock is an optimization to avoid contention and wasted work; the constraint is the actual correctness guarantee.

21
Very HardYou reduced API latency 30% via "multi-level Redis caching, N+1 elimination with JPA batch fetching, HikariCP connection-pool tuning." What were the cache levels, and how did you keep them consistent when the underlying data changed?

A typical two-level design: a small local/in-process cache (fastest — no network hop — but limited in size and not shared across instances) sitting in front of a shared Redis cache (a network hop slower than local memory, but shared across every instance and much larger), with the relational database as the source of truth behind both.

Consistency uses the cache-aside pattern: reads populate the cache on a miss, and writes explicitly invalidate (or update) the relevant key at both levels the moment the underlying row changes, rather than relying purely on a TTL, which would leave a window of visibly wrong data after every write. TTL is a safety net, not the main mechanism. Two cache levels means two places that can go stale, which is the complexity cost of the extra speed. Be ready for the other two parts of the 30% as well: how you spotted the N+1 (SQL logs showing one query per row, fixed with JOIN FETCH, @EntityGraph or @BatchSize) and what you changed in HikariCP (pool size, connection timeout, leak detection).

Scenario-Based Questions

Practical, production-flavoured situations in the exact domain your resume already covers — debugging, incidents, trade-offs, and judgment calls. These test how you think under pressure, not just what you know.

Easy
01
EasyKafka resumeYour Kafka consumer group's lag suddenly spikes during peak traffic. What's your first step to diagnose it?

Check per-partition consumer lag first to see if it's uniform (a throughput problem) or concentrated on a few partitions (a skew/hot-key problem). Confirm every consumer instance in the group is actually alive and processing, not stuck or silently dead. Then check whether the consumer's own processing step includes a slow call (a downstream service, a DB query) — since consumer throughput is capped by how long each message takes to process, a slow-but-not-failing downstream call is the single most common real cause of a sudden lag spike under peak load.

02
EasyA colleague asks you to unit-test a new HyperTrack timesheet validation (e.g. "no more than 24 hours logged per day"). What would you mock, and what would you actually assert?

Mock any repository or external dependency the validator touches, so the test exercises only the validation logic. Feed a handful of representative inputs — a clearly passing case, a clearly failing case, and boundary cases right at the threshold (exactly 24 hours, 24 hours and 1 minute) — and assert both the pass/fail outcome and the specific error message returned. A rule that fails without a clear message is a production-support headache, so the message deserves an assertion too. JUnit 5's @ParameterizedTest keeps all those cases in one tidy test.

03
EasyYour team wants a new health check added to the centralized monitoring service ahead of a big release. What would you check, and how would you expose it?

Identify the specific new dependency the release introduces (a new downstream call, a new DB table, a new third-party API) and write a Spring Actuator custom HealthIndicator that checks it directly — a lightweight connectivity check, not a full functional test. That indicator is aggregated automatically into /actuator/health, which your monitoring service already polls and alerts on, so the new check plugs into existing infrastructure instead of needing its own monitoring path.

Medium
04
MediumAfter every deploy, users see errors for about 30 seconds while the new container starts. The team asks you to fix it. What's happening, and what would you change?

The pipeline stops the old container and then starts the new one, so for the Spring Boot startup time nothing is serving requests. Worse, the old container may be killed mid-request. Fix it in steps: enable graceful shutdown (server.shutdown=graceful) so in-flight requests finish; run two containers behind a reverse proxy such as Nginx and replace them one at a time; and only send traffic to the new container once its /actuator/health (readiness) is green. That is essentially a rolling or blue-green deployment on a single server.

Also make every release backward-compatible for one deploy cycle: during a rolling update, old and new versions serve traffic at the same time, so response and database changes must be additive first and only cleaned up in a later release.

05
MediumYour Resilience4j circuit breaker keeps tripping open even though you've confirmed the downstream service itself is healthy. What would you check in your config?

Check the failure-rate threshold and the sliding window size/type — a too-small window or an overly aggressive threshold can trip on ordinary transient blips that aren't a real outage. Check how "failure" is actually defined: if the timeout is set too tight, genuinely slow-but-successful calls get counted as failures, inflating the failure rate artificially. And don't rule out a real intermittent issue elsewhere in the call path that a surface-level "downstream looks fine" check wouldn't catch — confirm you're actually measuring the same thing the breaker is reacting to.

06
MediumKafka resumeA dead-lettered Kafka event needs reprocessing now that you've fixed the bug that failed it — but replaying it risks double-charging a customer. How do you reprocess it safely?

This is exactly why idempotent consumers were built in the first place: if the processing path is genuinely idempotent (keyed on a unique transaction/event ID), replaying the message through the same path is safe by design — if the charge already happened before the original failure, the idempotency check short-circuits it as a no-op; if it never happened, it completes normally now. The one thing worth confirming before replaying: exactly where in the original flow the failure occurred (before or after the side effect), so you're not assuming idempotency covers a path it was never actually built to cover.

07
MediumYour covering-index optimization improved dashboard read latency, but write throughput on that same table has since dropped noticeably. How do you explain this, and what do you do?

Every index has to be maintained on every INSERT/UPDATE/DELETE that touches an indexed column — this is the standard read/write trade-off of indexing, and a wider covering index costs more to maintain than a narrow one. The response isn't "remove the index" reflexively — first confirm this specific index is actually the cause (vs. some unrelated regression), then look at whether a narrower or partial index could deliver most of the same read speedup with less write overhead, or whether the write path itself can absorb the cost better (batching writes, for example).

08
MediumYour Jenkins pipeline builds and deploys fine for every feature branch, but fails intermittently only on the release branch. How do you debug this?

Start by isolating what's actually different about that one branch's pipeline run rather than assuming it's the same job under a different name: check whether the release branch triggers extra stages feature branches don't (the ACR push, the deploy to the server, different credentials), and whether it runs on a different agent than feature builds — a resource-constrained or differently configured agent is a very common source of "works everywhere except this one path." Pull the console output from a few failed release runs and compare it line by line against a successful run at the same stage, rather than guessing from the final error alone. Intermittent failures especially point toward a race condition (two release builds queued back-to-back sharing a workspace or the same image tag) or a flaky external dependency only the release stage calls (the Azure login, the registry, the SSH connection to the server).

09
MediumOn release day, the SonarQube quality gate starts failing every build, and the release is blocked. Your lead asks whether you can just skip the gate. What do you do?

First find out why it's failing: open the SonarQube report and check which condition broke (coverage on new code, a new bug, a vulnerability, an unreviewed security hotspot). Often it is small, e.g. a new class without tests dropping coverage below the threshold, and fixable in less time than the argument takes.

If the failure is a real vulnerability or bug, skipping the gate means shipping it knowingly, so push back and propose fixing just that issue. If it's a false positive, mark it in SonarQube with a written reason rather than disabling the gate for everyone. If the business truly needs the release now, get an explicit, recorded decision from the lead and create a ticket to fix it right after. Never quietly remove waitForQualityGate from the Jenkinsfile.

Hard
10
HardYour centralized Keycloak/SSO service goes down entirely. Walk through the blast radius across your 8+ dependent microservices, and what you'd want already built to limit the damage.

If every service validates JWTs locally against cached public signing keys (JWKS fetched and cached ahead of time, not fetched live per-request), already-authenticated traffic keeps working through the outage — tokens remain valid until their own expiry regardless of whether the issuer is currently reachable. The real damage in that design is limited to new logins and token refreshes failing until Keycloak recovers.

The dangerous alternative — and the thing worth actively designing against — is any service doing a live token-introspection call to Keycloak on every request. In that design, Keycloak going down becomes an instant, total authentication outage across all 8+ services simultaneously: a single point of failure hiding behind what was meant to be a resilience-improving centralization.

11
HardYou need a Flyway migration that renames a column on a large, busy HyperTrack table. A plain ALTER TABLE … RENAME would break the version still running during the deploy. How do you roll it out safely?

Use expand and contract across several releases instead of one breaking change. Release 1 (expand): a Flyway migration adds the new column; the code writes to both old and new columns and still reads the old one; a batch job copies existing data across in chunks, so no long table lock. Release 2: the code reads from the new column. Release 3 (contract): once nothing uses the old column, a final migration drops it.

Also: never edit a migration that has already run (Flyway's checksum check will fail, and other environments will drift). Fix mistakes with a new, forward migration. Test the migration against a copy of production-sized data to see how long it locks the table.

12
HardUnder real peak load, your retry policy against a flaky third-party service seems to be making the outage worse, not better. What's likely misconfigured?

Almost certainly missing or insufficient backoff-with-jitter. If failed calls retry immediately, or every client's retries land on the same fixed delay, retries arrive in synchronized waves that pile onto an already-struggling downstream — a retry storm that deepens the outage instead of riding it out. The fix is exponential backoff with randomized jitter so retries spread out over time instead of synchronizing. Also worth checking: that retries aren't being attempted on requests that will never succeed regardless (a validation error, a 400) — retrying those only burns capacity for zero chance of success — and that retry and circuit breaker are wired together, so retries actually stop once the breaker trips open, rather than continuing to hammer a downstream the breaker has already given up on.

13
HardDuring a DR drill, the failover completes and every service's health check is green — but the scheduled reconciliation jobs don't run, and one third-party banking integration times out. What do you check?

Green health checks only prove the apps started; they don't prove the DR site is wired like production. For the jobs: check whether the scheduler is actually enabled on the DR instances (often a config flag or profile that differs per site), whether a job lock such as ShedLock or a DB lock row is still held by the primary site, and whether the job's database user and connection point at the DR database.

For the integration: the bank almost certainly whitelists your server IPs, so the DR site's outbound IPs may not be on the partner's allowlist; also check DNS, firewall rules, and that the certificates and encryption keys used for that integration exist on the DR site. The lesson worth saying: add these checks (a test transaction per integration, a job heartbeat) to the post-switchover validation checklist so the next drill catches them in minutes.

Very Hard
14
Very HardA regulator asks you to prove a specific banking transaction from 6 months ago was correctly authorized and hasn't been tampered with since. What in your architecture actually answers that, and where might the real gaps be?

The audit records (who initiated and approved the transaction, under which role from the RBAC setup, with which authenticated identity from SSO, at what time) answer the "correctly authorized" half. But "hasn't been tampered with since" is a stronger, different claim: AES-256 encryption protects confidentiality in transit to the third party; it says nothing about whether the stored audit record itself could be edited afterwards by someone with database access.

A defensible answer needs a separate tamper-evidence mechanism: an append-only/write-once audit store, a cryptographic hash chain over audit records, or at least row-level signatures that would visibly break if a record were altered. If the real system only has an audit table in an otherwise normal, mutable database, the honest answer is that this is a real gap that encryption doesn't cover. Recognizing that distinction, rather than overclaiming, is what a strong candidate does here.

15
Very HardKafka resumeTwo microservices consume the same Kafka topic, but one processes twice as fast as the other and drifts far ahead in "understanding" recent events. Could this create a consistency problem, and how would you design around it?

Yes, if anything assumes the two services stay roughly in sync. If the fast service (already having processed event N+5) makes a synchronous call to the slow service expecting it to already reflect a state change from event N+2, and the slow service is still stuck back at event N, that call gets answered with stale state — a real, silent consistency bug, not a crash.

The robust design avoids the assumption entirely: each consumer should be independently correct based only on the stream itself, maintaining its own view of the data rather than depending synchronously on a sibling's current position. Where a genuine ordering dependency can't be avoided, make it explicit — e.g. the fast service checks "has the slow service processed at least up to offset/version X" before proceeding. This is the practical meaning of "eventual consistency" in an event-driven system, and naming the specific failure mode it creates, not just the term, is what this question is testing.

On: Camunda multi-level approval workflows
09
MediumAn approver is on leave for two weeks and timesheets are stuck waiting on them. What does your escalation actually do, and after how long?

Describe the real mechanism: a timer boundary event on the approval user task (e.g. a duration such as P2D, two days) that fires if the task isn't completed. 10
HardYou change the approval BPMN (add a new approval level) while hundreds of process instances are already running on the old version. What happens to them?

Camunda versions process definitions: deploying the new BPMN creates version 2, new instances start on it, and running instances keep executing on version 1 until they finish. Usually that is fine: old timesheets finish under the old rules. If running instances must move to the new flow, Camunda's process instance migration API can map activities from version 1 to version 2, but you need to test the mapping carefully, especially for instances waiting on a task that no longer exists. Keep the Java delegates backward-compatible while both versions are live.

Very HardIf one specific microservice needs a slightly different authorization rule than the rest, how does the centralized design accommodate that exception without re-introducing per-service special-casing?

On: distributed locking in the rental platform
13
HardWhich specific distributed locking mechanism did you use, and why that one over the alternatives?

Common real options worth being able to compare: a Redis-based lock (fast, already in your stack since Redis is used for caching too, but needs careful TTL/lease handling to be safe — Redisson's RLock handles much of this), a PostgreSQL advisory lock (no new infrastructure, transactionally tied to the database you already trust, but scoped to a single DB connection/session), or a dedicated coordination service like ZooKeeper (the strongest correctness guarantees, but real operational overhead for a system that doesn't already run one). A strong answer picks one, names the real trade-off against at least one alternative, and explains why that trade-off fit this specific use case.

14
Very HardWhat lock timeout/lease duration did you choose, and how did you decide it was long enough for the critical section but short enough not to hold up other users on a crash?

This is a genuine engineering trade-off worth reasoning through explicitly rather than stating a number in isolation: the lease needs to comfortably exceed the critical section's realistic worst-case duration (including a slow DB write or an occasional GC pause) to avoid the lock expiring while still legitimately in use — which would let a second request in concurrently despite the first not actually being done. But too generous a lease means a genuine crash holds up every other user on that resource for that whole duration. A strong answer names an actual value and the reasoning behind it (e.g. "3x the p99 observed duration of the critical section"), not just "we set a timeout."

16
HardAfter failing back to the primary site, how did you confirm no transactions were lost or duplicated during the switch?

REF Before the interview

How to Use This

A practical run-through, in order
  • Conceptual Questions first, closed-book. If any of these make you hesitate, that's a real gap to close before anything else — they're the ones any competent interviewer expects instantly.
  • Resume-Based Questions next — answer out loud, then compare to the model answer. The goal isn't to memorize the model answer verbatim; it's to check whether your own real experience can get to the same level of specificity (the actual mechanism, not just the headline number).
  • Scenario-Based Questions as a stress test. These deliberately extend beyond exactly what's on the resume — practice reasoning through them live, since a real interview will do the same.
  • Deep-Dive Follow-ups, and be honest with yourself. If a follow-up exposes a detail you genuinely don't know about your own project, that's more useful to discover now than in the room — go find the real answer, or be ready to say plainly "we didn't design for that" if it's a genuine gap.
  • Behavioral Questions last, out loud, not just in your head. A story that sounds complete when you think it through silently often turns out to have gaps once you actually say it — practice these the same way you'd practice the technical ones, not as an afterthought the night before.
Difficulty is directional, not absolute

These tags reflect typical interview difficulty for someone at a senior-engineer level, not an objective scale — a "Hard" question you've genuinely lived through in production should feel easier than an "Easy" concept you've only read about. Weight your prep time toward wherever your real confidence is thinnest, regardless of the label.

A note on the model answers

The Resume-Based and Scenario answers are written to be technically strong and grounded in the exact numbers your resume states — but for details your resume doesn't specify (which exact locking library, which exact config values), they describe the reasoning and common real choices rather than inventing a false specific. Swap in your own actual implementation details wherever they differ — an interviewer values a correct, specific account of what you really built far more than a polished generic one.
