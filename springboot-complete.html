01 Core Concepts

IoC & Dependency Injection

Every Spring app you'll ever touch rests on one inversion: your classes stop constructing their own collaborators, and instead declare what they need — the container builds the graph and hands it to them.

8 min read Beginner-friendly

Inversion of Control, precisely

In plain Java, an object that needs a collaborator typically creates it: new PaymentGateway(). Inversion of Control flips who's in charge — the IoC container (Spring's ApplicationContext) creates, configures, and wires objects, and your class simply declares what it needs. Dependency Injection is the specific mechanism that implements this: dependencies are supplied to an object rather than built by it.

Component classes@Service, @Repository...
Component scandiscover candidates
ApplicationContextthe IoC container
Wired object graphready to use

The container reads your annotations (or Java config), figures out the dependency graph, instantiates every bean in the right order, and injects each one's dependencies — all before your code ever runs.

Three ways to inject, one clear winner

TypeHowNotes
ConstructorVia constructor parametersRecommended. Fields can be final, the object is never in a half-wired state, missing dependencies fail fast at startup, and tests just call new with mocks — no Spring required
SetterVia a setter methodReasonable for genuinely optional dependencies
Field@Autowired directly on a fieldLooks concise, but hides dependencies from the constructor signature and makes the class impossible to instantiate without Spring or reflection in tests — avoid it
OrderService.java
@Service
public class OrderService {
    private final PaymentGateway gateway;      // final — enforced, never null after construction

    public OrderService(PaymentGateway gateway) {  // constructor injection
        this.gateway = gateway;              // @Autowired is optional here — a single constructor is inferred
    }
}

Spring's stereotypes

All of these are specializations of the same underlying idea (a Spring-managed bean) — the different names exist purely to communicate a class's role, and some (like @Repository) add real behavior on top.

AnnotationRole
@ComponentGeneric Spring-managed bean — the base annotation the others build on
@ServiceBusiness logic layer (semantic marker, behaves like @Component)
@RepositoryPersistence layer — also enables automatic translation of database-specific exceptions into Spring's unified DataAccessException hierarchy
@Controller / @RestControllerWeb layer — the latter adds implicit JSON body serialization on every method
@Configuration + @BeanJava-based bean definitions, for objects you don't own the source of (a third-party client)

Resolving ambiguity

  • Spring resolves @Autowired by type first. If multiple beans match that type, it falls back to matching by name.
  • @Qualifier("beanName") — explicitly pick one specific bean among several candidates of the same type.
  • @Primary — designate a default winner when multiple beans of a type exist and no qualifier is given.
  • @Profile("dev") — only register a bean when a given profile is active, the standard way to swap implementations between environments.
Circular dependency

Bean A needs bean B, which needs bean A. With constructor injection, Spring detects this at startup and refuses to start — which is exactly the point: a real circular dependency almost always indicates a design problem. Fix it by extracting the shared behavior into a third bean both depend on. @Lazy or setter injection can paper over the cycle, but treat that as a last resort, not a habit.

BeanFactory vs. ApplicationContext — what's the actual difference?

BeanFactory is the base container interface — lazy bean instantiation, minimal features. ApplicationContext extends it with everything a real application actually wants: eager singleton initialization at startup (so config errors surface immediately, not on first use), internationalization, application-event publishing, and first-class annotation support. Every Spring Boot app uses an ApplicationContext; BeanFactory is mostly of historical/academic interest now.

Quick summary
  • IoC means the container controls object creation and wiring; DI is the mechanism that supplies dependencies rather than letting objects build their own.
  • Constructor injection is the default choice — immutable, fails fast, testable without Spring.
  • Stereotypes (@Service, @Repository, @Controller) are semantic markers on top of @Component — @Repository additionally translates persistence exceptions.
  • Ambiguous injections resolve by type, then name; @Qualifier, @Primary, and @Profile give you explicit control.
IoC vs. DITap to reveal

IoC is the principle (container controls wiring); DI is the mechanism that implements it (dependencies supplied, not built).

Why constructor injectionTap to reveal

Immutable final fields, fails fast on missing deps, and testable with plain new + mocks — no Spring context needed.

@Repository's extra jobTap to reveal

Translates database-specific exceptions into Spring's unified DataAccessException hierarchy.

Circular dependencyTap to reveal

Constructor injection catches it at startup by refusing to start — treat it as a design smell, not a bug to route around.

Why is field injection (@Autowired directly on a field) discouraged compared to constructor injection?
Field injection has no runtime performance cost — the issue is purely design: the dependency isn't visible in the constructor, the field can't be final, and testing requires either a Spring context or reflection tricks instead of a plain new ClassUnderTest(mockDep).
Two beans implement the same interface. You inject the interface type with no qualifier and no @Primary. What happens?
Spring refuses to guess. Without a name match, a @Qualifier, or a @Primary designation, an ambiguous injection point is a startup failure — deliberately, so the ambiguity is caught immediately rather than resolved unpredictably.

Bean Lifecycle & Scopes

A bean isn't just "constructed" — it passes through a defined sequence of hooks before it's ready to use, and how long it lives depends entirely on its scope. Both are frequent sources of subtle, hard-to-diagnose bugs.

7 min read Intermediate

The full lifecycle

Instantiateconstructor runs
Populateinject dependencies
@PostConstructinit hook
In useproxies wrap it here
@PreDestroysingletons only

The full ordering: instantiate → populate properties → Aware callbacks (BeanNameAware, ApplicationContextAware) → BeanPostProcessor.postProcessBeforeInitialization → @PostConstruct → InitializingBean.afterPropertiesSet() → custom init-method → BeanPostProcessor.postProcessAfterInitialization (this is exactly where AOP proxies get created) → the bean is in service → @PreDestroy → DisposableBean.destroy() → custom destroy-method.

CacheLoader.java
@Component
public class CacheLoader {
    @PostConstruct
    public void warmUp() { /* load cache before the bean serves traffic */ }

    @PreDestroy
    public void flush() { /* persist state before shutdown */ }
}
Why proxies matter for this ordering

AOP proxies (the mechanism behind @Transactional, @Cacheable, custom aspects) are created in the second BeanPostProcessor phase — after your @PostConstruct logic has already run on the real, unproxied object. This is exactly why calling one advised method from another method inside the same @PostConstruct block still bypasses the proxy: it hasn't been wrapped yet at that point in the lifecycle.

InitializingBean/DisposableBean vs. the annotations

The lifecycle hooks above didn't start out as annotations — Spring's original mechanism was a pair of interfaces, and they still work exactly the same way today.

CacheLoader.java (interface style)
@Component
public class CacheLoader implements InitializingBean, DisposableBean {
    @Override
    public void afterPropertiesSet() { /* load cache before the bean serves traffic */ }

    @Override
    public void destroy() { /* persist state before shutdown */ }
}

Functionally identical to the @PostConstruct/@PreDestroy version above — same position in the lifecycle, same guarantees. The difference is entirely about coupling: implementing the interface ties the class directly to the Spring API (the method names afterPropertiesSet/destroy are fixed by the interface contract), while the annotations let you name the method anything you like and keep the class technically framework-agnostic. Spring's own reference documentation recommends the annotation style for exactly this reason — reach for the interfaces mainly when you're writing framework or library code that can't assume annotation processing is configured a certain way.

Reacting to events: ApplicationListener & @EventListener

Bean-level hooks only ever fire for the one bean that declares them. Spring's event system solves a different problem: letting any number of independent beans react to something that happened elsewhere in the application, without depending on whatever published it.

OrderEvents.java
public record OrderPlacedEvent(String orderId, BigDecimal total) {}

@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public void placeOrder(Order order) {
        // ... persist the order ...
        publisher.publishEvent(new OrderPlacedEvent(order.id(), order.total()));
    }
}

@Component
public class ReceiptMailer {
    @EventListener
    public void onOrderPlaced(OrderPlacedEvent event) {
        // runs synchronously, on the same thread, right after publishEvent() — add @Async to change that
        mailClient.sendReceipt(event.orderId(), event.total());
    }
}

OrderService never references ReceiptMailer at all — it just publishes a fact. Any number of other listeners (an analytics recorder, a fraud check, an inventory decrement) can subscribe to the exact same event with zero changes to OrderService, which is the whole point: publisher and listeners stay decoupled, and adding a new reaction to "an order was placed" never means touching the code that places it.

Spring publishes its own lifecycle milestones through this same mechanism — ContextRefreshedEvent fires once the ApplicationContext has fully initialized, and ApplicationReadyEvent fires after that, once the application is genuinely ready to serve requests (the embedded server is up and listening). ApplicationReadyEvent is the idiomatic place for startup work that needs the entire context available — unlike @PostConstruct, which only guarantees that one bean's own dependencies are ready, not the whole application.

Bean scopes

ScopeLifetime
singleton (default)Exactly one instance for the entire container
prototypeA brand-new instance every time it's injected or looked up
requestOne instance per HTTP request (web applications)
sessionOne instance per HTTP session (web applications)
applicationOne instance per ServletContext
The prototype-in-singleton trap

Inject a prototype-scoped bean directly into a singleton-scoped one, and you get exactly one prototype instance — created once, at the moment the singleton itself was wired, then reused forever. The singleton is only assembled once, so the injection only happens once. To get a genuinely fresh instance on every use, inject an ObjectProvider<T> (or Provider<T>) and call .getObject() each time, or use method injection via @Lookup.

Singleton beans must be stateless

A singleton is shared across every thread handling every request. Storing per-request or per-user data in a singleton's instance fields is a direct path to concurrency bugs — two requests racing to overwrite the same field. Keep singleton state either immutable (set once at construction) or externalized (a database, a cache, thread-local storage used carefully).

A singleton bean has a prototype bean injected via the constructor. You call a method on the singleton 100 times, expecting a fresh prototype each time. What actually happens?
The singleton is constructed exactly once, so its constructor injection happens exactly once — whatever prototype instance was injected then is the only one it will ever hold. Getting a fresh instance per call requires ObjectProvider or @Lookup, not plain injection.
Quick summary
  • The lifecycle order is instantiate → populate → Aware callbacks → BeanPostProcessor (before) → init hooks → BeanPostProcessor (after, AOP proxies created here) → in service → destroy hooks.
  • Singleton is the default scope and must stay stateless; prototype creates a fresh instance per lookup — but only per lookup, not automatically per use inside a singleton.
  • Fix the prototype-in-singleton trap with ObjectProvider or @Lookup, not by changing the singleton's own scope.
  • InitializingBean/DisposableBean are the original interface-based hooks — functionally identical to @PostConstruct/@PreDestroy, just more tightly coupled to the Spring API.
  • @EventListener lets independent beans react to something published elsewhere via ApplicationEventPublisher, with no direct dependency between them; ApplicationReadyEvent and ContextRefreshedEvent are Spring's own built-in events on the same mechanism.
03 Core Concepts

Spring Boot Essentials

Plain Spring gives you IoC and DI; Spring Boot's entire contribution is removing the tedium around them — one annotation, curated dependencies, an embedded server, and a mountain of sensible defaults you're free to override.

7 min read Intermediate

What Spring Boot actually adds on top of Spring

Auto-configuration

  • Configures beans automatically based on what's on the classpath and what properties are set

Starters

  • Curated dependency bundles — spring-boot-starter-web, -data-jpa, -security — so you stop hand-picking compatible versions
  • Version alignment comes from inheriting spring-boot-starter-parent as your Maven parent POM (or importing spring-boot-dependencies as a Gradle/Maven BOM) — it pins one known-compatible version for every dependency in the Spring ecosystem, so you stop guessing which Jackson version plays nicely with which Spring Data release

Embedded server

  • Tomcat/Jetty/Undertow ships inside your app — run it as a plain, standalone JAR, no external server to install

Opinionated defaults

  • Sensible out-of-the-box configuration for everything — all overridable, none mandatory

@SpringBootApplication is three annotations wearing a trenchcoat

AnnotationPurpose
@ConfigurationMarks this class as a source of bean definitions
@EnableAutoConfigurationThe actual trigger for classpath-driven auto-configuration
@ComponentScanScans this package and its sub-packages for @Component-annotated classes

How auto-configuration actually decides what to build

Auto-configuration classes are listed in a metadata file bundled with each starter (META-INF/spring/...AutoConfiguration.imports, formerly spring.factories). Each one is wrapped in conditional annotations that only activate it when specific circumstances hold.

ConditionalActivates when
@ConditionalOnClassA specific class is present on the classpath
@ConditionalOnMissingBeanNo bean of that type has already been defined — your explicit bean always wins
@ConditionalOnPropertyA specific configuration property is set to a specific value
A concrete example, worked through

Add spring-boot-starter-data-jpa to your classpath, and Boot's auto-configuration checks: is DataSource.class present? Yes (the starter pulled it in). Has the developer already defined their own DataSource bean? No. So Boot creates one automatically from your application.yml connection properties. Define your own DataSource bean explicitly, and @ConditionalOnMissingBean makes the auto-configured one back off entirely — your bean wins, with zero configuration changes needed elsewhere.

DataSourceAutoConfiguration.java (simplified)
@Configuration
@ConditionalOnClass(DataSource.class)
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public DataSource dataSource(DataSourceProperties props) {
        // only ever created if the app hasn't already registered its own DataSource bean
        return props.initializeDataSourceBuilder().build();
    }
}

This is a simplified sketch of the real thing, but it's mechanically exact: two conditions gate the bean, and both have to hold. @ConditionalOnClass checks the classpath once, at startup; @ConditionalOnMissingBean is re-checked against whatever else the application context has already registered. Define your own @Bean DataSource anywhere in your own configuration, and this one simply never runs — no error, no override flag, nothing to remember.

Debugging auto-configuration

Run with --debug, or hit /actuator/conditions on a running app, to get a full report of every auto-configuration class considered, whether it matched, and exactly which condition made it match or not — indispensable the first time "why isn't my bean being created" comes up.

How the embedded server & packaging actually work

The web starter pulls in an embedded server (Tomcat by default) as an ordinary library dependency — Spring Boot starts it programmatically inside your own main() method, rather than deploying your code into a separately-installed server. The build produces a self-contained "fat JAR": your compiled classes plus every dependency, including the server itself, bundled together with a special nested-JAR layout and a small JarLauncher that knows how to unpack and run it — runnable anywhere with just java -jar app.jar.

Isn't "magic" auto-configuration risky in production?

Less than it sounds — every decision is inspectable (/actuator/conditions), every default is overridable by defining your own bean or setting a property, and the conditional system is deliberately designed so your explicit choices always take precedence. The "magic" only ever fills gaps you haven't already filled yourself.

Why is @ConditionalOnMissingBean described as "the key to override-friendly defaults"?
This is exactly how Boot avoids ever conflicting with your explicit configuration: the auto-configured bean is annotated to only activate when no bean of that type exists yet — your own @Bean definition always wins without any extra effort on your part.
How is a Spring Boot app typically packaged and run in production?
The embedded server model means there's no separate application server to install and deploy into — the JAR contains everything needed to run, which is exactly what makes containerizing a Spring Boot app in Docker so straightforward.
Quick summary
  • Spring Boot's job is auto-configuration, starters, an embedded server, and opinionated (but overridable) defaults — nothing about IoC/DI itself changes.
  • @SpringBootApplication bundles @Configuration + @EnableAutoConfiguration + @ComponentScan.
  • Auto-configuration is entirely conditional — @ConditionalOnClass and @ConditionalOnMissingBean are the two you'll reason about most.
  • /actuator/conditions or --debug shows exactly why each auto-configuration decision was made.

Configuration & Profiles

The same JAR needs to behave differently in dev, staging, and production — different database URLs, different log levels, different feature flags — without a single line of code changing between them.

6 min read Beginner-friendly

Externalized configuration

application.properties / application.yml hold configuration that lives outside your compiled code — database URLs, ports, feature flags, timeouts. Profiles let you layer environment-specific overrides on top: application-dev.yml or application-prod.yml, activated by setting spring.profiles.active=dev. Only the values that differ need to appear in the profile-specific file; everything else falls through to the base file.

Type-safe configuration binding

@ConfigurationProperties binds a whole group of related properties to a single, type-safe object — preferred over scattering individual @Value("${...}") annotations across the codebase, especially as a config group grows past two or three properties.

MailProps.java
@ConfigurationProperties(prefix = "app.mail")
public record MailProps(String host, int port, boolean tls) {}
// binds app.mail.host, app.mail.port, app.mail.tls from application.yml — validated at startup, not on first use
Why this beats scattered @Value

A typo in a @Value("${app.mial.host}") string silently resolves to nothing and fails at runtime, wherever that field happens to get used. A misconfigured @ConfigurationProperties record fails immediately at startup, in one place, with a clear binding error — and refactoring an IDE can actually track, since it's a real type, not a String key scattered across dozens of files.

Nested configuration & relaxed binding

Real configuration is rarely flat, and the property names in a YAML file rarely match Java's camelCase convention exactly. Extending the same MailProps from above with a nested retry group demonstrates both at once.

MailProps.java (nested)
@ConfigurationProperties(prefix = "app.mail")
public record MailProps(String host, int port, boolean tlsEnabled, Retry retry) {
    public record Retry(int maxAttempts, Duration backoff) {}
}
// app.mail.retry.max-attempts and app.mail.retry.backoff bind straight into the nested Retry record
app:
  mail:
    host: smtp.example.com
    port: 587
    tls-enabled: true
    retry:
      max-attempts: 3
      backoff: 2s

Notice tls-enabled and max-attempts in the YAML but tlsEnabled/maxAttempts in the Java. This is relaxed binding: Spring Boot normalizes kebab-case, snake_case, and even upper-case environment-variable style (APP_MAIL_TLS_ENABLED) down to the same canonical form before matching them against your camelCase property names. Kebab-case is the conventional style in YAML/properties files precisely because relaxed binding treats it as equivalent to the rest — you never have to remember which casing a particular property source expects, and an env var can override a YAML key without the two ever needing to look alike.

Property precedence

When the same property is set in more than one place, Spring Boot resolves it by a strict precedence order — higher up the list always wins:

Command-line argshighest priority
Environment variables
Profile-specific fileapplication-dev.yml
application.ymllowest priority

This ordering is exactly what lets you ship one immutable container image and configure it differently per environment purely through env vars or a mounted config file — the 12-factor app pattern.

Common mistake

Baking environment-specific values (a production database password, a real API key) directly into application.yml and relying on profile activation alone to keep them separate. Profiles control which defaults apply — they're not a secrets boundary. Real secrets belong in environment variables or a secrets manager, injected at deploy time, never committed to the repo regardless of which profile "owns" them.

The same property is set in both application.yml and as an environment variable at deploy time. Which one wins?
Command-line args and environment variables outrank file-based configuration specifically so the same built artifact can be reconfigured per environment without editing or rebuilding it — the foundation of shipping one immutable image everywhere.
Quick summary
  • Profiles layer environment-specific overrides on top of a shared base configuration file.
  • @ConfigurationProperties gives type-safe, startup-validated config binding — preferred over scattered @Value for anything beyond a couple of properties.
  • Precedence: command-line args > environment variables > profile-specific file > base application.yml.
  • Profiles are not a secrets mechanism — real secrets belong in env vars or a secrets manager regardless of profile.
05 Cross-Cutting Concerns

Aspect-Oriented Programming

Logging, security checks, transactions, metrics — none of them belong to any one class's actual job, yet without AOP they'd be copy-pasted into every method that needs them. This is the single most misunderstood piece of "magic" in Spring, and the proxy mechanic behind it explains half of Spring's famous gotchas.

7 min read Advanced

Cross-cutting concerns & terminology

A cross-cutting concern is behavior that spans many otherwise-unrelated classes — logging every service call, wrapping every repository method in a transaction. AOP lets you define that behavior once and have it apply everywhere it's needed, without touching the business logic itself.

TermMeaning
AspectA module encapsulating one cross-cutting concern — an @Aspect-annotated class
Join pointA point during execution where an aspect could apply — in Spring AOP specifically, always a method execution
PointcutAn expression that selects which join points a piece of advice applies to
AdviceThe actual action taken at a matched join point
WeavingLinking aspects into the target objects — Spring does this at runtime, via proxies

Advice types

LoggingAspect.java
@Aspect @Component
public class LoggingAspect {
    @Around("execution(* com.app.service..*(..))")  // the pointcut expression
    public Object logTime(ProceedingJoinPoint pjp) throws Throwable {
        long t = System.nanoTime();
        try { return pjp.proceed(); }         // actually invoke the real method
        finally { log.info("{} took {}ns", pjp.getSignature(), System.nanoTime()-t); }
    }
}

@Around is the most powerful advice type — it wraps the entire call and decides whether/how to invoke the real method via proceed(). The others are simpler, single-purpose hooks: @Before, @After (runs regardless of outcome, like finally), @AfterReturning (only on success), @AfterThrowing (only on exception).

AuditAspect.java
@Aspect @Component
public class AuditAspect {
    @AfterReturning(pointcut = "@annotation(Audited)", returning = "result")
    public void logSuccess(JoinPoint jp, Object result) {
        // "result" must match the returning attribute name exactly — Spring binds the return value into it
        log.info("{} returned {}", jp.getSignature(), result);
    }

    @AfterThrowing(pointcut = "@annotation(Audited)", throwing = "ex")
    public void logFailure(JoinPoint jp, Exception ex) {
        // "ex" must match the throwing attribute name exactly — only fires when the method actually threw
        log.warn("{} threw {}", jp.getSignature(), ex.getMessage());
    }
}

Both binding attributes are name-matching contracts, not positional ones: whatever string you pass to returning/throwing has to be spelled identically as a method parameter name, and Spring wires the actual value into that parameter by matching the name. Get the two out of sync and Spring fails fast at startup with a pointcut-parameter mismatch, rather than silently passing null at runtime. Notice the pointcut itself is @annotation(Audited) rather than an execution(..) expression — it matches any method carrying a custom @Audited marker annotation, regardless of which package or class it lives in, which scales far better than an execution pattern once "audited methods" are scattered across many unrelated packages.

How Spring AOP actually works: proxies

Spring doesn't modify your class's bytecode. Instead, at bean-creation time, it wraps your bean in a proxy — a generated object with the same public interface that intercepts calls, runs the matched advice, then delegates to the real object.

Callerholds a reference to the bean
ProxyJDK dynamic proxy or CGLIB subclass
Advice runs@Before, or @Around's pre-proceed logic
Target methodthe real, unproxied object

The reference every other bean holds is the proxy's, not the target's — which is exactly why a call that never goes through that reference (self-invocation via this) never reaches the advice at all. After the target method returns, control unwinds back through the same proxy so any @AfterReturning/@After/@Around post-processing can run before the caller finally gets its result.

JDK dynamic proxy

  • Used when the bean implements at least one interface
  • Implements the same interface(s), delegating to the real object

CGLIB proxy

  • Used when the bean has no interface — a runtime-generated subclass instead
  • Cannot proxy final classes or methods, since it works by subclassing
The self-invocation pitfall — Spring's single most common "gotcha"

Calling one @Transactional, @Cacheable, or otherwise-advised method from another method in the same class goes through this, not through the proxy — so the advice silently does not run. No error, no warning; the annotation is simply inert for that call path. Fixes: inject the bean into itself (via @Lazy to break the circular reference) and call through that reference, extract the advised method into a separate bean, or use AopContext.currentProxy() (requires exposing the proxy explicitly) as a last resort.

Why does self-invocation bypass the proxy, mechanically?

When Spring creates the proxy, only the reference held by the container (and injected into other beans) points at the proxy. Inside the class's own methods, this still refers to the original, unwrapped target object — the compiler generated that call as a plain, direct method invocation on the real object, with no proxy anywhere in the path. The advice logic genuinely lives only in the proxy, so any call that never passes through it never triggers the advice.

A method annotated @Transactional is called from another method in the same class, via this.processOrder(). What happens to the transaction?
The proxy only intercepts calls that arrive through the bean reference the container manages. A same-class call via this never touches the proxy, so the @Transactional advice simply never runs — with no error to signal it.
A class has no interface and Spring needs to proxy it for AOP. What proxy mechanism is used, and what's a real limitation of it?
CGLIB works by generating a subclass at runtime and overriding methods — which is structurally impossible for a final class (can't be subclassed) or a final method (can't be overridden).
Quick summary
  • AOP factors cross-cutting concerns (logging, transactions, caching) out of business logic and into reusable aspects.
  • Weaving happens at runtime via proxies — JDK dynamic proxies for interfaces, CGLIB subclassing otherwise.
  • Self-invocation (calling an advised method from within the same class via this) silently bypasses the proxy — the most common source of "my @Transactional/@Cacheable isn't working" bugs.
  • @AfterReturning/@AfterThrowing bind their result/exception into the advice method by matching parameter name to the returning/throwing attribute string — get the names out of sync and startup fails fast.
  • @annotation(Audited) and similar pointcut designators target a marker annotation directly, scaling better than an execution(..) expression once matching methods are scattered across unrelated packages.
06 Cross-Cutting Concerns

Validation

Bad input should never reach your business logic. Bean Validation lets you declare the rules once, on the data itself, instead of hand-writing if checks at the top of every method that touches it.

5 min read Beginner-friendly

Bean Validation basics

Spring uses Bean Validation (the jakarta.validation specification, JSR-380), implemented by Hibernate Validator. Annotate the fields of a DTO with constraints, then trigger validation with @Valid at the point that data enters your system.

CreateUserReq.java
public record CreateUserReq(
    @NotBlank String name,
    @Email String email,
    @Min(18) int age,
    @Size(min = 8) String password) {}

@PostMapping
public UserDto create(@Valid @RequestBody CreateUserReq req) { ... }
AnnotationChecks
@NotNull / @NotEmpty / @NotBlankNot null / not an empty collection or string / not null-empty-or-whitespace
@Size, @Min, @MaxLength bounds / numeric bounds
@Email, @PatternBuilt-in email format / arbitrary regex
@Positive, @Past, @FutureNumeric sign / date relative to now

@Valid vs. @Validated

  • @Valid (standard Java/Jakarta annotation) triggers validation and cascades into nested objects — a @Valid List<LineItem> field validates every item in the list too.
  • @Validated (Spring's own annotation) is class-level, and unlocks two things @Valid alone can't: validation groups (different rule sets for "create" vs. "update") and method-level validation on plain service beans, not just controller parameters.
Failure handling

A failed @Valid check on a @RequestBody throws MethodArgumentNotValidException — caught centrally in a @RestControllerAdvice (see the Exception Handling chapter) to return a clean, consistent 400 response listing every failed field, rather than a raw stack trace.

Custom constraints

When the built-ins don't cover a business rule (a password matching a specific policy, a date range that must be internally consistent), define a custom annotation plus a ConstraintValidator implementation — the same declarative style, extended to your own domain logic.

ValidPostcode.java
@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = PostcodeValidator.class)
public @interface ValidPostcode {
    String message() default "invalid postcode format";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
PostcodeValidator.java
public class PostcodeValidator implements ConstraintValidator<ValidPostcode, String> {
    private static final Pattern PATTERN =
        Pattern.compile("^[A-Z]{1,2}\\d[A-Z\\d]?\\s?\\d[A-Z]{2}$");

    @Override
    public boolean isValid(String value, ConstraintValidatorContext ctx) {
        if (value == null) return true;  // let @NotNull own presence checks separately
        return PATTERN.matcher(value.trim().toUpperCase()).matches();
    }
}

The annotation is just metadata — @Constraint(validatedBy = ...) is what wires it to the class that does the actual work. Hibernate Validator instantiates PostcodeValidator once, then calls isValid() for every value the annotation is applied to, reporting the annotation's message() on failure. Returning true for null is deliberate: null-checking belongs to @NotNull, not to this constraint — folding both concerns into one validator makes it harder to tell "missing" from "present but malformed" apart in the resulting error message.

Common mistake

Validating only at the web layer and assuming that's sufficient. Any service method callable from elsewhere (a scheduled job, another service, a message consumer) that skips the controller entirely also skips @Valid on the request DTO. For genuinely critical invariants, validate again at the service layer with @Validated method validation, or enforce the constraint at the database level too (a CHECK constraint, a NOT NULL column) as defense in depth.

You need different validation rules for "create" (password required) vs. "update" (password optional) using the same DTO class. What's the mechanism for this?
Validation groups let the same annotated class apply different subsets of its constraints depending on which group is active for a given call — exactly the tool for "the same shape, different rules depending on context."
Quick summary
  • Bean Validation constraints live on the DTO itself; @Valid triggers and cascades them into nested objects.
  • @Validated adds validation groups and method-level validation on service beans — capabilities plain @Valid doesn't have.
  • A failed validation throws MethodArgumentNotValidException — handle it centrally for a consistent error response.
  • Controller-layer validation alone isn't enough for critical invariants reachable from non-HTTP entry points.
  • A custom constraint is just an annotation plus a ConstraintValidator<Annotation, Type> — @Constraint(validatedBy = ...) is the wire between them.

Exception Handling

Every controller throwing its own ad-hoc error responses is how APIs end up with five different error JSON shapes. Centralizing exception handling is what makes an API's failures as predictable as its successes.

6 min read Intermediate

Centralizing with @RestControllerAdvice

A class annotated @RestControllerAdvice intercepts exceptions thrown from any controller in the application, and each @ExceptionHandler method inside it maps one exception type to a specific HTTP response.

GlobalExceptionHandler.java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ApiError notFound(ResourceNotFoundException ex) {
        return new ApiError(404, ex.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ApiError invalid(MethodArgumentNotValidException ex) {
        var msgs = ex.getBindingResult().getFieldErrors().stream()
            .map(e -> e.getField() + ": " + e.getDefaultMessage()).toList();
        return new ApiError(400, "Validation failed", msgs);
    }
}
MechanismScope
@ExceptionHandler aloneJust the one controller it's declared in
@RestControllerAdviceGlobal — every controller in the application

RFC 7807 and a consistent error schema

RFC 7807 ("Problem Details for HTTP APIs") standardizes a machine-readable error shape — type, title, status, detail, instance — so clients can parse errors from your API the same way regardless of which endpoint failed. Spring Boot 3's ProblemDetail return type implements this directly, without you hand-rolling an error DTO.

Best practice: pick one error shape and never deviate

Whatever fields you choose — timestamp, status, an internal error code, a human message, a path, a list of field-level errors — return that exact shape from every single error response in the API, success or not, 400 or 500. A consistent shape is what lets client code write one error-parsing function instead of one per endpoint.

Never leak internals to the client

A raw stack trace or a database error message in an HTTP response is both a security leak (schema details, file paths, library versions) and a poor client experience. Catch broadly at the top (a generic Exception handler as a last-resort fallback), log the full detail server-side, and return only a generic message plus a correlation/trace ID the client can quote back to support — never the exception's own message for unexpected, unclassified failures.

@RestControllerAdvice can't see everything

An exception thrown inside a servlet filter — a custom JwtFilter failing to parse a malformed token, for instance — never reaches @RestControllerAdvice, no matter how broadly its handlers are written. Filters run before DispatcherServlet ever dispatches to a controller, and @RestControllerAdvice is itself advice wrapped around controller method invocations — it has no hook into the filter chain that runs ahead of it entirely. Handling a filter-level failure needs its own mechanism: typically an AuthenticationEntryPoint/AccessDeniedHandler pair wired into the SecurityFilterChain, writing the error response directly rather than throwing something for a controller-layer advice to catch. See the Spring Security Integration chapter for exactly where a custom JwtFilter sits in that chain, ahead of everything this chapter covers.

Why is a global @RestControllerAdvice generally preferred over per-controller @ExceptionHandler methods?
Without centralization, each controller either duplicates the same handler logic or (more likely) drifts into slightly different error responses over time. One global advice class is both less code and a structural guarantee of consistency.
Quick summary
  • @RestControllerAdvice + @ExceptionHandler centralizes error handling across every controller in one place.
  • RFC 7807 / Spring's ProblemDetail gives you a standard, machine-parseable error shape for free.
  • Pick one error response schema and use it everywhere, without exception.
  • Never return raw stack traces or internal exception messages to the client — log them, return a generic message and a correlation ID instead.
  • A servlet filter's exceptions never reach @RestControllerAdvice — that's a job for an AuthenticationEntryPoint/AccessDeniedHandler in the security config instead.

Spring Security Integration

OAuth2, OIDC, JWT, and CORS are protocols — the Security & Auth module covers that theory in depth. This chapter is the other half: how Spring Security actually wires those protocols into a running app, request by request.

8 min read Advanced

The filter chain: a gauntlet before your controller ever runs

In a secured Spring Boot app, no request reaches your @RestController directly. It first passes through a chain of servlet filters that Spring Security registers in front of DispatcherServlet — and any one of them can reject the request outright, long before your controller code ever executes.

SecurityContextHolderFilterloads the SecurityContext
UsernamePasswordAuthenticationFilterhandles form login
JwtFiltervalidates the JWT, every request
ExceptionTranslationFiltersecurity exceptions → 401/403
FilterSecurityInterceptorfinal authorization check

Only after every filter in the chain approves does the request finally reach DispatcherServlet and your controller. A rejection at any stage short-circuits the rest — the controller method body never runs.

The custom JwtFilter is deliberately written as extends OncePerRequestFilter rather than implementing Filter directly. A plain servlet filter can run more than once per client request — internal forwards (an error dispatch to /error, an async dispatch, a RequestDispatcher.forward()) all re-enter the filter chain. OncePerRequestFilter guarantees its doFilterInternal runs exactly once per request regardless of how many times it's internally dispatched — critical for a filter whose whole job is "check the token," since running it twice is at best wasted work and at worst a source of subtle bugs.

Configuring the chain: SecurityFilterChain, not WebSecurityConfigurerAdapter

WebSecurityConfigurerAdapter — the old pattern of extending a base class and overriding configure(HttpSecurity) — is deprecated and removed as of Spring Security 6. The modern replacement is a SecurityFilterChain @Bean, built with the lambda DSL:

SecurityConfig.java
@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http, JwtFilter jwtFilter) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

.addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class) is what actually slots the custom filter into the chain at the right position. CSRF is disabled here deliberately — this is a stateless, token-authenticated API with no browser-managed session cookie for a forged request to ride on; the CSRF theory behind that trade-off (and when you'd want it back) is covered in security-auth-complete.html.

UserDetailsService and PasswordEncoder

UserDetailsService is a one-method contract — loadUserByUsername(String username) — that tells Spring how to fetch a user (and their granted authorities) from wherever they actually live: a database, an LDAP directory, anywhere. Spring's authentication machinery calls it during login and hands the result, plus the raw submitted password, to whichever PasswordEncoder bean is configured.

In practice that's almost always BCryptPasswordEncoder. BCrypt is one-way — there is no decode(), only a comparison — and it salts automatically, meaning passwordEncoder.encode("password123") produces a different hash string on every single call, even for the exact same input, because a random salt is generated and embedded directly in the output. That's also why you never compare hashes with .equals() — passwordEncoder.matches(rawPassword, storedHash) is the only correct check, since it extracts the salt from the stored hash before re-hashing the candidate.

JwtFilter: validating the token on every request

JwtFilter.java
public class JwtFilter extends OncePerRequestFilter {

    private final JwtUtil jwtUtil;
    private final UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String header = req.getHeader("Authorization");
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);
            String username = jwtUtil.extractUsername(token);
            if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
                UserDetails user = userDetailsService.loadUserByUsername(username);
                if (jwtUtil.isValid(token, user)) {
                    var auth = new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
                    SecurityContextHolder.getContext().setAuthentication(auth);
                }
            }
        }
        chain.doFilter(req, res);
    }
}

Note the null-check on getAuthentication() — if a filter earlier in the chain already authenticated this request, JwtFilter doesn't redo the work. Once SecurityContextHolder holds an Authentication, everything downstream — @PreAuthorize checks, FilterSecurityInterceptor, Authentication.getPrincipal() in your controller — reads from it.

The full JWT-secured request flow

Client POSTs credentials/auth/login
UserDetailsService + PasswordEncodervalidate the credentials
JwtUtil.generateTokenHS256-signed, expiry set
Token returned to clientstored client-side
Authorization: Bearer <token>sent on every request
JwtFilter validatessignature + expiry

Login happens once; validation happens on every subsequent request, since a JWT-secured API is stateless — there's no server-side session to remember the client was already checked.

Access tokens are deliberately short-lived — 15 minutes to a day is typical — so a leaked token has a small blast radius. That would force constant re-logins if it were the whole story, so it's paired with a longer-lived refresh token: when the access token expires, the client silently exchanges the refresh token for a new access token instead of asking the user to log in again. The full OAuth2/OIDC token-lifecycle theory behind this pattern lives in security-auth-complete.html — this is the Spring-side plumbing that issues and checks the tokens.

@PreAuthorize, and role vs. authority

@PreAuthorize("hasRole('ADMIN')") enforces authorization at the method level rather than the URL level — it protects a service method no matter which controller (or which other service) ends up calling it, which a SecurityFilterChain's URL-pattern rules can't do. It requires @EnableMethodSecurity on your configuration class, and is evaluated via an AOP proxy exactly like @Transactional or @Cacheable — meaning it's subject to the exact same self-invocation blind spot covered in the AOP chapter.

A 403 can look exactly like a 404

If Spring Security is enabled and a URL isn't covered by permitAll(), an unauthenticated or under-privileged request gets a 401 or 403 — not necessarily a helpful error body. It's a genuinely common first-time gotcha to spend ten minutes convinced a route is missing or misspelled, when the actual issue is that the security config never allow-listed it. Why does JwtFilter extend OncePerRequestFilter instead of implementing Filter directly?
A plain Filter can re-enter the chain on internal dispatch (an error forward, an async dispatch), potentially re-running validation logic. OncePerRequestFilter tracks that the request has already been processed and skips a second pass.
A method is annotated @PreAuthorize("hasAuthority('user:delete')"). What does Spring check this against?
hasAuthority does an exact string match against the principal's granted authorities — unlike hasRole, Spring never prepends ROLE_ to it.

Quick summary
  • Every secured request runs through a filter chain before reaching the controller — any filter can reject it first.
  • A custom JwtFilter extends OncePerRequestFilter to guarantee exactly one execution per request, even across internal dispatch.
  • SecurityFilterChain (a @Bean, lambda DSL) replaces the deprecated WebSecurityConfigurerAdapter.
  • UserDetailsService loads the user; PasswordEncoder (BCrypt) checks the password — one-way, auto-salted, never compared by string equality.

Real-Time & RPC

Not everything fits request/response. A chat app needs the server to push without being asked; a fleet of internal services calling each other thousands of times a second needs something leaner than JSON over HTTP/1.1; and a service pinned under thousands of slow, concurrent connections needs to stop spending one whole thread per request. Three different problems, three different tools.

11 min read Advanced

WebSockets: when the server needs to push

HTTP is fundamentally request/response — the client always speaks first. WebSockets upgrade a single TCP connection into a full-duplex channel, so the server can push data to the client at any time without the client asking again. It's the backbone of chat, live dashboards, notifications, and collaborative editing.

Scaling past one instance

Spring's default in-memory broker keeps subscriptions in that one JVM's heap — fine for a single node, broken the moment you scale out. If user A connects to instance 1 and user B to instance 2, a broadcast on instance 1 never reaches B. The fix is an external broker relay (point Spring at RabbitMQ/ActiveMQ so every instance shares the same broker) or a lighter Redis pub/sub relay, combined with sticky sessions at the load balancer so each client stays pinned to the instance actually holding its socket.

gRPC is a high-performance RPC framework built on Protocol Buffers (a compact binary contract) and HTTP/2 (multiplexed, streaming transport). It's built for exactly one job better than REST: fast, strongly-typed, internal service-to-service communication.

Reactive programming: WebFlux, Mono & Flux

Spring MVC — the default stack used everywhere else in this module — is blocking: a thread is checked out of a pool for the entire lifetime of a request, including any time it spends waiting on a database call, a downstream HTTP call, or anything else I/O-bound. That's a fine trade-off until the number of concurrent, slow, I/O-bound requests starts to outgrow the thread pool itself. Spring WebFlux is Spring's alternative stack, built on Project Reactor, that handles requests without dedicating a thread to each one for its full duration.

TypeRepresents
Mono<T>An asynchronous stream of 0 or 1 result — the reactive equivalent of a single value or an Optional<T>
Flux<T>An asynchronous stream of 0 to many results, delivered over time — the reactive equivalent of a List<T>, except it hasn't all arrived yet
UserController.java
@RestController
public class UserController {
    private final UserRepository repo;  // a ReactiveCrudRepository, not a JpaRepository

    @GetMapping("/users/{id}")
    public Mono<User> getUser(@PathVariable String id) {
        return repo.findById(id);  // returns immediately — no user has actually been fetched yet
    }

    @GetMapping("/users/{id}/orders")
    public Flux<Order> getOrders(@PathVariable String id) {
        return orderRepo.findByUserId(id);  // streams orders to the client as each one resolves
    }
}

Neither method blocks anything. getUser returns a Mono — a promise of a user, not the user itself — the instant it's called; the actual database round trip happens later, off the calling thread entirely, and WebFlux writes the HTTP response only once that promise resolves. The controller's own thread is freed to go handle a different request in the meantime, which is the entire point of the exercise.

Blocking (MVC)thread parked until the DB call returns

Request arrivespicked up by the event loop

Same two requests, two completely different threading models. MVC's thread-per-request model is simple to reason about but doesn't scale past however many threads you can afford to have parked at once; WebFlux's event loop scales to far higher concurrency on far fewer threads, at the cost of a genuinely different programming model — chained operators and callbacks instead of sequential, step-by-step code.

Reach for WebFlux when

  • You're I/O-bound with high concurrency — thousands of slow, simultaneous connections (streaming APIs, long-polling, a gateway fanning out to many downstream services)
  • You're already calling non-blocking clients end-to-end — WebClient, a reactive driver for MongoDB/R2DBC/Redis
  • Memory footprint under high concurrency genuinely matters — far fewer threads means far less stack memory reserved per in-flight request

Stick with Spring MVC when

  • Any dependency in the call path is still blocking — a JDBC driver, most conventional JPA setups — since one blocking call inside reactive code stalls the shared event-loop thread for every request it's currently handling, not just this one
  • The team's mental model, debugging tools, and stack traces all assume sequential, blocking code — reactive stack traces are notoriously harder to read
  • Traffic comfortably fits within what a thread-per-request pool already handles — the added complexity has no payoff if you were never going to hit that ceiling
The one rule that actually matters

Never call a blocking API (a JDBC Statement, Thread.sleep(), a synchronous RestTemplate call) from inside reactive code. WebFlux runs on a small, fixed number of event-loop threads shared across every in-flight request — block even one of them and every other request currently multiplexed onto it stalls too. This is the single most common way WebFlux adoption goes wrong: a team migrates the controller layer to return Mono/Flux but leaves a blocking JDBC repository underneath, and loses most of the benefit while taking on all of the complexity.

Your chat app's WebSocket broadcasts stop reaching some users after you scale from 1 to 3 server instances. What's the most likely cause?
The simple in-memory broker is per-instance by design. Without an external broker relay (RabbitMQ/ActiveMQ) or a Redis pub/sub relay to share subscription state across instances, a broadcast on one node simply never reaches clients connected to another.
You're building an internal service that streams live price updates to another internal service, thousands of times per second. Would you reach for REST or gRPC, and why?
This is exactly gRPC's sweet spot: high-frequency, internal, streaming, service-to-service. REST's JSON-over-HTTP/1.1 model would work but pay real overhead per message that gRPC's binary framing and HTTP/2 multiplexing avoid.
Quick summary
  • WebSockets flip HTTP's request/response model into full-duplex — STOMP+SockJS is the standard higher-level protocol Spring builds on.
  • The default WebSocket broker is per-instance; scaling out requires an external broker relay or Redis pub/sub.
  • gRPC trades JSON's readability for protobuf's speed and strict, code-generated contracts — built for internal, high-throughput, streaming-capable service calls.
  • Use gRPC east-west (between your own services) and REST north-south (public/browser-facing) — many systems run both.
  • WebFlux trades thread-per-request for an event loop — Mono (0-or-1) and Flux (0-to-many) represent asynchronous results instead of blocking return values.
  • Reactive only pays off when the entire call chain is non-blocking end-to-end; one blocking call inside reactive code stalls the shared event loop for every other in-flight request, not just its own.

Writing a custom HealthIndicator

The built-in checks cover infrastructure Spring already knows about — the database, disk space. For anything domain-specific — a downstream payment gateway, a third-party API this service can't function without — implement HealthIndicator, and Spring Boot automatically folds it into the aggregate /actuator/health response with no registration step required.

PaymentGatewayHealthIndicator.java
@Component
public class PaymentGatewayHealthIndicator implements HealthIndicator {
    private final PaymentGatewayClient client;

    @Override
    public Health health() {
        try {
            client.ping();
            return Health.up().withDetail("gateway", "reachable").build();
        } catch (Exception ex) {
            return Health.down(ex).withDetail("gateway", "unreachable").build();
        }
    }
}

Spring Boot discovers this bean automatically and merges it into the overall health tree under a key derived from the class name — paymentGateway here — with its own UP/DOWN status rolling up into the top-level status. Health.down(ex) attaches the exception's message as a detail automatically, which is exactly what shows up in /actuator/health when this specific dependency is what broke, instead of a generic "the app is unhealthy" with no further clue where to look.

Micrometer & the three pillars

Micrometer is a vendor-neutral metrics facade — often described as "the SLF4J of metrics" — that lets your code emit metrics once and ship them to Prometheus, Datadog, or whatever backend you choose, without changing instrumentation code. Modern observability rests on three pillars, correlated by a shared trace ID:

Metrics

  • Numeric time series — request counts, latencies, error rates, JVM stats

Logs

  • Discrete, timestamped events — the detailed narrative of what happened

Traces

  • The path a single request took across services, with per-step timing
Secure your actuator endpoints

By default, only a small, safe subset of endpoints is exposed. Expanding management.endpoints.web.exposure.include to * in production without also securing access is a real, common misconfiguration — /actuator/env can leak configuration secrets, and /actuator/heapdump can leak application memory contents. Expose only what you need, and put actuator behind the same authentication/network boundary as everything else sensitive.

Kubernetes health probes

Actuator's health groups map directly onto Kubernetes' two-probe model: /actuator/health/liveness answers "is this instance broken and needs restarting," and /actuator/health/readiness answers "is this instance ready to receive traffic right now." Wiring these up correctly is what makes a rolling deploy actually graceful instead of routing traffic to a pod that isn't ready yet.

Forward reference

This chapter covers only the Spring-specific plumbing for exposing signals. The broader discipline — what to actually measure, alerting thresholds, distributed tracing patterns, dashboards, and the metrics/logs/traces trade-offs at scale — belongs to the dedicated Observability module later in the roadmap (Phase 6).

Why does Kubernetes need two separate health probes (liveness and readiness) instead of one?
A pod can be alive (no restart needed) but not yet ready (still warming up a cache, waiting on a dependency) — routing traffic to it during that window would cause errors even though restarting it would be the wrong fix. The two probes exist specifically to separate these two decisions.

Performance & Production Optimization

An app that works correctly in dev and an app that survives production load are two different achievements. This chapter is the short list of levers that actually move the needle — most of them are configuration, not architecture.

7 min read Intermediate

HikariCP: why connection pooling exists

Opening a new database connection isn't free — TCP handshake, authentication, sometimes TLS negotiation, routinely costing on the order of 100ms. Paying that cost on every single request would make the database connection itself the slowest part of most APIs. HikariCP — Spring Boot's default connection pool since Boot 2 — keeps a fixed set of connections already open and hands them out on request, so a request borrows a connection and returns it instead of opening and closing a real socket every time.

application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 30000   # ms to wait for a free connection before giving up
      max-lifetime: 1800000       # 30 min — must be LESS than the DB's own connection timeout
      idle-timeout: 600000

max-lifetime has to be shorter than whatever timeout the database itself enforces on idle or long-lived connections (MySQL's wait_timeout, for instance). If Hikari holds onto a connection past the point the database silently closes it, the pool doesn't find out until it hands that dead connection to a request — which then fails with a confusing "connection is closed" error that has nothing to do with the code that received it.

The pool is worth watching, not just configuring once. hikaricp.connections.pending (exposed via Actuator/Micrometer) tracks how many requests are currently waiting for a connection to free up — if that metric sits above zero regularly rather than spiking briefly, the pool is undersized for the traffic it's serving.

"HikariCP pool exhausted" under load

This is one of the most common production incidents in a Spring Boot service, and it has two genuinely different causes that get treated as one. Either the pool is legitimately too small for the concurrency the service now handles — raise maximum-pool-size — or there's a connection leak: a repository or service somewhere isn't releasing a connection back to the pool (an unclosed resource, or a transaction held open far longer than the work inside it actually needs). Raising the pool size masks a leak instead of fixing it — it just takes longer to exhaust a bigger pool.

GZIP compression: a free win

One line of YAML, zero code changes, typically a ~90% reduction in the size of a JSON response over the wire:

server:
  compression:
    enabled: true
    mime-types: application/json,application/xml,text/html
    min-response-size: 1024

There's essentially no argument against turning this on — the CPU cost of compressing is trivial compared to what it saves in transfer time, especially for clients on a slow or metered connection. It's the rare optimization with no real trade-off attached.

@Async: don't make the client wait for work they don't need to wait for

A synchronous call blocks the caller until the entire method — including any side effects inside it — finishes. @Async runs the annotated method on a separate thread and returns control to the caller immediately; the caller doesn't wait for it to complete at all. It's the right shape for fire-and-forget background work: sending a signup confirmation email, generating a report nobody's staring at a spinner for, writing an audit-trail entry.

NotificationService.java
@Service
public class NotificationService {

    @Async("taskExecutor")
    public void sendSignupEmail(String to) {
        // runs on a pooled thread; the calling request already returned its response
        mailClient.send(to, "Welcome!");
    }
}

Two things have to be true for this to actually run async in production: @EnableAsync on a configuration class, and a real, bounded ThreadPoolTaskExecutor bean (named taskExecutor above) with an explicit corePoolSize/maxPoolSize/queueCapacity. Skip the second part and Spring falls back to SimpleAsyncTaskExecutor, which spins up a brand-new thread per call with no reuse and no upper bound — a resource leak waiting for enough concurrent calls to happen at once.

WebClient vs. RestTemplate: blocking vs. non-blocking outbound calls

RestTemplate is Spring's original HTTP client for calling other services, and it's now officially in maintenance mode — no new features, ever. It's blocking: the calling thread sits parked for the entire round trip of every outbound call. WebClient (from Spring WebFlux) is non-blocking, built on a small event-loop of threads that register a callback for each in-flight call and move on, rather than dedicating a thread to sit and wait.

RestTemplate — thread-per-request

  • Each outbound call holds its calling thread for the full round trip
  • 1,000 concurrent outbound calls ≈ 1,000 threads sitting idle, just waiting
  • Simple, familiar, synchronous — and in maintenance mode

WebClient — event loop

  • A small, fixed pool of threads handles many concurrent calls via callbacks
  • Threads are never blocked waiting on a response — they're freed to do other work
  • Scales to far higher concurrency with far fewer threads, at the cost of a reactive programming model

Architecture, Project Structure & Debugging

The difference between a codebase that's pleasant to work in a year from now and one that isn't usually isn't cleverness — it's whether the layers stayed honest about what they're each responsible for.

8 min read Intermediate

The five-layer flow

A conventional Spring Boot service is built from five layers, each with one job and (deliberately) no knowledge of the layers it isn't adjacent to:

DTO (request)what the client actually sends
ControllerHTTP layer, @Valid input
Servicebusiness logic, @Transactional lives here
RepositoryJpaRepository, DB access
EntityJPA persistence model

The explicit rule: Entity never crosses the controller boundary. Whatever comes back up this chain gets mapped into a response DTO before it ever reaches the client — the client only ever sees DTOs, in both directions.

This isn't ceremony. The controller shouldn't know how data gets persisted — it just needs the service to hand back something it can serialize. The repository shouldn't know it's serving an HTTP request — it just needs to answer a query. That separation is what lets you change the persistence layer (a new index, a caching layer in front of the repository, even swapping databases) without touching the controller, and rework an endpoint's shape without touching how anything is stored. DTOs are the mechanism that makes this possible: they decouple your API contract from your persistence model, so a column rename in the entity doesn't have to become a breaking API change, and a client-facing field addition doesn't have to become a schema migration.

A realistic package layout

  • com.example.approot package
    • controller/REST endpoints — @RestController, @Valid request bodies
    • service/business logic interfaces
      • impl/concrete implementations, @Transactional boundaries
    • repository/JpaRepository interfaces — no business logic
    • entity/JPA persistence model — never returned from a controller
    • dto/the actual API contract
      • request/inbound shapes, validated at the controller
      • response/outbound shapes, mapped from entities
    • config/beans — SecurityConfig, ObjectMapper customization, executors
    • exception/custom exceptions + GlobalExceptionHandler
    • util/entity ↔ DTO mapper utilities

Package-by-layer like this is the conventional default for a single-module Spring Boot service — it makes "where does this kind of code live" a one-second question for anyone new to the codebase.

Debugging a production issue — the interview-answer structure

"How would you debug a production issue" is asked often enough, and answered vaguely often enough, that having an actual order to walk through is worth more than any specific war story.

The methodology, in order

(1) Check the logs first — the root cause is usually something boring: a config value, a DB connection issue, a bad deploy. (2) If it looks like a data-layer problem, look at the actual generated SQL (enable show-sql temporarily, or check a slow-query log) to catch an N+1 pattern or a missing index directly rather than guessing. (3) Read the full stack trace from the bottom up — the root cause is almost always the deepest frame, and the top frames are just the call path that happened to be on the stack when it surfaced. (4) Reproduce with debug logging enabled in a non-prod environment — and never leave show-sql: true or root-level DEBUG logging on globally in production; the log volume alone can degrade performance, on top of the security exposure of logging bind parameters.

13 Interview Room

Spring Boot Interview Questions

Twenty-five questions built around internals, trade-offs, traps, and scenarios — the kind that separate "I've used @Autowired" from "I understand what the container is actually doing." Try answering before expanding each one.

17 min read High-frequency
IoC, DI & Bean Lifecycle
01
InternalsWhy does constructor injection catch a circular dependency at startup, when setter injection often doesn't?

A constructor needs all of its arguments fully resolved before it can even be called — if bean A's constructor needs bean B, and B's constructor needs bean A, Spring can't finish constructing either one first, and fails immediately with a clear circular-reference error.

Setter injection sidesteps this because the object can be instantiated (via a no-arg or partial constructor) before its setters run — Spring can create a "half-built" A, hand it to B's setter, then come back and finish wiring A. This is precisely why setter injection was historically used as an escape hatch for cycles — it doesn't fix the underlying design problem, it just lets the container tolerate it.

02
Trap"@Autowired always resolves to whichever bean is marked @Primary." What's incomplete about this claim?

@Primary is only a tiebreaker — it applies when Spring is choosing among multiple matching candidates and nothing more specific has been requested. An explicit @Qualifier("beanName") at the injection point overrides @Primary outright; the qualifier is a direct request, while @Primary is just a default preference.

The resolution order is really: exact type match with only one candidate wins immediately (no tiebreak needed) → a @Qualifier narrows multiple candidates to one → among remaining candidates, @Primary picks the default → failing all of that, startup fails with an ambiguity error. "@Primary always wins" skips the fact that it's the last resort, not the first rule.

03
ScenarioA singleton service injected with a prototype-scoped helper behaves as if it's reusing stale state across unrelated requests. What's happening, and what's the fix?

This is the classic prototype-in-singleton trap. The singleton is constructed exactly once, so its constructor (or field) injection of the prototype bean also happens exactly once — the "fresh instance per lookup" promise of prototype scope never actually triggers again after that first wiring. Every subsequent call reuses the very first prototype instance, accumulating whatever state it holds.

The fix is to stop injecting the prototype bean directly, and instead inject an ObjectProvider<HelperType> (or use @Lookup method injection) and call .getObject() at the point of actual use — that call genuinely asks the container for a new instance every time, rather than reusing whatever was wired at construction.

04
Trade-offGiven the strong general recommendation for constructor injection, when would setter injection genuinely be the better call?

When a dependency is genuinely optional — the bean is fully functional without it, and its presence only enables extra behavior (an optional metrics reporter, an optional cache warmer). Forcing an optional collaborator through the constructor implies it's mandatory, which is misleading to anyone reading the class, and complicates every test that doesn't care about that dependency.

It can also be the pragmatic choice when reconfiguring a dependency after construction is a legitimate requirement (some framework integration points expect mutable beans) — but that's rarer, and worth treating as the exception rather than a habit.

Spring Boot & Configuration
05
InternalsWalk through what actually happens, in order, from java -jar app.jar to the app accepting its first request.

The JAR's launcher unpacks/loads the nested dependency JARs and invokes your main(), which calls SpringApplication.run(). That creates the ApplicationContext, which triggers component scanning (discovering your @Component/@Service/etc. classes) and auto-configuration (evaluating every conditional auto-config class against your classpath and properties).

Beans are then instantiated and wired in dependency order, running the full bean lifecycle for each (construction → population → @PostConstruct → proxy creation). Only after the context fully refreshes does Spring Boot start the embedded server (Tomcat by default) and bind it to a port — the app is not accepting traffic until every singleton bean in the context has finished initializing.

06
Trap"Auto-configuration means Spring Boot decides everything for you, with no way to override it." Why is this wrong?

Auto-configuration is built entirely around backing off, not overriding. Nearly every auto-configured bean is annotated @ConditionalOnMissingBean — the moment you define your own bean of that type, the auto-configured default simply never activates. The "magic" only ever fills a gap you haven't already filled.

Beyond bean overrides, almost every auto-configuration decision is also tunable via a property (@ConditionalOnProperty), and /actuator/conditions or --debug shows exactly why each one did or didn't apply — the system is designed to be inspectable and overridable at every layer, which is the opposite of "no way to override."

07
ScenarioThe same property needs a different value in staging vs. production, but you want one build artifact deployed unchanged to both. How do you structure this?

Don't bake environment-specific values into the JAR at all — rely on Spring Boot's property-source precedence. Either use profile-specific files (application-staging.yml, application-prod.yml) selected via spring.profiles.active at deploy time, or — more common in containerized deployments — set environment variables per environment and let those override the base application.yml automatically, since env vars outrank file-based config.

The key design goal either way: the built artifact never changes between environments, only the configuration supplied alongside it does — exactly the 12-factor pattern that makes "works in staging" mean something for production.

08
Trade-offGiven that @ConfigurationProperties is generally preferred, when is a plain @Value still the right tool?

For a single, standalone value used in exactly one place — a feature-flag boolean read by one class, a one-off timeout — a whole @ConfigurationProperties record is unnecessary ceremony. @Value("${feature.new-checkout:false}") is simpler, and the default-value syntax handles the common case cleanly.

The line to watch for is growth: the moment a second or third related property shows up needing the same prefix, that's the signal to consolidate into a @ConfigurationProperties group — at that point the type safety and startup-time validation start paying for themselves.

AOP & Proxies
09
InternalsWhy can't Spring AOP intercept a call to a private method, even with a pointcut that seems to match it?

Spring's proxy-based AOP can only intercept calls that arrive through the proxy — and a private method can never be called from outside the class in the first place, by Java's own access rules. Every call to it is necessarily an internal, same-object call, which is exactly the self-invocation path that bypasses the proxy entirely, every single time.

This isn't a pointcut-matching limitation — the pointcut expression can technically reference it — it's a structural consequence of how proxying works: there is no external call path to a private method for the proxy to ever sit in front of.

10
TrapA developer extracts an inline block into a new private helper method within the same service, marks a nearby method @Cacheable, and calls the helper internally. Caching never seems to take effect. Why?

This is self-invocation again, just dressed differently. If the @Cacheable method is being called from another method in the same class — regardless of how recently that call site was refactored or how the helper method is structured — the call goes through this, not through the container-managed proxy, so the caching advice never runs.

The fact that the helper is newly extracted is a red herring; the actual condition is simply "same class, same-object call." The fix is unchanged from the general self-invocation pattern: move the @Cacheable method to a separate bean and call it through an injected reference, so the call genuinely passes through the proxy.

11
ScenarioYou need to log an audit entry every time any repository's save() method is called, across dozens of repositories, without touching each one. How would you design this?

This is a textbook cross-cutting concern — exactly what AOP exists for. Define an @Aspect bean with an @Around (or @AfterReturning) advice whose pointcut expression targets the pattern execution(* org.springframework.data.repository.Repository+.save(..)) (or more narrowly, your own repository package), capturing the target object and arguments to write the audit entry.

The key design win: this requires touching zero existing repository classes — the aspect is woven in at the pointcut level, so adding a new repository interface automatically gets audited too, with no per-repository code to remember to add.

12
InternalsTwo beans in the same application end up proxied differently — one via JDK dynamic proxy, one via CGLIB. What actually determines which one Spring picks?

It comes down to whether the bean's class implements at least one interface. If it does, Spring defaults to a JDK dynamic proxy implementing that same interface. If the bean is a concrete class with no interface, Spring has no interface to implement a proxy against, so it falls back to CGLIB — generating a runtime subclass of the bean's own class instead.

This is also exactly why a CGLIB-proxied bean can't have final methods advised (a subclass can't override a final method) — the choice of proxy mechanism isn't just an implementation detail, it directly constrains what can and can't be advised.

Real-Time, RPC & Observability
13
InternalsA gRPC unary call is "1 request, 1 response" — the same shape as a REST GET. What's actually meaningfully different about it?

The shape is the same, but the mechanics differ throughout the stack. The payload is protobuf — a compact binary encoding against a strict, code-generated schema — versus JSON's self-describing text. The transport is HTTP/2, which multiplexes many calls over one connection without head-of-line blocking at the application level, versus REST typically riding plain HTTP/1.1.

And the contract is enforced by tooling: the .proto file generates matching client and server stubs, so a mismatched field type is a compile-time error in both languages involved, not a runtime surprise the way a drifted REST/JSON contract can be.

14
Trap"It's fine to expose every actuator endpoint in production — they're all read-only." What's wrong with this?

Several actuator endpoints aren't purely read-only in the safe sense at all: /actuator/env can expose secrets embedded in configuration, /actuator/heapdump exposes a full memory snapshot (potentially including sensitive in-memory data), and /actuator/loggers lets a caller change log levels at runtime — a genuine write operation, and a way to flood logs or hide activity.

The correct posture is deliberate exposure: only include the endpoints actually needed externally (usually just health and Prometheus metrics), and put anything more sensitive behind the same authentication boundary as the rest of the application, not "open by default because it's Actuator."

15
ScenarioA live-updating WebSocket dashboard works perfectly in staging (one instance) but randomly drops updates in production, which runs three instances behind a load balancer. Diagnose it.

This is almost certainly the default in-memory broker being per-instance. A client connects to whichever instance the load balancer routes it to; a broadcast triggered on a different instance never reaches that client, since the two instances don't share subscription state. "Randomly drops" is the natural symptom of load-balanced traffic being distributed across instances that each only know about their own local subscribers.

The fix is either an external STOMP broker relay (RabbitMQ/ActiveMQ shared by all instances) or a Redis pub/sub relay so every instance can fan out to its own locally-connected clients — plus sticky sessions at the load balancer so a client's WebSocket connection itself doesn't get rerouted mid-session.

16
Trade-offA team is debating gRPC vs. REST for a brand-new internal service. What's the actual decision criterion, beyond "gRPC is faster"?

"Faster" is real but rarely decisive on its own — plenty of internal services are nowhere near the throughput where protobuf's efficiency matters. The sharper questions: does this need streaming (gRPC has first-class support; REST doesn't)? Is this consumed by a browser or only by other backend services (gRPC needs a proxy for browser access; REST doesn't)? Does the team value a strictly enforced, code-generated contract over the flexibility (and debuggability with a browser or curl) of plain JSON?

For a typical internal CRUD-ish service with no streaming need and occasional manual debugging via curl, REST's simplicity often wins even though gRPC would technically perform better — the "right" answer depends on the actual usage pattern, not a blanket performance argument.

Cross-Topic Scenarios
17
ScenarioTrace, mechanism by mechanism, what happens when an HTTP request arrives with invalid data and your service throws a business exception.

The embedded server hands the request to Spring MVC, which binds the JSON body to your DTO. If @Valid is present and a constraint fails, Bean Validation throws MethodArgumentNotValidException before your controller method body ever runs — caught by your @RestControllerAdvice's handler for that type, returning a 400 with field-level errors.

If validation passes but your service layer then throws a business exception (say, ResourceNotFoundException) — possibly from behind an AOP proxy doing something else entirely (logging, a transaction boundary) — that exception propagates up through the proxy chain and the controller, caught by a different handler method in the same advice class, mapped to its own status code. Either path ends at the same centralized advice, returning the same consistent error shape.

18
Trap"Since @PostConstruct runs during bean initialization, it's safe to call other @Transactional methods on the same bean from inside it." True or false?

False, and for a subtle reason on top of the usual one. AOP proxies are created in the second BeanPostProcessor phase — which runs after @PostConstruct. So inside @PostConstruct, the proxy doesn't exist yet at all; even calling the method through what looks like the bean reference is still hitting the raw, un-proxied target object.

This compounds the ordinary self-invocation problem: it's not just "same-class calls skip the proxy," it's "at this specific point in the lifecycle, there is no proxy for any call — internal or external — to go through yet." Any transactional or cached behavior needed at startup has to be triggered from outside the bean, after the context has fully finished refreshing.

19
ScenarioA code reviewer flags a new @Service class with 15 constructor-injected dependencies. What's actually wrong, and how does Spring's own design point at the fix?

Fifteen dependencies is a design smell, not a DI problem — it's an unmistakable sign this one class has taken on far too many responsibilities. Constructor injection is deliberately unforgiving about this: unlike field injection, which can hide an enormous, sprawling dependency list, a bloated constructor signature makes the problem visually obvious the moment you look at the class.

This is exactly the value constructor injection provides beyond testability — it turns an invisible design problem (a god-class quietly accumulating responsibilities) into a visible one (an unreadable constructor), which is a strong nudge toward splitting the class along its actual responsibilities rather than papering over the symptom with field injection.

DI & Bean Configuration Gotchas
20
TrapA developer puts @Autowired on a static field, expecting the container to inject it like any other field. It stays null. Why?

Spring's dependency injection operates on bean instances — after a bean is constructed, Spring reflectively sets its instance fields (or calls its setters/constructor) as part of that specific object's lifecycle. A static field doesn't belong to any instance at all; it belongs to the class itself, and it exists in memory before any bean lifecycle has run, before the ApplicationContext even starts. There is no instance-level injection point for Spring to act on, so the field is silently left exactly as it was — null — with no error, because from Spring's point of view there's nothing wrong: it successfully injected every instance field on every bean it created.

Beyond the mechanical reason, wanting a static reference to a Spring-managed bean is itself a design smell — it usually means something outside the container (a static utility method, typically) needs to reach into a singleton bean, which defeats the point of DI in the first place. The fix is almost always to make the calling code itself a Spring bean and inject the dependency normally, rather than reaching for a static holder.

21
Trade-offWhen do you reach for @Component versus an @Bean method in a @Configuration class?

@Component (and its specializations — @Service, @Repository, @Controller) is for a class you own and can annotate directly; component scanning finds it and registers it as a bean with essentially no ceremony. It stops being an option the moment the class comes from a third-party library — you can't add an annotation to a JAR you don't control.

That's exactly what @Bean methods inside a @Configuration class are for: registering a bean by writing the construction logic yourself, which is the only way to get a RestTemplate, an ObjectMapper, or any other third-party type into the container. It's also the right tool even for your own classes when construction needs custom logic — conditional setup, builder-style configuration, or picking between implementations at startup — that a bare @Component constructor can't express.

Security Integration
22
InternalsBCryptPasswordEncoder.encode("password123") is called twice on the exact same string and produces two completely different output strings. Is this a bug?

Not a bug — this is BCrypt working exactly as designed. Every call to encode() generates a fresh, cryptographically random salt, then folds that salt directly into the output string alongside the hash itself — the format is roughly $2a$<cost>$<22-char salt><31-char hash>. Different random salt in, different final string out, even for byte-for-byte identical input.

The reason this matters beyond trivia: it's exactly why you can never verify a password with .equals() against a stored hash. matches(raw, storedHash) is the only correct check, because it extracts the embedded salt from storedHash first, re-hashes the raw candidate with that same salt, and only then compares the two. Two users who happen to choose the same password still end up with two totally different stored hashes, which also means a stolen database can't be searched for duplicate passwords by simply diffing hash strings — a real defense-in-depth property a naive unsalted hash doesn't give you.

23
TrapA user's granted authority is stored and returned exactly as the string REPORT_EXPORT. A developer writes @PreAuthorize("hasRole('REPORT_EXPORT')") expecting it to match. It never does. Why?

hasRole() isn't a generic string-contains check — it silently prepends ROLE_ before comparing, so hasRole('REPORT_EXPORT') actually checks for a granted authority of ROLE_REPORT_EXPORT, not REPORT_EXPORT. Since the authority was granted as the bare string with no prefix, the two never match, and the check fails closed — the user is denied, with nothing in the response to explain why the "obviously correct" annotation didn't work.

The fix is either to change what's granted (name it ROLE_REPORT_EXPORT if it's genuinely meant to be a role) or, more often the right call for a fine-grained permission like this one, switch the check itself to hasAuthority('REPORT_EXPORT'), which does a bare, exact-match comparison with no prefix added. The underlying lesson: hasRole is really just hasAuthority with an assumed naming convention bolted on, not a fundamentally different check — reach for hasAuthority directly the moment a permission string was never meant to follow the ROLE_X convention.

Performance & Production
24
ScenarioAlerts start firing for "HikariCP pool exhausted" on a service that's run fine for months, right after a burst of increased traffic. Walk through how you'd actually diagnose this rather than just raising maximum-pool-size.

The instinct to immediately bump maximum-pool-size is exactly the trap here — it can mask either of two structurally different problems, and only one of them is actually fixed by a bigger pool. First check hikaricp.connections.pending via Actuator/Micrometer: if it spikes only during the traffic burst and recovers between bursts, that's consistent with a genuinely undersized pool for the new load — raising the size is the correct fix.

But if pending connections stay elevated even after traffic drops back to normal, or the active-connection count sits near the max long after the burst ends, that points to a leak — something acquiring a connection and never returning it, often a repository call missing try-with-resources, or a transaction held open across a slow, unrelated call (an external HTTP request made from inside a @Transactional block, for instance). The decisive move is a thread dump taken during the incident: threads stuck waiting on connection acquisition, correlated with which code path they're blocked in, points straight at the leaking call site. Raising the pool size in that case fixes nothing — it just buys a bit more runway before the exact same exhaustion happens again at a higher connection count.

25
TrapA method is annotated @Async and @EnableAsync is present on a configuration class. In production, under real concurrency, it behaves worse than the synchronous version it replaced. What was most likely missed?

@EnableAsync alone doesn't provide a bounded, reusable thread pool — it only switches on Spring's async proxy machinery. Without an explicit ThreadPoolTaskExecutor bean (typically named taskExecutor, or referenced explicitly via @Async("beanName")), Spring silently falls back to SimpleAsyncTaskExecutor, which doesn't pool threads at all — it spins up a brand-new thread for every single invocation and never reuses or caps them.

Under light load this is invisible, since a handful of new threads is cheap. Under real concurrency it's a resource leak with no backpressure: thousands of concurrent async calls means thousands of concurrent live threads, no queueing, no ceiling — eventually exhausting OS thread limits or memory, which is measurably worse than the blocking version that at least had an implicit cap on concurrent work. The fix is a real @Bean ThreadPoolTaskExecutor with an explicit corePoolSize/maxPoolSize/queueCapacity, wired either as the default taskExecutor bean or referenced by name — @Async without that bean behind it is a silent, un-alarmed footgun, not a safe default.

Interview delivery tips

(1) When asked "why doesn't X work," check for self-invocation and proxy timing first — it explains a surprising fraction of Spring "bugs." (2) Name the actual Spring mechanism (proxy, conditional, precedence order) rather than describing only the symptom. (3) For any "which technology" question, answer with the concrete deciding factor (streaming need, browser access, contract strictness), not a generic performance claim.
