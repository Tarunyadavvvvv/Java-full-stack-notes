1. Java Fundamentals Basic ↑ Contents

1.1 What is Java & how it runs

Java is a class-based, object-oriented, statically-typed, platform-independent language. Its tagline is "Write Once, Run Anywhere" (WORA): source code (.java) is compiled by javac into bytecode (.class), and the same bytecode runs on any machine that has a JVM.

Source (.java) --[javac compiler]--> Bytecode (.class) --[JVM interpreter/JIT]--> Native machine code

JDK vs JRE vs JVM

Relationship: JDK ⊇ JRE ⊇ JVM. You need a JDK to compile; an end-user only needs the JRE/JVM to run.

Primitives vs references: Primitives store the actual value on the stack (or inline in objects). Reference types (objects, arrays) store a reference (pointer) on the stack pointing to the object on the heap. Java is always pass-by-value — for objects, the reference value is copied.

1.3 Stack vs Heap

  • Stack: per-thread; stores local variables, method frames, primitive values and references. Fast, LIFO, auto cleaned when method returns.
  • Heap: shared across threads; stores all objects and arrays. Managed by the Garbage Collector.

equals/hashCode contract: If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true. Breaking this corrupts HashMap/HashSet behaviour. Always override both together.

1.6 Important keywords & concepts

  • static — belongs to the class, not instances; shared across all objects. Static methods can't use this or instance members.
  • this — reference to the current object. super — reference to the parent class.
  • Autoboxing/Unboxing — automatic conversion between primitives and wrappers (int ↔ Integer).
  • var (Java 10+) — local variable type inference; still statically typed.
  • Varargs — void f(int... nums) accepts zero or more arguments as an array.
Why is Java platform-independent but the JVM is platform-dependent?
Bytecode is portable and identical everywhere. The JVM is a native program compiled for each OS/CPU that translates that portable bytecode into platform-specific machine code, bridging the gap.
Is Java pass-by-value or pass-by-reference?
Always pass-by-value. For objects, the value being passed is a copy of the reference, so the method can mutate the object's state but cannot reassign the caller's variable.
Best practices: prefer primitives over wrappers in hot loops (avoid boxing); use var only when the type is obvious; never rely on finalize().

2.4 Other key concepts

Can you achieve multiple inheritance in Java?
Not with classes (avoids the diamond problem), but yes with interfaces. If two interfaces provide the same default method, the implementing class must override it and may call Interface.super.method().
What is runtime polymorphism and how does the JVM implement it?
Method overriding resolved at runtime via dynamic dispatch. Each object holds a pointer to its class's method table (vtable); the JVM looks up the actual method based on the object's real type, not the reference type.
Pitfall: Overriding equals() but not hashCode(); calling overridable methods from a constructor (subclass state not yet initialized); confusing field hiding (static binding) with method overriding (dynamic binding).

3. Strings & Wrapper Classes Basic ↑ Contents

3.1 String immutability

String is immutable — once created its value never changes. Any "modification" creates a new object.

  • Why immutable? Security (safe in class loaders, network connections), thread-safety (shareable without sync), caching (hashcode cached), and the String pool.
  • String pool: string literals are interned in a special area of the heap. "a" == "a" is true; new String("a") == "a" is false. intern() forces pooling.
String a = "hello";              // pooled
String b = "hello";              // same pooled object  -> a == b  : true
String c = new String("hello");  // new heap object     -> a == c  : false
System.out.println(a.equals(c)); // true (value equality)

3.2 String vs StringBuilder vs StringBuffer

StringStringBuilderStringBuffer
MutableNoYesYes
Thread-safeYes (immutable)NoYes (synchronized)
PerformanceSlow for concat in loopsFastestSlower than builder
Use whenFixed textSingle-threaded mutationMulti-threaded mutation
Pitfall: Concatenating Strings in a loop creates many temporary objects (O(n²)). Use StringBuilder instead.

3.3 Wrapper classes & Integer cache

Each primitive has a wrapper (int→Integer, etc.) enabling use in collections and providing utility methods. The JVM caches Integer values from -128 to 127.

Integer x = 100, y = 100;   // cached -> x == y : true
Integer p = 200, q = 200;   // not cached -> p == q : false
// Always use .equals() to compare wrapper values!
Why is String final/immutable?
To enable safe pooling, thread-safety without locks, secure use as map keys and in sensitive APIs (class loading, DB URLs), and to allow caching of the hashcode.

4.3 HashMap internals Important

  • Backed by an array of buckets (Node[]). Index = (n-1) & hash where hash is a spread of key.hashCode().
  • Collisions are chained in a linked list; since Java 8, a bucket with > 8 entries (and table ≥ 64) converts to a balanced red-black tree → lookup O(log n) instead of O(n).
  • Default capacity 16, load factor 0.75. When size > capacity × load factor, the table resizes (doubles) and rehashes.
  • Allows one null key and multiple null values. Not thread-safe.
put(key,value):
  1. h = spread(key.hashCode())
  2. i = (n-1) & h            // bucket index
  3. if bucket empty -> place node
     else traverse chain/tree; if equal key found -> replace value
     else append; treeify if chain too long
  4. if ++size > threshold -> resize()

How does HashMap handle collisions, and what changed in Java 8?
Entries with the same bucket index are chained. Java 8 converts a long chain (>8 with table size ≥64) into a red-black tree, improving worst-case lookup from O(n) to O(log n). It also improved hash spreading.
Why must a HashMap key be immutable / have stable hashCode?
The bucket is chosen from the hashCode at insert time. If the key mutates and its hashCode changes, the entry becomes unreachable — get() looks in the wrong bucket.
Best practices: Program to interfaces (List l = new ArrayList<>()); pre-size collections when count is known; prefer ArrayDeque over Stack; use ConcurrentHashMap not Hashtable.

5. Generics Intermediate ↑ Contents

Generics provide compile-time type safety and eliminate explicit casts. They are implemented via type erasure — type parameters are removed at compile time and replaced with Object (or bounds), so they exist only at compile time, not at runtime.

class Box<T> { private T val; T get(){return val;} void set(T v){val=v;} }
// Bounded type
<T extends Number> double sum(List<T> nums){ ... }

Wildcards & PECS

  • ? extends T — upper bound, read-only producer (Producer Extends).
  • ? super T — lower bound, write consumer (Consumer Super).
  • PECS: Producer Extends, Consumer Super.
Type erasure consequences: can't do new T(), T[], instanceof List<String>, or have overloads differing only by generic type. Generics don't work with primitives (use wrappers).

6.3 try-catch-finally & try-with-resources

// try-with-resources (Java 7+) auto-closes AutoCloseable resources
try (BufferedReader br = new BufferedReader(new FileReader("f.txt"))) {
    return br.readLine();
} catch (IOException e) {
    log.error("read failed", e);
    throw new DataAccessException("could not read file", e); // wrap, keep cause
}
  • finally always runs (except System.exit() / JVM crash) — use for cleanup.
  • try-with-resources closes resources in reverse order automatically, even on exception. Preferred over manual finally close.
  • Multi-catch: catch (IOException | SQLException e).

6.4 throw vs throws

  • throw — actually throws an exception instance: throw new IllegalArgumentException("x").
  • throws — method-signature declaration that a method may throw checked exceptions.
Pitfalls: swallowing exceptions (empty catch); return inside finally hides exceptions; catching Exception/Throwable broadly; losing the original cause when re-throwing (always pass e as cause).
Best practices: catch specific exceptions; fail fast; use custom domain exceptions; never use exceptions for normal flow control; log or rethrow, not both.
What happens if an exception is thrown in both try and finally?
The exception from finally wins and suppresses the original (which is lost unless using try-with-resources, where it's recorded as a "suppressed" exception). Avoid throwing from finally.

7. Multithreading & Concurrency Advanced ↑ Contents

7.1 Process vs Thread

A process has its own memory space; a thread is a lightweight unit of execution within a process sharing heap memory but having its own stack. Threads enable concurrency and better CPU utilization.

7.2 Creating threads

// 1. Extend Thread
class T extends Thread { public void run(){...} }
// 2. Implement Runnable (preferred - leaves inheritance free)
Runnable r = () -> System.out.println("run");
new Thread(r).start();
// 3. Callable + Future (returns a result / throws)
Callable<Integer> c = () -> 42;
Future<Integer> f = executor.submit(c);  int v = f.get();
start() vs run(): start() creates a new thread and calls run() on it. Calling run() directly executes on the current thread — no concurrency.

7.3 Thread lifecycle

7.4 Synchronization & the memory model

  • Race condition: outcome depends on thread interleaving on shared mutable state.
  • synchronized — mutual exclusion via an object's intrinsic lock (monitor); also establishes a happens-before relationship (visibility).
  • volatile — guarantees visibility and ordering of a variable across threads (reads/writes go to main memory), but not atomicity of compound ops like i++.
  • Atomic classes (AtomicInteger, AtomicLong) — lock-free atomic ops via CAS (compare-and-swap).
synchronizedvolatileAtomic
VisibilityYesYesYes
AtomicityYes (blocks)NoYes (single var)
BlockingYesNoNo (CAS)

7.5 Locks (java.util.concurrent.locks)

  • ReentrantLock — explicit lock with tryLock(), timeout, fairness, interruptibility (more flexible than synchronized). Always unlock in finally.
  • ReadWriteLock — many readers OR one writer; great for read-heavy data.
  • StampedLock (Java 8) — optimistic reads for even better throughput.

7.6 Deadlock, livelock, starvation

  • Deadlock: two+ threads each hold a lock the other needs. Prevent by global lock ordering, tryLock with timeout, or minimizing lock scope.
  • Livelock: threads keep reacting to each other and make no progress.
  • Starvation: a thread never gets CPU/lock (e.g. unfair scheduling).
Four Coffman conditions for deadlock: mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one to prevent deadlock.

7.7 Executor framework & thread pools

Don't create threads manually in production — use the ExecutorService to pool and reuse threads.

ExecutorService pool = Executors.newFixedThreadPool(10);
Future<String> f = pool.submit(() -> compute());
pool.shutdown();
FactoryBehaviour
newFixedThreadPool(n)Fixed n threads, unbounded queue
newCachedThreadPool()Grows/shrinks; reuses idle threads
newSingleThreadExecutor()One thread, sequential
newScheduledThreadPool(n)Delayed/periodic tasks
newVirtualThreadPerTaskExecutor()Virtual threads (Java 21 Project Loom)
Prefer a custom ThreadPoolExecutor with bounded queue + named threads + a sensible rejection policy in production rather than the Executors factories (which can hide unbounded queues / thread counts).

7.8 Higher-level concurrency utilities

  • CompletableFuture — async pipelines: supplyAsync().thenApply().thenCompose().thenCombine(), non-blocking composition.
  • CountDownLatch — wait for N tasks to finish (one-shot).
  • CyclicBarrier — threads wait for each other at a barrier (reusable).
  • Semaphore — limit concurrent access to a resource (permits).
  • ConcurrentHashMap — segment/bucket-level locking (Java 8: CAS + synchronized per bin), high concurrency, no full-map lock.
  • BlockingQueue — producer-consumer backbone (ArrayBlockingQueue, LinkedBlockingQueue).
  • ThreadLocal — per-thread variable copy (beware leaks in thread pools — always remove()).

7.9 Virtual threads (Java 21)

Lightweight threads managed by the JVM (not 1:1 with OS threads). Millions can run concurrently; ideal for I/O-bound blocking code without reactive complexity. Thread.ofVirtual().start(r).

7.10 Structured concurrency (Java 21 preview) Advanced

Structured concurrency (JEP 453, preview in Java 21) treats a group of related subtasks as a single unit of work. Instead of scattering Futures across an executor and hand-managing cancellation, you open a StructuredTaskScope, fork subtasks, then join() them together — the scope guarantees that all children finish (or are cancelled) before the parent proceeds. This eliminates thread leaks, orphaned tasks, and the classic "one subtask failed but the others keep running" problem.

// Enable with --enable-preview on Java 21.
// ShutdownOnFailure: if ANY subtask fails, the rest are cancelled immediately.
Response handle(Request req) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        Supplier<User>  user  = scope.fork(() -> loadUser(req.userId()));   // subtask 1
        Supplier<Order> order = scope.fork(() -> loadOrder(req.orderId())); // subtask 2

        scope.join();            // wait for BOTH to finish
        scope.throwIfFailed();   // propagate the first failure (others already cancelled)

        return new Response(user.get(), order.get()); // both succeeded
    }
}
PolicyBehaviourUse for
ShutdownOnFailureCancel siblings on first error; join needs all successesFan-out where every result is required (invoke-all)
ShutdownOnSuccessCancel siblings on first success; return the fastest resultRacing replicas / "invoke-any" (fastest wins)
Why it matters: structured concurrency pairs naturally with virtual threads — fork thousands of cheap virtual threads inside a scope for I/O fan-out, with automatic cancellation and clean error propagation. It brings the discipline of try-with-resources to concurrency: the task tree's lifetime is bound to a lexical block.
Difference between ConcurrentHashMap and synchronized HashMap (Collections.synchronizedMap)?
synchronizedMap locks the entire map on every operation (one global lock). ConcurrentHashMap locks only the relevant bin/segment, allowing concurrent reads and partitioned writes — far higher throughput. It also never throws ConcurrentModificationException.
Why is volatile not enough for a counter?
count++ is read-modify-write (three steps). Volatile guarantees visibility but not atomicity, so two threads can read the same value and lose an increment. Use AtomicInteger or synchronization.
Pitfalls: double-checked locking without volatile; not shutting down executors (thread leak); ThreadLocal leaks in pools; catching InterruptedException and swallowing it (restore the interrupt flag).
🐛 Production Gotchas — Concurrency. Watch for: (1) thread-pool starvation when a pooled task blocks waiting on another task in the same pool (classic deadlock in fixed pools); (2) ThreadLocal leaks in Tomcat/Executor pools where the value survives across requests — always remove() in a finally; (3) swallowed InterruptedException breaking graceful shutdown; (4) unbounded queues in Executors.newFixedThreadPool hiding a memory leak under load. 9. Streams API Advanced ↑ Contents

A Stream is a pipeline for processing sequences of elements in a declarative, functional style. Streams are lazy (nothing runs until a terminal op), don't store data, and don't modify the source.

9.1 Pipeline structure

// source -> intermediate ops (lazy) -> terminal op (eager, triggers execution)
list.stream()                       // source
    .filter(e -> e.getAge() > 18)   // intermediate (returns Stream)
    .map(Employee::getName)         // intermediate
    .sorted()                       // intermediate
    .collect(Collectors.toList());  // terminal

9.2 Common operations

TypeOperations
Intermediatefilter, map, flatMap, sorted, distinct, limit, skip, peek
Terminalcollect, forEach, reduce, count, min/max, anyMatch, allMatch, findFirst, toArray

9.3 Collectors

// grouping
Map<Dept,List<Emp>> byDept = emps.stream()
    .collect(Collectors.groupingBy(Emp::getDept));
// counting per group
Map<Dept,Long> counts = emps.stream()
    .collect(Collectors.groupingBy(Emp::getDept, Collectors.counting()));
// joining, averaging, partitioning, toMap...
String names = emps.stream().map(Emp::getName)
    .collect(Collectors.joining(", ", "[", "]"));

9.4 map vs flatMap

  • map — one-to-one transform; Stream<List<X>> stays nested.
  • flatMap — one-to-many; flattens nested streams into one: Stream<List<X>> → Stream<X>.

9.5 Parallel streams

list.parallelStream() splits work across the common ForkJoinPool. Use only for large, CPU-bound, stateless operations. Avoid for small data, I/O, or stateful/ordered logic.

Pitfalls: reusing a consumed stream (IllegalStateException); side effects in lambdas; peek for logic (it's for debugging); parallel streams sharing mutable state; assuming order in parallel.
Are streams faster than loops?
Not necessarily — for simple iterations loops can be faster. Streams win on readability, composability, and easy parallelism. Choose by clarity, not micro-performance.
What does "lazy evaluation" mean for streams?
Intermediate operations build a plan but don't execute until a terminal operation runs. This enables short-circuiting (e.g. findFirst, limit) and fusing operations in a single pass.

Generational hypothesis: most objects die young. New objects go to Eden; survivors copy between survivor spaces, then get promoted to Old Gen after surviving enough cycles.

10.6 Memory leaks & references

  • Strong — normal; never GC'd while reachable.
  • Soft — cleared only under memory pressure (good for caches).
  • Weak — cleared at next GC (WeakHashMap).
  • Phantom — for post-finalization cleanup.
Common leaks: static collections that grow forever; unremoved listeners; ThreadLocal in pools; unclosed resources; keys with mutable hashcodes.
How does the JIT compiler help?
The JVM starts by interpreting bytecode, profiles "hot" methods, then JIT-compiles them to optimized native code (with inlining, escape analysis, loop unrolling). This gives near-native speed after warm-up.
Difference between Stack and Heap memory errors?
StackOverflowError = too-deep/infinite recursion (thread stack exhausted). OutOfMemoryError: Java heap space = heap full of reachable objects (leak or under-sized heap).

Interview tip: Always pair a pattern with a real framework example. Spring is a pattern showcase: Singleton (beans), Factory (BeanFactory), Proxy (AOP/transactions), Template (JdbcTemplate/RestTemplate), Strategy, Observer (events), Front Controller (DispatcherServlet).
How is Singleton typically broken, and how to protect it?
By reflection, serialization, or cloning. Protect with: enum singletons (immune to all three), readResolve() for serialization, and a guard in the private constructor against reflection.
