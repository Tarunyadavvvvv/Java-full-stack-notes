Part I — Foundations

1. Introduction & IAM Basics Basic

1.1 What is Keycloak?

Keycloak is an open-source Identity and Access Management (IAM) solution (originally by Red Hat, now a CNCF project) that provides Single Sign-On (SSO), authentication, and authorization for modern applications and services. It lets you externalize identity — apps delegate login and user management to Keycloak instead of building their own.

SSOOAuth2 / OIDCSAML 2.0Social loginLDAP/AD federationMFAAdmin consoleFine-grained authz

1.2 Why use Keycloak (the problem it solves)

Without a central IAM, every app reimplements login, password storage, token issuance, MFA, and user management — duplicated, error-prone, and insecure. Keycloak centralizes all of this.

Before:  App1[own login]  App2[own login]  App3[own login]   (duplicated, inconsistent)
After:   App1 ─┐
         App2 ─┼──> [ KEYCLOAK ] ──> LDAP / Social / DB    (one login, SSO across apps)
         App3 ─┘

1.3 IAM fundamentals

TermMeaning
Authentication (AuthN)Verifying who you are (login)
Authorization (AuthZ)Determining what you can do (permissions)
SSOLog in once, access many apps without re-authenticating
Identity Provider (IdP)System that authenticates users (Keycloak acts as one)
Service Provider (SP) / Relying Party (RP)App that relies on the IdP for identity
FederationTrusting identities from external sources

1.4 Key features

  • SSO & Single Logout across all connected apps.
  • Standard protocols: OpenID Connect, OAuth 2.0, SAML 2.0.
  • Identity brokering — login via Google, GitHub, Facebook, other OIDC/SAML IdPs.
  • User federation — connect to LDAP / Active Directory.
  • Admin console & Account console — manage realms/users; self-service.
  • Fine-grained authorization, MFA/OTP, WebAuthn/passkeys, customizable login themes.
  • Admin REST API for automation.
Why use Keycloak instead of building your own auth?
It provides battle-tested, standards-compliant SSO, token issuance, MFA, social login, and user federation out of the box — saving development time and avoiding the serious security risks of a homegrown solution. You externalize a complex, high-risk concern to a dedicated, audited system.
Keycloak vs Okta/Auth0?
Keycloak is open-source and self-hosted (full control, no per-user cost, data stays in-house). Okta/Auth0 are managed SaaS (less ops burden, polished UX, paid). Choose Keycloak for cost control, customization, and on-prem/regulatory needs; SaaS for minimal operational overhead.

2. Core Concepts & Terminology Basic

2.1 The object hierarchy

Keycloak Server
 └── Realm (isolated tenant: "master", "myapp")
      ├── Clients      (applications: web app, API, SPA)
      ├── Users        (people / service accounts)
      ├── Roles        (realm roles + client roles)
      ├── Groups       (collections of users + role mappings)
      ├── Identity Providers (Google, LDAP broker, SAML IdP)
      └── Client Scopes, Mappers, Auth Flows, Sessions

2.2 Essential terms

ConceptDefinition
RealmAn isolated security domain/tenant. Users, clients, roles in one realm are invisible to another. master realm is for admin only.
ClientAn application or service that wants Keycloak to authenticate/authorize. Each app = a client.
UserAn entity (person/service) that can log in.
RoleA named permission grouping; realm-level or client-level. Roles can be composite.
GroupA set of users with shared roles/attributes; supports hierarchy.
Client scopeReusable set of protocol mappers & role scope shared across clients.

2.3 Public vs Confidential clients Important

ConfidentialPublic
Has a secret?Yes (can keep secrets)No (can't securely store secrets)
ExamplesServer-side web app, backendSPA (React/Angular), mobile app
Client authclient_id + secret (or mTLS/JWT)client_id only + PKCE
Recommended flowAuthorization CodeAuthorization Code + PKCE
Bearer-only (legacy term) clients never initiate login — they only validate tokens (APIs/resource servers). In newer Keycloak this is modeled via client settings (no standard flows, just token validation).
Why are realms important?
A realm is a fully isolated tenant — its own users, clients, roles, keys, and config. Use separate realms for multi-tenancy or strict environment isolation (e.g. different customers), and a single realm with groups for one organization's many apps.

3.2 Key internal components

ComponentRole
RuntimeQuarkus-based (Keycloak 17+); previously WildFly/JBoss

3.3 Session storage

  • User sessions & client sessions are kept in the Infinispan cache (fast), with the DB as backing store for offline sessions.
  • In a cluster, Infinispan replicates/distributes session data so any node can serve a request (enables horizontal scaling).
  • Offline sessions persist (survive restarts) for offline access via offline refresh tokens.

3.4 Token signing keys

Each realm has its own signing keys (RSA/EC). Keycloak publishes public keys at the JWKS endpoint so resource servers can verify token signatures. Keys support rotation.

Well-known discovery (OIDC):
GET /realms/{realm}/.well-known/openid-configuration
  -> lists authorization_endpoint, token_endpoint, jwks_uri, etc.
JWKS (public keys):
GET /realms/{realm}/protocol/openid-connect/certs
Pitfall: The master realm is only for managing Keycloak itself. Never put your application's users/clients in master — always create a dedicated realm.
How does Keycloak scale and stay highly available?
Run multiple stateless Keycloak nodes behind a load balancer, sharing one database and a distributed Infinispan cache (so sessions are available cluster-wide). Use sticky sessions or distributed caching; scale the DB with replicas. Health endpoints support orchestration (Kubernetes).

4. Realms, Clients, Users, Roles & Groups Intermediate

4.1 Roles: realm vs client, composite

TypeScopeExample
Realm roleGlobal within the realmadmin, user
Client roleSpecific to one clientorders-service:manage-orders
Composite roleA role that bundles other rolessuper-admin → {admin, audit, billing}

4.2 Groups vs Roles

RoleGroup
RepresentsA permissionA collection of users
HierarchyComposite rolesNested subgroups
Best useWhat you can doOrg structure; bulk-assign roles/attributes
Best practice: Assign roles to groups, then put users in groups. Managing membership becomes "add user to group" rather than re-assigning many roles per user.

4.3 User attributes & required actions

  • Attributes — custom key-value data on a user (e.g. department, tenant_id); can be mapped into tokens.
  • Required actions — tasks a user must complete at next login (verify email, update password, configure OTP).
  • Service accounts — a confidential client can have its own account for machine-to-machine auth (client credentials flow).

4.4 Client scopes & the audience

  • Default scopes are always applied; optional scopes are requested via the scope parameter.
  • Scopes carry protocol mappers — reusable claim definitions shared across clients.
  • Audience (aud) mapper ensures a token is intended for a specific resource server, which should validate it.
When would you use a composite role?
When several roles are commonly granted together. A composite role like manager can include view-reports, approve-leave, and edit-team — assigning one role grants all, simplifying administration.

Part II — Protocols & Flows

5. OAuth 2.0 & OpenID Connect Advanced

5.1 OAuth 2.0 vs OIDC

OAuth 2.0OpenID Connect (OIDC)
PurposeAuthorization (delegated access)Authentication (identity) on top of OAuth2
Answers"What can this app access?""Who is the user?"
Key outputAccess tokenID token (+ access token)
AnalogyValet key (limited access)Passport (proves identity)
OIDC = OAuth 2.0 + identity layer. It adds the ID token (a JWT proving who logged in), the userinfo endpoint, and standard scopes (openid, profile, email). Keycloak's default protocol is OIDC.

5.2 The OAuth2 roles

RoleWho
Resource OwnerThe user
ClientThe application requesting access
Authorization ServerKeycloak (issues tokens)
Resource ServerThe API holding protected resources

5.3 Endpoints (OIDC)

EndpointPurpose
/authAuthorization (login + consent)
/tokenExchange code/credentials for tokens
/userinfoGet user claims with an access token
/logoutEnd session (SLO)
/certs (JWKS)Public keys to verify token signatures
/token/introspectValidate/inspect a token (for opaque tokens)
Is OAuth2 for authentication?
No — OAuth2 is for authorization (granting access to resources). Using it for authentication is a common mistake. OIDC adds the authentication layer (the ID token) on top of OAuth2.

6. Authentication Flows (Grant Types) Advanced

6.1 Authorization Code Flow (+ PKCE) — the standard

The recommended flow for web apps and SPAs. The browser never sees the tokens directly until a back-channel code exchange — secure against token leakage.

1. App redirects user to Keycloak /auth?response_type=code&client_id=...&redirect_uri=...&scope=openid
2. User logs in at Keycloak
3. Keycloak redirects back with ?code=ABC (authorization code)
4. App exchanges code at /token (back-channel): code + client_secret (or PKCE verifier)
5. Keycloak returns access_token + id_token + refresh_token
PKCE (Proof Key for Code Exchange): the client sends a hashed code_challenge up front and the original code_verifier at token exchange. This stops an attacker who intercepts the code from using it — mandatory for public clients (SPAs/mobile).

6.2 Grant types compared

GrantUse caseStatus
Authorization CodeWeb apps, SPAs (with PKCE), mobileRecommended
Client CredentialsMachine-to-machine (no user)Recommended for services
Refresh TokenGet new access token without re-loginRecommended
Device CodeTVs, CLIs, input-constrained devicesRecommended
Implicit(Old SPA flow, tokens in URL)Deprecated — avoid
Resource Owner Password (ROPC)App collects username/password directlyDiscouraged — only legacy

6.3 Client Credentials flow (M2M)

POST /realms/myrealm/protocol/openid-connect/token
  grant_type=client_credentials
  &client_id=orders-service
  &client_secret=xxxxx
-> returns an access_token (no user context; the service IS the identity)
Why Implicit & ROPC are discouraged: Implicit exposes tokens in the browser URL/history (leak risk, no refresh tokens). ROPC requires the app to handle raw credentials, defeating SSO/MFA and central control. Use Authorization Code + PKCE instead.
Which flow for a React single-page app?
Authorization Code flow with PKCE, configured as a public client. PKCE secures the code exchange without a client secret (which an SPA can't keep secret).
How does service A call service B with no user present?
Client Credentials grant. Service A authenticates with its own client_id + secret (or its service account) and receives an access token representing the service itself, which it sends to service B.

7. Tokens (JWT, Access, Refresh, ID) Advanced

7.1 The three tokens

TokenPurposeAudienceLifespan
Access tokenAuthorize API calls (Bearer)Resource serverShort (~5 min)
ID tokenProve who logged in (OIDC)The client appShort
Refresh tokenObtain new access tokens silentlyAuthorization serverLonger (session)

7.2 JWT structure

header.payload.signature   (three Base64URL parts)
header:  { "alg": "RS256", "typ": "JWT", "kid": "..." }
payload: { "sub": "user-id", "iss": "https://kc/realms/myrealm",
           "aud": "account", "exp": 1700000300, "iat": 1700000000,
           "realm_access": { "roles": ["user","admin"] },
           "preferred_username": "alice", "email": "a@x.com" }
signature: RSASHA256(base64(header)+"."+base64(payload), privateKey)
ClaimMeaning
subSubject (user ID)
issIssuer (the realm URL)
audAudience (intended recipient)
exp / iatExpiry / issued-at
realm_access.roles / resource_accessRealm & client roles
scope, azpGranted scopes; authorized party

7.3 Token validation (what a resource server checks)

  • Signature — verify with Keycloak's public key (JWKS). Tampered tokens fail.
  • Expiry (exp), issuer (iss), audience (aud).
  • Optionally roles/scopes for authorization.
Validation typeHow
Local (JWT)Verify signature offline via public key — fast, no network call (most common)
IntrospectionCall /introspect — checks live revocation status; needed for opaque tokens

7.4 Refresh tokens & rotation

  • When the access token expires, the client sends the refresh token to /token (grant_type=refresh_token) for a new access token — no re-login.
  • Refresh token rotation issues a new refresh token each time & invalidates the old one (detects token theft/reuse).
  • Offline tokens (scope offline_access) are long-lived refresh tokens that survive Keycloak restarts — for background/offline jobs.
Pitfalls: using long-lived access tokens (revocation is hard — keep them short); not validating aud (token meant for another service accepted); storing tokens in localStorage (XSS risk — prefer secure, HttpOnly cookies or in-memory + BFF).
Access token vs ID token — can they be used interchangeably?
No. The ID token authenticates the user to the client app (it should never be sent to APIs). The access token authorizes calls to resource servers. APIs must validate access tokens, not ID tokens.
How do you revoke a JWT before it expires?
JWTs are stateless, so you can't truly "delete" one. Options: keep access tokens short-lived; revoke the refresh token / end the session in Keycloak (stops new access tokens); use token introspection or a revocation list for immediate effect; bump a "not-before" policy to invalidate all existing tokens.

8. SAML & Protocol Mappers Intermediate

8.1 SAML 2.0

An older XML-based protocol for SSO, still common in enterprise/legacy apps. Keycloak supports it both as an IdP and as a broker.

SAML 2.0OIDC
FormatXML assertionsJSON / JWT
TransportBrowser POST/redirect bindingsREST/HTTP
Best forEnterprise web SSO, legacyModern web, mobile, APIs
WeightHeavier, verboseLightweight
Rule of thumb: use OIDC for new apps, mobile, and APIs; use SAML only when integrating with systems that require it.

8.2 Protocol mappers

Mappers control what data appears in tokens/assertions — mapping user attributes, roles, and group memberships into claims.

Mapper typeAdds to token
User AttributeA custom attribute (e.g. department)
User PropertyBuilt-in fields (email, username)
Group MembershipGroup paths the user belongs to
Role mappersRealm/client roles into claims
AudienceTarget resource server in aud
Hardcoded claimA fixed value
How do you add a custom claim (e.g. tenant ID) to the access token?
Store it as a user attribute, then add a User Attribute protocol mapper (on the client or a shared client scope) that maps that attribute to a token claim, with "Add to access token" enabled.

Keycloak Authorization ServicesIn Keycloak (centralized)Fine-grained policies evaluated by Keycloak; app asks "can this user do X?"

9.2 RBAC vs ABAC vs ReBAC

ModelDecision based onExample
RBACRoles"admins can delete"

ReBACRelationships"owner of this document"

9.3 Keycloak Authorization Services concepts

ConceptMeaning
ResourceA protected item (e.g. "Invoice #42", "/api/orders")
ScopeAn action on a resource (read, write, delete)
PolicyA condition (role-based, user-based, time, JS/Rego, aggregated)
PermissionLinks resources+scopes to policies
PEP / PDPPolicy Enforcement Point (app) asks the Policy Decision Point (Keycloak)

Authorization decisions use the UMA 2.0 grant: the app exchanges an access token for an RPT (Requesting Party Token) containing granted permissions.

Best practice: Use simple role-based checks in tokens for most apps (fast, decentralized). Reserve Keycloak Authorization Services for genuinely fine-grained, centrally-managed, frequently-changing permissions — it adds complexity and per-request calls.
RBAC vs ABAC — when to choose which?
RBAC is simple and sufficient when access maps cleanly to roles. ABAC suits dynamic, context-dependent rules (department, ownership, time, location) that would explode the number of roles in pure RBAC ("role explosion").

10. Identity Brokering & Federation Intermediate

Identity brokering lets Keycloak delegate authentication to an external IdP — users log in with Google, GitHub, Microsoft, or any OIDC/SAML provider, and Keycloak issues its own tokens.

User -> App -> Keycloak -> (redirect) -> Google login -> back to Keycloak
        Keycloak creates/links a local user -> issues Keycloak tokens -> App
  • First-login flow — on first external login, Keycloak can auto-create a local user, link to an existing account, or require review.
  • Identity Provider Mappers — map external claims (e.g. Google groups) to Keycloak roles/attributes.
  • Use cases: social login, B2B SSO with partner IdPs, gradual migration.
Brokering vs Federation: brokering delegates the login to another IdP at runtime (redirect). User federation (next section) imports/syncs users from a store like LDAP and authenticates against it directly.

11. User Federation (LDAP / Active Directory) Intermediate

Connect Keycloak to an external user store so existing users authenticate without migration.

AspectNotes
ProvidersLDAP, Active Directory, Kerberos; custom via User Storage SPI
Sync modesImport (copy users into Keycloak DB, periodic sync) or read-through
Edit modeREAD_ONLY, WRITABLE (changes pushed to LDAP), UNSYNCED
MappersMap LDAP attributes & group memberships to Keycloak
Pitfall: With WRITABLE mode and import sync, conflicting edits or schema mismatches cause sync failures. Plan attribute mappings carefully and test sync direction. For huge directories, prefer on-demand import over full periodic syncs.
Identity brokering vs user federation?
Brokering = delegate login to another IdP via redirect (the other system authenticates). Federation = Keycloak directly authenticates against an external user store (LDAP/AD), optionally importing users. Use brokering for social/partner SSO; federation for an existing corporate directory.

12. Sessions, SSO & Logout Intermediate

12.1 How SSO works

After first login, Keycloak sets an SSO session cookie on its own domain. When the user visits another app and is redirected to Keycloak, the existing session means Keycloak issues tokens without prompting for credentials again — that's SSO.

12.2 Session types & timeouts

SettingMeaning
SSO Session IdleLogout after inactivity
SSO Session MaxAbsolute session lifetime
Access Token LifespanHow long an access token is valid (~5 min)
Client Session Idle/MaxPer-client session limits
Offline Session Idle/MaxFor offline tokens

12.3 Single Logout (SLO)

  • Front-channel logout — browser redirects to each client's logout URL (iframe/redirect).
  • Back-channel logout — Keycloak directly notifies clients server-to-server (more reliable; recommended).
  • Logging out of Keycloak ends the SSO session, propagating logout to connected apps.
A user logs out of one app but is still logged into others — why?
The app only cleared its local session, not the Keycloak SSO session. To log out everywhere, call Keycloak's end-session endpoint (OIDC RP-initiated logout) so the central session ends and back-channel logout notifies all clients.

13. Authentication Flows & MFA Advanced

13.1 Authentication flows

A Keycloak authentication flow is a configurable sequence of steps (executions) a user goes through to log in. Each step is Required, Alternative, Conditional, or Disabled.

Browser Flow (default):
  Cookie (auto SSO)            [Alternative]
  Identity Provider Redirector [Alternative]
  Username/Password Form       [Required]
  Conditional OTP              [Conditional -> Required if user has OTP]

You can copy and customize built-in flows to add steps (e.g. force MFA, add a custom authenticator via SPI, add terms-and-conditions).

13.2 Multi-Factor Authentication

FactorKeycloak support
OTP / TOTPGoogle Authenticator, FreeOTP (built-in)
WebAuthn / PasskeysHardware keys, biometrics, FIDO2
Email/SMS OTPVia extensions / custom authenticators
Recovery codesBackup codes
  • Enforce MFA via required actions (Configure OTP) or a conditional step in the flow (e.g. only for admins or risky logins).
  • Step-up authentication — require stronger auth (ACR/LoA) for sensitive operations only.
How would you force MFA only for admin users?
Customize the browser flow with a Conditional sub-flow using the "Condition - User Role" authenticator set to the admin role, containing a Required OTP step. Non-admins skip it; admins must complete OTP.

Part IV — Integration & Advanced

14. Integrating Applications Advanced

14.1 Spring Boot (resource server) integration

Modern Spring Boot uses Spring Security OAuth2 Resource Server to validate Keycloak JWTs (the older Keycloak adapters are deprecated).

# application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://kc.example.com/realms/myrealm
          # public keys auto-discovered from issuer's JWKS
@Configuration
@EnableMethodSecurity
public class SecurityConfig {
  @Bean
  SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(j ->
            j.jwtAuthenticationConverter(keycloakRolesConverter())));  // map realm_access.roles
    return http.build();
  }
}
Roles mapping gotcha: Keycloak puts roles in realm_access.roles / resource_access.{client}.roles, not in Spring's default scope claim. You must write a custom JwtAuthenticationConverter to extract them and prefix with ROLE_.

14.2 SPA & frontend

  • Use keycloak-js or a generic OIDC library; Authorization Code + PKCE, public client.
  • Configure valid redirect URIs and web origins (CORS) on the client.
  • Prefer the BFF (Backend-for-Frontend) pattern — tokens held server-side, browser uses a secure session cookie (mitigates token-in-browser XSS risk).

14.3 API gateways & reverse proxies

Gateways (Spring Cloud Gateway, Kong, NGINX, oauth2-proxy) can validate tokens at the edge and forward identity downstream, offloading auth from each service.

14.4 Admin REST API

# Get an admin token, then create a user
curl -X POST .../realms/myrealm/users \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","enabled":true,"email":"a@x.com"}'
Automation: Use the Admin REST API / kcadm.sh / Terraform (keycloak provider) to manage realms-as-code — reproducible across environments.

How do you run Keycloak behind a reverse proxy / load balancer?
Set the proxy-headers (e.g. xforwarded) and hostname options so Keycloak generates correct external URLs (issuer, redirect, token endpoints). Otherwise discovery documents and redirects point to the internal address and break clients.

17. Security Best Practices Advanced

  • Always HTTPS — never expose Keycloak or token endpoints over plain HTTP.
  • Short access-token lifespans + refresh token rotation; enable reuse detection.
  • Strict redirect URIs — no wildcards/open redirects (a top OAuth attack vector).
  • PKCE for all public clients; avoid Implicit & ROPC grants.
  • Validate aud and iss in every resource server.
  • Confidential clients for anything that can keep a secret; rotate secrets.
  • Least privilege roles; protect & restrict the master realm & admin console.
  • Brute-force detection (built-in) & account lockout; enable MFA for privileged users.
  • Keep Keycloak patched; audit login/admin events; rotate signing keys.
Token storage on clients: avoid localStorage (XSS-readable). Prefer HttpOnly secure cookies or the BFF pattern. Set SameSite on cookies to mitigate CSRF.

19. Interview Scenarios & Cheat-Sheet Advanced

19.1 Scenario questions

Design SSO for 5 internal apps + login with Google, with MFA for admins.
One realm; each app a client (web apps confidential, SPAs public+PKCE). Add Google as an identity provider (brokering). Define realm/client roles, assign via groups. Customize the browser flow with a conditional OTP step gated on the admin role. APIs validate JWTs locally (issuer + aud + signature).
How do microservices trust tokens without calling Keycloak each request?
They validate the JWT locally using Keycloak's public key (cached from JWKS) — checking signature, exp, iss, and aud. No per-request network call; refresh JWKS periodically and on key rotation (kid mismatch).
How do you migrate existing users from a legacy DB into Keycloak?
Options: bulk import via Admin REST API; a custom User Storage SPI to authenticate against the legacy store (optionally importing on first login); or LDAP federation if users live in a directory. Often combined with "update password" required action for rehashing.
Single realm vs multiple realms for multi-tenancy?
Separate realms give full isolation (per-tenant users, keys, config) — good for distinct customers, but more overhead and no cross-realm SSO. One realm + groups/attributes is simpler and enables shared SSO — good for one org's many apps. Choose based on isolation requirements.
