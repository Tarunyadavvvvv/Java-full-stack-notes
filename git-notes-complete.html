01 Foundations

Fundamentals & Mental Model

Git is a distributed version control system — every clone contains the complete history, not just the latest snapshot. That one fact explains almost every way Git behaves differently from older centralized systems.

6 min read Start here

Centralized vs. distributed

Centralized (SVN, CVS)Distributed (Git)
RepositoryOne central serverEvery clone is a full repo with full history
Offline workLimitedFull — commit, branch, view history offline
Single point of failureYes (the server)No — every clone is effectively a backup
SpeedNetwork-boundLocal operations are fast
Git vs. GitHub/GitLab

Git is the version-control tool itself — local, CLI-driven, works with zero network access. GitHub and GitLab are hosting platforms built on top of Git, adding collaboration (pull/merge requests), issue tracking, CI/CD, and access control. You can use Git fully without ever touching either.

first-time-setup.sh
# Run once per machine
git config --global user.name  "Alice Dev"
git config --global user.email "alice@example.com"
git config --global init.defaultBranch main

git config --list                # view effective config
git init                          # create a new local repo
git clone <url>                   # copy a remote repo locally
Config has three scopes

--system (every user on the machine) → --global (your user account, ~/.gitconfig) → --local (this repo only, no flag needed inside it) — each level overrides the one before it. A repo-specific user.email is exactly how people keep a work identity separate from a personal one.

Chapter summary
  • Git is distributed: every clone is a complete, independent copy of the full history.
  • No single point of failure, and most operations (commit, diff, log, branch) never touch the network.
  • Git ≠ GitHub/GitLab — the tool is separate from any hosting platform built on top of it.
  • Config resolves system → global → local, each scope overriding the last.
Distributed VCSTap to reveal

Every clone holds the complete history — enables full offline work and removes any single point of failure.

Git vs. GitHubTap to reveal

Git is the tool; GitHub/GitLab are hosting platforms that add collaboration, CI/CD, and access control on top.

Config scopesTap to reveal

system → global → local, in increasing order of precedence — local (per-repo) config wins.

git init vs. git cloneTap to reveal

init creates a brand-new empty repo; clone copies an existing remote repo (and its full history) to your machine.

Why is Git described as "distributed" rather than just "a version control tool"?
The defining trait is that every local clone is a fully independent, complete repository — you can commit, branch, and browse history with zero network connection.
You set user.email with --global, then set a different one with --local inside one specific repo. Which wins in that repo?
More specific scope always wins: local overrides global, which overrides system.
02 Foundations

Git Internals

Underneath every command, Git is a remarkably simple content-addressable database: four object types, all identified by the hash of their own content.

7 min read

Git stores snapshots, not diffs — conceptually, every commit points at a complete tree of the entire project at that moment. Unchanged files aren't re-stored; they're just referenced by the same content hash as before, so snapshots stay cheap.

ObjectStores
BlobRaw file contents — no filename, no metadata
TreeA directory listing: names, permissions, pointers to blobs/subtrees
CommitPointer to a root tree, plus parent commit(s), author, and message
TagAn annotated pointer to another object, usually a commit
commitauthor, message, parent
treeroot directory
treesrc/
blobApp.java contents

Each commit also points to its parent commit(s) — that chain of parent pointers is what forms the history DAG (directed acyclic graph).

Content-addressable

Every object's identity is the SHA-1 hash (Git is migrating toward SHA-256) of its own content. Identical content anywhere in history — the same file version committed twice, in two different commits — is stored exactly once. A commit's hash also depends on its parent's hash, so tampering with any historical commit changes every hash after it — history is tamper-evident by construction.

Refs & detached HEAD

A branch is nothing but a lightweight, movable pointer to a commit — a 40-byte file under .git/refs/heads/ holding a single hash. That's why creating a branch is O(1): no files are copied, only a pointer is written. HEAD is a pointer to whichever branch (or, sometimes, commit) you currently have checked out.

Detached HEAD

Checking out a specific commit hash or tag (instead of a branch name) points HEAD directly at that commit — you're no longer "on" any branch. New commits made here have no branch tracking them, and can become unreachable (eventually garbage-collected) the moment you switch away. If you want to keep work made in this state: git switch -c new-branch-name before doing anything else.

Does Git really never store diffs at all?
Conceptually, yes — every commit references a complete tree, and the "snapshot" model is how you should reason about Git's behavior. For actual disk efficiency, though, Git periodically packs loose objects into packfiles (git gc), which internally do use delta compression between similar objects to save space. This is purely a storage optimization underneath the snapshot model — it never changes how commits, branches, or history behave conceptually.
Chapter summary
  • Four object types: blob (file contents), tree (directory), commit (snapshot + parent + metadata), tag.
  • Everything is content-addressed by hash — identical content is stored once; tampering breaks every hash downstream.
  • A branch is just a movable pointer to a commit — cheap to create, cheap to switch.
  • Detached HEAD means you're pointed at a commit directly, not a branch — commit there and create a branch immediately if you want to keep the work.
Blob vs. tree vs. commitTap to reveal

Blob = file contents. Tree = a directory (names + pointers). Commit = a snapshot pointer + parent + author + message.

Why branches are cheapTap to reveal

A branch is a 40-byte file holding one commit hash — creating one writes a pointer, it never copies any files.

Detached HEADTap to reveal

HEAD points directly at a commit instead of a branch — new commits here risk becoming unreachable once you switch away.

PackfilesTap to reveal

A storage-layer optimization (via git gc) that delta-compresses similar objects — doesn't change the snapshot mental model, just saves disk.

Why is creating a new Git branch essentially instant, even in a repository with 500,000 commits?
Creating a branch writes a single 40-byte pointer file — its cost has nothing to do with how much history exists.
You run git checkout a1b2c3d (a commit hash) and make two new commits. What's the risk?
This is detached HEAD — the fix, before switching away, is git switch -c some-name to attach a real branch pointer to that work.
03 Foundations

The Everyday Workflow

Every Git session is a loop through three areas — and understanding why there's a staging area at all is the difference between memorising commands and actually using Git deliberately.

6 min read
Working directoryyour edits
Staging (index)git add
Repositorygit commit

git restore moves you back the other way — from repository/staging back toward the working directory.

Why have a staging area at all?

It lets you build a commit deliberately. git add -p stages individual hunks (parts of a file), not just whole files — so a debug print-statement and a real bug fix living in the same file can end up in two separate, clean commits instead of one messy one.

everyday-loop.sh
git status                 # what changed / what's staged
git add file.txt           # stage one file (git add . = everything)
git add -p                 # stage selectively, hunk by hunk
git commit -m "message"  # commit staged changes
git commit -am "message" # stage all tracked changes + commit, in one step
git log --oneline --graph  # view history
git diff                   # working dir vs. staged
git diff --staged          # staged vs. last commit
git show <commit>          # full diff of one commit
git blame file.txt         # who last changed each line
git push                   # send commits to the remote

File lifecycle

Untrackednew file
Stagedadd
Trackedcommit
Modifiededit again

Modern file-level commands

CommandWhat it does
git switch <branch>Change branches (modern, single-purpose)
git restore <file>Discard working-directory changes to a file
git restore --staged <file>Unstage a file, keep the edits
git commit --amendEdit the last commit (message and/or contents) — before pushing only
Why Git split checkout into switch/restore

The old git checkout did three unrelated things depending on its arguments (change branch, restore a file, or even create a branch) — a genuinely confusing overload. Modern Git split it into switch (branches) and restore (files), leaving checkout as a legacy catch-all. Mentioning this split unprompted reads well in an interview — it signals you keep up with the tool, not just the decade-old tutorial.

Chapter summary
  • Three areas: working directory (edits) → staging/index (what the next commit will contain) → repository (permanent history).
  • The staging area exists so you can craft deliberate, logical commits — including at the hunk level via add -p.
  • Modern Git prefers switch (branches) and restore (files) over the overloaded legacy checkout.
Staging area / indexTap to reveal

A snapshot-in-progress of what the next commit will contain — lets you build commits deliberately instead of "commit everything, always."

git add -pTap to reveal

Stage individual hunks within a file interactively — splits unrelated changes in the same file into separate, clean commits.

diff vs. diff --stagedTap to reveal

Plain diff = working directory vs. staging. --staged = staging vs. the last commit.

switch/restore vs. checkoutTap to reveal

Modern Git split checkout's overloaded behavior into switch (change branch) and restore (revert files) for clarity.

A file has both a debug print statement and a real bug fix mixed into unstaged changes. How do you commit only the fix?
The staging area operates at the hunk level via add -p — this is precisely the scenario it exists for.
git diff --staged shows what, exactly?
Plain git diff compares working directory to staging; --staged compares staging to the last commit — the "what will actually go into this commit" view.

Branching & Merging

A branch is a movable pointer; commits form a DAG through parent links. Merging is just how two diverged pointers get reconciled back into one history.

6 min read
merge-shape.txt
      A───B───C  (main)
               \
                D───E  (feature)

git merge feature   ->   creates merge commit F with two parents: C and E
Merge typeWhen it happensResult
Fast-forwardTarget branch hasn't diverged since the feature branched offPointer just moves forward — no merge commit at all
3-way mergeBoth branches have new commits since they divergedA new commit with two parents
--no-ffYou force a merge commit even when a fast-forward was possiblePreserves the fact a feature branch existed, as a visible grouping in history
Squash mergeYou want the feature's commits combinedOne clean commit on the target branch; original commits aren't preserved
merge-commands.sh
git merge feature              # fast-forward if possible, else 3-way merge
git merge --no-ff feature      # always create a merge commit
git merge --squash feature     # stage the combined diff as one new commit

Resolving conflicts

A conflict happens when both branches changed the same lines (or one edited a file the other deleted) and Git can't automatically reconcile them.

conflict-markers.txt
<<<<<<< HEAD
your current branch's version
=======
the incoming branch's version
>>>>>>> feature
resolve-workflow.sh
git status                 # see which files are conflicted
# edit the files: remove markers, keep the correct content
git add <resolved-file>    # mark it resolved
git commit                 # (for a merge) -- or: git rebase --continue
git merge --abort          # bail out entirely, back to the pre-merge state
Reducing conflicts before they happen

Pull/rebase frequently, keep branches short-lived and small, and communicate about shared files. Enabling git rerere ("reuse recorded resolution") makes Git remember how you resolved a specific conflict once, and auto-apply that resolution if the exact same conflict recurs — genuinely useful during a long rebase.

Chapter summary
  • Fast-forward: no divergence, pointer just moves. 3-way: both sides advanced, new merge commit with two parents.
  • --no-ff preserves a visible feature-branch grouping; squash collapses a feature's history into one commit.
  • Resolving a conflict: edit out the markers, git add the file, then commit (or rebase --continue).
Fast-forward mergeTap to reveal

When the target branch hasn't diverged, Git just moves its pointer forward to the feature tip — no merge commit created.

3-way mergeTap to reveal

Both branches advanced since diverging — Git creates a new commit with two parents to reconcile them.

Squash mergeTap to reveal

Combines every commit on a feature branch into a single new commit on the target — cleaner history, but loses the individual commits.

git rerereTap to reveal

"Reuse recorded resolution" — Git remembers how you resolved a conflict and reapplies it automatically if it recurs.

Main hasn't moved since you branched off feature. What happens on git merge feature?
Without divergence, there's nothing to reconcile — Git just advances the pointer, which is exactly what a fast-forward is.
You want to preserve the fact that a feature branch existed in history, even though a fast-forward is possible. What do you pass?
--no-ff forces a merge commit even when Git could have just fast-forwarded, explicitly preserving the branch's shape in history.
05 Foundations

Rebasing & Cherry-pick

Rebasing replays your commits onto a new base, one at a time — producing a clean, linear history at the cost of new commit hashes. This trade-off is one of the most common "very common Q" interview topics in all of Git.

7 min read Frequently asked
MergeRebase
HistoryPreserved as it truly happened (merge commits included)Rewritten — linear, no merge commits
Commit hashesUnchangedNew hashes for every replayed commit
ReadabilityCan get noisy with many merge commitsClean, linear git log
SafetySafe on shared/pushed branchesDangerous on shared/pushed branches
rebase-shape.txt
git switch feature
git rebase main

# before:          A─B─C (main)
#                       \
#                        D─E (feature)
#
# after:           A─B─C
#                       \
#                        D'─E' (feature, replayed on top of main's tip)
The Golden Rule of Rebasing

Never rebase commits that other people have already pulled. Rebasing rewrites history — new hashes for every replayed commit — so anyone who already has the old commits will diverge painfully from you. Rebase freely on local, unpushed work; use merge to integrate finished, shared work into a shared branch. Rebase locally, merge publicly.

Interactive rebase

interactive-rebase.sh
git rebase -i HEAD~4   # edit the last 4 commits

# in the editor, choose one action per commit:
#   pick    keep as-is
#   reword  change the commit message only
#   edit    pause here so you can amend it
#   squash  fold into the previous commit, keep both messages
#   fixup   fold into the previous commit, discard this message
#   drop    delete the commit entirely

Used to clean up history before opening a PR — squashing WIP commits, reordering, or fixing a typo'd message, all before anyone else has seen the branch.

rebase --onto (the three-argument form)

git rebase --onto main feature~3 feature moves just the last 3 commits of feature onto main, discarding the commits in between — used to pull a small set of commits off a branch that itself branched from something you don't want to bring along. Less common day-to-day, but a favorite "do you actually know rebase" interview probe.

Cherry-pick

cherry-pick.sh
git cherry-pick <commit>   # apply just this one commit onto the current branch

Use it for hotfixes that need to land on multiple release branches, or to grab a single useful commit without merging its entire source branch.

Chapter summary
  • Rebase replays commits onto a new base — linear history, new hashes, dangerous on shared branches.
  • The Golden Rule: never rebase history someone else has already pulled.
  • Interactive rebase (-i) lets you reorder, squash, reword, or drop commits before sharing a branch.
  • Cherry-pick applies one specific commit onto the current branch without merging its whole source branch.
Golden Rule of RebasingTap to reveal

Never rebase a branch that others have already pulled — it creates new commit hashes and diverges everyone else's history.

squash vs. fixupTap to reveal

Both fold a commit into the previous one — squash keeps both commit messages for editing, fixup silently discards the folded message.

cherry-pickTap to reveal

Applies one specific commit from anywhere in history onto your current branch, without touching anything else from its source branch.

rebase --ontoTap to reveal

The three-argument rebase form — moves a specific range of commits onto a new base, skipping everything else in between.

Your teammate already pulled your feature branch and built on top of it. Should you rebase it onto main to clean up history?
This is exactly the Golden Rule scenario — rebasing shared history rewrites hashes your teammate's work is already built on, forcing a painful, error-prone reconciliation.
During git rebase -i, what's the difference between squash and fixup?
Functionally the same fold, differing only in what happens to the commit message afterward.

Remote Workflows

A remote is just another copy of the repo somewhere else — fetch and pull are how you find out what changed there, and push is how you share what changed here.

6 min read

Fetch vs. pull

git fetchgit pull
Downloads remote commitsYesYes
Modifies your working branchNo — safe, review firstYes — merges (or rebases) automatically
Formula—fetch + merge (or --rebase)
The safer habit

git fetch then review with git log origin/main before integrating anything — or default to git pull --rebase for a linear history instead of an extra merge commit on every pull.

remote-tracking.sh
git remote -v                # list configured remotes
git remote add origin <url>  # add a remote named "origin"
git branch -vv               # show which remote branch each local branch tracks
git push -u origin main      # push + set upstream, so future push/pull need no args
git push --force-with-lease  # a safer force-push -- see callout below
--force vs. --force-with-lease

Plain --force overwrites the remote branch unconditionally — including any commits a teammate pushed since you last fetched, which you'd silently wipe out. --force-with-lease refuses if the remote has moved since you last looked at it, giving you a chance to fetch and check what you'd be overwriting first.

Clone vs. fork

CloneFork
What it isA local copy of a repoA server-side copy under your own account
Typical useWorking on a repo you can push to directlyContributing to a repo you can't push to (open source)
Staying in syncVia originAdd an upstream remote, fetch + merge/rebase from it
fork-sync.sh
# Keep your fork's main in sync with the original project
git remote add upstream <original-repo-url>
git fetch upstream
git merge upstream/main       # or: git rebase upstream/main

.gitignore & SSH vs. HTTPS

HTTPS remotes authenticate via tokens/credentials and work through most corporate firewalls; SSH uses key pairs — no password prompt on every push, once your public key is registered with the host.

.gitignore only affects untracked files

Adding a pattern to .gitignore does nothing for a file Git is already tracking — you have to explicitly stop tracking it first with git rm --cached <file>. And never commit secrets in the first place: once pushed, treat a credential as compromised even if you delete it in a later commit — it still exists in history until that history is rewritten.

Chapter summary
  • fetch downloads without touching your branch; pull = fetch + merge (or --rebase).
  • --force-with-lease is a safer force-push — it refuses if the remote moved since your last fetch.
  • Clone = your own copy of a repo you can push to; fork = a server-side copy for contributing to repos you can't.
  • .gitignore only prevents tracking new files — already-tracked files need git rm --cached too.
fetch vs. pullTap to reveal

fetch downloads and stops there (safe to review); pull downloads and immediately merges or rebases into your branch.

force-with-leaseTap to reveal

Refuses to force-push if the remote branch has moved since your last fetch — protects against silently overwriting a teammate's work.

upstream remoteTap to reveal

In a fork workflow, the remote pointing at the *original* repo (not your fork) — used to pull in changes you don't own.

.gitignore scopeTap to reveal

Only prevents Git from tracking new matching files — has zero effect on files already tracked before the pattern was added.

You want to see what changed on the remote before touching your own branch. Which command?
fetch downloads the remote's commits into your local origin/main reference without touching your checked-out branch at all — the safe way to look before integrating.
You added *.log to .gitignore, but debug.log — already tracked before that — still shows up in every diff. Why?
Git only consults .gitignore when deciding whether to *start* tracking a file — a file already under version control keeps being tracked regardless of what's added to the ignore file afterward.

Undoing Changes

Four different "undo" tools exist because they undo different things, at different layers, with very different safety guarantees on shared history.

7 min read High-value chapter

git reset — three modes

ModeMoves branch pointerStaging areaWorking directory
--softYesKept (still staged)Kept
--mixed (default)YesReset (unstaged)Kept
--hardYesResetDiscarded
reset-modes.sh
git reset --soft  HEAD~1   # undo last commit, keep changes staged
git reset --mixed HEAD~1   # undo commit + unstage, keep the edits
git reset --hard  HEAD~1   # undo commit AND throw away the changes -- danger
reset --hard permanently discards uncommitted work

Committed work can usually be recovered afterward via git reflog (see below) — but uncommitted changes that only ever existed in your working directory are gone the moment --hard runs. There's no reflog for changes that were never committed.

revert vs. reset

git revertgit reset
HowCreates a new commit that inverts a previous oneMoves the branch pointer backward
HistoryPreserved — nothing is rewrittenRewritten
Safe on shared/pushed branches?Yes — the recommended tool thereNo — rewrites public history
revert.sh
git revert <commit>     # safely undo an already-pushed commit via a new "undo" commit

git restore — modern, file-level undo

restore.sh
git restore file.txt               # discard working-directory changes to this file
git restore --staged file.txt      # unstage it, but keep the edits
git restore --source=HEAD~2 f.txt  # pull this file's contents from an older commit

git reflog — the safety net

Reflog records every movement of HEAD — every commit, reset, checkout, and rebase — for roughly 90 days by default, even ones no branch points at anymore.

reflog.sh
git reflog                    # see everywhere HEAD has been, even "lost" commits
git reset --hard HEAD@{2}     # jump back to a previous state by its reflog entry
A favorite interview rescue answer

"I did git reset --hard and lost commits — can I get them back?" Yes, if they were committed: find the lost commit's hash in git reflog, then git reset --hard <hash> or git cherry-pick it back. Uncommitted changes are the one thing reflog can't help with.

Chapter summary
  • reset: soft (keep staged) → mixed (keep, unstaged) → hard (discard) — increasingly destructive.
  • revert creates a new undo-commit, safe for already-shared history; reset rewrites history, unsafe there.
  • restore is the modern, file-scoped undo — discard working changes or unstage, without touching commits.
  • reflog remembers every HEAD movement for ~90 days — the recovery path for "lost" committed work.
reset --softTap to reveal

Moves the branch pointer back but keeps everything staged — useful for "redo this commit's message/contents."

revertTap to reveal

Creates a brand new commit that inverts a previous one — safe to use on shared branches since nothing is rewritten.

reflogTap to reveal

A log of every HEAD movement, ~90 days retained — the way to recover commits "lost" to a bad reset or rebase.

What reflog can't saveTap to reveal

Uncommitted changes — reflog only tracks commits and HEAD positions, never working-directory-only edits.

A bad commit was already pushed to a shared main branch. What's the correct way to undo it?
Revert creates a new commit undoing the change, preserving history for everyone who already pulled — reset+force-push would rewrite shared history out from under your teammates.
You ran git reset --hard and lost three committed changes. Recoverable?
Since they were committed, their hashes still exist in Git's object database and in the reflog even after the branch pointer moved — they're recoverable until garbage collection eventually cleans up truly unreachable objects.
08 Collaboration

Stashing & Tags

Two small, single-purpose tools: one shelves work you're not ready to commit, the other marks a specific commit as meaningful forever.

5 min read

git stash

stash.sh
git stash               # save uncommitted changes, clean the working dir
git stash -u            # also include untracked files
git stash list          # see all stashes
git stash pop           # reapply the most recent stash, remove it from the list
git stash apply         # reapply, but keep it in the stash list too
git stash push -- path/to/file.txt  # stash just one file's changes
git stash drop          # delete a stash you no longer need

Use it when you need to switch branches urgently — say, for a hotfix — but aren't ready to commit whatever you're mid-way through.

Recovering a stash conflict

If git stash pop conflicts with your current work, Git leaves the stash in the list rather than dropping it (so you don't lose it) — resolve the conflict, then manually git stash drop when you're satisfied. git stash branch <name> is the escape hatch: it creates a new branch from when the stash was made and applies it there instead, sidestepping the conflict entirely.

Tags

TypeCommandStores
Lightweightgit tag v1.0Just a name pointing at a commit
Annotated (recommended for releases)git tag -a v1.0 -m "Release 1.0"Author, date, message — and can be GPG-signed (-s)
tags.sh
git push origin v1.0    # push a single tag
git push --tags         # push every tag at once
Chapter summary
  • stash shelves uncommitted work so you can switch context, then restore it later with pop/apply.
  • Annotated tags (author, date, message, optional signature) are the right choice for releases; lightweight tags are just a name.
  • Tags don't push automatically — git push --tags or push them by name explicitly.
stash pop vs. applyTap to reveal

pop reapplies and removes the stash entry; apply reapplies but keeps it in the list for reuse elsewhere.

Annotated vs. lightweight tagTap to reveal

Annotated stores author/date/message and can be signed — use for releases. Lightweight is just a bare pointer to a commit.

stash branchTap to reveal

Creates a new branch from the stash's original point and applies it there — the fix when popping a stash conflicts.

Pushing tagsTap to reveal

Tags aren't included in a plain git push — push them explicitly by name, or all at once with --tags.

You need to mark a production release with author, date, and a signed message. Which tag type?
Annotated tags carry the metadata (and optional signature) that a release genuinely needs; lightweight tags are just a bare name-to-commit pointer.
You run git stash pop and it conflicts with your current changes. What happens to the stash?
Git is deliberately conservative here — it won't drop a stash you might still need, so you have to explicitly clean it up once you're sure the conflict is resolved correctly.

Collaboration Workflows

How a team actually agrees on when branches get made, how they get reviewed, and when they land — the part of Git that's really a team-process question wearing a technical name.

8 min read

Branching strategies

StrategyIdeaBest for
Git FlowLong-lived main + develop, plus feature/release/hotfix branchesScheduled releases, versioned products
GitHub FlowOne main, short feature branches, PR, deployContinuous deployment, web apps
GitLab FlowFeature branches + environment/release branchesA balance of the two, with environment promotion
Trunk-basedEveryone commits to main via tiny, short-lived branches + feature flagsHigh-velocity CI/CD teams
Forking workflowEach contributor forks; changes flow back via PR from the forkOpen source — contributors without direct push access

feature/*off develop

Git Flow's shape: hotfixes branch directly off main; everything else funnels through develop before a release cuts back to main.

Match the strategy to the deployment cadence

Git Flow is structured and heavier — good for products with real version numbers and parallel maintenance. GitHub Flow/trunk-based is lightweight and fast — good for continuous delivery. Modern teams increasingly trend toward trunk-based + feature flags for speed, deploying unfinished features dark rather than managing long-lived branches.

Pull/merge requests & code review

A PR (GitHub) / MR (GitLab) proposes merging one branch into another — the vehicle for review, discussion, and automated checks before anything lands.

Anatomy of a good PR

  • Small, focused, single-purpose
  • Clear title + description: what, and why
  • Linked issue
  • Passing CI (build/tests/lint)
  • Required reviewer approvals, resolved conversations

Code review priorities

  • Correctness, readability, security, test coverage
  • Not style nitpicks — automate those with a linter instead
  • Be specific and kind; suggest, don't demand
  • Approve small good changes quickly; use draft PRs for early feedback
Merge optionResultUse when
Merge commitPreserves every commit + adds a merge commitYou want the full, true history
Squash & mergeCombines everything into one commit on mainClean linear history — the most common default
Rebase & mergeReplays commits individually, no merge commitLinear history while keeping individual commits
PR vs. MR — is there a real difference?

Functionally, no — same concept, different platform naming (GitHub: Pull Request, GitLab: Merge Request). GitLab's name is arguably more accurate, since you're literally requesting a merge, not just a "pull."

Chapter summary
  • Branching strategy should follow deployment cadence: Git Flow for versioned releases, GitHub Flow/trunk-based for continuous delivery.
  • A good PR is small, focused, well-described, CI-green, and reviewed before merging.
  • Squash-merge is the common default for a clean linear main; merge commits preserve full history when that matters more.

Hooks & Repository Security

Hooks let Git itself run code at specific points in your workflow — the mechanism behind "why did my commit just get rejected" long before any CI server ever saw it.

7 min read

Git hooks

A hook is just an executable script Git runs automatically at a specific lifecycle point — living in .git/hooks/, one file per hook name, with the executable bit set. They run locally, before anything ever reaches a remote or a CI pipeline.

HookRunsCommon use
pre-commitBefore a commit is createdLint staged files, run fast unit tests, block a commit containing debug statements
commit-msgAfter the message is written, before the commit is finalizedEnforce a message format (e.g. Conventional Commits: feat:, fix:)
pre-pushBefore git push sends anythingRun the full test suite, block pushing directly to main
pre-receive (server-side)On the remote, before accepting pushed refsReject force-pushes, enforce commit-message policy centrally
post-receive (server-side)On the remote, after accepting a pushTrigger a deploy, notify a Slack channel
.git/hooks/pre-commit
#!/bin/sh
# Block a commit if any staged file still has a debugger statement
if git diff --cached | grep -q "debugger;"; then
  echo "Error: remove debugger statements before committing."
  exit 1
fi
Local hooks aren't shared or enforced automatically

.git/hooks/ isn't version-controlled — cloning a repo doesn't bring anyone else's hooks along. Teams that want hooks enforced for everyone typically use a shared tool (husky, pre-commit, lefthook) checked into the repo itself, or — for anything that must truly not be bypassable — a server-side hook / branch-protection rule, since a local pre-commit can always be skipped with git commit --no-verify.

Client-side vs. server-side hooks — why does the distinction matter?
Client-side hooks (pre-commit, commit-msg, pre-push) run on the developer's own machine — fast feedback, but skippable (--no-verify) and never guaranteed to have run at all. Server-side hooks (pre-receive, update, post-receive) run on the Git server itself when a push arrives — they can't be bypassed by the pushing client, which is why anything that must be a hard rule (message format, no force-push, no secrets) belongs server-side or in a platform's branch-protection settings, not just a local hook.

Removing a leaked secret

(1) Rotate/revoke the credential immediately — assume it's compromised the moment it's pushed. (2) Remove it from history with git filter-repo (the modern tool — filter-branch is deprecated) or BFG Repo-Cleaner. (3) Force-push the rewritten history; every collaborator must re-clone (their old clones still have the secret in their local history). Rewriting history alone is not the fix — rotation is the only thing that actually neutralizes a leaked credential.

Repo hygiene: Git LFS & monorepo vs. polyrepo

Git LFS (Large File Storage) keeps large binaries out of the main repo's history via pointer files, so clones stay fast. Monorepo (one big repo) enables atomic cross-project changes and shared tooling; polyrepo (many repos) gives clearer ownership boundaries and independent deploy cycles — neither is universally "correct," it's a genuine trade-off worth naming explicitly.

  • Git LFS keeps large binaries out of the main history; monorepo vs. polyrepo trades atomic changes against clear ownership.

14 Interview Room

Interview Questions

Sixteen deep-dive questions — why, not just what. Try answering before revealing.

16 questions
Internals & Why
01
InternalsWhy does Git store snapshots instead of diffs, if diffs are so much smaller?

Snapshots make history operations trivially fast and simple: checking out any commit means reading its tree directly, with no need to replay a chain of diffs from some base version. Diff-based systems (like older CVS/SVN) can make certain operations — like a full checkout of very old history — noticeably slower, since they have to reconstruct a version by applying deltas. Git gets the storage efficiency back a different way: identical file content across commits is stored only once (content-addressing), and periodic packfile compression applies delta-encoding at the storage layer without changing the snapshot model applications and commands actually reason about.

02
InternalsWhy is a Git commit's hash affected by its parent commit's hash, not just its own content?

A commit object literally includes its parent's hash as part of its own content, which then gets hashed. This chains every commit to everything before it — changing anything in a historical commit (even one line, or the message) changes that commit's hash, which changes every child commit's hash, cascading all the way to the current tip. This is what makes Git history tamper-evident: you can't quietly alter something three commits back without every subsequent hash visibly changing.

03
InternalsWhat actually happens on disk when you run git branch new-feature?

Git writes a single new file at .git/refs/heads/new-feature containing the 40-character hash of the current commit — nothing else happens. No files are copied, no history is duplicated. This is exactly why branching in Git is O(1) regardless of repository size, unlike systems where a "branch" means a full filesystem copy.

Trade-offs
04
Trade-offYour team wants both a clean, linear main-branch history AND full traceability of every individual commit a contributor made. Can you have both?

Not fully — it's a genuine trade-off. Squash-merge gives you the cleanest main-branch history (one commit per feature) but discards the individual commits entirely. Rebase-merge preserves individual commits in a linear history, but requires each commit to be independently sensible (no "WIP" or "fix typo" noise) since they all land on main permanently. Regular merge commits preserve everything, including messy in-progress commits, at the cost of a noisier log with merge commits scattered throughout. Most teams pick squash-merge for exactly this reason — they value main's readability more than preserving a feature branch's exact commit-by-commit story, which usually only mattered during review anyway.

05
Trade-offWhy would a team choose Git Flow over trunk-based development in 2026, when trunk-based is widely considered the "modern" default?

Trunk-based development assumes you can deploy continuously and hide unfinished work behind feature flags — that assumption breaks down for shipped, versioned software (embedded firmware, mobile apps with app-store review delays, on-prem enterprise software with scheduled release trains) where you genuinely need to maintain multiple released versions in parallel and backport hotfixes to older ones. Git Flow's develop/release/hotfix structure exists specifically to support that multi-version maintenance reality — it's not obsolete, it's matched to a different deployment model than continuous SaaS delivery.

06
Trade-offSubmodules and subtrees both let you embed one repo inside another. When would you actually prefer submodules despite the extra complexity?

When you need to push changes back to the embedded repository regularly and want an explicit, visible pin to exactly which upstream commit you depend on. Submodules keep the embedded repo as a genuinely separate, independently-versioned project — useful for a shared internal library consumed by many other repos, where you want each consumer to explicitly control (and be able to see, in a diff) exactly when it upgrades to a newer version of the dependency. Subtree is simpler for consumers but muddies the line between "your code" and "vendored code," and pushing changes back upstream is comparatively awkward.

Traps
07
TrapA developer runs git pull on a branch with local, uncommitted changes and gets unexpected merge conflicts in files they never touched. What likely happened?

git pull is fetch + merge (or rebase) — it tries to reconcile the remote's new commits with your local branch state including uncommitted changes if they overlap with incoming changes on the same lines, even in files unrelated to what the developer was actively working on if the remote touched them too. The safer habit is committing or stashing local work before pulling, or using git fetch first to review what's incoming before merging it in deliberately.

08
TrapYou revert a merge commit on main with git revert -m 1 <merge-commit>. Weeks later you try to re-merge that same feature branch, and none of its changes show up. Why?

The revert commit exists in history as an explicit "undo" of every change the merge introduced. Git sees that main already contains the inverse of the feature branch's changes, so a plain re-merge appears to have "nothing new" to bring in relative to that undone state. To properly re-apply the feature later, you typically need to revert the revert commit first (undoing the undo), then merge again — a classic, easy-to-miss gotcha with reverted merges specifically.

09
TrapA CI pipeline step runs git clone --depth 1 for speed, and later a git log-based versioning script in the same pipeline silently produces wrong version numbers. What's the connection?

A shallow clone (--depth 1) only fetches the single most recent commit — deliberately discarding the rest of history to save time and bandwidth. Any tooling that depends on full history (counting commits since the last tag for a version number, walking parent commits, running git log across a range) will silently see an artificially truncated history and produce wrong results, often with no error at all. The fix is either fetching full history for jobs that need it, or explicitly fetching just the tags/depth actually required (git fetch --deepen or --tags).

10
TrapSomeone adds node_modules/ to .gitignore in a repo where it was already accidentally committed months ago. They're confused why git status still shows it as tracked. What's missing?

.gitignore only controls whether Git starts tracking a new, currently-untracked file or directory — it has zero effect on something already committed. They need git rm -r --cached node_modules/ to explicitly stop tracking it (leaving the actual files on disk untouched) and then commit that removal — only after that will the .gitignore entry actually take effect going forward.

Scenario
11
ScenarioYou accidentally committed and pushed a database password to a public repository. Walk through your response in order.

(1) Rotate/revoke the credential immediately, before anything else — treat it as compromised the second it was pushed publicly. (2) Remove it from history using git filter-repo (or BFG Repo-Cleaner; the older filter-branch is deprecated and slower). (3) Force-push the rewritten history, and have every collaborator re-clone rather than pull, since their local history still contains the old commits. (4) Audit anywhere else it might have been cached — CI logs, forks, third-party mirrors. Removing it from Git history without rotating it first is the single most common mistake here — the secret is compromised the moment it's pushed, regardless of what you later do to history.

12
ScenarioYour feature branch is 40 commits behind main and you need to open a PR. How do you bring it up to date, and does your answer change if a teammate is also committing to your feature branch?

If it's genuinely just your branch, unshared: git fetch && git rebase origin/main for a clean linear history against main, resolving any conflicts as they surface commit-by-commit. If a teammate is also actively committing to the same feature branch, rebasing would rewrite commit hashes they've already built on top of — git merge origin/main instead, accepting one extra merge commit in exchange for not breaking their local history. The deciding factor is always "has anyone else already pulled this branch," not personal preference for a cleaner log.

13
ScenarioTwo developers both modified the same function in the same file on different branches, and merging produces a conflict. Walk through resolving it.

Run the merge, then git status to see which files are conflicted. Open each one, find the <<<<<<</=======/>>>>>>> markers, and manually decide the correct combined content — sometimes one side wins, sometimes both changes need merging together, sometimes neither is fully right and a new version is needed. Remove the markers entirely, git add the resolved file, then commit (or git rebase --continue if this happened during a rebase). If it goes badly, git merge --abort backs out completely to the pre-merge state. Prevent recurrence with smaller, shorter-lived branches and more frequent syncing with main.

14
ScenarioA new hire asks why your team enforces Conventional Commits (feat:, fix:, docs:) via a commit-msg hook instead of just asking people nicely in the PR template. What's the actual justification?

Beyond readability, Conventional Commits are machine-parseable: tooling can auto-generate a changelog by scanning commit prefixes, and can auto-determine semantic version bumps (a fix: is a patch release, a feat: is a minor release, a BREAKING CHANGE: footer forces a major release) without a human deciding the version number by hand. A PR template is a suggestion a rushed developer can ignore; a commit-msg hook that rejects a malformed message actually blocks the commit from being created at all — enforcement versus a polite request.

15
ScenarioYour repository has grown to 4GB, mostly from binary assets committed over several years, and clones are now painfully slow. What's your remediation plan?

Migrate large binary assets to Git LFS going forward (pointer files replace the actual binary content in the main history), and for the historical bloat already in the repo, use git filter-repo to rewrite history and move existing large blobs into LFS retroactively (or simply purge genuinely unneeded historical binaries). This requires a force-push and a full team re-clone, same as the secret-removal scenario — communicate it as a coordinated, scheduled migration, not a surprise. Going forward, add a pre-commit hook or CI check that rejects new commits containing large files outside LFS, so the problem doesn't quietly recur.

16
Guess the outcomeYou run git reset --hard origin/main to "clean up" your local branch before starting new work. What have you actually done?

You've discarded every local commit and uncommitted change your branch had that wasn't already on origin/main — permanently, for anything uncommitted. If any of your local commits hadn't been pushed anywhere, they're now recoverable only via git reflog (and only because they were committed at some point); any uncommitted edits in your working directory are gone with no recovery path at all. "Clean up my branch" almost always actually means something safer, like git switch -c fresh-branch origin/main to start clean without destroying the old one.

Interview delivery tips

(1) Always distinguish Git the tool from GitHub/GitLab the platforms — conflating them reads as inexperience. (2) For any "undo" question, pick reset/revert/restore explicitly based on whether the history is shared. (3) State the rebasing Golden Rule unprompted when rebase comes up. (4) Mention reflog and bisect as recovery/debugging power tools — real signals of hands-on experience, not textbook knowledge. (5) Tie branching-strategy answers to deployment cadence, not personal preference.
