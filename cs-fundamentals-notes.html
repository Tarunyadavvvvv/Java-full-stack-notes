Part I — Operating Systems

1. OS Fundamentals Basic

1.1 What is an Operating System?

An OS is system software that sits between hardware and applications. It is a resource manager (CPU, memory, I/O, files) and an abstraction layer that gives programs a clean interface (system calls) instead of raw hardware.

┌─────────────── Applications ───────────────┐
│        (browsers, editors, your code)       │
├──────────── System Call Interface ──────────┤
│         Operating System (Kernel)           │
│  Process | Memory | File | I/O | Network mgr │
├─────────────────── Hardware ────────────────┤
│        CPU · RAM · Disk · Devices            │
└─────────────────────────────────────────────┘

1.2 Kernel & modes

  • Kernel — the core of the OS, always in memory, with full hardware access.
  • User mode vs Kernel mode: user code runs in restricted user mode; privileged operations (I/O, memory mapping) require a switch to kernel mode via a system call (a software interrupt/trap).
  • Monolithic kernel (Linux) — all services in kernel space (fast, less isolated). Microkernel (minimal kernel, services in user space) — more modular & robust, but more context-switch overhead.

1.3 Key terms

TermMeaning
System callControlled entry into the kernel (e.g. read, fork, open)
InterruptHardware/software signal that diverts the CPU to a handler
Context switchSaving one process/thread's state & loading another's
MultiprogrammingKeep CPU busy by switching among jobs
MultitaskingTime-sharing the CPU among tasks (illusion of parallelism)
MultiprocessingMultiple CPUs/cores executing truly in parallel
What happens during a system call?
The program executes a trap instruction, the CPU switches to kernel mode, the kernel validates arguments and performs the privileged operation, then returns to user mode with the result. This boundary protects the system from buggy/malicious user code.

2. Processes & Threads Basic

2.1 Process vs Thread

ProcessThread
DefinitionA program in executionA lightweight unit within a process
MemoryOwn address spaceShares process memory (heap, code)
CommunicationIPC (pipes, sockets, shared mem)Shared variables (needs sync)
OverheadHeavy (separate memory)Light (shared memory)
Crash impactIsolatedCan crash whole process
Each thread has its own stack, registers, and program counter, but shares the heap, code, and open files with sibling threads — which is why shared data needs synchronization.

2.2 Process states & the PCB

NEW -> READY -> RUNNING -> TERMINATED
        ▲          │
        │          ▼
       WAITING (blocked on I/O / event)

The Process Control Block (PCB) stores per-process state: PID, program counter, registers, memory maps, open files, scheduling info. A context switch saves/restores PCBs.

2.3 Process creation & special cases

  • fork() creates a child (copy of parent); exec() replaces the process image with a new program.
  • Zombie process — finished but its exit status not yet reaped by the parent (entry lingers).
  • Orphan process — parent died first; adopted by init/systemd.

2.4 Inter-Process Communication (IPC)

MechanismNotes
Pipes / named pipesByte stream between related/unrelated processes
Message queuesDiscrete messages
Shared memoryFastest; needs synchronization
SocketsAcross machines too
SignalsAsync notifications (e.g. SIGKILL)

2.5 User vs kernel threads

  • User-level threads — managed by a library; fast but one blocking call blocks all (many-to-one).
  • Kernel-level threads — scheduled by the OS; true parallelism (one-to-one, the common model today).
Why are threads called "lightweight"?
Creating a thread and switching between threads is cheaper than for processes because threads share the same address space — no new memory map to set up and a cheaper context switch.

3. CPU Scheduling Intermediate

3.1 Goals & metrics

MetricMeaning (goal)
CPU utilizationKeep CPU busy (maximize)
ThroughputProcesses completed per unit time (max)
Turnaround timeCompletion − arrival (min)
Waiting timeTime in ready queue (min)
Response timeFirst response after submit (min)
Preemptive vs non-preemptive: preemptive scheduling can interrupt a running process (better responsiveness); non-preemptive runs a process until it blocks or finishes.

3.2 Scheduling algorithms

AlgorithmIdeaPros / Cons
FCFSFirst come, first served (queue)Simple; convoy effect (long job blocks short ones)
SJFShortest job firstOptimal avg wait; needs burst prediction; starvation
SRTFPreemptive SJFBetter response; starvation of long jobs

PriorityHighest priority firstFlexible; starvation → fix with aging
Multilevel Queue / FeedbackMultiple queues, jobs move between themAdapts to behaviour; complex tuning

3.3 Worked example (avg waiting time)

FCFS, arrival=0:  P1(burst 24), P2(3), P3(3)
Gantt: | P1 (0-24) | P2 (24-27) | P3 (27-30) |
Wait: P1=0, P2=24, P3=27  -> avg = (0+24+27)/3 = 17
With SJF order P2,P3,P1: wait = 0,3,6 -> avg = 3  (much better!)
Starvation: low-priority/long jobs may never run under SJF or priority scheduling. Fix with aging (gradually raise a waiting process's priority).
How do you choose the Round Robin time quantum?
Too large → behaves like FCFS (poor response). Too small → excessive context-switch overhead. A good rule: quantum slightly larger than the typical CPU burst so most jobs finish within one quantum.

4. Synchronization & Deadlocks Advanced

4.1 The critical section problem

When multiple threads access shared data, a race condition can occur. The critical section is the code accessing shared resources; a correct solution must satisfy:

  • Mutual exclusion — only one thread in the CS at a time.
  • Progress — if no one is in the CS, a waiting thread can enter.
  • Bounded waiting — no thread waits forever.

4.2 Synchronization primitives

PrimitiveDescription
Mutex / LockBinary lock; only the owner can unlock
SemaphoreCounter; wait(P) decrements, signal(V) increments. Binary (=mutex) or counting
MonitorHigh-level construct bundling lock + condition variables (Java synchronized)
SpinlockBusy-waits in a loop; good only for very short critical sections
Condition variablewait/notify on a condition while holding a lock
// Counting semaphore (pseudo)
wait(S):   while (S <= 0) ; S--;   // P / acquire
signal(S): S++;                     // V / release

4.3 Classic problems

  • Producer-Consumer (bounded buffer) — semaphores for empty/full slots + a mutex.
  • Readers-Writers — many readers OR one writer.
  • Dining Philosophers — deadlock illustration; fix by ordering forks or limiting diners.

4.4 Deadlock

A set of processes each waiting for a resource held by another — none can proceed. Requires all four Coffman conditions simultaneously:

ConditionMeaning
Mutual exclusionResource held in non-shareable mode
Hold and waitHolding one resource, waiting for another
No preemptionCan't forcibly take a resource
Circular waitCycle of processes each waiting on the next

4.5 Handling deadlock

StrategyHow
PreventionBreak one Coffman condition (e.g. global lock ordering kills circular wait)
AvoidanceBanker's algorithm — grant only if system stays in a safe state
Detection & recoveryDetect cycles in resource-allocation graph, then kill/rollback
Ignore (Ostrich)Assume it's rare; reboot if needed (used by many OSes)
Deadlock vs Livelock vs Starvation: deadlock = stuck waiting forever; livelock = busy but no progress (keep reacting); starvation = perpetually denied resources due to scheduling.
Difference between a mutex and a semaphore?
A mutex is a locking mechanism with ownership (only the locker unlocks), for mutual exclusion. A semaphore is a signaling mechanism with a counter that any thread can signal — it can allow N concurrent accesses and coordinate ordering between threads.

5. Memory Management Intermediate

5.1 Why & address binding

The OS manages allocation of physical RAM to processes and translates logical (virtual) addresses (used by programs) into physical addresses (RAM) via the MMU (Memory Management Unit) at runtime.

5.2 Contiguous allocation & fragmentation

ProblemMeaning
External fragmentationFree memory split into small unusable holes between allocations
Internal fragmentationAllocated block larger than needed; wasted space inside

Allocation strategies: First-fit (fast), Best-fit (least waste but slow + tiny holes), Worst-fit. Compaction reduces external fragmentation by relocating.

5.3 Paging

Divide logical memory into fixed-size pages and physical memory into frames of the same size. A page table maps page → frame. Eliminates external fragmentation (minor internal frag in the last page).

Logical address = [ page number | offset ]
        page number -> page table -> frame number
Physical address = [ frame number | offset ]
  • TLB (Translation Lookaside Buffer) — a cache of recent page→frame translations, so the MMU avoids a memory access for the page table on every lookup.
  • Multi-level / inverted page tables reduce page-table memory for large address spaces.

5.4 Segmentation

Memory divided into variable-size logical segments (code, stack, heap) matching the program's structure. Suffers external fragmentation. Modern systems often combine segmentation + paging.

PagingSegmentation
Block sizeFixed (page)Variable (segment)
FragmentationInternalExternal
ViewPhysicalLogical/programmer

6. Virtual Memory & Paging Advanced

6.1 Virtual memory & demand paging

Virtual memory lets a process use more memory than physically available by keeping only needed pages in RAM and the rest on disk (swap). With demand paging, a page is loaded only when accessed.

  • Page fault — accessing a page not in RAM. The OS traps, fetches it from disk into a free frame (evicting one if needed), updates the page table, and resumes.
  • Benefits: run large programs, more processes in memory, isolation. Cost: page-fault latency.

6.2 Page replacement algorithms

AlgorithmEvictsNotes
FIFOOldest loaded pageSimple; suffers Belady's anomaly
Optimal (OPT)Page used farthest in futureTheoretical best; needs future knowledge
LRULeast recently usedGood approximation of OPT; costly to track exactly
Clock / Second-chanceApproximate LRU via a reference bitPractical, low overhead
Belady's anomaly: with FIFO, adding more frames can increase page faults — counterintuitive. LRU and OPT (stack algorithms) don't suffer from it.

6.3 Thrashing

Thrashing = the system spends more time paging (swapping) than executing, because processes don't have enough frames for their working set. CPU utilization collapses.

  • Working set model — track pages used in a recent window; give each process enough frames for its working set.
  • Fixes: reduce multiprogramming degree, add RAM, use the working-set/PFF (page-fault frequency) policy.
Why does LRU approximate Optimal well?
By the principle of locality, recently used pages are likely to be used again soon. So evicting the least recently used page is usually close to evicting the one needed farthest in the future.

7. File Systems & Disk Intermediate

7.1 File system concepts

  • File — named collection of data; metadata stored in an inode (size, permissions, pointers to data blocks).
  • Directory — maps names to inodes.
  • Allocation methods: contiguous (fast read, fragmentation), linked (no random access), indexed (inode/index block — the common approach).

7.2 Disk scheduling algorithms

Minimize seek time (head movement) when servicing I/O requests.

AlgorithmIdea
FCFSService in arrival order (fair, lots of seeking)
SSTFShortest seek time first (starvation risk)
SCAN (elevator)Head sweeps to one end then back
C-SCANSweeps one direction, jumps back to start (uniform wait)
LOOK / C-LOOKLike SCAN but only goes as far as the last request
SSDs have no seek time (no moving head), so these algorithms matter far less; I/O schedulers shift focus to parallelism & wear-leveling.

7.3 RAID (brief)

LevelTechnique
RAID 0Striping — speed, no redundancy
RAID 1Mirroring — redundancy
RAID 5Striping + distributed parity (1 disk failure)
RAID 10Mirror + stripe (speed + redundancy)
What is stored in an inode?
File metadata: type, permissions, owner, size, timestamps, link count, and pointers to data blocks (direct + single/double/triple indirect). The file name is not in the inode — it's in the directory entry pointing to the inode.

Which layer does a router vs a switch operate at?
A switch operates at Layer 2 (Data Link) using MAC addresses within a LAN. A router operates at Layer 3 (Network) using IP addresses to forward packets between networks.

9. Physical & Data Link Layer Intermediate

  • MAC address — 48-bit hardware address, unique per NIC; used for local delivery within a LAN.
  • ARP (Address Resolution Protocol) — resolves an IP address to a MAC address on the local network.
  • Switch — learns MAC→port mappings, forwards frames only to the right port (vs a hub that broadcasts).
  • Error detection: CRC/checksum in the frame; flow control & MAC protocols (CSMA/CD for Ethernet, CSMA/CA for Wi-Fi) manage shared medium access.
  • Collision domain vs broadcast domain — switches separate collision domains; routers/VLANs separate broadcast domains.

10. Network Layer (IP & Routing) Intermediate

10.1 IP addressing

IPv4IPv6
Size32-bit (~4.3B addresses)128-bit (vast)
Notation192.168.1.12001:db8::1
ConfigDHCP / static, NAT commonAutoconfig, no NAT needed
  • Public vs private IPs — private ranges (10.x, 172.16–31.x, 192.168.x) used internally; NAT translates them to a public IP for internet access.
  • Subnetting & CIDR — 192.168.1.0/24 means 24 network bits, 8 host bits (254 usable hosts). The subnet mask separates network vs host portions.
CIDR /24 -> mask 255.255.255.0 -> 256 addresses (254 usable)
CIDR /26 -> mask 255.255.255.192 -> 64 addresses (62 usable)

10.2 Routing

  • Routing determines the path packets take across networks using routing tables.
  • Protocols: OSPF (link-state, intra-domain), BGP (path-vector, the protocol of the Internet between ASes), RIP (distance-vector, legacy).
  • ICMP — control/error messages (used by ping, traceroute).
What is NAT and why is it used?
Network Address Translation maps many private IPs to one (or few) public IPs by rewriting address/port info. It conserves scarce IPv4 addresses and adds a layer of isolation, but complicates inbound connections (needs port forwarding).

11.3 How TCP achieves reliability

  • Sequence & acknowledgement numbers — track bytes, detect loss, reorder.
  • Retransmission — resend unacked segments (timeout / fast retransmit on 3 dup ACKs).
  • Flow control — the receiver's sliding window prevents overwhelming it.
  • Congestion control — slow start, congestion avoidance (AIMD), fast recovery prevent overwhelming the network.
Why does TCP need a 3-way (not 2-way) handshake?
Both sides must agree on initial sequence numbers and confirm each other's send/receive ability. Two messages can't confirm the client received the server's SYN; the third ACK closes that loop and prevents old duplicate connection requests from causing confusion.
Flow control vs congestion control?
Flow control protects the receiver from being overrun (receiver-advertised window). Congestion control protects the network from overload (sender adjusts a congestion window based on perceived loss/delay).

13.3 Inheritance & the diamond problem

  • Java supports single class inheritance (one extends) but multiple interface inheritance.
  • Avoids the C++ "diamond problem"; if two interfaces give the same default method, the class must override it (Interface.super.method()).
  • Every class implicitly extends Object (root of all classes).

    @Override String sound(){ return "Woof"; }   // overriding
}
Animal a = new Dog();
a.sound();   // "Woof" -> resolved at runtime by the object's real type

13.7 Constructors & keywords

  • this = current object; super = parent reference.
  • static — belongs to the class, shared across instances (can't use this).
  • final — constant variable / non-overridable method / non-extendable class.

13.9 SOLID principles

Common pitfalls: overriding equals() without hashCode(); calling overridable methods from a constructor (subclass not yet initialized); confusing field hiding (static binding) with method overriding (dynamic binding); deep inheritance trees.
Can you achieve multiple inheritance in Java?
Not with classes (avoids the diamond problem), but yes through multiple interfaces. If two interfaces supply the same default method, the implementing class must override it and can disambiguate with InterfaceName.super.method().
How does runtime polymorphism work internally?
Each object holds a pointer to its class's method table (vtable). On an overridden method call, the JVM dispatches based on the object's actual type at runtime, not the reference's declared type — this is dynamic (late) binding.
Abstraction vs Encapsulation?
Abstraction is design-level — hiding complexity by exposing only essential behaviour (via interfaces/abstract classes). Encapsulation is implementation-level — hiding data by restricting access (private fields + accessors). Abstraction hides "how it works"; encapsulation hides "the data".

16. Normalization Intermediate

Organizing tables to reduce redundancy and avoid anomalies (insert/update/delete). Each normal form builds on the previous.

FormRule
1NFAtomic values; no repeating groups/arrays
2NF1NF + no partial dependency (non-key fully depends on whole PK)
3NF2NF + no transitive dependency (non-key depends only on the key)
BCNFStronger 3NF: every determinant is a candidate key
Memory aid (3NF): every non-key attribute depends on "the key, the whole key, and nothing but the key."
Denormalization trade-off: normalization reduces redundancy but adds joins. For read-heavy/analytical workloads, controlled denormalization (duplicating data) improves read performance at the cost of write complexity.
What anomalies does normalization prevent?
Update anomaly (same fact in many rows → inconsistent updates), insertion anomaly (can't add data without unrelated data), and deletion anomaly (deleting a row loses unrelated facts).

17. SQL Intermediate

17.1 Query execution order

SQL is written one way but executed another — knowing this explains why aliases/WHERE/HAVING behave as they do:

Written:  SELECT ... FROM ... JOIN ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT
Executed: FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY -> LIMIT
Why it matters: you can't use a SELECT alias in WHERE (WHERE runs first), and WHERE filters rows while HAVING filters groups (after aggregation).

17.2 Joins

JoinReturns
INNEROnly matching rows in both
LEFT (OUTER)All left + matched right (nulls if none)
RIGHT (OUTER)All right + matched left
FULL OUTERAll rows from both
CROSSCartesian product
SELFTable joined to itself

17.3 Aggregations & key clauses

SELECT dept, COUNT(*) AS cnt, AVG(salary) AS avg_sal
FROM   employees
WHERE  active = true            -- filter rows
GROUP BY dept                    -- group
HAVING COUNT(*) > 5              -- filter groups
ORDER BY avg_sal DESC
LIMIT 10;

17.4 Subqueries, CTEs & window functions

-- Window function: rank salaries within each department
SELECT name, dept, salary,
       RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
FROM employees;

-- CTE (readable, reusable)
WITH high_earners AS (
  SELECT * FROM employees WHERE salary > 100000
)
SELECT dept, COUNT(*) FROM high_earners GROUP BY dept;

17.5 Common interview SQL: 2nd highest salary

-- Using a subquery
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
-- Using window function
SELECT DISTINCT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) r FROM employees
) t WHERE r = 2;
Function familyExamples
AggregateCOUNT, SUM, AVG, MIN, MAX
WindowROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD
String/DateCONCAT, SUBSTRING, COALESCE, NOW
WHERE vs HAVING; DELETE vs TRUNCATE vs DROP?
WHERE filters rows before grouping; HAVING filters after aggregation. DELETE removes rows (logged, can rollback, can have WHERE); TRUNCATE quickly empties a table (no WHERE, minimal logging); DROP removes the table structure entirely.
RANK vs DENSE_RANK vs ROW_NUMBER?
ROW_NUMBER gives unique sequential numbers. RANK leaves gaps after ties (1,1,3). DENSE_RANK has no gaps (1,1,2).

MVCC is why modern databases scale reads well: a SELECT reads a consistent snapshot without locking out concurrent writes.
Two users update the same row at once — how do you handle it?
Optimistic locking with a version column — the second update fails if the version changed, prompting retry (best for low contention). Pessimistic locking (SELECT ... FOR UPDATE) — lock the row first (best for high contention).

19. Indexing & Storage Advanced

19.1 Why indexes

An index is a data structure that speeds up lookups (O(log n) vs O(n) full scan), at the cost of extra storage and slower writes (index must be maintained).

19.2 Index types

TypeNotes
B+ TreeDefault; great for range & equality queries; sorted leaves linked
HashO(1) equality only; no range queries
ClusteredTable physically ordered by this key (one per table; usually PK)
Non-clustered (secondary)Separate structure pointing to rows
CompositeMulti-column; leftmost-prefix rule applies
CoveringIndex contains all queried columns → no table lookup
Pitfalls: too many indexes slow writes & waste space; functions on indexed columns (WHERE YEAR(date)=2024) prevent index use; low-cardinality columns (e.g. boolean) gain little; composite index order matters (leftmost prefix).

19.3 Query optimization

  • Use EXPLAIN/EXPLAIN ANALYZE to see the query plan (index scan vs full scan, join type, rows examined).
  • Index columns used in WHERE, JOIN, ORDER BY. Avoid SELECT *. Beware N+1 queries from ORMs.
Clustered vs non-clustered index?
A clustered index defines the physical row order (only one per table; the PK in InnoDB). A non-clustered index is a separate structure storing the key + a pointer/row locator to the actual row, so it needs an extra lookup unless it's covering.

20.2 Scaling techniques

  • Replication — copies for read scaling + HA (primary-replica).
  • Sharding (partitioning) — split data across nodes by a shard key for write scaling.
  • CAP theorem — under a network partition, choose Consistency or Availability. (CP vs AP.)
  • BASE — Basically Available, Soft state, Eventually consistent (NoSQL philosophy vs ACID).
When would you choose NoSQL over a relational DB?
When you need massive horizontal scale, flexible/evolving schemas, very high write throughput, or simple access patterns (key lookups) — and can tolerate eventual consistency. Stick with SQL for complex relationships, multi-row transactions, and strong consistency.

22. Cryptography Advanced

22.1 Symmetric vs Asymmetric

SymmetricAsymmetric
KeysOne shared secret keyPublic + private key pair
SpeedFastSlow
Problem solvedBulk encryptionKey exchange, signatures
ExamplesAES, ChaCha20RSA, ECC, Diffie-Hellman
Hybrid (TLS) approach: use slow asymmetric crypto to securely exchange a symmetric session key, then fast symmetric encryption for the actual data. Best of both.

22.2 Hashing

  • One-way function: easy to compute, infeasible to reverse; deterministic; collision-resistant (SHA-256). Used for integrity & password storage.
  • Encryption is reversible (with key); hashing is not.
  • Password storage: never plaintext, never plain hash. Use salt (unique per user, defeats rainbow tables) + a slow KDF (bcrypt, scrypt, Argon2). Pepper = secret added server-side.

22.3 Digital signatures & certificates

Sign:   hash(message) -> encrypt with SENDER's PRIVATE key = signature
Verify: decrypt signature with SENDER's PUBLIC key -> compare to hash(message)
=> proves authenticity + integrity + non-repudiation
  • PKI & CAs — Certificate Authorities issue certificates binding a public key to an identity; browsers trust a chain of CAs.
  • TLS handshake — verify server cert, agree on cipher, exchange session key, then encrypt traffic.
Why salt passwords if you already hash them?
Without salt, identical passwords produce identical hashes, and attackers can use precomputed rainbow tables. A unique random salt per user makes each hash unique and forces attackers to brute-force each one individually.

23. Authentication & Authorization Intermediate

Authentication (who you are)Authorization (what you can do)
Passwords, MFA, biometrics, tokensRoles, permissions, scopes, ACLs
  • MFA — combine factors: something you know (password), have (phone/token), are (biometric).
  • Sessions vs JWT — server-side session store vs stateless signed tokens (see Networks §12.4). JWTs scale but are hard to revoke (use short TTL + refresh tokens).
  • OAuth 2.0 — delegated authorization (grant an app limited access without sharing your password). OIDC adds an identity/authentication layer on top.
  • RBAC vs ABAC — role-based vs attribute-based access control.
Common mistake: using OAuth purely for authentication, or treating a JWT as revocable like a session. Understand the distinction and design token lifetimes/refresh carefully.

24.2 SQL Injection example & fix

// VULNERABLE: string concatenation
String q = "SELECT * FROM users WHERE name = '" + input + "'";
// input = ' OR '1'='1   -> returns all rows / auth bypass

// SAFE: parameterized query (PreparedStatement)
PreparedStatement ps = conn.prepareStatement(
    "SELECT * FROM users WHERE name = ?");
ps.setString(1, input);   // input treated as data, never code

How do parameterized queries stop SQL injection?
The query structure is sent to the DB and compiled separately from the parameter values. User input is bound as data, never parsed as SQL, so it can't alter the query's logic regardless of its content.

Secure coding best practices: validate all input, encode all output, use prepared statements, hash+salt passwords, enforce HTTPS, apply least privilege, keep dependencies patched, never log secrets, rate-limit auth endpoints, and store secrets in a vault (not in code).
How does HTTPS protect against a man-in-the-middle attack?
TLS encrypts the channel (confidentiality) and authenticates the server via a CA-signed certificate. An attacker can't read the traffic or impersonate the server without a valid certificate the client trusts, and tampering breaks integrity checks.

26. Interview Scenarios & Cheat-Sheet Advanced

26.1 Cross-topic scenario questions

What happens, end to end, when you load a web page? (ties OS+Net+DB+Sec)
DNS resolves the domain → TCP handshake → TLS handshake (security) → HTTP request hits the server (a process scheduled by the OS) → server queries the DB (indexes, transactions) → response travels back through the layers → browser renders. A great answer touches all five subjects.
A web request is slow — how do you diagnose across the stack?
Check each layer: DNS/network latency, TLS overhead, server CPU/scheduling/GC, DB slow queries (missing index, locks, N+1), and downstream services. Use metrics/tracing to localize before optimizing.
Design a secure login system.
HTTPS everywhere; store passwords with bcrypt/Argon2 + per-user salt; parameterized queries; rate-limit + lockout on failed attempts; MFA; secure session/JWT with short TTL + refresh; CSRF protection; least-privilege DB account; audit logging.
