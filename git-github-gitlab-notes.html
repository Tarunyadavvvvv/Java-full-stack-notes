Part I — Git Fundamentals

1. Version Control & Git Basics Basic

1.1 What is version control?

A Version Control System (VCS) tracks changes to files over time so you can recall specific versions, collaborate, branch, and revert mistakes. Git is a distributed VCS created by Linus Torvalds (2005) for Linux kernel development.

1.2 Centralized vs Distributed VCS

Centralized (SVN, CVS)Distributed (Git)
RepositoryOne central serverEvery clone is a full repo (full history)
Offline workLimitedFull (commit, branch, history offline)
Single point of failureYes (server)No (every clone is a backup)
SpeedNetwork-boundLocal operations are fast
Git vs GitHub/GitLab: Git is the version-control tool (runs locally/CLI). GitHub & GitLab are hosting platforms built around Git that add collaboration, pull/merge requests, issues, CI/CD, and access control. You can use Git without them.

1.3 First-time setup

git config --global user.name  "Alice Dev"
git config --global user.email "alice@example.com"
git config --global init.defaultBranch main
git config --list                 # view config
git init                          # create a new local repo
git clone <url>                    # copy a remote repo locally
Why is Git "distributed" and why does it matter?
Every clone contains the complete history, not just the latest snapshot. This enables full offline work (commits, branches, diffs), removes the single point of failure, makes most operations fast (local), and allows flexible collaboration workflows.

2. Git Internals (How Git Works) Advanced

2.1 Git is a content-addressable snapshot store

Unlike older systems that store deltas (diffs between versions), Git stores a snapshot of the entire project at each commit. Unchanged files are stored as references to the previous identical content (deduplicated), so snapshots are cheap.

2.2 The four object types (the .git object database)

ObjectStores
BlobFile contents (no name/metadata)
TreeA directory: names + permissions + pointers to blobs/trees
CommitSnapshot pointer (root tree) + parent(s) + author + message
TagAnnotated tag pointing to an object
commit ──points to──> tree (root dir)
                        ├── blob  (README.md)
                        └── tree  (src/) ──> blob (App.java)
each commit also ──> parent commit(s)  => forms the history DAG

2.3 SHA-1 hashing & integrity

  • Every object is identified by a SHA-1 hash (40 hex chars) of its content — content-addressable. Identical content → same hash → stored once.
  • A commit's hash depends on its content and its parent, so history is tamper-evident (changing anything changes all later hashes). (Git is migrating toward SHA-256.)

2.4 References (branches, HEAD)

  • A branch is just a lightweight, movable pointer to a commit (a file in .git/refs/heads). Creating a branch is O(1) — just writes a 40-byte hash.
  • HEAD is a pointer to the current branch (or commit). Detached HEAD = HEAD points directly to a commit, not a branch.
Does Git store diffs or snapshots?
Conceptually snapshots — each commit references a complete tree. Unchanged files point to existing blobs (so no duplication). For storage efficiency, Git later packs objects using delta compression in packfiles, but the model you reason about is snapshots.
Why is creating a branch so cheap in Git?
A branch is just a 40-byte file containing a commit hash. No files are copied — creating or switching branches only moves a pointer, which is why Git encourages frequent branching.

3. The Three Areas & Basic Workflow Basic

3.1 The three states / areas

Working Directory ──git add──> Staging Area (Index) ──git commit──> Repository (.git)
   (your edits)                  (staged snapshot)                  (permanent history)
        ▲                                                                │
        └──────────────── git checkout / restore ◄───────────────────────┘
AreaMeaning
Working directoryYour actual files; where you edit
Staging area (index)What will go into the next commit (lets you craft commits selectively)
Repository (.git)Committed history (objects + refs)
Why a staging area? It lets you build a commit deliberately — staging only some files or even some lines (git add -p) — so each commit is a clean, logical unit rather than "everything I changed."

3.2 File lifecycle

Untracked ──git add──> Staged ──git commit──> Tracked/Unmodified
                                                     │ (edit)
                                                     ▼
                                                 Modified ──git add──> Staged

3.3 The everyday loop

git status                # what changed / staged
git add file.txt          # stage a file   (git add .  = all)
git add -p                # stage selectively (hunk by hunk)
git commit -m "message"   # commit staged changes
git log --oneline --graph # view history
git push                  # send commits to remote
Difference between working directory, staging area, and repository?
The working directory holds your editable files. The staging area is a snapshot you've marked for the next commit. The repository stores committed history permanently. add moves working → staging; commit moves staging → repository.

Part II — Branching & History

5. Branching & Merging Intermediate

5.1 What a branch really is

A branch is a movable pointer to a commit. Commits form a DAG (directed acyclic graph) via parent links. Branching lets parallel lines of work proceed independently, then merge.

      A───B───C  (main)
               \
                D───E  (feature)
git merge feature  ->  creates merge commit F with parents C and E

5.2 Types of merges

Merge typeWhenResult
Fast-forwardTarget hasn't divergedPointer just moves forward; no merge commit
3-way mergeBoth branches advancedNew merge commit with 2 parents
--no-ffForce a merge commit even if FF possiblePreserves feature-branch grouping in history
Squash mergeCombine all feature commits into oneClean single commit on target
git merge feature              # fast-forward if possible, else 3-way
git merge --no-ff feature      # always create a merge commit
git merge --squash feature     # stage combined changes as one commit
What is a fast-forward merge and when does it NOT happen?
When the current branch hasn't diverged, Git just moves its pointer forward to the feature tip — no merge commit. It can't fast-forward if the base branch has its own new commits (divergence), so Git performs a 3-way merge instead.

6. Merge vs Rebase Advanced — very common Q

MergeRebase
HistoryPreserves true history (merge commits)Rewrites — linear, no merge commits
CommitsKeeps original commit hashesCreates new commits (new hashes)
ReadabilityCan be noisy with many mergesClean, linear log
SafetySafe on shared branchesDangerous on shared/pushed branches
# Rebase feature onto latest main (replays D,E on top of main's tip)
git switch feature
git rebase main
#   A─B─C (main)            A─B─C
#        \          =>            \
#         D─E (feature)            D'─E' (feature, rebased)
The Golden Rule of Rebasing: Never rebase commits that others have already pulled / that exist on a shared branch. Rebasing rewrites history (new hashes); collaborators' repos diverge, causing painful conflicts. Rebase only local, unpushed work.
Practical guidance: rebase your feature branch on top of main to keep it current and clean before opening a PR; use merge to integrate the finished feature into main. "Rebase locally, merge publicly."

6.1 Interactive rebase

git rebase -i HEAD~4    # edit last 4 commits
# in the editor, per commit choose:
#   pick    keep as-is
#   reword  change message
#   edit    pause to amend
#   squash  fold into previous (keep both messages)
#   fixup   fold into previous (discard message)
#   drop    delete the commit

Used to clean up history before sharing — squash WIP commits, reorder, fix messages.

When would you rebase instead of merge?
To keep a clean, linear history — e.g. updating a local feature branch with the latest main before review, or squashing messy WIP commits. Avoid rebasing shared branches; use merge there to preserve everyone's history.

7. Undoing Changes (reset / revert / restore) Advanced

7.1 git reset — three modes

ModeMoves branchStagingWorking dir
--softYesKept (staged)Kept
--mixed (default)YesReset (unstaged)Kept
--hardYesResetDiscarded
git reset --soft  HEAD~1   # undo last commit, keep changes staged
git reset --mixed HEAD~1   # undo commit + unstage, keep edits
git reset --hard  HEAD~1   # undo commit AND throw away changes (danger!)
reset --hard permanently discards uncommitted work. Committed work can often be recovered via git reflog, but uncommitted changes are gone.

7.2 revert vs reset

git revertgit reset
HowNew commit that inverts a previous oneMoves branch pointer back
HistoryPreserved (safe)Rewritten
Use on shared branches?Yes — recommendedNo (rewrites public history)
git revert <commit>     # safely undo a pushed commit (creates an "undo" commit)

7.3 restore (modern, file-level)

git restore file.txt              # discard working-dir changes
git restore --staged file.txt     # unstage but keep edits
git restore --source=HEAD~2 f.txt # restore file from an old commit
A bad commit was already pushed to main — how do you undo it?
Use git revert <commit>. It creates a new commit that reverses the change, preserving history so collaborators aren't disrupted. Never reset --hard + force-push a shared branch unless the whole team coordinates.

8. Stash, Cherry-pick, Tags & Reflog Intermediate

8.1 git stash — shelve work temporarily

git stash                 # save uncommitted changes, clean working dir
git stash -u              # include untracked files
git stash list            # see stashes
git stash pop             # reapply + remove from stash
git stash apply           # reapply, keep in stash
git stash drop            # delete a stash

Use when: you need to switch branches urgently but aren't ready to commit.

8.2 git cherry-pick — copy a specific commit

git cherry-pick <commit>   # apply one commit from another branch onto current

Use when: applying a hotfix to multiple branches, or grabbing one commit without merging the whole branch.

8.3 Tags

TypeCommand
Lightweightgit tag v1.0
Annotated (recommended for releases)git tag -a v1.0 -m "Release 1.0"
Push tagsgit push origin v1.0 / --tags
Annotated tags store author, date, message, and can be signed — use them for releases. Lightweight tags are just a name pointing to a commit.

8.4 git reflog — the safety net

git reflog                 # log of where HEAD has been (even "lost" commits)
git reset --hard HEAD@{2}   # jump back to a previous state
Lifesaver: Reflog records every HEAD movement (commits, resets, rebases) for ~90 days. If you "lose" commits via a bad reset/rebase, find them in the reflog and recover — a favourite interview rescue answer.
You did git reset --hard and lost commits — can you recover?
Yes, if they were committed. Use git reflog to find the lost commit's hash, then git reset --hard <hash> or git cherry-pick it. Uncommitted changes, however, are unrecoverable.

9. Resolving Conflicts Intermediate

A merge conflict happens when two branches change the same lines (or one edits a file the other deleted) and Git can't auto-merge.

<<<<<<< HEAD
your current branch's version
=======
the incoming branch's version
>>>>>>> feature
# Resolve workflow
git status                # see conflicted files
# edit files, remove markers, keep the correct content
git add <resolved-file>    # mark resolved
git commit                # (merge) or  git rebase --continue
git merge --abort         # bail out and return to pre-merge state
Reduce conflicts: pull/rebase frequently, keep branches short-lived & small, communicate on shared files, and use a merge tool. Enable git rerere to auto-reuse recorded conflict resolutions.
How do you resolve a merge conflict?
Run the merge/rebase, open conflicted files (marked with <<</===/>>>), manually choose/combine the correct content, remove the markers, git add the files, then commit (or git rebase --continue). Use git merge --abort to back out entirely.

Part III — Workflows & Collaboration

10. Remotes & Collaboration Intermediate

10.1 Remote-tracking branches

origin/main is a remote-tracking branch — your local snapshot of where the remote's main was at your last fetch. Your local main tracks it (upstream).

git branch -vv             # show tracking relationships
git push -u origin main    # set upstream so future push/pull need no args

10.2 Clone vs Fork

CloneFork
WhatLocal copy of a repoServer-side copy under your account
UseWork on a repo you can push toContribute to repos you can't push to (open source)
Sync upstreamvia originadd upstream remote, fetch + merge
# Fork workflow: keep your fork in sync with the original ("upstream")
git remote add upstream <original-repo-url>
git fetch upstream
git merge upstream/main        # or: git rebase upstream/main

10.3 SSH vs HTTPS & .gitignore

  • HTTPS — uses tokens/credentials; works through firewalls. SSH — key-based, no password each push.
  • .gitignore — patterns for files Git should not track (build output, secrets, node_modules, IDE files).
Pitfall: .gitignore only ignores untracked files. If a file is already tracked, you must git rm --cached <file> to stop tracking it. Never commit secrets — once pushed, assume they're compromised even if later removed.

11.3 GitHub Flow (simple & common)

1. Branch off main:   git switch -c feature/login
2. Commit + push:     git push -u origin feature/login
3. Open a Pull Request -> review + CI checks
4. Merge to main      -> auto-deploy
5. Delete the branch
Interview framing: Git Flow = structured, heavier, good for versioned releases. GitHub Flow / Trunk-Based = lightweight, fast, good for continuous delivery. Modern teams trend toward trunk-based + feature flags for speed.
Which branching strategy would you use and why?
It depends on release cadence. For continuous deployment of a web app, GitHub Flow or trunk-based (short branches, fast PRs, feature flags). For products with scheduled, versioned releases and parallel maintenance, Git Flow (develop/release/hotfix). The key is matching the team's deployment model.

12. Pull / Merge Requests & Code Review Intermediate

A Pull Request (GitHub) / Merge Request (GitLab) proposes merging one branch into another, enabling review, discussion, and automated checks before integration.

12.1 Anatomy of a good PR/MR

  • Small, focused, single-purpose; clear title + description (what & why); linked issue.
  • Passing CI (build, tests, lint); required reviewer approvals.
  • Resolved conversations before merge.

12.2 Merge options when closing a PR

OptionResultUse when
Merge commitPreserves all commits + merge commitWant full history
Squash & mergeCombines into one commit on mainClean linear history (most common)
Rebase & mergeReplays commits, no merge commitLinear history, keep individual commits

12.3 Code review best practices

  • Review for correctness, readability, security, tests — not style nitpicks (automate those with linters).
  • Be specific and kind; suggest, don't demand; approve small good changes quickly.
  • Use draft PRs for early feedback; require branch protection (reviews + green CI) on main.
PR vs MR — any real difference?
Functionally the same concept; just different names (GitHub: Pull Request, GitLab: Merge Request). Both propose merging a branch with review and CI gating. GitLab's "Merge Request" name is arguably more accurate (you're requesting a merge).

15.1 Concepts

15.2 GitHub Actions example

name: CI
on: [push, pull_request]
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '21' }
      - run: ./mvnw -B verify          # build + test
      - uses: actions/upload-artifact@v4
        with: { name: jar, path: target/*.jar }

Building blocks: workflow → jobs → steps; jobs run in parallel by default; use needs: for ordering, secrets for credentials, and matrix to test multiple versions.

15.3 GitLab CI/CD example

# .gitlab-ci.yml
stages: [build, test, deploy]
build:
  stage: build
  script: ./mvnw -B package
  artifacts: { paths: ["target/*.jar"] }
test:
  stage: test
  script: ./mvnw -B test
deploy:
  stage: deploy
  script: ./deploy.sh
  only: { refs: [main] }            # deploy only from main
Best practices: fail fast (lint/test early), cache dependencies, keep secrets in the platform's secret store (never in YAML), require green pipeline before merge, use environments + manual approval for production, and make pipelines reproducible.
CI vs CD vs Continuous Deployment?
CI = automatically build & test every change. Continuous Delivery = every passing build is release-ready and auto-deployed to staging, with a manual approval gate to production. Continuous Deployment goes further — every passing change auto-deploys to production with no manual gate.

16.1 Removing a leaked secret

If a secret was committed: (1) rotate/revoke it immediately — assume it's compromised. (2) Remove it from history with git filter-repo (or BFG Repo-Cleaner) — filter-branch is deprecated. (3) Force-push the rewritten history and have collaborators re-clone. Removing from history alone is not enough — rotation is mandatory.

16.2 Large files & repo hygiene

  • Git LFS (Large File Storage) — store large binaries (videos, datasets, models) outside the main repo via pointers, keeping clones fast.
  • Don't commit build artifacts, dependencies, or secrets; use .gitignore.
  • Monorepo vs polyrepo — one big repo (shared tooling, atomic cross-project changes) vs many (independent deploys, clear ownership).
How do you completely remove a sensitive file from Git history?
Rotate the secret first (non-negotiable). Then rewrite history with git filter-repo --path secret.env --invert-paths (or BFG), force-push, and have everyone re-clone. Also clear it from any caches/forks/CI logs. History rewriting changes all subsequent commit hashes.

Part V — Advanced & Interview

17. Advanced Git & Troubleshooting Advanced

17.1 git bisect — find the commit that broke it

git bisect start
git bisect bad                 # current commit is broken
git bisect good v1.0           # this old commit worked
# Git checks out the midpoint; you test & mark each:
git bisect good   # or  git bisect bad
# ... binary search until Git names the first bad commit
git bisect reset               # finish

Binary search through history — finds a regression among thousands of commits in ~log₂(n) steps.

How would you find which commit introduced a bug?

18. Best Practices & Common Pitfalls Intermediate

18.1 Best practices

  • Commit small & often, each a logical unit; write clear messages (imperative mood: "Add login validation").
  • Follow Conventional Commits (feat:, fix:, docs:) for automated changelogs/semver.
  • Branch per feature; keep branches short-lived; pull/rebase frequently.
  • Never commit secrets or large binaries; maintain .gitignore.
  • Protect main (reviews + CI); use PRs/MRs for all changes.
  • Rebase local work, merge shared work; clean up history before sharing.

18.2 Good commit message format

feat(auth): add password strength validation

- enforce min 8 chars, 1 number, 1 symbol
- show inline error messages

Closes #142

18.3 Common pitfalls

Avoid: git push --force on shared branches (use --force-with-lease); rebasing public history; committing secrets/node_modules; giant "misc fixes" commits; long-lived divergent branches (merge hell); working directly on main; ignoring .gitignore until files are already tracked.
What makes a good commit and commit message?
A good commit is small, atomic, and self-contained (one logical change, builds & passes tests). A good message has a concise imperative summary line (≤50 chars), a blank line, then a body explaining why (not just what), and references the issue.

19. Interview Scenarios & Cheat-Sheet Advanced

19.1 Scenario questions

You accidentally committed a secret and pushed it. What now?
1) Immediately rotate/revoke the secret (assume compromised). 2) Remove it from history (git filter-repo/BFG). 3) Force-push and have collaborators re-clone. 4) Audit logs/CI caches. Removing from history is not enough — rotation is the real fix.
Two developers edited the same file and there's a conflict on merge. Walk me through it.
Run the merge, identify conflicted files via git status, open them and resolve the <<</===/>>> sections (keep correct content, remove markers), git add the resolved files, then commit. Prevent recurrence with smaller branches and frequent rebasing/pulling.
Your feature branch is 30 commits behind main. How do you update it cleanly?
If it's local/unshared: git fetch && git rebase origin/main for a clean linear history. If others share the branch: git merge origin/main to avoid rewriting their history. Resolve any conflicts during the operation.
How do you revert a merge that's already on main?
git revert -m 1 <merge-commit> — the -m 1 specifies which parent is the mainline to keep. Be aware re-merging that branch later needs care (revert the revert or rebase), a classic gotcha.
Explain the difference between reset, revert, and checkout in one breath.
reset moves the branch pointer (can rewrite history & discard work); revert creates a new commit that undoes a previous one (safe for shared history); checkout/restore change what's in your working tree/which branch you're on.
